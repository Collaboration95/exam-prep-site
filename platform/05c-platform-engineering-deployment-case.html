Deployment Case Study: Splitting the Payment Table

8 slides · about 8 min · open the deck · JSON

This case splits Payment into ChequePayment and ApplePayPayment without a single disruptive cutover. Follow the lecture’s four stages: add tables, release code that reads both layouts, backfill historical data, then switch reads. The key reasoning is data compatibility: reducing live exposure with a canary does not itself preserve every rollback path.

Big ideas

  • Split a breaking schema change into additive structure, compatibility code, backfill and final read cutover.
  • Choose rolling for the additive schema stage and canary for behaviour changes, as in the lecture.
  • V1.1 writes new tables and reads them first, falling back to Payment for missing historical rows.
  • A retained old table preserves historical data, but does not contain new-only writes; a rollback plan must account for those.
  • Tombstone deletes so fallback and migration do not resurrect removed records.
  • Validate the migration and retain the compatible reader before switching to new-only reads.

Scenario and constraints

Splitting a table is a breaking change, so it needs a multi-release plan.

  • The change: Payment currently holds all payment types. Cheque and Apple Pay capture different fields, so Version 2 should write to ChequePayment and ApplePayPayment instead of Payment.
  • Why stage it: V2 cannot retrieve old Payment rows until they are migrated. Reverting to V1 can also hide payments written only to the new tables. Separate schema expansion, compatible code, historical migration and final read cutover; assess rollback data at every stage.
Tombstone
Marking a row as deleted without physically removing it.

Now read slides 2–3 →

Check yourself

V1 of the Payment service writes every payment to one Payment table; V2 will write cheque and Apple Pay payments to two new tables. Why is a direct switch from V1 to V2 unsafe?
V2 cannot read the historical rows that remain in Payment, so old payments would vanish from its view. If V2 accepts new payments only in the new tables, switching back to V1 hides those too. Any plan has to keep both historical and newly accepted payments readable at every step, including rollback.
A teammate proposes doing the table split in a two-hour maintenance window with the service down, instead of the staged plan. When would that be acceptable, and what does the staged plan buy?
It is acceptable if the customers can tolerate the downtime and the window fits the migration; the lecture's first question is who your customers are, and banks or e-commerce sites usually cannot. The staged plan keeps payments flowing and gives a rollback point at each step. Its cost is several releases and transitional code that reads both layouts.

Steps 1 and 2: new tables, then V1.1 canary

Add the tables, then canary V1.1 with new-table writes and fallback reads. Check the data needed by both versions before rolling back.

  • Step 1, add tables: create ChequePayment and ApplePayPayment without changing V1. The lecture chooses a rolling update of database scripts. Dropping unused new tables reverses this step; that is no longer harmless once they contain accepted payments.
  • Step 2, canary V1.1: write new payments to the new tables; read there first and fall back to Payment when absent. Mark deletes with tombstones. Start with about 5–10% of transactions, observe behaviour, then roll out.
  • Rollback caveat: the lecture calls rollback “okay” because Payment is untouched and exposure is limited. This preserves old rows but does not explain how V1 reads new-only payments, or how mixed V1/V1.1 instances route reads of them. A complete plan must resolve that compatibility gap before using the canary in production.

Now read slides 4–6 →

Check yourself

Why does V1.1, which writes to the new tables and falls back to Payment for reads, go out as a canary rather than a straight rolling update?
A canary exposes only 5 to 10% of transactions to the changed write and read behaviour, so problems show up on a small surface before wider rollout. It limits the blast radius; it does not by itself make rollback safe. Before relying on rollback, check how V1 would see payments that V1.1 wrote into the new tables.
A teammate proposes that V1.1 physically delete payment rows instead of tombstoning them. What would go wrong?
If a payment is deleted from the new table, V1.1's fallback read finds the old row in Payment and the deleted payment reappears, and a later backfill could copy it back. A tombstone marks the row as deleted, so reads and the backfill know to skip it. Every reader and the backfill must honour the marker for this to work.
During the canary, V1.1 records a payment only in ApplePayPayment. A later request for that payment reaches a V1 instance, which reads only Payment. What must the rollout plan address?
V1 cannot find a payment that was accepted, so the customer sees it as missing. The plan must keep accepted payments visible across mixed versions and after any rollback, for example by keeping a reader that checks the new tables first, or by limiting where new-table writes are served until every instance can read them. Keeping Payment untouched and the canary small reduces exposure but does not solve this.

Steps 3 and 4: migrate, then V1.2 becomes 2.0

Backfill old rows, validate the result, then canary new-only reads. Rollback should restore compatible reading without hiding new payments.

  • Step 3, backfill: copy historical payments into the new tables while V1.1 continues new-first, old-fallback reads. Honour tombstones and avoid overwriting newer data. The lecture suggests identifying migrated rows by updated date for rollback; use that only if it distinguishes migration copies from genuine new or changed payments.
  • Step 4, new-only reads: after confirming all required historical rows are migrated, canary V1.2 and roll it out, then tag it 2.0. Restore the V1.1 compatible reader if needed: it still reads new payments and falls back for old ones. Returning to an old-only reader is unsafe when new-only writes exist.
  • Lesson: retain data and the reader needed by each rollback target. Traffic strategies limit exposure; they do not reverse database writes. The lecture leaves concurrent updates, backfill validation and full data reconciliation unspecified.

Now read slides 7–8 →

Check yourself

The backfill copies old rows from Payment into the new tables while V1.1 is live. A payment was updated in the new table yesterday, and the backfill is about to copy its older version from Payment. What must the backfill do?
Never overwrite a newer row: compare update dates and skip rows that already exist in the new tables, and skip anything tombstoned. V1.1 keeps working during migration because it reads the new tables first and falls back only for missing rows. Validate counts and samples before moving on, because the next step stops reading Payment altogether.
V1.2 reads only from the new tables. What makes rolling it back safe?
Rolling back to V1.1, which reads the new tables first and falls back to Payment for missing rows, keeps both migrated and newly written payments visible. Rolling back to V1 would not, because Payment lacks everything written since cutover. So V1.1 and the data it depends on must be kept until V1.2 has proven itself.
Why does the case tag V1.2 as 2.0 rather than writing a fresh V2?
V1.2 is already proven: it has passed a canary and a rollout reading only the new tables. Tagging it avoids shipping a new, untested build at the riskiest moment. The major version marks the point where the old Payment table is no longer part of the contract, which is the breaking change.

Exam-style questions

Answer aloud or on paper before opening.

Propose a near-zero-downtime plan to split an Orders table into two tables owned by different new schemas, and say how each step can be rolled back.
Step 1: add the new tables only, with no code change; rollback drops them. Step 2: canary a compatibility release that writes new orders to the new tables, reads new-first with fallback to Orders, and tombstones deletes; make sure every version that can serve traffic, or be rolled back to, can still see new-table orders. Step 3: backfill historical rows without overwriting newer rows or tombstones, and validate. Step 4: canary a release that reads only the new tables, keeping the compatibility release as the rollback target, then tag it as the new major version. The cost is several releases and temporary dual-read code.
Why is canary preferred over blue/green for the transitional version in the Payment case, and what does neither strategy solve?
A canary exposes only a small share of transactions to the changed data behaviour, so problems surface before full rollout, and it needs no second environment. Blue/green switches all traffic at once; it switches back quickly, but every user hits the new data path at the same moment. Neither undoes writes to the shared database or makes them readable by old code, so the compatibility plan (dual reads, tombstones, a retained reader) is still required.
A teammate's plan for the Payment split is: (1) canary V2, which writes and reads only the new tables, at 10%; (2) migrate the old data; (3) roll out V2. Critique the plan and correct it.
During step 1, V2 cannot see historical payments, and V1 instances cannot see payments V2 accepted, so customers on both sides see missing payments. Rolling back loses visibility of V2's writes, and nothing marks deletes, so migrated rows could reappear. Correct it as the lecture does: add the tables first, canary V1.1 with new-table writes, fallback reads and tombstones, backfill and validate, then canary V1.2 reading only the new tables and tag it as 2.0. Each step stays backward compatible with the one before.
How is rollback handled at each stage of the Payment case, and where does the lecture's shortcut need more design?
Step 1: drop the unused new tables. Step 2: stop the V1.1 rollout, but keep every payment it accepted, since V1 alone may not read them. Step 3: if needed, remove only migrated copies identified by updated date, never live changes. Step 4: go back to V1.1's new-first, old-fallback reader. The lecture says canary rollback is fine because Payment is untouched, but that misses payments written to the new tables in the meantime, so reconciliation and mixed-version reads still need designing.
