Data Management

56 slides · about 28 min · open the deck · JSON

Choose datastores from the workload: required queries, write volume, consistency, availability, latency and schema evolution. This topic compares replication, sharding and caching, explains CAP during network partitions, then surveys key-value, document, wide-column, search, graph and SQL-over-files models. Treat named products as lecture examples rather than guarantees of every deployment.

Big ideas

  • RDBMS fits many workloads; horizontal distribution, schema evolution and relationship traversals can motivate other models.
  • Read replicas distribute reads; shards divide data and write load; caches reduce repeated reads, while write durability depends on the acknowledgement path.
  • CAP is a trade-off during partitions: preserve consistent answers by refusing some requests, or keep answering while accepting divergent data.
  • The lecture labels Redis, MongoDB and HBase CP and Elasticsearch AP; reason from partition behaviour and configuration rather than the product name alone.
  • CQRS separates command and query models; the lecture illustrates independently scaled databases with asynchronous projections.
  • Choose key-value for point lookup, document for nested data, wide-column for sparse write-heavy records, search for ranked retrieval and graph for traversals.
  • SQL-over-files separates query processing from stored files. Do not infer that every named analytics product lacks managed database capabilities.

What we need from a datastore and where RDBMS stands

Datastore requirements (scale, consistency, availability, latency, evolvability) and an honest assessment of RDBMS against them.

Datastores must match the apps

Applications are built to be available, fault-tolerant, performant and gracefully degrading, so datastores must be too, while coping with IoT and analytics-driven data volume.

  • Beyond storing and reading data, we want:
  • Wish list →
    • scalability (vertical/horizontal)
    • consistency
    • availability
    • low latency
    • evolvability
    • analytics
    • security

Scalability and availability are usually related.

Data organisation

  • Structured → follows a defined model, such as relational rows and columns
  • Semi-structured → carries labels or hierarchy, such as JSON or XML
  • CSV → the lecture also groups it as semi-structured; a fixed CSV table can be treated as structured
  • Unstructured → content such as images or prose; lacks a predefined application-level record model

RDBMS is great for most scenarios

  • Entities map to tables
  • SQL
  • Flexible querying on any column
  • Logical data model
  • Good read/write performance
  • Strong ACID consistency

RDBMS trade-offs

  • Scaling across machines while keeping strong consistency requires coordination
  • Schema changes need planning
  • Object models must map to tables, sometimes through an ORM
  • An ORM is optional, not a relational requirement
  • Deep relationship traversal can favour a graph model, depending on the query
Structured data
Defined model of rows and columns with strict schema.
Semi-structured data
Labelled or hierarchical records, such as JSON or XML, without a fixed relational table layout.
Unstructured data
Content without a predefined application-level record model, such as prose or images.

Check yourself

A platform's domain model changes almost weekly, and every change needs a table migration and an update to the object-relational mapping. Which datastore requirement is the relational database weakest on here, and what would you consider?

Weakest on evolvability.

  • Strict schema → has to be migrated
  • Domain entities must be translated to tables through an ORM
  • Consider a schema-free document store → smoother schema evolution, because the schema travels with the data

Trade-off: most document stores give up joins, constraints and complex transactions → switch only if those matter less than the pace of change.

A teammate says: 'Relational databases don't scale, so our 2,000-user internal app needs NoSQL.' Do you agree?

No.

  • The lecture says an RDBMS is great for most scenarios: flexible SQL on any column, strong ACID guarantees, good read and write performance
  • What is hard: scaling horizontally while staying consistent → replication and sharding exist for that
  • 2,000 users rarely need it

Reach for another model when a specific need appears, such as graph-like relationships, very high write volume or constant schema change.

A platform stores invoices as rows, partner webhook payloads as JSON, and scanned receipts as images. Classify each kind of data and say what it implies for storage.
  • Invoices → structured data with a strict schema → relational tables
  • Webhook payloads → semi-structured, schema attached to the data → document store or a JSON column
  • Scanned receipts → unstructured → store as files or objects, keep their metadata in a queryable store

One platform therefore often needs more than one kind of store.

Scaling databases: replication, sharding, caching

Use replicas to distribute reads, shards to divide the dataset and caches for hot data. Separate read caching from the durability policy for writes.

Read replication scales reads

  • Only the master accepts writes
  • Read replicas → full read-only copies
  • Clients are routed to any replica for reads
  • If a replica is down, others serve
  • Small replication lag → reads can be slightly stale

Sharding scales writes (and reads)

  • Shard → a subset of data (horizontal partitioning)
  • One master per shard, partitioned across machines
  • Locator service → tells clients which master owns which shard

Algorithmic sharding removes the locator

  • Algorithm sits in the client, like a HashMap
  • Fixed sharding key → may distribute poorly
  • Hash-based partitioning → distributes more evenly
  • If shards change, masters publish events

Caching: read and write modes

  • Read-through → fetches from the database on a cache miss
  • Write-through → acknowledge only after the backing store has accepted the write under its durability policy
  • Write-behind (delayed flushing) → acknowledging an in-memory write first risks data loss if the cache fails

The lecture mentions both durability and pre-flush loss; distinguish the acknowledgement timing.

Read replica
Read-only copy of the full dataset.
Shard
A subset of the data with its own master.
Locator service
Tells clients which shard master owns which data.
Write-through
Write via the cache to the backing store before acknowledging success; durability depends on that store’s guarantee.

Check yourself

Writes saturate the primary database at peak, so the team adds three more read replicas. What effect will this have?

Almost no effect on the bottleneck.

  • Replicas are read-only copies; every write still goes to the single master
  • To spread writes, shard the data → each shard has its own master → improves both write and read throughput

Sharding costs routing, either a locator service or a client-side algorithm, and makes queries across shards harder.

Orders are sharded by country, and 70% of orders come from one country. What happens, and what would you change?

That shard's master becomes a hot spot while the others sit idle.

  • Cause: a fixed sharding key does not distribute data evenly
  • Change: hash-based partitioning on a high-cardinality key such as order ID → spreads load more evenly
  • With algorithmic sharding, the client computes the shard without a locator

Cost: you lose locality, since one country's orders are now spread across shards, and shard changes must be announced to clients.

A cache in front of the database acknowledges writes from memory and flushes them to disk every 30 seconds. Is that acceptable for payments? For page-view counters?
  • Payments: not acceptable
    • If the cache fails before flushing → acknowledged payments are lost
    • Use write-through: acknowledges only after the backing store has the write
    • Accept slower writes for durability
  • Page-view counters: acceptable
    • Losing a few seconds of counts is usually acceptable
    • Delayed persistence can buy the speed of in-memory writes
Reads are routed to replicas. After updating their profile, some users see the old version on the next page load. Diagnose the problem and suggest fixes.

Replication lag: the write reached the master, but the replica serving the next read has not caught up.

  • Fix: route a user's reads to the master for a short time after they write
  • Fix: read critical views from the master

Either way the master takes more read load, so accept lag wherever stale data is harmless.

CAP: consistency vs availability

CAP constrains behaviour during a network partition. Decide whether refusing some operations or serving potentially inconsistent data is acceptable for the business.

CAP: three properties

  • Consistency → operations behave as if using one current copy
  • Availability → requests to non-failing nodes receive results rather than being refused to preserve consistency
  • Partition tolerance → accounts for network links failing between nodes

During a partition, a distributed system cannot guarantee both C and A for all operations.

CP vs AP behaviour

  • CP → reject or delay operations that cannot be answered consistently
  • AP → keep accepting operations on separated nodes, allowing divergence and later reconciliation

Outside a partition, CAP does not require choosing only consistency or availability.

Interpreting the lecture examples

  • Master-only read path → illustrates a CP choice when an isolated node cannot serve inconsistent data or take over unsafely
  • Read routing alone is not proof: failover, replication and write acknowledgement also matter
  • A stale replica read alone does not establish full AP availability

Business requirement first

  • Stale feed or cart → may be preferable to no service
  • Payment balance → may justify refusing an unsafe operation
  • Make the choice per operation, then check the implementation

A convenient data model does not determine CAP behaviour.

CAP theorem
During a network partition a store must choose consistency or availability.
CP system
Keeps consistency, may refuse some requests.
AP system
Stays available, may return stale reads (eventual consistency).

Check yourself

A shopping cart is replicated across two regions, and the network between them fails. Should the cart stay available or refuse changes?

Stay available (AP).

  • A slightly stale or diverging cart is better than no cart
  • The lecture's point: this is a business decision more than a technical one
  • Cost: reconciling the diverged copies when the partition heals
  • Risk: a user briefly sees an old cart

Checkout, which takes money, may still need a stricter rule.

A payments ledger is replicated across two data centres, and the link between them fails. What should the system do?

Favour consistency (CP).

  • Refuse or delay the operations that cannot be applied consistently, such as debits on the side that cannot reach the authoritative copy
  • → Rather than risk double-spending
  • Some customers get errors during the partition, which the business accepts as the lesser harm for money
  • Reads of the balance may also be refused or marked as possibly stale
The lecture's shortcut says that if reads go to the master only, the system is CP. What must you check before relying on that?

Check what happens during a partition:

  • Can an isolated old master still accept writes?
  • How does failover choose a new master?
  • When are writes acknowledged relative to replication?

If failover can promote a replica that missed acknowledged writes, the system is not as consistent as the shortcut suggests: master-only reads are the lecture's simplified illustration, not a full guarantee.

A teammate says their single-node database avoids the CAP trade-off entirely. How do you respond?

True but beside the point.

  • A single instance is not a distributed system → CAP does not apply
  • But it is also a single point of failure
  • The lecture says distributed datastores must tolerate partitions → once you add a replica for availability or scale, you must choose consistency or availability for partition time

The single node has avoided the choice by giving up availability whenever it fails.

Why NoSQL and polyglot data models

Platforms have unique, changing requirements, so they use several databases, and NoSQL fills the gaps RDBMS leaves.

Each platform differs

  • Write-heavy
  • Read-heavy
  • Analytics-based consumption
  • Varied query patterns
  • Scalability/availability needs
  • Schema changes are the norm in fast-moving platforms

CQRS

Separate the model accepting commands from the model serving queries.

  • Lecture flow →
    • writes update an RDBMS
    • events feed an event store
    • a projection builds an in-memory read database
  • The two sides scale independently
  • Asynchronous projection → reads can lag writes
  • CQRS does not inherently require all these components

NoSQL trade-offs

  • Can improve scale or latency via partitioning, replication, flexible records, workload-specific indexes
  • Transaction scope, consistency and durability vary by store and configuration
  • Flexible schema does not remove the need to validate records or evolve their meaning

NoSQL models covered

  • Key-value
  • Document
  • Column family (wide column)
  • Search engines
  • Graph
CQRS
Separating the write model from the read model so each scales independently.

Check yourself

In the lecture's CQRS design, a command succeeds but the next query still shows the old value. Is that necessarily a failed write?

No.

  • The command commits to the write store
  • The read database is updated asynchronously from published events → the query can run before the projection catches up
  • Check event delivery and projection progress before suspecting the write

This lag is the price of scaling reads and writes independently.

To reduce operational cost, an architect wants one database technology for the whole platform. The platform has a write-heavy telemetry feed, a product catalogue whose attributes change often, and a social graph. How do you respond?

One model rarely fits all three.

  • Telemetry: write-heavy and sparse
  • Catalogue: needs schema flexibility and rich queries
  • Social graph: about traversing relationships
  • The lecture notes that most modern platforms use multiple databases for exactly this reason

The architect's concern is real, since every extra store adds operations work → add a store only where the workload clearly needs it.

Order history is read about 100 times for every write, while writes need strict validation. Would CQRS help, and what would it cost?

Yes.

  • Commands → a write API with full validation → the write store
  • Events are projected into a read model shaped for the history screens
  • Read APIs scale independently of writes
  • Cost: the lag between a write and its appearance in the read model, plus the work of running the event flow and projections

If users must see their own change immediately, serve that view from the write side.

Key-value stores

The lecture’s hash-map model makes exact-key lookup cheap; arbitrary field and range queries need additional indexing or a different model.

Key-value: problem solved

  • Given a key, fetch the whole record as fast as possible (in memory)
  • Roughly a distributed HashMap with unique keys replicated across servers
  • Uses →
    • shopping carts (Amazon, Alibaba)
    • recently uploaded files (Box)
    • Istio rate limits
    • cache
    • session cache
    • application config

Key-value: strength and limit

  • Strength → a hash-style key lookup is fast
  • Limit → does not automatically provide ordered range scans or queries on value fields
  • Lecture emphasises in-memory stores → their capacity and persistence policy affect cost and durability
  • Those traits should not be assumed for every key-value implementation

Redis in the lecture

  • In-memory store with richer data structures
  • Illustrated with reads and writes through one shard master
  • Labelled CP
  • Preserve that example, but check actual partition and failover behaviour before claiming consistent failover or no data loss
Point query
Lookup of one record by its exact key.

Check yourself

Shopping carts are kept in a key-value store for fast lookup by cart ID. A product team now wants 'all carts updated in the last hour' from the same store. Advise.
  • Key-value stores are built for point queries by key; range queries are expensive by design → this would mean scanning everything
  • Instead: publish cart updates to a store or index built for that query, or maintain a separate time-ordered index
  • Keep the key-value store for what it does best
A team plans to keep two terabytes of rarely read historical records in an in-memory key-value store because lookups are fast. What would you point out?
  • Most key-value stores keep everything in memory and flush to disk occasionally → need large amounts of memory, and persistence affects performance
  • Paying for memory to hold cold data wastes the store's strength
  • Keep hot data there, such as carts, sessions and rate-limit counters
  • Move historical records to a cheaper store suited to infrequent reads
The lecture's key-value architecture sends all reads and writes for a key through its shard's master and labels it CP. What does that mean during a partition, and what should you still verify?
  • During a partition: if a shard's master is unreachable, its keys are unavailable until failover, rather than being served stale from a replica
  • Verify how failover works and when writes are acknowledged: promoting a replica that missed recent writes can lose acknowledged data

The CP label describes the illustrated design, not every configuration of every product.

Document stores

Embed related records in JSON documents to avoid some joins. Evaluate query indexes, transaction scope and validation needs for the chosen store.

Document store: problem solved

  • Richer querying on all fields without the limits of a strict schema
  • Uses →
    • eBay search suggestions and product catalogue
    • MetLife client 360
    • Shutterfly image store
    • RDBMS replacement

Document model

  • Nest related child data inside a parent document → for example an order with line items
  • So one fetch can return it
  • Flexible fields ease evolution
  • But old and new record shapes still need validation and compatible readers

Document trade-offs (lecture)

  • Field indexes support rich queries
  • Embedding avoids many joins
  • Deck warns about →
    • joins
    • complex transactions
    • SQL
    • constraints
    • triggers
  • MongoDB has some join support

These are comparison points to verify for the chosen product, not universal absences across document stores.

MongoDB in the lecture

  • JSON-style CRUD
  • Master-based architecture, labelled CP
  • Use that as the illustrated configuration; consistency still depends on replication, failover and operation settings
Embedding
Nesting child entities inside the parent document.

Now read slides 31–37 →

Check yourself

An order, its line items and its shipping address are always read and written together, and the attributes vary by product type. Document or relational store?

A document store.

  • Embed the line items and address in the order document → one id-based fetch returns everything
  • The schema-free model handles varying attributes
  • Works because the order is the natural unit of reading and writing

The relational model would fit better if line items were updated independently by many processes, or reporting needed joins across orders and products.

A team wants to move its accounting system, which depends on joins, constraints and triggers, to a document store for schema flexibility. Advise.

Keep it relational.

  • The lecture warns most document stores lack joins, complex transactions, SQL, constraints and triggers
  • Accounting relies on exactly those to protect integrity
  • Schema flexibility does not justify losing those guarantees

A document store could still serve a derived, read-only view if some screens need flexible documents.

Column family (wide column) stores

Write-heavy, sparse, massively scalable nested maps keyed by row key, column key and timestamp.

Column family: problem solved

  • Write-heavy workloads (tens of thousands of records a second)
  • Very flexible and sparse schema
  • Fetch an entire record by key
  • Uses →
    • web crawl store (Google, Yahoo)
    • Facebook inbox search and messenger (Cassandra then HBase)
    • Mozilla crash data
    • Twitter data backup for analytics

Wide-column structure (lecture)

  • A distributed nested map indexed by row key, column family/qualifier and a timestamp version
  • Rows may have different columns
  • This is the HBase-style example → use its keys to reason about retrieval, rather than assuming all wide-column products expose an identical key model

Column family trade-offs

  • Sparse rows and partitioned storage suit high write volume
  • Plan queries around the row key
  • Joins are not the normal access path; secondary indexes may be costly
  • SQL-like interfaces (lecture) → CQL for Cassandra, Phoenix over HBase
  • Scale still depends on partition balance and query shape

HBase

  • Each region owned by a single server
  • Replication via HDFS (typically 3 replicas)
  • A CP system
Column family
Group of related columns; column key = family.qualifier.
Wide column
Another name for column-family store; columns can vary per row.

Check yourself

A fleet of sensors sends 50,000 readings a second, each sensor reporting a different, sparse set of fields. The main query is 'all readings for sensor X over a time range'. Which data model fits, and how would you design the key?

A wide-column store.

  • Linearly scalable, handles very high write volumes
  • Lets each row have a different set of columns
  • Design the row key around the query, e.g. sensor ID plus time → one sensor's range is read contiguously
  • The key must spread writes across shards → avoid keys where all current writes land on one region
Later, analysts want 'every sensor whose temperature ever exceeded 80' across the whole fleet. What happens with the wide-column design, and what would you do?
  • Nothing in the row key supports that query → it needs a full scan or a secondary index, which the lecture says is significantly slower and expensive
  • A wide-column store is not a general-purpose database, and there are no joins
  • Do: copy the data into an analytics engine, such as SQL over files, or a store designed for that query

Search engines

Elasticsearch-style stores for ranking, range, wildcard, filtering and aggregations, not as a primary store.

Search engine: problem solved

  • Advanced queries →
    • ranking
    • point
    • range
    • wildcard
    • filtering
    • aggregations
  • Uses →
    • StackOverflow search
    • GitHub code search
    • Netflix service operations and security logs
    • LinkedIn and Medium production debugging (logging)

Use as a derived search index

  • Tokenisation, analysis and index maintenance add write cost
  • Lecture warns against relying on it for relational-style joins and transactions
  • Keep authoritative payment/order data elsewhere; rebuild the searchable view from that source

Search engine architecture

  • Data nodes → hold searchable data
  • Master → manages cluster-wide metadata, node membership and shard allocation
  • Lecture labels Elasticsearch AP
  • That shorthand does not guarantee every request succeeds during every failure → analyse the concrete topology and operation
Tokenisation
Splitting text into searchable terms during indexing, which slows insertion.

Now read slides 44–48 →

Check yourself

A team proposes writing orders only to the search engine, since it already powers order search and returns results quickly. Do you agree?

No. The lecture says search engines are not recommended as a primary datastore.

  • Insertions are slow because of tokenisation and analysis
  • No joins or transactions
  • Keep orders in a transactional system of record and derive the search index from it
  • Accept a short delay before new orders become searchable

The index can then be rebuilt from the source if it is lost or corrupted.

Product search needs ranking, wildcards, filters and aggregations over ten million products, whose source of truth is a document store. Design the data flow, and say where search results must not be trusted.
  • Data flow: publish product changes from the system of record → an indexer updates the search engine
  • Ranking, wildcard, range and filter queries run there
  • The lecture's search architecture is AP → results can be briefly stale or inconsistent

Fine for browsing, but stock levels and prices at checkout must be read from the system of record.

Graph stores, SQL over files, and choosing

Use graph models when traversing relationships is central. SQL-over-files engines provide a query layer over externally stored analytical data.

Graph stores: relationships are the point

  • Shine for →
    • social graphs
    • organisation dependencies
    • clusters and similarity
    • key members of a cluster
  • Uses →
    • Adidas real-time recommendations
    • eBay logistics and routing
    • investment banks analysing client-fund relationships
    • VCs analysing which investors co-invest
  • Example → Neo4j

Graph trade-offs

  • Traversals crossing machine boundaries add coordination and network cost → partitioning is difficult
  • Broad aggregations can require large scans; not every aggregation necessarily visits every node
  • Choose by traversal shape, dataset and distribution needs

SQL over files

  • Lecture groups Hive, Athena, BigQuery and Snowflake
  • They do SQL parsing, job generation and metadata management over files
  • Learn the separation of query compute from stored data
  • The broad label "not a database" is a teaching simplification, not a reliable classification of every listed analytics product

Choosing a datastore overall

  • Key-value → fastest key lookup (carts, sessions, caches)
  • Document → rich querying with flexible schema
  • Column family → write-heavy sparse data at massive scale
  • Search engine → advanced search and logs
  • Graph → relationships
  • SQL-over-files → analytics on stored files
Graph database
Stores entities and relationships and answers connection queries by traversal.
SQL over files
Engines like Hive/Athena that run SQL on files via parser, job generator and metadata manager.

Check yourself

A venture-capital firm wants to find investors who co-invest with investors who co-invested with investor X, three hops out. Which data model fits, and what are its limits?

A graph store.

  • The question is about relationships between things → traversing a few hops is natural there, whereas relational joins three levels deep get expensive
  • Limit: horizontal scaling is hard, because splitting a graph across machines needs costly coordination
  • Limit: aggregations require traversing the entire database

Keep it for relationship queries and do the totals elsewhere.

Analysts want ad hoc SQL over five years of log files already sitting in file or object storage, a few times a week. Would you load them into a relational database or use a SQL-over-files engine?

Use a SQL-over-files engine.

  • Not a database but a SQL parser, job generator and metadata manager over the existing files → nothing has to be loaded or managed in tables
  • Suits occasional analytical queries over large data

Trade-off: individual queries are slower than on an indexed transactional database, and it does not manage transactional records, so it is not a replacement for the application's store.

Exam-style questions

Answer aloud or on paper before opening.

A global shopping app needs a cart, a product catalogue with varied attributes, order history with financial integrity, product search, and 'customers also bought' recommendations. Choose a data model for each, justify it, and name the main cost of the overall design.
  • Cart → key-value store: fast lookup by cart ID, replicated and kept available during partitions, since a stale cart beats no cart
  • Catalogue → document store: nested, varying product attributes fit schema-free documents
  • Orders → relational store: ACID transactions and constraints
  • Search → search engine index derived from the catalogue, never the primary store
  • Recommendations → graph store: traverse customer-product relationships

Main cost: operational: five stores to run, plus the event flows that keep the derived ones in step → drop any store whose workload does not justify it.

Using CAP, decide how (a) a social media timeline and (b) a payments ledger should behave during a network partition between data centres, and explain why the decision is a business one.

During a partition a distributed store must choose: keep answering and risk stale or divergent data (AP), or refuse some operations to stay consistent (CP).

  1. (a) Timeline → stay available: some posts are better than none, and stale feeds are a minor annoyance
  2. (b) Ledger → prefer consistency: reject debits it cannot apply safely, because a wrong balance costs far more than a temporary error
  3. Business decision: the question is which harm users and the company can tolerate, not which technology is better
A ticketing platform must accept 60,000 seat purchases in the first two minutes of a sale. The database has one primary and one read replica, and performance tests show write throughput is the bottleneck. Propose a plan to scale writes, including the changes to software, and identify two side effects to monitor.

Replicas cannot help, because all writes go to the one primary.

  1. Shard the seat inventory, e.g. by hash of event and seat block → each shard has its own master
  2. Software change: services need shard-aware routing, through a client-side algorithm or a locator service
  3. Serve the heavy seat-map reads from a cache or a CQRS read model → the shards spend their capacity on purchases
  4. Use write-through for anything that must not be lost
  5. Monitor
    • (1) Hot shards: one popular event can concentrate writes on one master
    • (2) Staleness of cached or projected seat maps → can show seats as free after they are sold

Cross-shard queries such as sales reports also get harder.

When would you avoid a document store for a new service, and what would you use instead? Give two concrete cases.
  • Case 1: joins, multi-record transactions, constraints → relational store
    • Avoid it when the service relies on joins across many entities, multi-record transactions, or enforced constraints and triggers, which most document stores lack
    • e.g. an accounting or ledger service should use a relational store
  • Case 2: write-heavy stream → wide-column store
    • Avoid it when the data is a write-heavy stream of sparse, timestamped records read by key and time range, where a wide-column store fits better
  • Also: when the core queries traverse relationships → a graph fits

A document store remains a good choice when an entity and its children are read and written as one unit and the schema keeps changing.

Compare a key-value store and a wide-column store for an IoT platform that writes 50,000 readings a second and reads 'last value for device X' and 'device X over the past week'. Which would you choose, or would you use both?
  • Key-value store
    • Answers 'last value for device X' fastest, as an in-memory point lookup
    • Handles range queries poorly and needs a lot of memory for history
  • Wide-column store
    • Absorbs heavy writes, scales linearly
    • Serves 'device X over the past week' well if the row key is device ID plus time
  • Defensible design: use both: wide-column for the history + a key-value cache for the latest value
  • Cost: writing each reading twice and running two stores

If the last-value query is rare, the wide-column store alone is enough.

Order history is read far more often than it is written, writes go through strict business validation, and the history screens need a different shape from the write model. Design a CQRS solution, and say what users might notice and how you would limit it.
  • Write side: commands → a write API with full validation → a relational write store; each committed change publishes an event
  • Read side: a projector builds a read model shaped for the history screens, e.g. documents or an in-memory read store, served by read APIs that scale independently
  • Users may notice: not seeing a change they just made, because projection is asynchronous
  • Limit it: serve 'my latest order' from the write side, or show it as pending until the projection catches up
  • Monitor projection lag and make the projector idempotent so replays do not duplicate history
