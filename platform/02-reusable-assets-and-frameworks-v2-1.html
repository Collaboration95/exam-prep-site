Reusable Assets and Frameworks

61 slides · about 29 min · open the deck · JSON

Platforms offer reusable services, frameworks and shared libraries. Domain-Driven Design (DDD) helps find cohesive service boundaries through bounded contexts and ubiquitous language, then shapes their internals with aggregates and domain events. The Scrum and Maid2Order cases apply these ideas; the final sections explain framework design and the coupling risks of shared libraries.

Big ideas

  • Three reusable assets by scale of reuse: services (across features and use cases), frameworks (to build many clients and services), shared libraries (smaller, ad-hoc reuse among clients and services).
  • A reusable service is long-lived, single-responsibility (stable, cohesive), loosely coupled and horizontally scalable on its own.
  • DDD finds service boundaries: strategic design (bounded contexts, ubiquitous language, subdomains, context mapping) is coarse-grained; tactical design (aggregates, domain events) is fine-grained.
  • A bounded context is a semantic boundary inside which each entity has one specific meaning, described by one ubiquitous language; the same word (e.g. Policy) can mean different things in different contexts.
  • The lecture recommends one owning team, source repository and database schema per BC; a team may own several BCs. These support clear service boundaries.
  • Without bounded contexts a domain model grows into a Big Ball of Mud: tangled models, blurred languages, no explicit boundaries.
  • DDD supports domain cohesion and loose coupling in IDEALS; it does not automatically supply delivery automation, resilience or an appropriate consistency policy.
  • Good frameworks are simple, scenario-driven and layered (simple things simple, complex things possible); shared libraries couple services and clients, so apply DRY within a service but relax it across services.

Reusable assets in a platform

The three kinds of reusable asset in a platform and how their scale of reuse differs.

Where the assets sit

A platform's architecture has:

  • Clients → iOS, Android, web browser
  • API gateway, web server, service registry, WebSocket server
  • Microservices in containers, application servers
  • Data stores, event queues
  • SMS and email gateways
  • Identity services → IAM, OpenID provider

Each client and service is built from reusable assets: services, plus frameworks (FW) and shared libraries (LIB) on both client and server sides.

Three kinds of reusable asset

  • Services: reusable across features or use cases
    • e.g. the Customer service can be used by both the Purchase and Delivery services
  • Frameworks: reusable to build multiple clients and services
    • e.g. Spring Boot can be used to build both the Purchase and Delivery services
  • Shared libraries: reusable across multiple clients and services, at a smaller scale than frameworks
    • e.g. a Purchase shared library lets the Purchase client and service share common entities

Order of scale and course goals

  • Services and frameworks → enable larger-scale reuse
  • Libraries → smaller-scale, ad-hoc reuse
  • Course goals:
    • design reusable components from domain analysis
    • design common services
    • architect frameworks
Reusable service
A service reused across features or use cases (e.g. Customer service used by Purchase and Delivery).
Shared library
Classes shared among services, among clients or across both.

Check yourself

The Purchase client and the Purchase service both need the same Order entity classes, and the Purchase and Delivery services both need customer details. Which kind of reusable asset fits each need?
  • Order entities → a shared library used by the Purchase client and service → reuse of classes at a small scale
  • Customer details → a Customer service that Purchase and Delivery both call → reuse of a business capability across features

Each choice has a cost: the library ties client and service releases together; the service adds a remote call.

A platform team must build ten new services quickly, all with the same web conventions, configuration and request handling. Should it reuse a service, a framework or a shared library?

A framework, such as Spring Boot in the lecture.

  • Framework → reused to build many clients and services, giving them a common structure and behaviour
  • Not a service → provides a capability at runtime, not a way to build services
  • Not a library → supplies classes without imposing the overall structure

Catch: a good framework is expensive to design → pays off only when many services will use it.

Identifying reusable services with DDD

What makes a service reusable, why DDD is used to find service boundaries, how it differs from OOAD and how it relates to IDEALS and onion architecture.

Characteristics of a reusable service

  • Used for the long haul → maintainable, extensible, resilient
  • Stable and cohesive functions → single-minded, under the Single Responsibility Principle
  • As decoupled as possible → even message-driven for the loosest coupling
  • Horizontally scalable → without depending on the scalability of other services

Service boundaries should be aligned with business requirements and facilitate those characteristics.

DDD finds the boundaries

DDD is the technique for finding the service boundaries:

  • Identifies services
  • Maps dependencies among them
  • Groups domain entities into right-sized clusters

DDD definition (Eric Evans)

An approach to complex software that:

  • Connects implementation to an evolving model
  • Focuses on the core domain and domain logic
  • Bases complex designs on a model of the domain
  • Collaboration → technical and domain experts iteratively refine a conceptual model

Coined by Eric Evans.

DDD vs OOAD

The lecture contrasts:

  • OOAD → progression from use cases to analysis, design and framework objects
  • DDD → focus on domain objects; useful for finding cohesive service boundaries
  • Caveat → technical concerns still need engineering outside the domain model

IDEALS principles

  • Interface segregation → gives each client a suitable contract
  • Deployability → requires automated packaging and release
  • Event-driven interaction → loosens coupling
  • Availability over consistency → allows delayed updates where the business permits
  • Loose coupling → limits ripple effects
  • Single responsibility → keeps services cohesive

DDD supports the domain design; DevOps supplies deployment automation. Neither availability nor resilience follows from DDD alone.

DDD and onion architecture

  • Independent object model → the application is built around it
  • Inner layers define interfaces, outer layers implement them
  • Coupling points toward the centre
  • Application core can be compiled and run apart from infrastructure

Onion layers, centre outward

  1. Domain Model → entities, value objects
  2. Domain Services
  3. Application Services
  4. Outer ring → user interface, infrastructure (DB, file system, web services) and tests

DDD concentrates on the domain services and domain model at the core.

DDD
Domain-Driven Design: modelling the core domain collaboratively with domain experts to drive design (Eric Evans).
Single Responsibility Principle
A service has one cohesive purpose and one reason to change.
IDEALS
Interface segregation, Deployability, Event-driven, Availability over consistency, Loose coupling, Single responsibility.
Onion architecture
Layered design with the domain model at the centre; dependencies point inward only.

Check yourself

A proposed Customer service can scale only when the Order service scales with it, because the two share an in-process session cache. Which reusable-service characteristic does this break, and what would you change?
  • Breaks: horizontal scalability without depending on other services, and loose coupling
  • Change: give each service its own state; talk through its interface or messages (the lecture's loosest coupling)

Cost: some duplicated data and accepting eventual consistency between the two.

A team used DDD to find well-bounded services, but each release still takes a week of manual packaging and deployment. A manager blames the domain design. Do you agree?

Mostly no.

  • DDD produces designs that satisfy the IDEALS principles except Deployability
  • Deployability comes from DevOps automation of packaging and deployment → fix is pipelines, not boundaries

The manager would have a point only if the boundaries force several services to be released in lockstep → that is a coupling problem in the design.

In a code review, a domain entity class imports the database driver and saves itself. Which onion-architecture rule does this break, and why does it matter for a reusable service?
  • Rule broken: dependencies must point toward the centre
  • Inner layers define interfaces; outer layers implement them → the application core compiles and runs without infrastructure
  • Fix → define a repository interface in the core and implement it in the outer layer
  • Why it matters → the core can then be tested and reused with a different store

Cost: one more interface and adapter.

While modelling a service with DDD, a team adds RetryPolicy and HttpClientWrapper classes to the domain model. Should these be there?

No.

  • DDD focuses squarely on domain objects and leaves out non-domain concerns
  • OOAD, by contrast, would add design and framework objects in later stages
  • Retry and HTTP handling still need designing → in the outer layers around the domain model
  • Mixing them in → blurs the ubiquitous language and ties the core to infrastructure

DDD strategic and tactical design

The two levels of DDD and the toolkit of each: bounded contexts, ubiquitous language, subdomains and context mapping (strategic); aggregates and domain events (tactical).

Two levels of design

  • Strategic design → coarse-grained concerns: how the whole system is divided
  • Tactical design → fine-grained concerns inside a context

The nesting

  1. System contains bounded contexts
  2. Each bounded context contains aggregates
  3. Each aggregate groups domain entities
  4. Domain entities are named in the ubiquitous language

Strategic tools

  • Bounded contexts → define semantic boundaries
  • Ubiquitous language → names concepts precisely within each boundary
  • Core, supporting and generic areas → identify business importance
  • Context mappings → describe integration

The lecture illustrates these areas as BCs, but their business role and their language boundary answer different design questions.

Tactical tool: Aggregate

A collection composed of related entities, treated as a unit. Textbook rule:

  • One root entity
  • Consistency and transaction boundary
  • Outside objects reference only the root
  • Small → each aggregate is small

Tactical tool: Domain Event

  • Definition → a record of a business-significant occurrence in a bounded context
  • Example → the backlog item committed event (the lecture's Scrum example)
  • Named in the past tense
  • Carries information to other aggregates, inside the same context or in another
  • Loose integration → contexts integrate loosely instead of through shared tables

Worked example

  • Bounded Context 1 → the core domain, holding Aggregates 1A and 1B
  • Bounded Context 2 → a subdomain, holding Aggregate 2A
  • Context mapping → joins the two contexts
  • Domain event emitted from Aggregate 1A → triggers reactions in 1B and in 2A

Why it matters here

  • Strategic design → answers where service, team, repository and database boundaries go
  • Tactical design → shapes what is inside each service and how services communicate
  • Events → fit the Event-driven and Loose-coupling IDEALS principles

Check yourself

You receive a 60-entity domain model for a new platform and two weeks to propose services. Do you start by designing aggregates or by drawing bounded contexts?

Bounded contexts first.

  • Strategic design = coarse-grained: divides the domain into contexts, sets each one's ubiquitous language, classifies core and subdomains
  • Aggregates = tactical, fine-grained clusters inside one context
  • Aggregates first → risks clusters that cut across what should be separate contexts

Revisit the context boundaries once aggregate design shows where invariants really sit.

When a backlog item is committed to a sprint, the resource-management context must update team availability. A teammate proposes that resource management reads the core context's tables directly. What would you use instead, and why?

Use a domain event, not direct table reads.

  • Core publishes a domain event, e.g. BacklogItemCommitted
  • Resource management reacts to it in its own transaction
  • Why: each context keeps its own schema and model → the core can change its tables without breaking a consumer

Price: eventual consistency → availability is updated shortly after the commit, not in the same transaction.

An e-commerce firm wins business through its pricing and recommendation engine; identity, billing and notifications look like everyone else's. Which is the core domain, and what does that classification change in your design?
  • Core domain: pricing and recommendation → the context critical to the business
  • Supporting or generic subdomains: identity, billing, notifications
  • What the classification changes:
    • where the model needs the most refinement
    • which generic contexts are candidates to split out and reuse across systems

Bounded contexts and ubiquitous language in depth

The service-identification questions BCs and UL answer, how BCs map to teams, repositories and databases, why a single model becomes a Big Ball of Mud, and how to find BCs.

Questions BCs and UL answer

  • Extract → how to extract domain entities from requirements, and who should be involved
  • Segregate → how to segregate entities into services
  • Name → how to name entities consistently within a service and resolve name clashes across services
  • Assign → which team, source repository and database each service gets

Ubiquitous Language (UL)

  • Definition → the language used among team members and implemented in the software model
  • Must be rigorous → strict, exact, tight
  • Analogy → like the official languages of EU nations

Bounded Context (BC)

  • Definition → a semantic contextual boundary within which each entity has a specific meaning and does specific things
  • Transcends problem and solution spaces → BCs appear in discussions of the problem and are where solutions are implemented

DDD is primarily about modelling a UL in an explicitly bounded context.

BC to team, repository, database

  • One BC → exactly one team (a team may work on several BCs)
  • Own source code repository → holds source, acceptance tests and unit tests together
  • Own database schema
  • The team defines the BC's official interfaces
  • Cleanly separates responsibilities → some firms go further, e.g. Amazon's 'You built it, you run it'

Boundaries of a BC can also be the boundaries of services, repositories and databases.

Without BCs: the Big Ball of Mud

  1. Starts: a system begins with a few entities
  2. Piles more onto the same domain model as features arrive
  3. Ends with multiple tangled models, blurred languages and no explicit boundaries

With BCs: embrace differences

  • DDD embraces differences → segregates entities into different BCs, each with its own language
  • Policy example → the same name means different things in the contexts:
    • Underwriting
    • Claims
    • Inspections
  • Each context has its own Policy model
  • Alignment → business stakeholders and technical teams must align on each entity's meaning per context

Benefits of BCs

  • Functionally cohesive entities → non-cohesive entities are pushed to other BCs
  • One UL specifies all entities in a BC
  • Multiple BCs prevent monolithic design
  • Smaller test sets per BC
  • Teams assigned per BC

How to identify BCs

  • Involve both software developers and domain experts (possibly different experts per business function)
  • Don't be consumed by technology → developers must not ignore the business; the domain model is more complex than the technical aspects
  • Extract entities from the domain experts' mental model
  • Brainstorm and iterate to a combined domain model
  • Challenge whether each entity belongs in the UL
Big Ball of Mud
Single model that has grown tangled, with blurred languages and no explicit boundaries.
Semantic boundary
Limit within which a term has one precise meaning.
You built it, you run it
Amazon's practice of the building team also operating the service.

Check yourself

Underwriting, Claims and Inspections all use the word 'Policy'. An architect proposes one canonical Policy entity shared by all three teams. Do you agree?

No.

  • Inside each bounded context, Policy has a specific meaning and does specific things
  • One shared entity → must carry every context's attributes and rules → coupled to all three teams
  • DDD → segregates them into separate models with their own ubiquitous language, translating at the boundaries

Cost: business and technical people must agree explicitly on what Policy means in each context.

Two teams share one repository and one database schema for the Claims bounded context, and both change its interfaces. What problems would you expect, and what does the lecture prescribe?
  • Expected problems:
    • conflicting changes to the model and interfaces
    • unclear ownership
    • schema changes from one team breaking the other
  • Lecture prescribes:
    • one team per bounded context (a team may own several)
    • a separate repository with source, acceptance and unit tests together
    • a separate schema
    • interfaces defined by the owning team

If the context is too big for one team, the boundary itself is probably wrong.

Every new feature adds entities to one shared domain model. The test suite now takes hours and teams disagree about what 'Account' means. Diagnose the problem and propose a fix.
  • Diagnosis: Big Ball of Mud → tangled models, blurred language, no explicit boundaries
  • Fix: split the entities by functional cohesion into bounded contexts, each with one ubiquitous language → 'Account' can mean different things in different contexts
  • Each context → a smaller test set; can become the boundary for a service, repository, schema and team

Cost: integration work between contexts that used to share objects.

A group of developers tries to find bounded contexts from the existing database schema alone, without domain experts. What is the risk?
  • Schema reflects the current, possibly tangled, model → tends to reproduce the Big Ball of Mud rather than the business's own boundaries
  • Lecture requires domain experts → their mental model drives entity extraction
  • Developers must engage with business aspects instead of being consumed by technology

The schema is useful evidence, but boundaries should come from iterating on a combined model with the experts.

Case study: splitting a model and developing the UL

Split the Scrum tool by business responsibility, then derive each context’s language and acceptance tests from concrete scenarios.

The case: a Scrum team tool

  • Scrum core → products, backlog items, releases, sprints and tasks
  • Collaboration → forums, discussions, shared calendars
  • Multi-tenant support → tiered plans and payments
  • Human-resource availability and utilisation
  • Likely more features later

Modelled as one domain model, this becomes a Big Ball of Mud.

The lecture's split

The single model is divided by functional cohesion into a core and supporting bounded contexts; the rest are subdomains, and the supporting context labels describe their entity groups.

  • Agile Project Management Core (the core domain) →
    • Product, BacklogItem, Release, Sprint, Task
    • ScheduledBacklogItem, CommittedBacklogItem
    • Volunteer, EstimationLogEntry
    • Team, ProductOwner, TeamMember
    • its own Discussion
  • Identity/tenancy context → Tenant, User, Role
  • Billing context → Account, Payment
  • Support context → SupportPlan, Incident
  • Collaboration context → Forum, Discussion, Post, Calendar, CalendarEntry
  • Resource-management context → ResourceManager, TimeConsumingResource, Schedule, Availability

Procedure behind the split

  1. Identify BCs by functional cohesion of domain entities
  2. Classify each as core or subdomain
  3. Split a BC further if the resulting BCs are more reusable across systems

Note: Discussion appears both in the core and in collaboration: the same name in two contexts, each with its own meaning and model, which is exactly what ubiquitous language per BC allows.

Developing the UL of a BC

  • Write concrete scenarios describing how the domain model should behave, including:
    • nouns, verbs and adverbs
    • pre-conditions, post-conditions and constraints
  • Entities → likely to be the nouns
  • Some nouns → really properties of an entity
  • Some properties → group into an entity
  • Entities must live inside the BC

Acceptance test (Given / When / Then)

  1. Given:
    • a backlog item scheduled for release
    • the product owner
    • a target sprint
    • quorum approval
  2. When the owner commits the item
  3. Then it is committed and BacklogItemCommitted is created
  4. If moving it between sprints → uncommit the old association and notify both sprints

Conditions and outcomes make the shared language testable.

Concrete scenario
Prose example of the domain model in action, with pre-conditions, post-conditions and constraints.
Executable specification
Given/When/Then restatement of a scenario that serves as an acceptance test.

Check yourself

From the scenario 'the product owner commits a backlog item to a sprint only if it is scheduled for release and a quorum of team members approved', a junior developer makes Quorum an entity. Do you agree?

Probably not.

  • Nouns are candidate entities, but some nouns are properties of an entity (lecture warning)
  • Quorum approval here is a pre-condition on the commitment → model it as part of the commitment rule

It would become an entity only if individual approvals must be tracked and changed over time.

A team records its ubiquitous language as a glossary document kept apart from the code and tests. What does the lecture's approach add?
  • Restate the concrete scenarios as executable Given/When/Then specifications → serve as acceptance tests
  • Language stays tied to verifiable behaviour, e.g. the backlog item becoming committed and the BacklogItemCommitted event being created

A separate glossary drifts from the code without anyone noticing.

In the Scrum tool split, Discussion appears in both the core context and the collaboration context. A reviewer flags it as duplication to remove. How do you respond?

It is not a defect.

  • Each bounded context has its own ubiquitous language and model → the same name can mean and do different things in each
  • Merging them → recreates a shared model that couples the core to collaboration features

What is needed is an explicit mapping between them wherever the two contexts interact.

Another product line also needs tenant billing with accounts and payments, which the Scrum tool already has in its billing context. What does the lecture's procedure suggest?
  • Procedure: split a bounded context further if the resulting contexts are more reusable across systems
  • Keep billing as a separate generic subdomain with no dependency on project-management concepts → the other product can reuse it

The billing context then needs a stable interface and an owner who serves both consumers.

Workshop: Maid2Order entities, BCs and ULs

Applying the technique to a platform that connects customers with maid agencies: the lecture's sample solution turns the scenarios into seven service-sized bounded contexts with consistently named entities.

The task: Maid2Order

Maid2Order connects customers needing maid services with agencies that supply them.

  • Features:
    • management of agents, customers and maids
    • ordering of maid services and loans
    • billing and payment
  • From six concrete scenarios, identify:
    • domain entities and relationships
    • the BCs
    • name entities consistently from each BC's UL

What the scenarios supply

  • Enrolment and archiving lifecycles for agencies, customers and maids → system admin or agent admin registers, maintains particulars, archives on leaving
  • Automatic monthly billing of agencies for platform usage
  • Maids' daily job schedules
  • Customer orders:
    • one-time ad-hoc
    • usage plans OnceAFortnight, OnceAWeek, TwiceAWeek with preferential rates
  • Agency-to-agency maid loans:
    • ad-hoc
    • Weekly/Monthly plans
  • Billing frequency → depends on service type
  • Payments via gateway:
    • bank transfer, credit card, PayNow, or mailed cheque
    • auto receipt for electronic payments
    • admin-created receipt for cheques

Sample solution: seven service BCs

Seven service-sized BCs (stereotype service):

  • CustomerManager → Customer
  • UserManager → UserAccount, SystemAdmin
  • AgencyManager → MaidAgency, AgentAdmin, Maid, JobSchedule, PlatformUsage, PlatformMonthlyBill
  • MaidOrderManager → MaidUsage, MaidUsageBill, MaidUsagePlan
    • MaidUsagePlan specialised into OneTime, OnceAFortnight, OnceAWeek and TwiceAWeek plans
  • MaidLoanManager → MaidLoanUsage, MaidLoanBill, MaidLoanPlan
    • MaidLoanPlan specialised into OneTime, Weekly and Monthly
  • BillingManager → Bill
  • PaymentManager → Payment, Receipt
    • Payment specialised into Cheque and ElectronicPayment
    • ElectronicPayment specialised into BankTransfer, PayNow and CreditCardPayment

Lessons in the solution

  • Separate contexts → ordering for customers (MaidOrderManager) vs loans between agencies (MaidLoanManager)
  • Parallel but distinct names → MaidUsage vs MaidLoanUsage, MaidUsageBill vs MaidLoanBill
  • Billing is its own context → the platform monthly bill, maid usage bill and maid loan bill all lead to the common Bill, which Payment settles
  • Payment variants → modelled as specialisations
  • Relationships cross contexts → contexts integrate through references rather than shared models
    • Customer to MaidAgency
    • Customer to MaidUsage
    • JobSchedule to MaidUsage

Typical exam use

  • Expect a business narrative
  • Request for:
    • entities
    • BCs
    • names per UL
    • how contexts integrate, e.g. a maid-usage order leading to a bill and then a payment
  • The lecture's car rental samples (drawn in Visual Paradigm) → only illustrate the entity-relationship notation expected

Check yourself

A teammate proposes merging MaidOrderManager and MaidLoanManager into a single ServiceOrderManager, because both have plans, usages and bills. Do you agree?

No.

  • Different business functions: customer orders vs agency-to-agency loans, with different parties and plans
  • Plans
    • Customers: OnceAFortnight, OnceAWeek, TwiceAWeek
    • Loans: Weekly, Monthly
  • Own ubiquitous language each

  • Merged context → would change for two unrelated reasons and blur those terms

Maid2Order adds a new digital-wallet payment method. Using the lecture's sample solution, which contexts change, and which should not?
  • Changes: only PaymentManager → add a new ElectronicPayment specialisation alongside BankTransfer, PayNow and CreditCardPayment, still producing a Receipt
  • Unchanged: BillingManager, MaidOrderManager, MaidLoanManager → they deal with bills, and a payment simply settles a Bill

If they did need to change, that would show the payment details had leaked across the boundary.

A teammate proposes moving MaidUsageBill, MaidLoanBill and PlatformMonthlyBill into BillingManager so that every bill type lives in one place. Do you agree?

No.

  • Each specific bill belongs to the context whose business activity produces it
  • BillingManager holds only the common Bill they lead to
  • Pulling the specific types in → BillingManager depends on ordering, loan and platform-usage rules → changes whenever they do and cannot be reused elsewhere

Cost of the lecture's design: a translation from each specific bill to Bill at the boundary.

In the sample solution, Customer in CustomerManager holds only the customer's particulars. Where should the customer's current usage plan live, and why?

In MaidOrderManager, as a MaidUsage under a MaidUsagePlan that refers to the customer.

  • Why: ordering is that context's responsibility → CustomerManager stays small and reusable
  • The two contexts are linked by a reference, not a shared object

Cost: a screen showing both needs data from two services.

Reusable frameworks for platforms

What a framework is, why a platform provider standardises on frameworks, and examples (Java RMI, Singapore Government Tech Stack, DBS Developers Platform).

Characteristics of a reusable framework

  • Solves a specific domain problem (UI, data access) → with a set of communicating design patterns
  • Partial implementation of the domain architecture in a specific environment → e.g. Spring Web MVC for web applications; building those classes from scratch is not economical
  • Designed for reuse across systems
  • A system may need several frameworks for different layers:
    • Spring Web MVC → presentation and business layers
    • Spring Data → data access

Why a platform provider cares

  • Many constituent systems that may span enterprises and clients:
    • backend, legacy and partner services
    • web and mobile clients
    • each using multiple frameworks
  • Use frameworks to standardise and reuse:
    • common behaviours shared by services and clients
    • common interactions between services
    • common interactions between clients and services

Framework examples

  • Java RMI → a framework for remote invocation: stubs and a registry between client and server (lecture example: a weather app)
  • Singapore Government Tech Stack (SGTS)
    • problem: each agency builds its own services and infrastructure
    • answer: a common platform of tools and services on common infrastructure
    • agencies build digital services quickly with consistent, secure experiences and easy data exchange
    • examples: myinfo.gov.sg, mycareersfuture.sg
  • DBS Developers Platform → exposes 200+ consumer-banking APIs in 20+ categories
    • funds transfer, rewards, PayLah!, real-time payments
    • DBS does not share its design
Spring Web MVC
Framework for building web applications (presentation and business layers).
SGTS
Singapore Government Tech Stack: common platform of tools and services for agencies' digital services.

Designing frameworks well

Qualities of a good framework, the fundamentals and principles of framework design, the two process models and the pitfalls.

Eight design qualities

  • Simple → test simplicity with sample client code before fixing the API
  • Expensive to design → dedicated design effort
  • Full of trade-offs
  • Borrow from the past
  • Designed to evolve
  • Integrated
  • Consistent
  • Testable

Framework design fundamentals

  • Powerful and easy to use → simple things simple, complex things possible
  • 80/20 rule → concentrate on the important 20% of scenarios and APIs
  • Design explicitly for a broad range of developers and programming languages
    • styles, requirements, skill levels
    • e.g. a strongly typed API can trouble dynamically typed languages

Four design principles

  • Scenario-Driven Design → start with usage scenarios and sample client code
  • Low Barrier of Entry → make experimentation and error correction easy
  • Self-Documenting Object Models → names, types and exceptions explain simple uses
  • Layered Architecture → convenient common-case APIs over powerful lower-level APIs

Framework design process

  1. Analyse the domain and collect application examples
  2. Build an initial whitebox framework implementing them
  3. Use it to build other applications → find weak points and improve it, usually becoming more blackbox
  4. Release when suggestions for improvement become rare

Two development models

  • (1) Framework designers do not design applications
    • app designers extend the framework and give feedback
    • suits larger groups and external users
    • more popular
  • (2) Framework designers also build applications
    • alternating between extending and revising
    • suits small groups that can budget revision effort

Framework design pitfalls

  • Immature domain → misunderstanding and extra iterations
  • Unstable interfaces → ripple through application classes (unstable behaviour is easier to revise)
  • Unrepresentative original examples → valid applications left unsupported
  • Publishing prematurely → release only once proven and validated through small pilot projects
Whitebox vs blackbox framework
Whitebox is extended by subclassing and knowing internals; blackbox is used via configuration and composition without internals.
80/20 rule
Focus effort on the important 20% of scenarios and APIs.
Client-first programming
Write sample client code first to test whether an API is simple.

Users of your framework fall into two groups: beginners who want one call to send a payment, and experts who need control over retries and the wire format. How do you serve both?

Use a layered architecture.

  • Lower layer → rich, low-level types, exposes all the power
  • Higher layer → wraps it in convenient calls for the common case
  • Result → simple things simple, complex things possible, which a single-layer API cannot do

Cost: designing and keeping two consistent layers.

A three-person team is building a framework for its own applications; a 20-person team is building one for external partners. Which framework-design process model fits each?
  • Small team (three people, own applications) → the model in which designers alternate
    • between building applications on the framework
    • and consolidating good extensions
    • provided they can budget effort for revision
  • Larger group targeting external users (20 people, partners) → the more popular model
    • designers design and test
    • application builders extend it and give feedback
    • designers revise

That model only works if designers have enough time set aside for the revisions.

Partners are pressing for a framework, and the team wants to publish v1 to all of them after one internal application has used it. Advise.

Hold back.

  • One application is unlikely to be representative
  • Publishing while the design is still changing → unstable interfaces ripple into every partner's code
  • Instead: validate through a few small pilot projects; release once suggestions for improvement become rare

Partners wait longer but avoid painful rework, and 'you can always add, you cannot ever remove' argues against shipping half-finished parts just to have them.

A design review finds that one module of the framework names things and handles errors differently from the rest. Why is this a concern, and when could it be justified?
  • Consistency across the framework → promotes productivity and lets knowledge transfer from one part to another
  • A deviation signals that the part is genuinely different
  • Accidental inconsistency → sends that signal falsely → confuses users

Justified only when the module really has a unique consideration → then the difference should be deliberate and documented.

Shared libraries: use and pitfalls

What shared libraries share, their drawbacks, the DRY trap across services, client library pitfalls (Netflix vs AWS) and guidelines.

What shared libraries are

  • Classes shared among services, among clients, or across clients and services
  • What they share:
    • state specification → attributes of a super class
    • behavioural specification → abstract operations or interfaces
    • behavioural implementation → operations implemented in a super class
  • Essential building blocks of frameworks
  • Source → the platform provider or third parties

General drawbacks of shared libraries

  • Loss of true technology heterogeneity → language- and platform-specific
  • Independent scaling is curtailed → parts tied by library constructs (static variable, mutex)
  • Few obvious seams for resilience measures
  • A new library version needs redeploying the whole process → less of an issue for dynamically linked libraries
  • Shared communication code is a point of coupling → e.g. Java RMI brittleness: a changed endpoint needs new stubs that hit clients that did not need the change

DRY across service boundaries

  • Sharing domain-object code → services depend on one model, so a change can force coordinated releases
  • Keep each BC's model private
  • Within a service → avoid duplication
  • Across services → accept some duplication to preserve autonomy
  • Shared technical utilities → evaluate by their coupling cost

Client libraries: pros and cons

  • Pros → make services easy to consume and avoid duplication
  • Server logic can creep in (especially if one team owns both) →
    • erodes the server's cohesion
    • forces changes in many clients to roll out a server fix
  • Mandating them → limits clients' technology choices

Client libraries: Netflix vs AWS

  • Netflix: client libraries handle
    • service discovery
    • failure modes
    • logging
  • Netflix trade-off → make clients easy to run reliably, but coupling between clients and server is worrisome
  • AWS: exposes SOAP/REST APIs with SDKs
    • written by the community or an AWS team that does not work on the APIs → good separation
    • clients decide when to upgrade

Guidelines for client libraries

  • Separate transport-protocol handling from things specific to the destination service → clients on other technology stacks can still call the APIs
  • Let clients control when they upgrade the library → preserves the ability to release services independently

Summary of the topic

  • Reusable assets boost platform team productivity
  • Services and frameworks → larger-scale reuse
  • Shared libraries → smaller, ad-hoc reuse
  • DDD → identifies and designs services
  • Guidelines exist for frameworks
  • Overusing shared libraries → can unnecessarily constrain platform components
DRY
Don't Repeat Yourself: avoid duplicating system behaviour and knowledge.
Client library
Library that makes it easy for clients to call a service (e.g. an SDK).
Point of coupling
Shared code through which a change in one component forces change in others.

To obey DRY, a teammate proposes a common-domain library of Customer, Order and Payment classes used by all 12 services. Do you agree?

No.

  • Shared domain library couples every service to it → one change forces coordinated changes and redeployments across all 12
  • → undermines independent release and blurs bounded contexts
  • Lecture's rule: don't violate DRY within a service; be relaxed about DRY across services

Price: some duplicated code, which is cheaper than lockstep releases.

Your platform will publish client libraries for its APIs. Option A: the API team writes a smart client that handles discovery, failures and logging, and all callers must use it. Option B: thin SDKs maintained separately, with callers choosing when to upgrade. Choose.

Option B for a platform with varied consumers.

  • Option B, like the AWS SDKs → keeps clients loosely coupled to the server; they upgrade on their own schedule
  • Option A, the Netflix style
    • gets clients running quickly and reliably
    • but couples them tightly, invites server logic into the client
    • and limits technology choices if it is mandated

A could suit a single organisation on one technology stack that values uniform resilience.

After a fix to a shared library, three services that did not need the fix have to be rebuilt and redeployed, and a Python client cannot use the library at all. Which drawbacks are these, and what would reduce them?
  • Drawback 1: a new library version cannot be deployed without redeploying the whole process
  • Drawback 2: the library is language-specific → technology heterogeneity is lost
  • Shared communication code = a coupling point, much like regenerated RMI stubs
  • Reduce by:
    • not sharing code across service boundaries
    • separating transport-protocol code from service-specific code
    • letting clients decide when to upgrade
The team that owns the Order service also writes its client library, and order-validation rules have started to appear in the library. What is the risk?

A ride-hailing platform's NotificationService defines every notification type itself, including TripAssigned, FareReceipt, DriverPayoutReady and PromoOffer, each with content specific to another service's responsibility. The company wants to reuse it in its new food-delivery platform without major adaptation. Identify the most likely cause of poor reusability, propose a countermeasure by revising the domain model, and give its main drawback.
  1. Cause: the service is not cohesive or single-minded
    • holds knowledge that belongs to the Trip, Payment, Payout and Marketing contexts
    • → coupled to this platform's domain
  2. Countermeasure: make it a generic subdomain that models only generic concepts
    • e.g. a notification with recipient, channel, template and delivery status
    • move each specific notification's content into the context that owns the event
    • that context requests sending through a published interface or by publishing domain events
  3. Drawback
    • every owning service now has to compose its own notifications
    • more integration and some repeated formatting code across services
A logistics company has one shared model in which 'Shipment' means a customer order in Sales, a truck load in Dispatch and a customs declaration in Compliance. One team of 25 owns the code and a single database. Propose a restructuring of contexts, teams, repositories and data, and name one new problem it creates.
  1. Contexts: split into Sales, Dispatch and Compliance bounded contexts, each with its own ubiquitous language
    • 'Shipment' gets a precise meaning in each, e.g. Order, Load and Declaration
    • or the same name with separate models
  2. Teams, repositories, data: per context
    • one owning team
    • its own repository with code and acceptance and unit tests
    • its own schema
    • interfaces defined by that team
  3. Integration: through explicit interfaces or domain events, not shared tables
  4. New problem: a change that spans contexts needs coordination and translation between models → eventual consistency instead of one local transaction
In the Scrum tool, the product owner commits a backlog item to a sprint; it must already be scheduled for release, a quorum must approve, and if it is in another sprint it must be uncommitted first. Write the Given/When/Then specification, identify the aggregate or aggregates involved, and say how both sprints learn about the change.
  1. Given/When/Then
    • Given a backlog item scheduled for release, its product owner, a target sprint and quorum approval
    • When the product owner commits it to the sprint
    • Then it is committed to the sprint and a BacklogItemCommitted event is created
  2. Aggregate: the backlog item
    • the commitment rule sits with it, as the aggregate whose invariant it is
    • the sprint is referenced, not changed in the same transaction
  3. How both sprints learn: the previous sprint and the new sprint react to the domain event
    • keeps each transaction small
    • but makes their views eventually consistent

The scenario wording also becomes part of the context's ubiquitous language and doubles as an acceptance test.

Maid2Order adds corporate customers: a company subscribes to maid services for several offices and wants one monthly invoice. Using the lecture's seven-context solution, place the new concepts, justify each placement, and name one context that should not change.
  1. Corporate customer and its offices → CustomerManager, as a kind of Customer → that context holds the party's particulars
  2. Per-office services → stay in MaidOrderManager as MaidUsage under usage plans → ordering rules live there
  3. Single monthly invoice → BillingManager → its common Bill can consolidate the usage bills
