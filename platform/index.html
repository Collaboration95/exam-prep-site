Whole-course questions

Try after all the days. Explain your choices before opening the answer.

Maid2Order expects to grow from 5 to 50 maid agencies and add a corporate-customer interaction within a year, while releasing weekly without downtime. Explain how you would fit together its domain boundaries, APIs, data stores and release process, and name the riskiest trade-off.
  • Domain boundaries: keep the bounded contexts as separately owned services with their own schemas
    • Customer, agency, maid order, maid loan, billing, payment
    • → The new corporate-customer interaction plugs in as new entities or contexts, not changes to the core
  • APIs
    • Expose them through level 2 REST APIs with major-only versioning behind a gateway
    • Integrate between contexts with domain events, plus sagas with compensation where a flow spans services
  • Data stores: choose each store by workload, e.g. relational for bills and payments
  • Release process
    • Rolling or canary deployments that stay backward compatible with the data
    • Watch traces, yield and task success

Riskiest trade-off: eventual consistency between contexts. It buys independent releases and scaling, but users can briefly see in-progress or compensated states → the screens and support processes must allow for that.

An internal developer platform team is asked to offer a 'create a new service' golden path. Using the whole course, say what the golden path should give every team by default, and what should remain each application team's decision.
  • Default in the golden path
    • A service template built on the platform's framework
    • REST conventions: plural nouns, correct verbs and status codes, idempotency keys, major-only versioning
    • Gateway registration with central authentication and rate limits
    • Service discovery by alias; circuit breakers and timeouts through interceptors
    • Trace-ID propagation, centralised logging and standard metrics
    • A canary or rolling deployment pipeline with rollback
    • Security checks built in as guardrails (shifting down), not handed to developers as a checklist
  • Each application team's decision
    • Its bounded context and domain model
    • Its choice of data model for its workload
    • Its event contracts

Standardising those too would bring back the shared-model coupling that DDD exists to avoid.
