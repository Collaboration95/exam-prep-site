Reusable Services and API Gateway

79 slides · about 37 min · open the deck · JSON

Reusable services need explicit boundaries and deliberate integration. Context mappings describe relationships between bounded contexts; aggregates protect local invariants; domain events carry changes to other aggregates or services. This topic applies those ideas to car rental, compares orchestration with choreography, then explains gateway discovery and client SDKs.

Big ideas

  • A bounded context is the unit of a reusable service; each has its own ubiquitous language, so integrations must mediate between languages.
  • Context mapping kinds: Shared Kernel, Partnership, Customer-Supplier, Conformist, Anticorruption Layer, Open Host Service, Published Language, Separate Ways.
  • Avoid shared internal databases and files across contexts. Messaging removes temporal coupling; synchronous REST or RPC suits interactions requiring an immediate reply.
  • An aggregate is a transactional consistency boundary with one root: modify one aggregate per transaction, keep it small, reference others by identity only.
  • Domain events record business outcomes in past tense. Persist the aggregate change and event together, then deliver to subscribers that update in separate transactions.
  • Messaging needs at-least-once delivery plus idempotent receivers.
  • Orchestration = central brain, explicit, god-service risk; choreography = event-driven, implicit, loosely coupled, needs monitoring.
  • An API gateway is the server-side discovery router: it load balances, offers client-specific APIs, aggregates calls and translates protocols.

Characteristics of microservices

The defining traits of the microservice style (Fowler) and how each contrasts with the monolith or ESB way of working.

What microservices are

  • Small services, each in its own process
  • Built around business capabilities
  • Independently deployable
  • Lightweight mechanisms to talk → often an HTTP resource API
  • Minimal central management
  • Freedom in language and data store

Componentization via services

Services, not shared libraries.

  • Out-of-process →
    • deploy independently
    • explicit interfaces
    • keep encapsulation
  • The cost:
    • remote calls are slower than in-process calls → APIs must be coarser-grained
    • moving responsibility between components across process boundaries is harder

Organise around business capabilities

  • Conway's law → a system's structure copies the organisation's communication structure
  • Cross-functional teams per service → UX, database, project management
  • Siloed functional teams →
    • simple changes become cross-team projects
    • tempt people to push logic into whatever application they can reach

Smart endpoints, dumb pipes vs ESB

  • Microservices
    • logic in the endpoints
    • simple message router or REST
    • decoupled, cohesive, cache-friendly
  • ESB
    • routing, transformation, choreography and business rules in the bus
    • heavy protocols such as BPEL or WS-Choreography

Decentralised governance and data

  • Cross-functional teams own services and their data
  • Different stacks may be chosen
  • Operate what they build
  • Local transactions protect each service
  • Cross-service work → often eventual consistency and compensation

Independent evolution is a benefit, balanced against distributed-system overhead.

Automation and design for failure

  • CI/CD pipelines are the norm → automated tests, deployment and production management
  • Any service call can fail → clients degrade gracefully
  • Teams monitor
    • architecture metrics → database throughput
    • business metrics → orders per minute
Conway's law
A system's design mirrors the communication structure of the organisation that builds it.
Smart endpoints, dumb pipes
Logic lives in services; the messaging layer only routes.
Compensating operation
An action that undoes or corrects an earlier step when there is no distributed transaction.

Check yourself

A team splits a monolith by turning each in-process method call into a remote call one for one. A single page now makes 40 remote calls and is slow. Diagnose the problem.

Remote calls cost far more than in-process calls → remote APIs need to be coarser-grained than the library-style interfaces they replaced.

  • Services should expose fewer, larger operations around business capabilities
  • May mean revisiting the boundaries

Moving responsibilities between services later is harder once they sit across process boundaries, so the split deserves care up front.

Order and Inventory now own separate databases. A manager asks for 'one ACID transaction across both, like before'. How do you respond?

Microservices favour decentralised data: each service manages its own database and coordinates with others without a shared transaction.

  • → eventual consistency plus compensating operations, such as releasing stock if the order fails
  • If the business truly needs both changes to commit atomically → that suggests the data belongs in one service rather than a distributed transaction
A company has separate UI, backend and database teams, and every new feature becomes a cross-team project needing budget approval. What does Conway's law predict about its system, and what would you change?
  • Prediction: the system will mirror those silos
    • Layers owned by different teams, tangled together
    • Logic pushed into whichever part a team can touch
  • Change
    • Organise cross-functional teams around business capabilities, each with the full range of skills from user experience to database
    • → each team's service matches a capability
    • Teams own their service end to end, including running it
An architect proposes putting routing, message transformation and business rules into a central message bus so the services can stay simple. Critique the proposal.

That is the enterprise-service-bus style, with smarts in the pipe.

  • Microservices prefer smart endpoints and dumb pipes: the logic stays in cohesive services and the bus only routes messages
  • A smart central bus couples every service to one shared component and its team → changes queue up there

Cost of the microservice style: each service owns more of its own logic.

Decoupling services with context mappings

Bounded contexts (the reusable services) still depend on each other; context mappings are the DDD vocabulary for designing those couplings and the team relationships behind them.

Bounded contexts are not fully independent

  • Each bounded context (BC) has its own ubiquitous language (UL) and domain model
  • Shared entities: one BC may use an entity owned by another
  • Events: one BC may need to know about events on another's entities

These couplings must be designed deliberately so BCs are not needlessly tied together.

A context mapping

Designs a relationship between two BCs.

  • Upstream/downstream patterns → one supplies a model or service, the other consumes it
  • Shared Kernel and Partnership → mutual agreement instead
  • Different ubiquitous languages still need deliberate mediation → e.g. Agile Project Management consumes Discussion from Collaboration

Mappings: tight to loose collaboration

  • Closest (mutual)
    • Shared Kernel → small common model, needs constant agreement
    • Partnership → teams continuously align schedules
  • Upstream/downstream relationships
    • Customer-Supplier → supplier upstream, has the final say but tries to serve the customer
    • Conformist → downstream just adopts the upstream model

Conformist vs Anticorruption Layer

The key choice for a downstream team.

  • Conformist → fits when the upstream model is large, well established and unresponsive, and translating is too costly
  • Anticorruption Layer (ACL) → translates the upstream UL into the downstream UL to protect the downstream model
  • ACL cost → effort to maintain
  • ACL use case → a great way to integrate with an upstream Big Ball of Mud (legacy)

OHS, Published Language, Separate Ways

OHS and Published Language make the upstream easy to consume.

  • Open Host Service (OHS) → exposes the context as a set of services via a protocol or interface; reduces the need for an ACL downstream
  • Published Language → well-documented exchange format (XML Schema, JSON Schema); an OHS often provides one
  • Separate Ways → no integration at all, when the payoff is too small
Bounded context (BC)
A boundary within which one domain model and one ubiquitous language apply; the unit used to find reusable services.
Ubiquitous language (UL)
The shared vocabulary of a BC's team and its model; the same word may mean different things in another BC.
Upstream / Downstream
The supplier of a model or service (U) and its consumer (D).
Anticorruption layer
Downstream translation layer isolating its model from the upstream model.
Open Host Service
Upstream publishes an open protocol/interface to its context.

Check yourself

Your small Shipping team must integrate with a large, established ERP whose team will not change anything for you. Should Shipping be a Conformist or build an Anticorruption Layer?

It depends on whether Shipping's model can live with the ERP's.

  • Conform if it can, and the team cannot sustain the effort of translating → it is cheaper
  • Build an Anticorruption Layer if the ERP is a Big Ball of Mud that would distort Shipping's model → translates to Shipping's ubiquitous language

ACL trade-off: accept the cost of maintaining the translation.

Eight downstream contexts each maintain their own translation of the Customer context's model, and every Customer change breaks several of them. What should the Customer team offer instead?

An Open Host Service with a Published Language.

  • Open Host Service: a protocol or set of services giving access to the context
  • Published Language: such as a documented JSON Schema
  • → downstream teams can consume and translate easily; an anticorruption layer becomes less crucial for them

Cost: the Customer team takes on keeping that public interface stable and versioned.

Marketing wants a small piece of Billing's data, but Billing's model does not really provide what Marketing needs, and integrating would take months. What mapping fits?

Separate Ways.

  • Integration would not give a significant payoff: the functionality sought is not fully provided by the source ubiquitous language
  • Marketing builds its own specialised solution

Cost: some duplicated capability, which is cheaper than months of integration.

Two teams propose a shared kernel of 40 classes so they can stop translating between their contexts. What concerns would you raise?
  • A shared kernel should be a small common model
  • Even then it is hard to conceive and maintain: needs open communication and constant agreement between both teams
  • Forty classes → would bind their release schedules together

Alternative: a Customer-Supplier relationship, or an Open Host Service with a Published Language, keeps the teams more independent.

Integration styles between contexts

Choose immediate synchronous replies or asynchronous messages according to the business flow. Reliable messages still require duplicate-safe handling.

Integration styles

  • Avoid integrating through a shared database or file system
  • Typical styles:
    • RPC via SOAP
    • RESTful HTTP
    • Messaging

RPC (SOAP): simple but brittle

  • Looks like a local call, but the request must cross the network, reach the remote system and return
  • Vulnerable to network failure, latency and upstream failure
  • Strongly couples client to service and to a specific protocol
  • Best practice:
    • upstream provides an Open Host Service with a Published Language
    • downstream uses an Anticorruption Layer

RESTful HTTP

  • Centres on resources and the four primary operations (POST, GET, PUT, DELETE)
  • → well-defined APIs
  • Still susceptible to network and upstream failure
  • Mitigates this by relying on the reliability and scalability of the Web

Messaging removes temporal coupling

  • Durable event: a publisher can leave one for a consumer to process later
  • Tolerates temporary consumer outages
  • Accepts delay and requires operating the messaging infrastructure
  • Synchronous calls → when an immediate result is necessary

Neither style removes network failure.

Safe delivery and handling

  • At-least-once delivery → retries until acknowledgement (assuming the broker retains the message and recovery is possible)
  • Duplicates can occur → receivers must de-duplicate or safely reapply changes
  • Acknowledge after successful processing → failure does not silently discard work
Temporal coupling
Both parties must be up at the same time, as in blocking calls.
At-least-once delivery
Messages are redelivered until acknowledged, so duplicates are possible.
Idempotent receiver
A receiver whose handling produces the same result however many times a message arrives.

Check yourself

When an order is placed, the Loyalty context must add points. Loyalty is offline for 20 minutes every night for maintenance. Would you integrate with REST or messaging?

Messaging.

  • Order publishes a domain event; Loyalty processes it when it comes back
  • → removes the temporal coupling of a blocking REST call that would fail or stall orders during the outage
  • Needs at-least-once delivery and an idempotent receiver in Loyalty

Trade-off: points appear later rather than immediately.

After a broker redelivery, the Loyalty subscriber processes the same OrderPlaced event twice and awards double points. What is the fix?

At-least-once delivery means redelivery is expected → the receiver must be idempotent.

  • Record processed event IDs and skip duplicates
  • Or make the update safe to reapply: 'set points for order X' instead of 'add points'

Switching off redelivery would just swap duplicates for lost messages.

To save time, the Reporting context reads the Order context's tables directly. What is wrong with this?

Database integration is the type to avoid.

  • Couples Reporting to Order's internal storage
  • Breaks the bounded context's encapsulation
  • Any change to Order's schema can break Reporting without warning
  • Fix: use Order's published API, or subscribe to its domain events and build Reporting's own read model

Cost: some lag.

A team chose SOAP RPC between two contexts because the call looks just like a local procedure call. What risks does that hide, and what practices reduce them?
  • Hidden risks: the call still crosses the network
    • Lacks robustness against latency, network failure and upstream failure
    • Couples the client strongly to the service and protocol
  • Practices from the lecture
    • Open Host Service with a Published Language upstream
    • Anticorruption Layer downstream
  • If the flow does not need an immediate answer → messaging would remove the temporal coupling

Aggregates

An aggregate is a cluster of entities inside one BC that is loaded, changed and saved as a single unit; the rules of thumb say how to size them, reference them and keep them consistent.

Aggregate = transactional consistency boundary

  • Cluster of domain entities in one BC treated as a unit (think of elements that live and die together)
  • Aggregate Root → one entity that owns all others
  • Value Objects → optional
  • One transaction → modify and commit only one aggregate
  • Consistency across aggregates → handled by separate transactions

Entity vs Value Object vs Aggregate Root

  • Entity → unique identity; usually mutable (state changes over time)
  • Value Object → no identity; immutable conceptual whole with attributes and behaviour; qualifies (describes, quantifies, measures) an entity
  • Aggregate Root → the root entity that owns everything else

Protect business invariants inside the boundary

  • Example → when all Task instances have hoursRemaining of zero, the BacklogItem status must be DONE; must hold at the end of the transaction
  • Business logic belongs in the aggregate
  • Avoid an Anemic Domain Model → only getters/setters
  • Do not leak logic into application services or helper classes

Design small aggregates

Single-minded (Single Responsibility).

  • Small ones:
    • load quickly
    • use less memory
    • collect faster
    • succeed in transactions more often
    • are easier to work on and test
  • Example → break a huge Product (containing many BacklogItems, Releases, Sprints) into separate aggregates

Reference other aggregates by identity only

  • BacklogItem, Release and Sprint hold a ProductId, not a Product object
  • Identities are easy to persist
  • Same rule applies across BCs
  • Model identities as value objects (immutable)

Eventual consistency between aggregates

They may be in the same BC or different BCs.

  1. BacklogItem stores SprintId and records BacklogItemCommitted in one transaction
  2. Sprint later stores BacklogItemId in its own transaction

If one business invariant requires an atomic update, reconsider the boundary: consider merging within a BC, or revisit the cross-context business process.

Persistence: one repository per aggregate

  • Repository persists the whole aggregate → root, entities, value objects
  • Possibly via several DAOs and tables
  • Factory Method → may build complex aggregates
  • Aggregate (domain model) is not a DTO → one aggregate may map to several DTOs
Aggregate
Cluster of entities and value objects in a BC treated as one unit of consistency and transaction.
Aggregate root
The one entity through which the aggregate is accessed; owns the other elements.
Value object
Immutable, identity-less object that describes or measures an entity.
Business invariant
A business rule that must be true at the end of every transaction.
Anemic domain model
Anti-pattern: aggregates with accessors only, logic elsewhere.

Check yourself

A Sprint aggregate holds direct object references to all its BacklogItems, which hold all their Tasks. Loading a sprint takes three seconds and concurrent edits often fail. What would you change?

Design small aggregates and reference other aggregates by identity.

  • Make BacklogItem its own aggregate that holds a SprintId value object
  • Sprint holds BacklogItemIds rather than objects
  • → smaller aggregates load faster, use less memory and succeed more often under concurrency

Changes that span both are then made through domain events in separate transactions → eventual consistency.

The business says that when a backlog item is committed, the sprint's capacity must never be exceeded, checked at the same commit. Today Sprint and BacklogItem are separate aggregates updated by a domain event. What do you do?

This invariant must hold within one transaction; the delay of a domain event would allow unacceptable inconsistency.

  • Consider merging the commitment data into one aggregate within the same bounded context
  • The lecture advises this when two must be updated immediately one after the other

Cost: a larger aggregate with more contention, so first check whether the business could accept detecting and correcting an over-commit instead.

In code review, the Order aggregate has only getters and setters, while an OrderService checks that the total does not exceed the credit limit and then sets the status. What is the problem?

Anaemic domain model: business logic has leaked out of the aggregate into an application service.

  • Other code paths can set the status without checking the rule
  • → the invariant is not protected inside the boundary
  • Fix: move the rule into a method on Order, such as place(), that enforces it before changing state
A team models Money as an entity with its own ID and table, and Customer as a value object. Critique the model.

It is backwards.

  • Money is a value object: no identity of its own, immutable, describes an amount
  • Customer is an entity: a unique identity whose attributes change over time
  • Making Money an entity → adds needless IDs and invites shared mutable amounts
  • Making Customer a value object → impossible to track one customer across changes

Domain events

A domain event records a business-significant occurrence in a BC; this section covers what they are, why order matters, and how to identify, name, shape and commit them.

Domain event (DE)

  • Record of a business-significant occurrence in a BC
  • Loosely coupled integration mechanism
  • Means for one aggregate or BC to tell others what happened
  • Used for:
    • messaging-type context mappings
    • propagating change between aggregates

Order matters: causal consistency

  • Causally related operations must be seen in the same order by every dependent node of a distributed system
  • Wallet example:
    • Sue's 'I lost my wallet!' must be followed by Gary's 'That's terrible!'
    • if replies and posts are seen out of order, 'That's great!' appears after the lost-wallet post and makes no sense

Identify events from the integration points

  • Each context mapping of messaging type → find the business functions that rely on it and the events they require
  • Each propagation of change from one aggregate to another → also add an event

Name events as past-tense verbs

  • Already happened → past tense
  • Command-triggered → name the event after the command:
    • CreateProduct → ProductCreated
    • CommitBacklogItemToSprint → BacklogItemCommitted

Event properties

  • Copy the business properties of the triggering command (in the lecture), then enrich where needed
  • Example → ProductCreated might carry tenantId, productId, name and description
  • Enough context for subscribers to react without querying the publisher
  • Event data describes the completed outcome

Commit state and event together

  1. Same transaction → changing BacklogItem and durably recording BacklogItemCommitted succeed or fail together
  2. After commit → deliver it reliably to subscribers
  3. Subscribers update their own aggregates in later transactions

Recording an event is distinct from delivering it over a network.

Domain event
Immutable record of a business-significant thing that happened in a BC, named in past tense.
Causal consistency
Causally related events are observed in the same order by all dependent nodes.
Enriched event
An event carrying extra data so consumers need not call back the publisher.

Check yourself

A service commits an Order and then publishes OrderPlaced as a separate step. Occasionally the process crashes between the two. What is the consequence, and what is the fix?

The order exists but the event is lost → subscribers such as Inventory and Billing never learn about it and stay stale.

  • Fix: commit the modified aggregate and the domain event in the same transaction
  • Then deliver recorded events reliably afterwards, including after recovery

Subscribers still need to be idempotent, because that delivery can repeat.

Shipping receives OrderPlaced events carrying only the orderId and calls the Order API back for the address and tenantId on every event. The Order API is now overloaded. What would you change?
  • Make the event carry all the properties of the command that caused it
  • Enrich it with extra data such as tenantId and the delivery address → consumers need not query the publisher
  • → removes the remote calls and decouples Shipping from Order's availability

Cost: larger events and an event schema that must be kept stable for every consumer.

On a forum, replies sometimes appear on other users' screens before the post they answer. Which property is violated, and what must the design guarantee?

Causal consistency: causally related operations must be seen in the same order by every dependent node.

  • A reply depends on its post → its event must never be applied before the post's event
  • Give events an order within each conversation; consumers apply them in that order, waiting for missing predecessors

Ordering every event globally would be stricter and more costly than needed.

Maid2Order's MaidOrderManager must tell BillingManager through messaging when a customer's usage should be billed. Identify, name and shape the domain event.
  1. Start from the messaging context mapping and the business function that relies on it (billing a customer's maid usage); ask what occurrence BillingManager needs to know about
  2. Name it in the past tense, for example MaidUsageBillIssued, following the command that caused it
  3. Shape: give it the command's properties, such as the bill, customer and usage IDs, amount and period, and enrich it with anything Billing would otherwise query back for

A name like IssueBill would describe a request, not something that happened.

Car rental example and workshop

A worked case showing how splitting an oversized aggregate and replacing a direct cross-context update with a domain event yields independent microservices.

Car Rental: starting problem

  • Bounded contexts → Rental Manager and Vehicle Manager (Car Rental System)
  • Extending a rental needs:
    • verify the vehicle's usability (a call into Vehicle Manager)
    • update the rental date
  • Problem → the rental model is assumed to have an excessive memory footprint

Fix: smaller aggregates + an event

  1. Split: Rental Manager divided into Rent Ctrl and Rent Ext aggregates; Vehicle Manager has Vehicle Ctrl
  2. Rent Ext verifies usability with Vehicle Ctrl
  3. Rent Ext publishes a Rental Extended event
  4. Rent Ctrl is updated from that event, rather than in the same operation

Applies small aggregates plus eventual consistency.

Resulting architecture

  • Each BC becomes a microservice → RentalMgr, VehicleMgr, CustomerMgr
  • Each has its own transaction scope, data repository, database, team and code repository
  • RentalMgr publishes VehicleRented and VehicleReturned domain events

Aggregates and events thus define service boundaries and data ownership.

Workshop task

  1. Choose two significant services (BCs) from the earlier entity/BC/UL workshop
  2. Design their aggregates → roots, entities and value objects
  3. Design at least three domain events → names and assumed properties

Check yourself

In the car-rental example, the Rental Manager's aggregate was too large, and extending a rental updated the rental record directly. What did the redesign do, and what does it cost?
  • Split the aggregate into smaller ones: Rent Ctrl and Rent Ext
  • Replaced the direct update with a Rental Extended domain event → each transaction changes one small aggregate

Cost: eventual consistency: for a short time the rental date is not yet updated.

After that redesign, a teammate proposes one shared database for RentalMgr, VehicleMgr and CustomerMgr to make reporting easier. How do you respond?

No.

  • In the resulting architecture each service has its own transaction scope, data repository, database, team and code repository
  • VehicleRented and VehicleReturned events are how they integrate
  • A shared database would recouple them through schema changes

Instead: build reporting from those events into its own read model, accepting some lag.

For the workshop, design the aggregates of Maid2Order's MaidOrderManager. Which entity is a root, and what do the others reference?

One defensible design:

  • MaidUsage = aggregate root for a customer's ordered service, holding the CustomerId and a MaidUsagePlanId by identity
  • Why by identity: plans are a shared catalogue that changes independently
  • MaidUsageBill is its own aggregate referencing the MaidUsage by ID → issuing a bill does not lock the usage
  • Changes propagate through events such as MaidUsageCreated and MaidUsageBillIssued

If a plan change must be reflected in the bill at the same commit, that is the signal to merge.

Orchestration vs choreography

Two ways to run a business flow that spans several services, with their trade-offs; they can be mixed.

Why the choice arises

  • Business logic grows → a business function stretches across service boundaries
  • The flow must be implemented by orchestration or choreography (or a mix)

Orchestration: a central brain

One service tells others what to do. New-customer example:

  • Customer service creates the record, then requests:
    • Loyalty Points Bank → create a loyalty record
    • Post service → dispatch a welcome pack
    • Email service → send a welcome email
  • Pros → simpler; the flow is explicit; a rules engine can be used
  • Con → tends to create overly smart 'god' services

Choreography: services react to events

  • Customer service creates the record and emits an event
  • Loyalty, Post and Email each receive it and do their part
  • Cons → more complex; implicit flow
  • Relies on domain events; more loosely coupled
  • Must monitor and track that the flow is carried out as expected

Decision rule

  • Orchestration → for simplicity and visibility of the flow
  • Choreography → for loose coupling and to avoid a god service, accepting the monitoring burden
Orchestration
A central service directs other services with explicit requests.
Choreography
Services react independently to published events; no central controller.

Check yourself

A new-customer flow currently creates the customer, then loyalty points, a welcome pack and a welcome email. Next quarter three other teams will add SMS, CRM and fraud-screening reactions. Orchestration or choreography?

Choreography.

  • The Customer service emits one event; each new team subscribes without changing the Customer service → services stay loosely coupled
  • Orchestration would make Customer a growing 'god' service that knows every step

Cost: an implicit flow, so you must monitor that each reaction happens.

The onboarding flow is choreographed, and the operations team cannot tell whether a given customer ever received the welcome pack. What is missing?

Monitoring and tracking: choreography needs them to confirm that the implicit flow completes as expected.

  • Correlate the events for each customer with a shared ID and trace them
  • Alert when an expected reaction has not happened within a time limit

If visibility of progress is essential, orchestrate that part, since the lecture says the two can be mixed.

A refund process has strictly ordered steps, and support staff need to see exactly which step each refund has reached. Which approach fits, and what is its risk?

Orchestration.

  • Explicit flow in one coordinator → a clear view of each refund's progress
  • Enforces the order of steps, and can use a rules engine

Risk: an overly smart 'god' service → keep the coordinator limited to directing the flow, and leave each step's business logic in the service that owns it.

Service discovery and API gateway

What a microservice system needs before it is production ready: service discovery and load balancing, with the API gateway as the single router in front.

From sample to production

  • Problem → hard-coded locations miss new or moved instances
  • Add discovery and load balancing
  • API gateway (in the sample) → gives clients one stable entry point
  • Replicate each service's owned database for its scaled instances
  • Keep the message broker available
  • Do not turn this into a database shared across different BCs

Server-side discovery with a service registry

Instances in virtualised or containerised environments change in number and location dynamically, so clients cannot know addresses.

  • Instances register themselves with the registry
  • Client calls a router (load balancer) at a well-known location
  • Router queries the service registry
  • Router load balances and forwards to an available instance

API gateway = that router, plus more

  • Clients oblivious to how the application is partitioned
  • Optimal API for each client
  • Multiple services in a single trip for a client
  • Protocol translation → public API protocol to whatever internal protocols are used

Example: Spring Cloud

The production-ready sample uses Spring Cloud tools on Spring Boot, some originating from Netflix:

  • Registration and discovery
  • Routing
  • Service-to-service calls
  • Load balancing
  • Circuit breakers
  • Distributed messaging

Example: AWS API Gateway

Creates, publishes, maintains, monitors and secures APIs at any scale. Handles:

  • Concurrent calls
  • Traffic management
  • Authorisation and access control
  • Monitoring
  • API version management
Service registry
Database of available service instances and their locations; instances register themselves.
Server-side discovery
A router queries the registry and forwards requests, so clients need no discovery logic.
API gateway
Single entry point that routes, load balances, adapts APIs per client and translates protocols.

Check yourself

The Gamification service is configured with the Multiplication service's IP address. Operations scale Multiplication to three instances, and later one instance restarts at a new address. What happens?
  • Gamification keeps calling the one configured address → the new instances get no traffic
  • The call breaks once that instance moves
  • Why: in virtualised or containerised environments instances are ephemeral
  • Fix: a registry and a router that looks up available instances and load-balances
  • Server-side discovery → the client calls a well-known router and never needs instance addresses
A web app and a smartwatch app need differently shaped data from the same four services. What can an API gateway do for them, and what does it cost?

The gateway can:

  • Offer each client its optimal API
  • Aggregate the four calls into one trip
  • Translate the public protocol to internal ones
  • Hide how the application is partitioned
  • → clients get simpler and faster; services can be split or moved behind it

Cost: client-specific gateway logic to maintain, and the gateway becomes a critical component that must be highly available.

After adding a gateway and a registry, the team scales each service to three instances. Which single points of failure remain in the lecture's sample architecture?
  • Databases shared by each service's instances → need high availability
  • Message broker → needs high availability
  • Gateway and registry must themselves be replicated, or they become new single points of failure

Scaling the stateless service instances alone does not remove these.

    • plus Android, iOS and mobile web
  • Native code → applications call AWS services through it

Feign (Spring Cloud stack in the lecture)

  • Declarative clients → map interface methods to REST requests
  • Integrates with Eureka, Ribbon and Hystrix → discovery and resilience
  • The illustrated stack, not a requirement for every SDK
  • Calls still cross a network → can time out or fail

How the pieces fit

  • Context mappings → describe dependencies between BCs
  • Aggregates → define local transaction scope; reference other aggregates by ID
  • Domain events → propagate outcomes
  • Orchestration or choreography → coordinates larger flows
  • Gateways → simplify client access
  • SDKs → ease calls, without removing network boundaries

Check yourself

A Feign client method looks just like a local method call. Can the calling code treat it as equally reliable?

No. It still performs a remote HTTP call.

  • → latency, timeouts and possible partial failure
  • Discovery and load balancing find a healthy instance
  • But timeouts, circuit breakers and safe retries are still needed

The convenience hides the network; it does not remove it.

A teammate says: 'Our services follow bounded contexts, so they are decoupled; we don't need context maps, aggregates or domain events.' How do you respond?

Bounded contexts are not totally decoupled: they still use each other's entities and need to know about each other's events.

  • Context mappings → model how they integrate
  • Aggregates → break direct references between services and set transaction scope
  • Domain events → loosely coupled integration

Without these, the coupling still exists, just undesigned and hidden in ad hoc calls and shared data.

Exam-style questions

Answer aloud or on paper before opening.

In an online-auction platform, the Bidding context's Auction aggregate holds every Bid placed on it, often thousands. A live leaderboard is computed by querying the Bidding database each time one of up to 50,000 concurrent viewers refreshes. You doubt viewers will see the latest bids promptly. Identify the most likely cause, propose a countermeasure by revising the domain model, and give its drawback.
  1. Cause
    • Oversized Auction aggregate → every bid loads and locks a large object graph → bids contend and transactions slow down
    • Leaderboard reads compete with bid writes on the same transactional store
  2. Countermeasure (revise the domain model)
    • Make Bid its own small aggregate referencing AuctionId
    • Auction keeps only the invariants it must protect at commit, such as the current highest valid bid
    • Publish an enriched BidPlaced event in the same transaction as the bid
    • A Leaderboard context maintains its own read model from those events and pushes updates to viewers
  3. Drawback
    • The leaderboard is eventually consistent
    • Events must be applied in order per auction and processed idempotently
    • More components to run and monitor
A platform has been split into Order, Inventory and Billing services, and Billing must also integrate with a legacy finance system that nobody will change. Design the context mappings and integration types, and justify each.
  • Order depends on Inventory: Customer-Supplier: Inventory, upstream, tries to meet Order's requests but has the final say
  • Inventory and Billing expose Open Host Services with a Published Language, such as JSON Schema → downstream contexts consume them with little translation
  • Billing vs the legacy finance system: Anticorruption Layer protects Billing's model, accepting the cost of maintaining the translation
  • Avoid database or file integration
  • Messaging with domain events where an immediate reply is not needed, with at-least-once delivery and idempotent receivers
  • REST only where the caller needs an answer now
A customer places an order that must reduce stock held in an Inventory aggregate in another service. Design this with aggregates and domain events, and say what you would do if the business cannot accept delayed stock allocation.
  1. Order commits its change and an OrderPlaced event in one local transaction, referencing products by ID
  2. The event, carrying the order lines and any data Inventory would otherwise query, is delivered reliably
  3. Inventory decrements stock in its own transaction, handling duplicates idempotently
  4. A failure publishes a compensating outcome, such as StockReservationFailed → the order can be cancelled

If allocation must be immediate, events cannot promise that: either move the reservation into the same aggregate and context, or reserve stock synchronously before confirming the order, accepting tighter coupling.

A new-customer flow must create loyalty points, dispatch a welcome pack and send an email; legal now requires proof that every customer received the privacy email within 24 hours. Compare orchestration and choreography for this flow and recommend a design.
  • Orchestration
    • Explicit flow in the Customer service → simple and easy to audit
    • Risk: a 'god' service coupled to every step
  • Choreography
    • The Customer service emits one event that each service reacts to → loosely coupled, easy to extend
    • But the flow is implicit and must be monitored
  • Recommend: a mixed design fits
    • Choreograph the loyalty points and welcome pack
    • Orchestrate or explicitly track the privacy email: record its completion against the customer ID and alert if it is missing after 24 hours

Cost: two styles to understand and operate.

At peak, 500 payments a minute are confirmed. Each confirmation must update the Order context and trigger a customer notification; the Notification service is available 99% of the time. Would you integrate by REST or messaging, and what must be true for your choice to be safe?

Messaging.

  • Publishing PaymentConfirmed lets Payment finish even when Notification is among its 1% of downtime; the queued events catch up later
  • Synchronous REST would make payment confirmation depend on Notification being up
  • Safe only if the event is
    • Committed with the payment state
    • Delivered at least once
    • Handled by idempotent receivers in Order and Notification

Cost: the order status and notification lag slightly behind the payment, so if the user's screen must show the result at once, read it from Payment directly.

A prototype microservice system has a browser calling services by fixed address, one database per service shared by its instances, and a single message broker. It must now scale each service to several instances. Explain what to add and which failure points to address.
  • Add a service registry and server-side discovery: clients call a router, here the API gateway, at a well-known location → it looks up available instances and load-balances across them
  • The gateway also gives each client a suitable API, aggregates calls and translates protocols
  • Single points of failure left after scaling instances
    • The shared databases → need high availability
    • The message broker → needs high availability
    • The gateway and registry must themselves be replicated
