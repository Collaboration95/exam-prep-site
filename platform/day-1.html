Whole day

To obey DRY, a platform team proposes one shared Customer class library used by its Sales, Billing and Support services. Where does reuse help, and where does it harm the domain design?
  • Reuse helps: for stable technical pieces and for capabilities offered as services, e.g. a Customer service other contexts call by ID
  • A shared domain class harms
    • Each bounded context gives Customer its own meaning and rules → one class must carry everyone's attributes
    • Every change forces coordinated releases across three teams
  • Lecture's rule: DRY within a service, relaxed DRY across services
  • Translate between contexts through explicit contracts

Cost: some duplicated code, which is cheaper than lockstep releases.

A bank's platform team serves internal developers through an IDP and fintech partners through a public API platform. Leadership wants a single success metric for both. Do you agree?

No. Track a small set of measures for each and report them separately.

  • IDP: users are developers → success shows in DORA metrics against a baseline and developer NPS
  • Partner platform: adoption, useful interactions and business impact, as with any API product
  • A single number would hide failure on one side, e.g. fast internal deployments while partners abandon the API
A start-up is building an event-ticketing platform where organisers sell tickets to fans, and plans a merchandise platform next year. Identify the seed, producers, consumers and interaction, propose bounded contexts, and explain how you would make the notification capability reusable by the merchandise platform.
  • Platform elements
    • Seed: an event listing with its tickets
    • Producers: organisers
    • Consumers: fans
    • Interaction: list, discover, buy, attend
  • Candidate bounded contexts: EventCatalogue, Venue, TicketSales, Payment, Notification
    • Each owned by one team with its own repository and schema
  • Reusable Notification: a generic subdomain
    • Knows only recipients, channels, templates and delivery status
    • TicketSales and Payment publish domain events such as TicketPurchased and request notifications through its published interface
    • Ticket-specific content stays out of it → the merchandise platform can reuse it unchanged

Cost: each producer context must compose its own message content.

Introduction to Platforms

A food-delivery company wants to open its ordering, delivery-tracking and payment capabilities to independent restaurants and couriers. (a) Identify the seed, producers, consumers and core interaction. (b) The CEO wants to launch restaurant booking, grocery delivery and a courier marketplace in the same release. Advise. (c) Give two engineering concerns that follow from opening the APIs to outside parties.
  1. (a) Roles
    • Seed: a menu item or order
    • Producers: restaurants and couriers
    • Consumers: diners
    • Interaction: browse, order, match a courier, deliver, pay
  2. (b) Build one interaction at a time, as LinkedIn did
    • Get food ordering adopted and growing producers through the magnet before adding new interactions
    • Design modular, extensible components so later ones plug in
  3. (c) Engineering concerns
    • Toolbox → needs usable APIs and SDKs
    • Many outside parties now depend on the platform → architect for availability, security and scalability

Trade-off: slower initial scope in exchange for a stable core.

A company with 40 application teams has a five-day ticket wait for databases, each team maintains its own pipeline scripts, and leadership wants evidence of value within six months. Propose the first steps of an IDP, the measures you would use, and one thing you would deliberately not build first.
  1. Baseline first: document the cost of the pain
    • ticket wait, lead time, failure rates
  2. Minimum viable platform aimed at the top pain
    • automated database provisioning through IaC
    • a shared CI/CD golden path
    • an orchestrator or pipeline behind it
  3. Measures: DORA metrics and developer NPS against the baseline
    • expand scope only where they improve
  4. Don't build first: a full developer portal
    • backend comes before portal
    • a portal over ticket-driven provisioning would show nothing in six months
On an IDP, developers submit workload specs. Staging deployments work, but production sometimes gets a different database size and nobody can explain why. Using the reference architecture and GitOps, diagnose where to look and what to change.
  1. Look at the orchestrator (integration and delivery plane)
    • it generates environment-specific configuration as a resource graph
    • → compare the production and staging graphs and the rules that produce them
  2. Check GitOps: was production state changed outside Git?
    • Git should be the single source of truth
    • every infra change should go through a reviewed PR
  3. Fix: move environment differences into versioned config and let CD sync from Git
  4. Observability plane → should record what was deployed, so the next difference is visible without detective work
An organisation with 300 developers has a DevOps culture and an SRE team that owns SLOs and error budgets, but onboarding a new service still takes three weeks. The CIO asks whether to grow the SRE team or create a platform team. Advise, and say what would change your answer.

Create a platform team.

  • Symptom = slow onboarding and missing self-service → these are platform engineering's concerns
  • Platform team offers: golden paths, standardised provisioning, lower cognitive load, with developers treated as customers
  • SRE keeps owning reliability; the platform can make SLO monitoring a default for every new service

What would change it: if the main problem were frequent outages or missed SLOs instead of slow onboarding → growing SRE would be the better answer.

A regulated firm requires secret scanning, dependency checks and policy checks for every service. Option A gives each team a checklist to run before release. Option B builds the checks into the platform's golden path. Choose one and give the trade-off.

Choose B, shifting down.

  • Option B = shifting down: checks embedded as automated guardrails and secure defaults
    • removes repeated manual toil
    • applies the rules consistently
    • makes the compliant path the easiest one
    • fits the security plane being cross-cutting
  • Option A = shifting left: checks happen early, but
    • every team carries the work
    • compliance depends on each team's discipline

Trade-off: B costs platform investment up front, and teams that leave the golden path still need a way to show compliance.

A bank's architecture group plans to give its teams (a) a shared code skeleton with abstract classes, (b) a utility code package for date and currency handling, and (c) a hosted environment exposing identity and payment services through APIs, which partners may also use. Classify each, and explain which one creates an ecosystem and what that obliges the bank to do.
  1. (a) Framework: teams use it and it dictates structure
  2. (b) Library: teams call it where they choose
  3. (c) Platform: hosted, accessed by APIs, and extensible by outside parties
  4. Ecosystem: only (c) → partners can build complementary products through its interfaces
    • Obliges the bank to keep those interfaces stable so internal change does not break partners
    • Obliges the bank to architect for availability, security and scalability

Reusable Assets and Frameworks

A ride-hailing platform's NotificationService defines every notification type itself, including TripAssigned, FareReceipt, DriverPayoutReady and PromoOffer, each with content specific to another service's responsibility. The company wants to reuse it in its new food-delivery platform without major adaptation. Identify the most likely cause of poor reusability, propose a countermeasure by revising the domain model, and give its main drawback.
  1. Cause: the service is not cohesive or single-minded
    • holds knowledge that belongs to the Trip, Payment, Payout and Marketing contexts
    • → coupled to this platform's domain
  2. Countermeasure: make it a generic subdomain that models only generic concepts
    • e.g. a notification with recipient, channel, template and delivery status
    • move each specific notification's content into the context that owns the event
    • that context requests sending through a published interface or by publishing domain events
  3. Drawback
    • every owning service now has to compose its own notifications
    • more integration and some repeated formatting code across services
A logistics company has one shared model in which 'Shipment' means a customer order in Sales, a truck load in Dispatch and a customs declaration in Compliance. One team of 25 owns the code and a single database. Propose a restructuring of contexts, teams, repositories and data, and name one new problem it creates.
  1. Contexts: split into Sales, Dispatch and Compliance bounded contexts, each with its own ubiquitous language
    • 'Shipment' gets a precise meaning in each, e.g. Order, Load and Declaration
    • or the same name with separate models
  2. Teams, repositories, data: per context
    • one owning team
    • its own repository with code and acceptance and unit tests
    • its own schema
    • interfaces defined by that team
  3. Integration: through explicit interfaces or domain events, not shared tables
  4. New problem: a change that spans contexts needs coordination and translation between models → eventual consistency instead of one local transaction
In the Scrum tool, the product owner commits a backlog item to a sprint; it must already be scheduled for release, a quorum must approve, and if it is in another sprint it must be uncommitted first. Write the Given/When/Then specification, identify the aggregate or aggregates involved, and say how both sprints learn about the change.
  1. Given/When/Then
    • Given a backlog item scheduled for release, its product owner, a target sprint and quorum approval
    • When the product owner commits it to the sprint
    • Then it is committed to the sprint and a BacklogItemCommitted event is created
  2. Aggregate: the backlog item
    • the commitment rule sits with it, as the aggregate whose invariant it is
    • the sprint is referenced, not changed in the same transaction
  3. How both sprints learn: the previous sprint and the new sprint react to the domain event
    • keeps each transaction small
    • but makes their views eventually consistent

The scenario wording also becomes part of the context's ubiquitous language and doubles as an acceptance test.

Maid2Order adds corporate customers: a company subscribes to maid services for several offices and wants one monthly invoice. Using the lecture's seven-context solution, place the new concepts, justify each placement, and name one context that should not change.
  1. Corporate customer and its offices → CustomerManager, as a kind of Customer → that context holds the party's particulars
  2. Per-office services → stay in MaidOrderManager as MaidUsage under usage plans → ordering rules live there
  3. Single monthly invoice → BillingManager → its common Bill can consolidate the usage bills
  4. Should not change: PaymentManager → it simply settles a Bill

If corporate contracts turn out to have very different rules, a separate context may be justified, at the cost of more integration.

A platform's 15 services all need (a) customer-profile lookups, (b) the same request logging, tracing and configuration conventions, and (c) a Money value class. Choose service, framework or shared library for each, and state the risk of each choice.
  1. (a) A Customer service
    • reuse of a business capability, scaled and released independently
    • Risk: remote-call latency and failures → callers need timeouts
  2. (b) A framework
    • standardises common behaviour for building many services
    • Risk: expensive to design well; ties services to its release cycle
  3. (c) A shared library
    • for a small, stable value class
    • Risk: coupling and language lock-in → share only stable technical types; keep domain models within each service
A four-person platform team must deliver an integration framework for 30 partner companies in nine months. Propose the design process and the qualities you would check, and name the pitfall you fear most.
  1. Design process
    • analyse example integrations from several representative partners
    • design scenario-first from sample client code
    • build a whitebox version for them
    • pilot it with two or three partners, collect feedback (the external-user process model)
    • make the framework more blackbox
    • release widely only when suggestions become rare
  2. Qualities to check
    • simplicity, low barrier of entry, self-documenting names
    • a layered design for power users
    • consistency, testability, backward compatibility
  3. Biggest pitfall: premature release under schedule pressure with unrepresentative examples
    • unstable interfaces would then ripple into 30 partners' code
