Whole day

During the Payment table split, old and new service versions share live traffic. What evidence would make a rollback safe?
Show that the version you would roll back to can still read every current payment, including those the new version wrote to the new tables, and that tombstoned deletes stay deleted. That usually means keeping the new-first, old-fallback reader, backfilling and reconciling data, and watching errors and latency during the canary. A traffic switch alone cannot undo an incompatible schema change or recover data the old code cannot see.
A payment succeeds but appears late on the CQRS-based dashboard. Does this show a CAP failure?
No. In CQRS the read model is updated asynchronously from events, so projection lag can occur with no network partition at all. Trace the event from the write side to the projector and check projection progress. CAP concerns the choice between consistency and availability during a partition, which is a different problem.
On a sale day, traffic rises tenfold. The payment database's writes are saturated, one partner is flooding the API, and a canary of the new checkout is at 10%. In what order would you act, and what does each action cost?
First, rate-limit the flooding partner per client and plan, which protects capacity for everyone at the cost of errors for that partner. Next, pause or roll back the checkout canary so you are not debugging a new version during an overload, which costs a delayed release. Then put circuit breakers and timeouts on calls to payment so callers fail fast instead of clogging. The lasting fix for saturated writes is to shard the payment data and take reads off the primary with caches or read models, which adds routing, hot-shard risk and possible staleness. Throughout, watch yield, latency percentiles and traces to confirm each step helps.

Platform Management

A platform runs ten microservices on a container orchestrator, each auto-scaling from 2 to 20 instances. Design how services find each other, how that mechanism stays available, and what you would not build yourself.
Callers refer to each service by alias, resolved through a registry that works like an internal DNS: instances register, callers look up, then connect, so scaling and restarts never require configuration changes. The registry runs as a consensus-backed cluster of three or five nodes, tolerating one or two failures respectively; an even size adds nothing. Use the orchestrator's built-in DNS discovery rather than writing client and server discovery code, which takes engineers away from business requirements. Discovery handles traffic between services; user traffic still enters through the gateway.
The Payment service becomes slow, and the Agency service, which calls it, starts failing all its requests. Identify the cause, propose a countermeasure, and give the countermeasure's main drawback.
Cause: Agency's threads block waiting on Payment, so its thread pool clogs and it cannot serve even unrelated requests, and its callers clog in turn, a cascading failure. Countermeasure: a circuit breaker in an interceptor, through a resilience library or service mesh, that counts failures and timeouts in a window, opens to fail fast, then goes half-open after an interval to send sample requests, with exponential backoff, and closes on success. Add rate limiting if Payment is overloaded by volume. Drawback: while the circuit is open, payment-dependent features fail fast or degrade for every user, and badly tuned thresholds can open the circuit on brief blips.
Choose a deployment strategy for (a) a routine, backward-compatible security patch; (b) a new recommendation model whose effect on user behaviour must be measured; (c) a major release that must be switchable back instantly. Justify each and give one shared precondition.
(a) A rolling update: no downtime and no extra resources, ideal for patches, provided capacity holds during replacement. (b) A canary with 5 to 10% of traffic, to assess cohort behaviour live; shadowing would let you compare outputs without exposure but cannot measure user reaction. (c) Blue/green: V2 runs alongside V1 and traffic switches back at once, at the cost of double capacity. Shared precondition: versions must stay backward compatible with the data, because switching traffic does not undo writes.
An order spans CustomerManager (CreateOrder), MaidOrderManager (CreateMaidOrder) and PaymentManager (MakePayment), each with its own database and asynchronous messaging. Design the consistency mechanism, its failure handling, and what users may observe.
Use a saga, because two-phase commit needs synchronous calls and ACID support across all databases. Each step has a compensation: if MakePayment fails, run CancelMaidOrder then CancelOrder. Choose an orchestrator for central visibility, made highly available to avoid a single point of failure, or choreography for independent reactions at the cost of harder debugging. Trace every step with a shared trace ID and make steps and compensations idempotent. Users may see in-progress or cancelled orders, because sagas have no read isolation, so show such orders as pending.
Over a 90-day quarter (2,160 hours), a platform had four failures, each taking 3 hours to recover. The SLA promises 99.9%. Using the lecture's metrics, does it comply, which metric matters most to users, and what would you change?
MTBF is 2,160 / 4 = 540 hours, so uptime = (540 - 3) / 540 = 99.44%, which misses 99.9% (about 9 hours of downtime a year). To comply with the same failure rate, MTTR must fall to about 0.54 hours, so invest in tracing, centralised logs and fast rollback, and reduce failures with canaries and circuit breakers. Yield matters more than uptime to users: an outage at 3 a.m. with no traffic costs little, while one at peak costs many requests, so also report successful over total requests and the harvest of data served.
Users report intermittent errors on a flow that crosses five services, and nobody can reproduce them. Which observability tools would you use, in what order, and what does each contribute?
Start with metrics: error rate and latency percentiles per service show when the errors happen and which service's numbers move. Then distributed tracing, with one ID created at the root and propagated in headers, shows which span fails or slows in an affected request, and child spans narrow it down within a service. Finally, centralised logs searched by that trace ID give the exception and context without logging into each container. Together they lower MTTR; the cost is instrumenting every service and running the back-ends.

Deployment Case Study: Splitting the Payment Table

Propose a near-zero-downtime plan to split an Orders table into two tables owned by different new schemas, and say how each step can be rolled back.
Step 1: add the new tables only, with no code change; rollback drops them. Step 2: canary a compatibility release that writes new orders to the new tables, reads new-first with fallback to Orders, and tombstones deletes; make sure every version that can serve traffic, or be rolled back to, can still see new-table orders. Step 3: backfill historical rows without overwriting newer rows or tombstones, and validate. Step 4: canary a release that reads only the new tables, keeping the compatibility release as the rollback target, then tag it as the new major version. The cost is several releases and temporary dual-read code.
Why is canary preferred over blue/green for the transitional version in the Payment case, and what does neither strategy solve?
A canary exposes only a small share of transactions to the changed data behaviour, so problems surface before full rollout, and it needs no second environment. Blue/green switches all traffic at once; it switches back quickly, but every user hits the new data path at the same moment. Neither undoes writes to the shared database or makes them readable by old code, so the compatibility plan (dual reads, tombstones, a retained reader) is still required.
A teammate's plan for the Payment split is: (1) canary V2, which writes and reads only the new tables, at 10%; (2) migrate the old data; (3) roll out V2. Critique the plan and correct it.
During step 1, V2 cannot see historical payments, and V1 instances cannot see payments V2 accepted, so customers on both sides see missing payments. Rolling back loses visibility of V2's writes, and nothing marks deletes, so migrated rows could reappear. Correct it as the lecture does: add the tables first, canary V1.1 with new-table writes, fallback reads and tombstones, backfill and validate, then canary V1.2 reading only the new tables and tag it as 2.0. Each step stays backward compatible with the one before.
How is rollback handled at each stage of the Payment case, and where does the lecture's shortcut need more design?
Step 1: drop the unused new tables. Step 2: stop the V1.1 rollout, but keep every payment it accepted, since V1 alone may not read them. Step 3: if needed, remove only migrated copies identified by updated date, never live changes. Step 4: go back to V1.1's new-first, old-fallback reader. The lecture says canary rollback is fine because Payment is untouched, but that misses payments written to the new tables in the meantime, so reconciliation and mixed-version reads still need designing.

Data Management

A global shopping app needs a cart, a product catalogue with varied attributes, order history with financial integrity, product search, and 'customers also bought' recommendations. Choose a data model for each, justify it, and name the main cost of the overall design.
Cart: a key-value store for fast lookup by cart ID, replicated and kept available during partitions, since a stale cart beats no cart. Catalogue: a document store, because nested, varying product attributes fit schema-free documents. Orders: a relational store for ACID transactions and constraints. Search: a search engine index derived from the catalogue, never the primary store. Recommendations: a graph store to traverse customer-product relationships. The main cost is operational: five stores to run, plus the event flows that keep the derived ones in step, so drop any store whose workload does not justify it.
Using CAP, decide how (a) a social media timeline and (b) a payments ledger should behave during a network partition between data centres, and explain why the decision is a business one.
During a partition a distributed store must choose: keep answering and risk stale or divergent data (AP), or refuse some operations to stay consistent (CP). (a) The timeline should stay available: some posts are better than none, and stale feeds are a minor annoyance. (b) The ledger should prefer consistency and reject debits it cannot apply safely, because a wrong balance costs far more than a temporary error. It is a business decision because the question is which harm users and the company can tolerate, not which technology is better.
A ticketing platform must accept 60,000 seat purchases in the first two minutes of a sale. The database has one primary and one read replica, and performance tests show write throughput is the bottleneck. Propose a plan to scale writes, including the changes to software, and identify two side effects to monitor.
Replicas cannot help, because all writes go to the one primary. Shard the seat inventory, for example by hash of event and seat block, so each shard has its own master. The services then need shard-aware routing, through a client-side algorithm or a locator service. Serve the heavy seat-map reads from a cache or a CQRS read model, so the shards spend their capacity on purchases, and use write-through for anything that must not be lost. Monitor (1) hot shards, since one popular event can concentrate writes on one master, and (2) the staleness of cached or projected seat maps, which can show seats as free after they are sold. Cross-shard queries such as sales reports also get harder.
When would you avoid a document store for a new service, and what would you use instead? Give two concrete cases.
Avoid it when the service relies on joins across many entities, multi-record transactions, or enforced constraints and triggers, which most document stores lack; an accounting or ledger service should use a relational store. Also avoid it when the data is a write-heavy stream of sparse, timestamped records read by key and time range, where a wide-column store fits better, or when the core queries traverse relationships, where a graph fits. A document store remains a good choice when an entity and its children are read and written as one unit and the schema keeps changing.
Compare a key-value store and a wide-column store for an IoT platform that writes 50,000 readings a second and reads 'last value for device X' and 'device X over the past week'. Which would you choose, or would you use both?
A key-value store answers 'last value for device X' fastest, as an in-memory point lookup, but it handles range queries poorly and needs a lot of memory for history. A wide-column store absorbs heavy writes, scales linearly, and serves 'device X over the past week' well if the row key is device ID plus time. A defensible design uses both: wide-column for the history and a key-value cache for the latest value, at the cost of writing each reading twice and running two stores. If the last-value query is rare, the wide-column store alone is enough.
Order history is read far more often than it is written, writes go through strict business validation, and the history screens need a different shape from the write model. Design a CQRS solution, and say what users might notice and how you would limit it.
Commands go through a write API with full validation into a relational write store, and each committed change publishes an event. A projector builds a read model shaped for the history screens, for example documents or an in-memory read store, served by read APIs that scale independently. Users may not see a change they just made, because projection is asynchronous, so serve 'my latest order' from the write side or show it as pending until the projection catches up. Monitor projection lag and make the projector idempotent so replays do not duplicate history.
