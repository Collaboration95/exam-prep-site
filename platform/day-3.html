Whole day

During the Payment table split, old and new service versions share live traffic. What evidence would make a rollback safe?
  • Read compatibility: the version you would roll back to can still read every current payment, including those the new version wrote to the new tables
  • Tombstoned deletes stay deleted
  • Usually means
    • Keeping the new-first, old-fallback reader
    • Backfilling and reconciling data
    • Watching errors and latency during the canary

A traffic switch alone cannot undo an incompatible schema change or recover data the old code cannot see.

A payment succeeds but appears late on the CQRS-based dashboard. Does this show a CAP failure?

No.

  • CQRS: the read model is updated asynchronously from events → projection lag can occur with no network partition at all
  • Diagnose: trace the event from the write side to the projector; check projection progress
  • CAP concerns the choice between consistency and availability during a partition, which is a different problem
On a sale day, traffic rises tenfold. The payment database's writes are saturated, one partner is flooding the API, and a canary of the new checkout is at 10%. In what order would you act, and what does each action cost?
  1. Rate-limit the flooding partner per client and plan
    • Protects capacity for everyone
    • Cost: errors for that partner
  2. Pause or roll back the checkout canary
    • So you are not debugging a new version during an overload
    • Cost: a delayed release
  3. Circuit breakers and timeouts on calls to payment
    • Callers fail fast instead of clogging
  4. Lasting fix for saturated writes
    • Shard the payment data; take reads off the primary with caches or read models
    • Cost: routing, hot-shard risk and possible staleness

Throughout, watch yield, latency percentiles and traces to confirm each step helps.

Platform Management

A platform runs ten microservices on a container orchestrator, each auto-scaling from 2 to 20 instances. Design how services find each other, how that mechanism stays available, and what you would not build yourself.
  1. Finding each other: callers refer to each service by alias, resolved through a registry
    • Works like an internal DNS: instances register, callers look up, then connect
    • → Scaling and restarts never require configuration changes
  2. Staying available: a consensus-backed cluster of three or five nodes
    • Tolerates one or two failures respectively
    • An even size adds nothing
  3. Don't build it yourself: use the orchestrator's built-in DNS discovery
    • Writing client and server discovery code takes engineers away from business requirements

Discovery handles traffic between services; user traffic still enters through the gateway.

The Payment service becomes slow, and the Agency service, which calls it, starts failing all its requests. Identify the cause, propose a countermeasure, and give the countermeasure's main drawback.
  1. Cause: a cascading failure
    • Agency's threads block waiting on Payment → its thread pool clogs → it cannot serve even unrelated requests
    • Its callers clog in turn
  2. Countermeasure: a circuit breaker in an interceptor, through a resilience library or service mesh
    • Counts failures and timeouts in a window
    • Opens to fail fast
    • Goes half-open after an interval to send sample requests, with exponential backoff
    • Closes on success
    • Add rate limiting if Payment is overloaded by volume
  3. Drawback
    • While the circuit is open, payment-dependent features fail fast or degrade for every user
    • Badly tuned thresholds can open the circuit on brief blips
Choose a deployment strategy for (a) a routine, backward-compatible security patch; (b) a new recommendation model whose effect on user behaviour must be measured; (c) a major release that must be switchable back instantly. Justify each and give one shared precondition.
  1. (a) Security patch → rolling update
    • No downtime and no extra resources, ideal for patches
    • Provided capacity holds during replacement
  2. (b) Recommendation model → canary with 5 to 10% of traffic
    • Assesses cohort behaviour live
    • Shadowing would let you compare outputs without exposure but cannot measure user reaction
  3. (c) Major release → blue/green
    • V2 runs alongside V1 and traffic switches back at once
    • Cost: double capacity

Shared precondition: versions must stay backward compatible with the data, because switching traffic does not undo writes.

An order spans CustomerManager (CreateOrder), MaidOrderManager (CreateMaidOrder) and PaymentManager (MakePayment), each with its own database and asynchronous messaging. Design the consistency mechanism, its failure handling, and what users may observe.

Use a saga, because two-phase commit needs synchronous calls and ACID support across all databases.

  • Failure handling: each step has a compensation; if MakePayment fails → run CancelMaidOrder then CancelOrder
  • Coordination
    • Orchestrator for central visibility, made highly available to avoid a single point of failure
    • or choreography for independent reactions, at the cost of harder debugging
  • Trace every step with a shared trace ID; make steps and compensations idempotent
  • Users may see in-progress or cancelled orders, because sagas have no read isolation → show such orders as pending
Over a 90-day quarter (2,160 hours), a platform had four failures, each taking 3 hours to recover. The SLA promises 99.9%. Using the lecture's metrics, does it comply, which metric matters most to users, and what would you change?
  1. Comply? No
    • MTBF = 2,160 / 4 = 540 hours
    • Uptime = (540 - 3) / 540 = 99.44% → misses 99.9% (about 9 hours of downtime a year)
  2. Matters most to users: yield, more than uptime
    • An outage at 3 a.m. with no traffic costs little, while one at peak costs many requests
    • So also report successful over total requests and the harvest of data served
  3. What to change
    • To comply with the same failure rate → MTTR must fall to about 0.54 hours → invest in tracing, centralised logs and fast rollback
    • Reduce failures with canaries and circuit breakers
Users report intermittent errors on a flow that crosses five services, and nobody can reproduce them. Which observability tools would you use, in what order, and what does each contribute?
  1. Metrics first
    • Error rate and latency percentiles per service → show when the errors happen and which service's numbers move
  2. Distributed tracing
    • One ID created at the root and propagated in headers
    • Shows which span fails or slows in an affected request
    • Child spans narrow it down within a service
  3. Centralised logs last
    • Searched by that trace ID → the exception and context without logging into each container

Together they lower MTTR; cost: instrumenting every service and running the back-ends.

Deployment Case Study: Splitting the Payment Table

Propose a near-zero-downtime plan to split an Orders table into two tables owned by different new schemas, and say how each step can be rolled back.
  1. Step 1: add the new tables only, with no code change
    • Rollback: drop them
  2. Step 2: canary a compatibility release
    • Writes new orders to the new tables
    • Reads new-first with fallback to Orders
    • Tombstones deletes
    • Make sure every version that can serve traffic, or be rolled back to, can still see new-table orders
  3. Step 3: backfill historical rows
    • Without overwriting newer rows or tombstones
    • Validate
  4. Step 4: canary a release that reads only the new tables
    • Keep the compatibility release as the rollback target
    • Then tag it as the new major version

Cost: several releases and temporary dual-read code.

Why is canary preferred over blue/green for the transitional version in the Payment case, and what does neither strategy solve?

Canary over blue/green.

  • Canary exposes only a small share of transactions to the changed data behaviour → problems surface before full rollout; needs no second environment
  • Blue/green switches all traffic at once; it switches back quickly, but every user hits the new data path at the same moment

Neither undoes writes to the shared database or makes them readable by old code → the compatibility plan (dual reads, tombstones, a retained reader) is still required.

A teammate's plan for the Payment split is: (1) canary V2, which writes and reads only the new tables, at 10%; (2) migrate the old data; (3) roll out V2. Critique the plan and correct it.
  1. Critique
    • During step 1: V2 cannot see historical payments, and V1 instances cannot see payments V2 accepted → customers on both sides see missing payments
    • Rolling back loses visibility of V2's writes
    • Nothing marks deletes → migrated rows could reappear
  2. Correction, as the lecture does
    • Add the tables first
    • Canary V1.1 with new-table writes, fallback reads and tombstones
    • Backfill and validate
    • Canary V1.2 reading only the new tables → tag it as 2.0

Each step stays backward compatible with the one before.

How is rollback handled at each stage of the Payment case, and where does the lecture's shortcut need more design?
  1. Step 1: drop the unused new tables
  2. Step 2: stop the V1.1 rollout, but keep every payment it accepted, since V1 alone may not read them
  3. Step 3: if needed, remove only migrated copies identified by updated date, never live changes
  4. Step 4: go back to V1.1's new-first, old-fallback reader

Shortcut gap: the lecture says canary rollback is fine because Payment is untouched, but that misses payments written to the new tables in the meantime → reconciliation and mixed-version reads still need designing.

Data Management

A global shopping app needs a cart, a product catalogue with varied attributes, order history with financial integrity, product search, and 'customers also bought' recommendations. Choose a data model for each, justify it, and name the main cost of the overall design.
  • Cart → key-value store: fast lookup by cart ID, replicated and kept available during partitions, since a stale cart beats no cart
  • Catalogue → document store: nested, varying product attributes fit schema-free documents
  • Orders → relational store: ACID transactions and constraints
  • Search → search engine index derived from the catalogue, never the primary store
  • Recommendations → graph store: traverse customer-product relationships

Main cost: operational: five stores to run, plus the event flows that keep the derived ones in step → drop any store whose workload does not justify it.

Using CAP, decide how (a) a social media timeline and (b) a payments ledger should behave during a network partition between data centres, and explain why the decision is a business one.

During a partition a distributed store must choose: keep answering and risk stale or divergent data (AP), or refuse some operations to stay consistent (CP).

  1. (a) Timeline → stay available: some posts are better than none, and stale feeds are a minor annoyance
  2. (b) Ledger → prefer consistency: reject debits it cannot apply safely, because a wrong balance costs far more than a temporary error
  3. Business decision: the question is which harm users and the company can tolerate, not which technology is better
A ticketing platform must accept 60,000 seat purchases in the first two minutes of a sale. The database has one primary and one read replica, and performance tests show write throughput is the bottleneck. Propose a plan to scale writes, including the changes to software, and identify two side effects to monitor.

Replicas cannot help, because all writes go to the one primary.

  1. Shard the seat inventory, e.g. by hash of event and seat block → each shard has its own master
  2. Software change: services need shard-aware routing, through a client-side algorithm or a locator service
  3. Serve the heavy seat-map reads from a cache or a CQRS read model → the shards spend their capacity on purchases
  4. Use write-through for anything that must not be lost
  5. Monitor
    • (1) Hot shards: one popular event can concentrate writes on one master
    • (2) Staleness of cached or projected seat maps → can show seats as free after they are sold

Cross-shard queries such as sales reports also get harder.

When would you avoid a document store for a new service, and what would you use instead? Give two concrete cases.
  • Case 1: joins, multi-record transactions, constraints → relational store
    • Avoid it when the service relies on joins across many entities, multi-record transactions, or enforced constraints and triggers, which most document stores lack
    • e.g. an accounting or ledger service should use a relational store
  • Case 2: write-heavy stream → wide-column store
    • Avoid it when the data is a write-heavy stream of sparse, timestamped records read by key and time range, where a wide-column store fits better
  • Also: when the core queries traverse relationships → a graph fits

A document store remains a good choice when an entity and its children are read and written as one unit and the schema keeps changing.

Compare a key-value store and a wide-column store for an IoT platform that writes 50,000 readings a second and reads 'last value for device X' and 'device X over the past week'. Which would you choose, or would you use both?
  • Key-value store
    • Answers 'last value for device X' fastest, as an in-memory point lookup
    • Handles range queries poorly and needs a lot of memory for history
  • Wide-column store
    • Absorbs heavy writes, scales linearly
    • Serves 'device X over the past week' well if the row key is device ID plus time
  • Defensible design: use both: wide-column for the history + a key-value cache for the latest value
  • Cost: writing each reading twice and running two stores

If the last-value query is rare, the wide-column store alone is enough.

Order history is read far more often than it is written, writes go through strict business validation, and the history screens need a different shape from the write model. Design a CQRS solution, and say what users might notice and how you would limit it.
  • Write side: commands → a write API with full validation → a relational write store; each committed change publishes an event
  • Read side: a projector builds a read model shaped for the history screens, e.g. documents or an in-memory read store, served by read APIs that scale independently
  • Users may notice: not seeing a change they just made, because projection is asynchronous
  • Limit it: serve 'my latest order' from the write side, or show it as pending until the projection catches up
  • Monitor projection lag and make the projector idempotent so replays do not duplicate history
