API Design

96 slides · about 43 min · open the deck · JSON

This topic covers how to design, version, secure and operate APIs well. It starts with treating APIs as products and the design principles behind them, then covers REST constraints, resource and HTTP method best practices, the Richardson Maturity Model and GraphQL as an alternative. It moves on to versioning, OAuth-based security, resilience and testing, and distributed transactions across microservices. For the exam, expect to design or critique an API for a scenario and justify style, versioning and security choices.

Big ideas

  • Manage APIs as a product: outside-in, data-driven, MVP first, success measured by adoption.
  • REST has six constraints: client-server, stateless, uniform interface, layered, caching and optional code on demand. Stateless requests simplify scaling; resource data remains on the server.
  • Resources are plural kebab-case nouns; path identifies, query params filter/sort/paginate; verbs carry the action.
  • Safe methods request no business-state change. GET, HEAD, OPTIONS, PUT and DELETE are idempotent; POST and PATCH are not guaranteed idempotent.
  • Richardson Maturity Model: 0 one endpoint, 1 resources, 2 HTTP verbs, 3 hypermedia (HATEOAS).
  • GraphQL lets clients select fields through a typed schema, often reducing round trips; REST fits resource-oriented APIs and standard HTTP caching.
  • Version with MAJOR.MINOR.PATCH via URI or header; never remove or change meaning abruptly.
  • Across microservices use SAGA (events plus compensation) or two-phase commit instead of a single DB transaction.

API as a product and design principles

Treat an API as an ongoing product: design for consumers, measure adoption and keep its contract useful and stable.

Product ownership

  • APIs contribute to revenue → lecture examples: Salesforce, eBay, Expedia
  • Owner balances the stakeholders:
    • developers
    • consumers
    • operations
    • security
    • end users
  • Adoption and usage data guide improvements

Outside-in vs inside-out strategy

  • Outside-in: design from the needs of consuming developers and end users
  • Inside-out (avoid): design from whatever internal resources happen to exist
  • Data-driven:
    • how often?
    • what calls?
    • is behaviour changing?
  • Reach developers through forums and conferences
  • Measure success by adoption and business impact

Time to market

  1. Launch an MVP
  2. Mature the API through iterations, feedback and backlog grooming
  3. Easy to discover: APIs must also be discoverable

API design principles (part 1)

  • Developer empathy
    • user-centric
    • simple
    • fit for purpose
    • act on feedback
  • Granularity
    • identify key entities
    • design at the lowest practical level so APIs can be recombined
    • apply the Single Responsibility and Interface Segregation principles
  • Ubiquitous standards
    • well-accepted standards
    • no assumptions about consumer technology
    • SDKs for many technologies
    • security for sensitive APIs

API design principles (part 2)

  • Security
    • proportional to risk
    • applied at each granular level
  • Documentation
    • discoverable
    • linked from the endpoint
    • feedback channel
    • kept aligned with the API
  • Endpoint stability
    • availability matching the platform
    • backward-compatible versions
    • explicit service levels for A/B versions
Outside-in API strategy
Designing APIs around consumer and end-user needs rather than exposing existing internal resources.
API product owner
Role accountable for the API as a product: usage, adoption, roadmap and stakeholder needs.
SRP / ISP for APIs
Single Responsibility and Interface Segregation: small, focused APIs that consumers can combine.

Check yourself

A bank exposes each table of its core system as its own API and calls the job done. Six months later almost nobody uses them. Diagnose the problem.

Inside-out design: the APIs expose existing resources rather than what consumers need → developers find them hard to use or not useful.

  • Outside-in strategy: start from the needs of developers and end users
  • Launch an MVP
  • Measure success by adoption and business impact through usage analytics
  • API as a product: the bank should treat the APIs as a product with an owner who iterates on that feedback
An API team is disbanded the week after launch because 'the project is delivered'. What goes wrong over the next year?
  • Nobody acts on usage analytics or developer feedback → the API stops improving
  • Versions, documentation and endpoint stability no longer managed → consumers meet breaking changes and stale docs

The lecture's point: manage APIs as products, not projects: a product owner keeps a backlog from feedback and matures the API through iterations.

A single endpoint, /process-customer, creates a customer, opens an account and sends a welcome pack in one call. A partner only needs to create customers. Critique the design.

Breaks the granularity principles: one API with several responsibilities.

  • Forces the partner to depend on behaviour it does not use → against single responsibility and interface segregation
  • Design at the lowest practical level: separate customer and account resources → consumers can combine them in different ways

Trade-off: clients that need all three steps now make more calls, which a composite at the gateway can hide if needed.

A platform publishes its API with only a Java SDK and a custom binary protocol. Which design principle does this break, and what would you change?

Breaks ubiquitous standards: develop APIs on well-accepted standards and make no assumptions about the consumer's technology.

  • Custom protocol + one SDK → excludes consumers on other stacks and slows adoption
  • Fix: expose a standard protocol such as HTTP with JSON and maintain SDKs for several technologies

Cost: more SDKs to maintain.

API styles and the REST constraints

A quick map of the main API styles, then the six REST constraints (client-server, stateless, uniform interface, layered, caching, code on demand) and why each helps scale.

Choose API style by interaction

  • SOAP → enterprise integration (example in the lecture)
  • REST → exposes web resources
  • GraphQL → changing field requirements
  • gRPC → low-latency service calls
  • WebSocket → continuous two-way communication
  • Webhooks → notify a registered URL of events

Security still needs deliberate design for every style.

REST: six guiding constraints

  • Client-server
  • Stateless
  • Uniform interface
  • Layered architecture
  • Caching
  • Code-on-demand → the only optional one

All the others are required for a service to be called RESTful.

Stateless requests

  • Each request carries the context needed to process it
  • No stored client session: the server does not rely on earlier requests
  • Any suitable instance can handle it → simplifies load balancing
  • Persistent resource data still lives on the server
  • Cacheability depends on response semantics and headers

Uniform interface

  • Resources have URIs
  • Self-descriptive messages
  • Representations: clients manipulate resources through them
  • Hypermedia links describe next actions
  • Method + resource URI → GET /employees/1/photos/1
    • the verb is not part of the URI

HATEOAS

Hypermedia as the Engine of Application State

  • Responses carry links
  • Server drives application state and URL structure
  • Clients discover and navigate the API by following links
  • → loose coupling

Layers and caches

  • Layered architecture: a client may reach the API through a gateway or load balancer
  • Cache locations:
    • client
    • CDN
    • gateway
    • application
    • shared cache service
  • Shared cache pros: reduces separate per-instance copies; survives application restarts
  • Shared cache cons: adds network latency and operating cost
  • Consistency and durability of caches depend on configuration

Code on demand (optional)

  • Server extends the client by sending scripts or applets
  • → fewer features need pre-implementing in the client
Stateless
Each request carries all context; the server stores no client application state between calls.
HATEOAS
Hypermedia links in responses tell the client what it can do next, so the server drives navigation.
Code on demand
The only optional REST constraint: server sends executable code to extend the client.
Webhook
Event-driven callback: the server calls a URL you registered when something happens.

Check yourself

An API keeps each user's session in the memory of the instance that served the login, so the load balancer uses sticky sessions. Traffic triples during a sale and one instance crashes. What goes wrong, and what does REST's stateless constraint suggest?
  • Sessions lost: users pinned to the crashed instance lose their sessions
  • Uneven load: requests must return to their own instance → load cannot be spread evenly
  • Statelessness: the client holds the application state and each request carries its own context
  • → any instance can serve any request → scale by adding instances, with no server-side session synchronisation

Persistent resource data still needs a shared store.

An API runs on eight instances, each with an in-process cache of product prices. Users see different prices depending on which instance answers. Diagnose the problem and propose a fix.

Each in-process cache is local to its instance → updates reach the caches at different times.

  • Fix: distributed cache → consistent across requests to multiple servers
  • Survives restarts and deployments

Trade-off: slower than local memory, another service to run, and still needs a policy for invalidating stale entries.

Pick an API style for (a) in-app chat, (b) telling a partner system the moment a file upload completes, and (c) a mobile dashboard whose data needs vary by screen. Justify each choice.
  1. (a) WebSocket: continuous two-way real-time messages
  2. (b) Webhook: an event notification that calls the partner when the upload happens → the partner does not have to poll
  3. (c) GraphQL: each screen asks for exactly the fields it needs in one request

These match the lecture's typical uses; a REST API could still serve (c) if HTTP caching matters more than flexible queries.

A reviewer says your API is not RESTful because the server never sends scripts for the client to run. Do you agree?

No. Code on demand is the one REST constraint that is not strictly required.

  • It lets the server extend a client by sending code → reduces what the client must pre-implement
  • Required constraints: client-server, stateless, uniform interface, layered system, caching

Review the API against the required ones instead.

Resource naming, HTTP methods and idempotency

Practical rules for URI design and for choosing HTTP methods, with the safe/idempotent distinction and how to keep payment-style calls from duplicating.

Name resources: nouns, plural, consistent

  • Nouns, not verbs: /customers, not /getCustomers
  • Plural nouns (exception: singleton sub-resources like /customers/{id}/address)
  • kebab-case for multi-word names: /order-items
  • No trailing slash, for consistency

Path variables vs query parameters

  • Path variables → identity and hierarchy
    • /customers/{customer-id}/orders/{order-id}/order-items reflects object relationships
  • Query parameters (belong in the query string) → shaping
    • filtering: /users?role=admin
    • sorting: /products?sort=price&order=desc
    • pagination: /products?page=2&limit=50

Paths identify a resource; query parameters adjust how it is returned.

Map verbs to intent

  • GET → retrieve
  • POST → create new resources and sub-resources
  • PUT → update/replace an existing resource
  • PATCH → partial update
  • DELETE → remove

PUT vs POST (vs PATCH)

  • PUT → sets the representation at a known URI; may create there if the contract permits
  • POST → submits data to a collection or operation; often creating a server-assigned resource
  • Idempotency: PUT is idempotent; POST is not guaranteed to be
  • PATCH → expresses a partial change
  • POST caching needs explicit cache semantics and suitable cache support

Safe vs idempotent

  • Safe = does not request a business-state change → GET, HEAD, OPTIONS (incidental logging is compatible with safety)
  • Idempotent = repeats have the same intended effect as one request
  • PUT, DELETE → idempotent but not safe
  • POST, PATCH → not guaranteed idempotent
  • DELETE may return 204 then 404 → without changing that property (still idempotent)

Payment retries: idempotency key

  1. One unique idempotency key per intended payment
  2. Reuse that same key on retries
  3. Server records the outcome and recognises repeats → prevents duplicate charges

Implements the goal in the lecture of preventing duplicate transactions.

HTTP message recap

  • Request =
    • method
    • URI
    • version
    • headers (client type, accepted formats, cache settings)
    • body
  • Response =
    • status code
    • version
    • headers (content length/type, date, server)
    • body
Idempotent
Repeating the request produces the same resulting state as sending it once.
Safe method
A method that does not request a business-state change; GET, HEAD and OPTIONS are safe.
Path vs query parameter
Path identifies the resource; query parameters filter, sort or paginate it.

Check yourself

Critique this orders API and rewrite it: POST /createOrder; GET /orders/delete?id=9; PUT /orders with the new order in the body; GET /getCustomers?customer-id=7&orders-id=9; GET /products/sort/price/page/2.

Resources should be plural nouns; fix each call:

  • Plural nouns, no verbs: POST /orders to create (201)
  • GET must be safe → deletion becomes DELETE /orders/9
  • PUT updates a known resource → PUT /orders/9 or PATCH /orders/9
  • Path variables for identity and relationships → GET /customers/7/orders/9
  • Query parameters only to shape results → GET /products?sort=price&page=2&limit=50
A mobile client times out on POST /payments and retries. How do you make sure the customer is not charged twice?
  1. Idempotency key: generate one for the intended payment and send the same key on every retry
  2. Server records the key with the outcome → on a repeat, returns the recorded result without charging again

Pitfalls: generating a fresh key per attempt defeats the protection; the server must keep keys long enough to cover the retry window.

A client times out on DELETE /orders/9, retries, and gets 404. A developer fears the retry did harm. Did it?

No. DELETE is idempotent.

  • Idempotency concerns server state: after one or several calls the order is gone either way
  • Only the response differs: typically 204 then 404

The client should treat a 404 on a retried delete as 'already deleted'.

A cart API offers PATCH /carts/5/items/3 with either {"quantity": 5} or {"increment": 1}. The client library retries PATCH automatically on timeout. Is that safe?

Only for the first form.

  • Setting quantity to 5: leaves the same state however often it repeats
  • Incrementing by 1: adds another item on every retry
  • PATCH is not guaranteed to be idempotent

Fix: either disable automatic retries for the increment or protect it with an idempotency key.

Meaningful responses and status codes

Return the right status class and examples so developers can succeed, and debug a production 500 methodically rather than by changing code blindly.

Tell the client who is at fault

  • 2xx → client and API worked
  • 4xx → client erred; should change the request
  • 5xx → the API erred

Good feedback and examples improve developer experience, speed up documentation and raise adoption.

Status codes to know

  • 200 OK → often GET
  • 201 Created → after a create, usually POST
  • 204 No Content → usually PUT/PATCH
  • 400 Bad Request
  • 401 Unauthorized → credentials not recognised
  • 403 Forbidden → credentials accepted but no permission
  • 404 Not Found
  • 500 Internal Server Error → generic
  • 503 Service Unavailable → retry headers are useful

401 vs 403

  • 401 → we do not know who you are
  • 403 → we know you, but you may not do this

Debugging a production 500

Posed as a question in the lecture; the method is standard practice.

  • Never change code randomly in production
  • Find the cause first → logs, metrics and traces
4xx
Client error: the request was wrong; client should modify it.
5xx
Server error: the API or backend failed.
401 vs 403
Unauthenticated versus authenticated but not permitted.

Check yourself

An API returns 200 with the body {"error": "customer not found"} for unknown customers, and 500 when the client sends malformed JSON. What is wrong, and what should it return?

Return 404 for the missing customer and 400 for the malformed request.

  • Status codes tell the developer who behaved wrongly: 4xx = the client did, 5xx = the API did
  • As built: clients cannot handle errors from the status code
  • Monitoring raises server alarms for client mistakes while missing real failures
A clerk with a valid token calls DELETE /accounts/7, which only managers may do, and the API returns 401. Is that the right code?

No, it should be 403: the credentials were accepted, but the caller lacks permission for this resource.

  • 401 = credentials missing or not recognised → the client may try to log in again, which cannot help
  • Clear codes improve developer experience → API easier to adopt
Since this morning's release, 2% of requests return 500. A developer proposes changing code directly on a production server to test a theory. How do you respond?

Don't: blind changes in production are the lecture's 'big mistake' → they can widen the outage and leave no audit trail.

  1. Correlate logs, metrics and traces to find the failing path
  2. Compare against what the release changed, and reproduce safely
  3. If the release is the cause → roll back, then ship a verified fix through the normal pipeline
A downstream dependency is down for planned maintenance for ten minutes. Should your API answer 500 or 503?

503 Service Unavailable, ideally with a retry header.

  • 503 → tells clients the condition is temporary; a later retry may succeed
  • 500 = generic server error → invites investigation rather than a timed retry

Clients still need backoff so they do not hammer the API when it comes back.

Richardson Maturity Model

RMM separates resource identification, HTTP semantics and hypermedia into levels 0–3. It describes API design, not a throughput measurement.

RMM adds REST capabilities

  • Level 1 → resources
  • Level 2 → HTTP methods and status codes
  • Level 3 → hypermedia
  • Can improve interoperability and evolution
  • Not a performance guarantee: a higher level does not by itself guarantee lower latency or higher capacity

Richardson levels + restaurant analogy

  1. Level 0 (Plain Old XML)
    • HTTP is only a transport to a single endpoint
    • like SOAP and XML-RPC
    • analogy: one takeaway serves everything; you order pizza, rice and curry from it
  2. Level 1 (Resources)
    • separate resources get their own URIs
    • but a single HTTP method is used
    • analogy: visit different restaurants per dish
  3. Level 2 (HTTP verbs)
    • resource nouns + proper verbs (GET, POST, PUT, DELETE) and status codes
    • analogy: change toppings at the pizza place, cancel at another
    • minimum the workshop asks for (Level 2 or 3)
  4. Level 3 (Hypermedia controls)
    • HATEOAS
    • the response tells you what you ordered, what other options exist and links to more information
    • the server directs application state
RMM
Richardson Maturity Model: levels 0-3 measuring adoption of REST ideas.
POX
Plain Old XML; level 0, HTTP used as a tunnel to one endpoint.

Check yourself

A booking API has one endpoint, POST /api, with bodies such as {"action": "getBooking", "id": 5} and {"action": "cancelBooking", "id": 5}. Which RMM level is it, and what changes would take it to level 2?

Level 0: HTTP is only a transport for RPC-style messages → no resources and no HTTP semantics.

  1. Level 1: each booking gets its own URI, /bookings/5
  2. Level 2: then use the verbs and status codes properly
    • Read: GET /bookings/5 (200 or 404)
    • Cancel: DELETE /bookings/5, or a PATCH of its status (204)
An API exposes GET /v1/rooms/{room-id} to read a room and GET /v1/rooms/{room-id}/book to make a booking. The team says it is level 2 because it has resources. Do you agree?

No: it has resource URIs, which is only level 1.

  • Uses GET for a state-changing action and puts a verb in the path → does not use HTTP verbs as level 2 requires
  • GET must be safe: caches, crawlers or retries could create bookings by accident
  • Fix: model bookings as a resource → POST /v1/rooms/{room-id}/bookings returning 201 with the new booking's location
A mobile client hard-codes 40 URL patterns and breaks whenever the server reorganises its URLs. Which RMM level addresses this, and what does it demand of the client?

Level 3, HATEOAS.

  • Responses carry hypermedia links to related resources and next actions
  • → the server controls URL structure; the client discovers it from responses
  • → looser coupling; lets the API evolve

Demand on the client: it must be written to follow links instead of building URLs, and responses get somewhat larger.

A teammate says moving the API from RMM level 2 to level 3 will raise its throughput under load. Do you agree?

Not as stated.

  • RMM grades how fully an API uses resources, HTTP semantics and hypermedia
  • The lecture links higher levels with scalability and evolvability through looser coupling and cacheable, uniform interfaces
  • But adding links does not by itself make requests faster

Throughput has to be shown with load tests.

GraphQL vs REST and API documentation standards

GraphQL as a client-driven alternative to REST, how it works, when each wins, and the specification formats used to document APIs.

GraphQL

  • Query language and runtime: clients select fields from a server-defined schema
  • One query, one endpoint → customer, order and product data together
  • → reduces client round trips and unwanted fields
  • Server still performs the underlying data access

How GraphQL works

  • Server-side
    • schema → describes available types and functionality
    • queries → ask for data
    • resolvers → functions that turn an operation into data from a database or legacy API
  • Client-side tools
    • GraphiQL → browser interface to test queries and mutations
    • Apollo Client → for JavaScript front ends

GraphQL operations vs REST

  • Query → read
  • Mutation → create, update or delete
  • Subscription → live updates
  • REST → create, retrieve, update, delete via HTTP verbs

GraphQL vs REST trade-off

  • GraphQL: typed field selection → suits changing mobile and dashboard requirements
  • REST: resource endpoints → fit standard HTTP caching, when responses allow it
  • GraphQL caching often needs specialised caching
  • Fewer client calls ≠ faster server execution (not guaranteed)

API documentation standards

  • OpenAPI → vendor-neutral API description standard, based on Swagger
  • Swagger → supplies design and documentation tools
  • RAML → machine-readable, human-friendly modelling language
  • API Blueprint → emphasises readable documentation and design before implementation

A specification describes the contract; tools use it to document or test that contract.

Resolver
Server function that turns a GraphQL operation into data.
Over-fetching / under-fetching
Over-fetching returns unwanted fields; under-fetching requires extra requests for missing data.
OpenAPI Specification
Vendor-neutral standard description format for REST APIs.

Check yourself

A mobile screen needs a customer, their last five orders and the product names, which now takes three REST calls over slow networks. Separately, a public product catalogue is read millions of times a day through HTTP caches. Would you use GraphQL for both?

No: use GraphQL for the mobile screen and REST for the catalogue.

  • Mobile screen → GraphQL: one query to one endpoint returns exactly those fields → avoids over- and under-fetching across three calls
  • Catalogue → keep REST: resource URLs and standard HTTP caching serve repeated identical reads cheaply
  • GraphQL queries are hard to cache in web caches

Cost: running two styles, justified by two different access patterns.

A team implements 'place order' as a GraphQL query because the call returns the new order. Critique this.

Placing an order changes data → it should be a mutation; queries are for reading.

  • As a query it misleads clients and tools that treat queries as safe to repeat or cache
  • → an automatic retry could place a second order
  • Subscriptions are the third operation type: pushing updates as they happen, such as order status changes
Team A writes the API code first and generates documentation afterwards. Team B agrees an OpenAPI description with consumers before writing code. What does B's design-first approach buy, and what does it cost?
  • Separates the interface from the backend implementation → consumers can review and build against the contract early
  • Documentation matches the API from the start
  • OpenAPI is a vendor-neutral standard format → tools and consumers on any stack can use it

Cost: upfront agreement time, and the contract must then be kept in sync with the code.

API versioning and security basics

How to evolve an API without breaking consumers, and the baseline security approach with a gateway, OAuth 2.0 and validation.

Three versioning rules

  • Do not take anything away abruptly
  • Do not change the meaning of an existing API
  • Additions are optional: consumers need not use them

Semantic version MAJOR.MINOR.PATCH

e.g. 1.0.0

  • MAJOR → breaking changes
  • MINOR → backward-compatible features
  • PATCH → backward-compatible fixes

Two versioning approaches

  • URI versioning → api.example.com/v1; visible and simple
  • Header versioning → keeps URIs stable
    • custom header: Accept-version: v1
    • Accept header with a vendor media type: application/vnd.example.v1+json

Security baseline

  • Validate parameters
  • Threat detection
  • SSL/TLS everywhere
  • Proven solutions
  • Authenticate, then authorise
  • OAuth 2.0 → the industry standard for authorization

API gateway is the gatekeeper

  • Consolidates API requests from mobile and web clients
  • Interfaces with back-end microservices or monolith APIs
  • Centralises security

Each back-end service must still validate requests.

Authorization code flow

  1. User approves access at the authorization server
  2. App receives a short-lived code
  3. Exchanges the code for an access token
  4. Presents the token to the resource API
  5. API validates the token and permissions

The API need not contact the authorization server on every call if it can validate the token locally.

Further topics

  • Rate limiting and quotas
  • HTTP caching headers
  • Circuit breakers and retries
  • Webhooks and callbacks
  • Usage analytics
Semantic versioning
MAJOR.MINOR.PATCH numbering: breaking, feature, fix.
OAuth 2.0
Industry-standard authorization framework issuing access tokens to clients.
Access token
Credential the client presents to the resource server instead of the user's password.

Check yourself

Your API is at version 2.4.1. Give the new version for each change: (a) an optional 'notes' field is added to the order response; (b) 'amount' is renamed to 'total'; (c) a rounding bug is fixed without changing the contract.
  1. (a) 2.5.0: a backward-compatible feature → bumps the minor version
  2. (b) 3.0.0: renaming a field breaks existing consumers → the major version goes up
  3. (c) 2.4.2: a backward-compatible fix → bumps the patch

Change (b) also needs version 2 kept available for a while, because the rules say not to take anything away abruptly.

An API puts its full version in every URI, such as /v1.1/orders, and changes the URI for every minor release, so all consumers must update their URLs each time. Propose a better strategy.

Version for breaking changes only.

  • Put just the major version in the URI (/v1/orders) or move it to an Accept or custom header
  • Make minor and patch releases backward compatible → the URIs consumers call stay the same
  • Keep the old major version running with an explicit service level while consumers migrate

URI versioning is visible and easy to test; header versioning keeps URIs stable but is harder to see and to try in a browser.

A field is deprecated and only 3% of calls still use it. The team wants to delete it next week. What do the versioning rules say?

Don't take anything away abruptly.

  • Removal is a breaking change → belongs in a new major version
  • The current version keeps the field under an explicit service level
  • The change is announced through the developer portal

The 3% may include an important partner, so check who they are before setting the deadline.

Each of 12 services currently implements its own token validation, rate limits and request validation, each slightly differently. What would you propose, and what must stay in the services?

Put an API gateway in front as the single gatekeeper.

  • → authentication, rate limits and schema validation enforced consistently for every client
  • Services must still authorise business actions: a valid token does not prove permission on a particular resource
  • Services must still validate the data they rely on

Risk: the gateway becomes a critical component and must be highly available.

Errors, logging, retries, pagination and monitoring

Operational practices that keep an API dependable in production: error handling, logging, resilience patterns, pagination and metrics.

Consistent errors

  • Global exception handling → stable response format
  • Oversized payload:
    • check the intended API limit
    • check gateway/server/action settings
    • raise limits only if that payload is legitimate and capacity supports it
    • otherwise return a clear error

Log to explain what happened

  • Logging gives a trail of activity before an event
  • Supplements exception records
  • Reveals how clients use the API
  • Records metrics
  • e.g. NLog in .NET Core

Resilience patterns

  • Retry → transient failures, with bounded exponential backoff
  • Timeouts → bound waiting
  • Circuit breaker → stop calls during persistent failure
  • Bulkheads → isolate resources
  • Fallback → degraded results

Retry only when repeating the operation is safe or duplicate-protected.

One request, several transactions

  • One API call can touch multiple services and databases
  • Not one atomic transaction just because it is one call
  • Identify partial-failure cases
  • Choose coordinated commit or compensation where needed

Pagination: offset vs cursor

  • Offset → skips a number of rows; may become slow or drift when data changes
  • Cursor → continues from the last position in a stable ordering
  • Unique ordering or tie-breaker → createdOn alone can skip records sharing a timestamp

Monitor what matters

  • Application metrics
    • requests per minute
    • latency
    • failure rate
  • Infrastructure metrics
    • API uptime
    • memory
    • CPU

Slow API, fast queries

  • Trace the full request before selecting a fix
  • Investigate
    • blocked threads
    • connection or worker pools
    • downstream calls
  • Fast individual queries do not prove the complete request path is fast
Circuit breaker
Stops calling a failing dependency for a while so failures do not cascade.
Bulkhead isolation

An activity feed receives new items every second and pages with ?page=N&limit=50. Users scrolling down see duplicate items. Diagnose the problem and fix it.

A client retries every failed call to a slow partner API five times immediately. During a partner outage, the partner receives six times its normal traffic and the client's threads are exhausted. What would you change?
  • Timeout → calls cannot wait indefinitely
  • Retry with exponential backoff
  • Circuit breaker in front of the partner → stops calling it after repeated failures and returns a fallback
  • Bulkhead isolation → keeps the partner's calls from using up threads needed for other work

Trade-off: users get degraded responses during the outage instead of eventual success.

An operations lead proposes CPU usage as the main health metric for a public API. Does it show what users experience?

No. CPU is an infrastructure metric.

  • An API can fail requests or respond slowly while CPU is low, for example while waiting on a dependency
  • Users experience latency, failure rate and uptime
  • Track both
    • Application metrics: requests per minute, latency, failure rate
    • Infrastructure metrics: uptime, memory and CPU

CPU is still useful for capacity planning.

Performance, testing and API architecture maturity

How to make APIs faster and lighter, how to test them beyond functionality, and a seven-level scale of API adoption in an organisation.

Compression (gzip)

  • Client asks for gzip → Accept-Encoding: gzip header (and a User-Agent hint)
  • Compress (standard rule) → large text payloads like JSON
  • Avoid → tiny responses or already-compressed content (JPEG, video), where CPU cost outweighs the gain

Partial resources

  • Partial response → returns selected fields to reduce read payloads
  • PATCH → sends a partial update
  • Media type and contract define how fields, parent objects, arrays and removals are applied
  • Not always a merge: do not assume every PATCH is a recursive merge

Treat the API as a contract when testing

  • Check endpoints
  • Object model reflects resources and types
  • No missing or duplicate functionality
  • Resource relationships are reflected
  • Test plans: manual or automated

Test flows

  • Isolated requests
  • Multi-step workflows
  • Combined UI and API tests

Test scenarios

  1. Happy-path positive tests
  2. Extended positive with optional parameters
  3. Negative with valid or invalid input
  4. Destructive tests

Verify status code, payload, headers, application state and basic performance.

Testing beyond functional

  • Security
    • deny by default
    • fail securely
    • least privilege
    • reject illegal inputs
    • authorisation tests
    • role permissions
    • HTTPS
    • no leaking internal data models
    • rate limiting and throttling
  • Performance → load and stress tests
  • Usability

Architecture maturity: seven levels

  1. Isolated applications
  2. Unstructured integrations → sockets, file sharing, queues
  3. Component-based → EJB, CORBA, web services
  4. Service-oriented → ESB, SOAP
  5. Private APIs on microservices → REST, API gateway, containers
  6. Open APIs → API platform, developer portal, WAF
  7. APIs as business → service mesh, GraphQL, gRPC

Levels 1-3 are not API-based, 4-5 partially, 6-7 fully.

A tester checks performance by repeatedly sending requests from a manual API client on a laptop, then reports that the API 'handles load fine'. The target is 3 seconds for 90% of requests at 5,000 concurrent users. Do you accept the result?

No.

Average responses are 2 KB of JSON, one report endpoint returns 3 MB of JSON, and the API also serves images. Where would you enable gzip?

Enable it for the large JSON report and other big text responses.

  • There the bandwidth saved outweighs the compression CPU
  • Skip small payloads: the cost is not worth it
  • Skip already-compressed content such as images

Measure response size and latency before and after, rather than turning it on everywhere.

A mobile list screen downloads full 40-field product objects to display three fields, and an edit screen sends the whole object with PUT to change one price. What would you change in each?
  • List → partial response: the server returns only the requested fields → cuts payload and parsing time
  • Edit → PATCH with only the fields to modify, plus any enclosing parent objects

Two different tools: a partial response trims what the server sends, and PATCH trims what the client sends.

OAuth vs JWT vs SAML, CORS and payload inspection

Telling the security standards apart, why browsers need CORS, how to fix CORS errors, and validating requests at the gateway.

OAuth vs JWT vs SAML

They solve different problems.

  • OAuth → authorization framework: a client obtains an access token from a central authorization server
  • JWT → token format (JSON with issuer, subject claims, expiry); can be used inside OAuth; independent of how the token is obtained
  • SAML → Single Sign-On standard; passes identity between sessions using signed XML

CORS

  • Browsers use server response headers to decide whether a web page may read a cross-origin API response
  • OPTIONS preflight: some requests first trigger one, for allowed origins, methods and headers
  • Does not authenticate callers
  • Does not stop non-browser clients from reaching the API

Typical CORS error causes

  • Server policy denies the domain, scheme, port, header, credential or method
  • Server errored on the pre-flight
  • API gateway not relaying pre-flight responses
  • Credentials (cookies, HTTP auth) were required but not sent

Payload inspection at the gateway

  • Content → validate size or JSON schema against the API schema
  • Parameters → headers, query, path
  • Responses → headers and status codes
  • Actions per parameter → prevent, detect or ignore
JWT
JSON Web Token: signed JSON carrying claims such as issuer, subject and expiry.
SAML
XML-based Single Sign-On standard for exchanging identity between systems.
CORS
Browser-enforced response-header policy controlling access to cross-origin responses; some requests require preflight.
Pre-flight request
Browser's preliminary request asking the server whether the real cross-origin request is allowed.

Check yourself

Match each need to OAuth, JWT or SAML: (a) a third-party budgeting app needs delegated access to a user's bank transactions; (b) staff already signed in to the corporate portal should reach a partner web app without logging in again; (c) the access token should carry the issuer, subject and expiry in a compact form.
  1. (a) OAuth: the authorisation framework through which the client obtains an access token from an authorisation server
  2. (b) SAML: a single sign-on standard that passes identity from an existing session using an XML document
  3. (c) JWT: a token format that can be used inside OAuth

A design note saying 'JWT instead of OAuth' confuses a token format with the framework for obtaining tokens.

A browser web app gets a CORS error calling your API, but the same request works from a command-line client. What do you check?

Check, in order:

  1. Server's CORS policy allows the app's
    • origin, scheme, port
    • methods, headers and credentials
  2. The server can answer the pre-flight request without error
  3. The API gateway relays the pre-flight response to the browser

The command-line client works because CORS is enforced only by browsers.

A teammate proposes a strict CORS policy as the main protection for a payment API. Is that enough?

No. CORS only controls whether a browser lets a page from another origin read the response.

  • Scripts, servers and other non-browser clients ignore it entirely
  • The API must still authenticate and authorise each call, validate payloads and apply rate limits
Your API receives a million requests a day, 30% of them with missing or null fields, and the application crashes on the nulls. How do you handle this in production?
  • Validate requests against the API schema at the edge: content, parameters and headers
  • Reject bad ones with a 400 that explains which field is wrong
  • Inside the service: handle optional fields defensively → one bad request cannot crash the process
  • Log and monitor the rejection rate: 30% suggests a client bug or a confusing contract worth fixing at the source

API gateway, orchestration and distributed transactions

A gateway simplifies client access; multi-service work still needs explicit handling of partial failures through distributed commit or sagas.

Why not call microservices directly?

Posed as a question in the lecture.

  • API gateway → one entry point
  • Handles cross-cutting concerns → security, routing, aggregation
  • → clients are not coupled to many services

API orchestration

The API manager calls services in order, e.g.:

  1. Validation service first
  2. Service A next

Defensive handling of bad data

A million requests a day, 30% with missing or null fields:

  • Validate input at the edge → schema validation
  • Handle nulls gracefully rather than crashing

Separate services, separate transactions

With separate databases, a local transaction cannot atomically update order and inventory together. Options:

  • Avoid that requirement
  • Distributed commit (2PC), where supported
  • Eventual consistency and compensation

Two-phase commit (2PC)

  1. Prepare: a coordinator asks all participants to prepare
  2. Commit: if all report done, it tells them to commit
  3. Abort: if one fails, it tells the others to abort

Strongly consistent, but couples services and blocks resources.

Saga

  • Services commit local steps
  • Later failure → business compensation for completed steps
  • Illustrated event-bus flow: a central coordinator directs Order and Inventory → orchestrated, despite its “choreographer” label
  • Choreography instead → services decide their reactions without a central controller
API orchestration
A central manager calls services in a defined order to fulfil one request.
Two-phase commit
Prepare then commit/abort protocol coordinating atomic commit across participants.
SAGA
Sequence of local transactions with compensations, coordinated centrally or through services reacting to events.
Compensation
An action that undoes an earlier completed step when a later step fails.

Check yourself

An Order service and an Inventory service have separate databases. At peak there are 2,000 orders a minute, and Inventory is sometimes slow. Would you use two-phase commit or a saga?

A saga.

  • Two-phase commit holds locks across both services until both are ready → a slow Inventory stalls every order and couples their availability
  • Saga: each service commits locally and publishes an event
  • A failure triggers compensation, such as cancelling the order

Trade-off: accept eventual consistency; must design compensations and idempotent handlers.

In the lecture's centrally directed saga, Inventory replies 'Failed to Reserve Items'. What happens next, and why is this orchestration even though messages go through an event bus?
  • Next: the coordinator sends a compensating 'Delete Order' to undo the order already committed, and notifies the user
  • Orchestration because one coordinator decides the next step; the event bus is only the transport
  • In choreography, each service would react to the failure event on its own
A mobile app calls six microservices directly, each with its own address, authentication scheme and response format. What problems does this cause, and what does an API gateway fix?
  • Problems
    • The app is coupled to each service's location and contract
    • Makes many round trips
    • Has to handle six security schemes
    • → every internal change risks breaking a released app
  • Gateway fixes
    • One entry point with central security and routing
    • Can compose several calls into one response
    • Lets services move or split behind it

Cost: it adds a hop and a component that must be highly available.

A clinic platform's first two APIs are designed as follows. API 1: URI /v2.3/appointments/{patient-id}/book, service BookingManager, input the patient id, output the list of all doctors, HTTP verb GET. API 2: URI /v2.3/appointments/{patient-id}/cancel, service BookingManager, inputs the patient id and patient name, output the list of all patients' appointments, HTTP verb GET.     • GET must be safe
  2. Versioning strategy: semantic versioning
    • Only the major version in the URI (/v2) or in a header
    • Keep minor and patch releases backward compatible → consumers unaffected by them
  3. Corrected interfaces
    • Book: POST /v2/patients/{patient-id}/appointments; inputs doctor id and time slot → 201 + the created appointment with its location
    • Cancel: DELETE /v2/patients/{patient-id}/appointments/{appointment-id}, or PATCH its status to cancelled → 204 or the updated appointment
    • Drop the redundant patient name and the unrelated lists of all doctors or all appointments

    • A thread or connection pool being exhausted
    • Larger payloads from the release
  2. Confirm
    • Distributed traces to find the slow span
    • Then check pool metrics and the release diff

A product team must choose between REST and GraphQL for a mobile dashboard that aggregates data from six microservices; a public catalogue endpoint on the same platform is mostly anonymous, repeated reads. Recommend a style for each and give the trade-offs.

  • Catalogue → REST
