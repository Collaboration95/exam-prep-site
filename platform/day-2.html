Whole day

An API gateway validates the caller's token before forwarding POST /orders. Why must the Order service still check authorisation and handle retries?
  • Authorisation: a valid token proves identity, not permission to act on a particular customer's order → the service must enforce business permissions and invariants itself
  • Retries: a client that times out will retry, and POST is not idempotent → a retry can create a second order
  • Fix: require an idempotency key and return the recorded outcome for repeats

The gateway centralises common policy; it does not replace the service's own rules.

A retried order request produces duplicate inventory events, and stock is reduced twice. Where is duplicate protection needed, and why is one place not enough?
  • At the API: reuse the request's idempotency key → a retried POST does not create a second order
  • In Inventory: process OrderPlaced idempotently, by recording processed event IDs or making the update safe to reapply → at-least-once delivery can redeliver the same event

Why both: request-level protection cannot prevent broker redelivery, and receiver-level protection cannot prevent a second order being created.

Design 'place order' for a platform whose mobile client talks to Order, Inventory and Payment services. Cover the client-facing API, integration between the services, and what the client sees when payment fails.
  • Client-facing API
    • POST /v1/orders through the gateway with an idempotency key
    • Returns 201 with the order's location and a pending status
    • Client reads progress with GET /v1/orders/{order-id}
  • Integration: a saga, orchestrated by Order if central visibility matters
    • Order commits the order and an OrderPlaced event together
    • Inventory reserves stock in its own transaction
    • Payment charges
    • Each handling events idempotently
  • Payment fails
    • Compensations release the stock and cancel the order
    • Client sees the status change from pending to cancelled with a clear reason

The client must be built to show in-progress states: there is no single atomic transaction.

API Design

A clinic platform's first two APIs are designed as follows. API 1: URI /v2.3/appointments/{patient-id}/book, service BookingManager, input the patient id, output the list of all doctors, HTTP verb GET. API 2: URI /v2.3/appointments/{patient-id}/cancel, service BookingManager, inputs the patient id and patient name, output the list of all patients' appointments, HTTP verb GET. (1) Do they comply with RMM level 2? (2) Propose a versioning strategy that affects consumers less. (3) Give corrected interfaces.
  1. RMM level 2? No.
    • Resource-like URIs → only level 1
    • But GET is used for state-changing actions and verbs sit in the path, so HTTP verbs aren't used as level 2 requires
    • GET must be safe
  2. Versioning strategy: semantic versioning
    • Only the major version in the URI (/v2) or in a header
    • Keep minor and patch releases backward compatible → consumers unaffected by them
  3. Corrected interfaces
    • Book: POST /v2/patients/{patient-id}/appointments; inputs doctor id and time slot → 201 + the created appointment with its location
    • Cancel: DELETE /v2/patients/{patient-id}/appointments/{appointment-id}, or PATCH its status to cancelled → 204 or the updated appointment
    • Drop the redundant patient name and the unrelated lists of all doctors or all appointments
Design a RESTful API for a cleaning-service platform. Customers make one-off orders or subscribe to OnceAFortnight, OnceAWeek or TwiceAWeek plans, change or cancel subscriptions, and pay; the mobile app retries on timeouts. Give resources, verbs and status codes, and explain how you handle retries.
  • Resources
    • /customers/{customer-id}/orders: POST creates a one-off order (201); GET lists orders with ?status= and pagination
    • /plans: GET
    • /customers/{customer-id}/subscriptions: POST subscribes (201); PATCH /subscriptions/{subscription-id} changes the plan (200 or 204); DELETE cancels (204)
    • /payments: POST (201)
  • Naming: plural kebab-case nouns, no verbs, path variables for identity and query parameters for filtering
  • Retries: retried POSTs to orders, subscriptions and payments carry an idempotency key → the server returns the recorded outcome for a repeat
  • Maturity: aim for level 2; add links (level 3) such as a subscription's cancel and change-plan links if clients would benefit
  • Versioning: version as /v1
A published API at version 1 has 200 partner integrations. You must split 'name' into 'firstName' and 'lastName', add an optional loyalty-points field, and fix a currency-rounding bug. Plan the releases and the partner impact.
  1. Bug fix → patch; optional loyalty field → minor release: neither breaks partners, so they need no changes
  2. Name split → version 2 (/v2 or a v2 media type)
    • Changes meaning and removes a field → breaking
    • Version 1 keeps returning 'name' under an explicit service level
  3. Announce the change and its timeline through the developer portal; track v1 usage per partner before retiring it

Cost: running two versions side by side for the migration period.

A public payment API serves a browser single-page app and partner servers. It receives a million requests a day, 30% with malformed or null fields, and retried POSTs have caused some duplicate charges. Design its security and robustness, and name one drawback of your design.
  • Gateway in front
    • TLS
    • OAuth 2.0 access tokens (JWT is one possible format)
    • Per-client rate limits and quotas
    • Schema validation that rejects malformed requests with a 400
  • Services still authorise each action and validate business invariants
  • Configure CORS for the single-page app's origin only, remembering that CORS is not authentication
  • Require an idempotency key on payment POSTs → retries return the original result
  • Add timeouts, circuit breakers on downstream calls, and monitoring of latency and failure rate

Drawback: the gateway is a critical shared component, and strict validation will initially reject many partner requests until partners fix their clients.

After a release, the 95th-percentile latency of GET /orders rose from 300 ms to 4 seconds, while database query times are unchanged. Give the most likely causes, how you would confirm them, a fix, and the fix's drawback.
  1. Likely causes: fast queries → the time is spent elsewhere
    • A new or slower downstream call
    • A thread or connection pool being exhausted
    • Larger payloads from the release
  2. Confirm
    • Distributed traces to find the slow span
    • Then check pool metrics and the release diff
  3. Fix (if a downstream call is the cause)
    • Add a timeout and circuit breaker with a fallback
    • Or call it in parallel, or cache the result
  4. Drawback: degraded or slightly stale responses when the fallback or cache is used → the change needs a load test before release
A product team must choose between REST and GraphQL for a mobile dashboard that aggregates data from six microservices; a public catalogue endpoint on the same platform is mostly anonymous, repeated reads. Recommend a style for each and give the trade-offs.
  • Dashboard → GraphQL
    • Client-driven: one query to one endpoint fetches exactly the fields needed from several services
    • → cuts mobile round trips and over-fetching
    • The schema and type system document the data
  • Catalogue → REST
    • Server-driven and resource-oriented
    • Identical repeated reads benefit from ordinary HTTP and CDN caching, which GraphQL makes hard

Cost: two styles to run and secure, plus resolvers that must call the six services efficiently.

Reusable Services and API Gateway

In an online-auction platform, the Bidding context's Auction aggregate holds every Bid placed on it, often thousands. A live leaderboard is computed by querying the Bidding database each time one of up to 50,000 concurrent viewers refreshes. You doubt viewers will see the latest bids promptly. Identify the most likely cause, propose a countermeasure by revising the domain model, and give its drawback.
  1. Cause
    • Oversized Auction aggregate → every bid loads and locks a large object graph → bids contend and transactions slow down
    • Leaderboard reads compete with bid writes on the same transactional store
  2. Countermeasure (revise the domain model)
    • Make Bid its own small aggregate referencing AuctionId
    • Auction keeps only the invariants it must protect at commit, such as the current highest valid bid
    • Publish an enriched BidPlaced event in the same transaction as the bid
    • A Leaderboard context maintains its own read model from those events and pushes updates to viewers
  3. Drawback
    • The leaderboard is eventually consistent
    • Events must be applied in order per auction and processed idempotently
    • More components to run and monitor
A platform has been split into Order, Inventory and Billing services, and Billing must also integrate with a legacy finance system that nobody will change. Design the context mappings and integration types, and justify each.
  • Order depends on Inventory: Customer-Supplier: Inventory, upstream, tries to meet Order's requests but has the final say
  • Inventory and Billing expose Open Host Services with a Published Language, such as JSON Schema → downstream contexts consume them with little translation
  • Billing vs the legacy finance system: Anticorruption Layer protects Billing's model, accepting the cost of maintaining the translation
  • Avoid database or file integration
  • Messaging with domain events where an immediate reply is not needed, with at-least-once delivery and idempotent receivers
  • REST only where the caller needs an answer now
A customer places an order that must reduce stock held in an Inventory aggregate in another service. Design this with aggregates and domain events, and say what you would do if the business cannot accept delayed stock allocation.
  1. Order commits its change and an OrderPlaced event in one local transaction, referencing products by ID
  2. The event, carrying the order lines and any data Inventory would otherwise query, is delivered reliably
  3. Inventory decrements stock in its own transaction, handling duplicates idempotently
  4. A failure publishes a compensating outcome, such as StockReservationFailed → the order can be cancelled

If allocation must be immediate, events cannot promise that: either move the reservation into the same aggregate and context, or reserve stock synchronously before confirming the order, accepting tighter coupling.

A new-customer flow must create loyalty points, dispatch a welcome pack and send an email; legal now requires proof that every customer received the privacy email within 24 hours. Compare orchestration and choreography for this flow and recommend a design.
  • Orchestration
    • Explicit flow in the Customer service → simple and easy to audit
    • Risk: a 'god' service coupled to every step
  • Choreography
    • The Customer service emits one event that each service reacts to → loosely coupled, easy to extend
    • But the flow is implicit and must be monitored
  • Recommend: a mixed design fits
    • Choreograph the loyalty points and welcome pack
    • Orchestrate or explicitly track the privacy email: record its completion against the customer ID and alert if it is missing after 24 hours

Cost: two styles to understand and operate.

At peak, 500 payments a minute are confirmed. Each confirmation must update the Order context and trigger a customer notification; the Notification service is available 99% of the time. Would you integrate by REST or messaging, and what must be true for your choice to be safe?

Messaging.

  • Publishing PaymentConfirmed lets Payment finish even when Notification is among its 1% of downtime; the queued events catch up later
  • Synchronous REST would make payment confirmation depend on Notification being up
  • Safe only if the event is
    • Committed with the payment state
    • Delivered at least once
    • Handled by idempotent receivers in Order and Notification

Cost: the order status and notification lag slightly behind the payment, so if the user's screen must show the result at once, read it from Payment directly.

A prototype microservice system has a browser calling services by fixed address, one database per service shared by its instances, and a single message broker. It must now scale each service to several instances. Explain what to add and which failure points to address.
  • Add a service registry and server-side discovery: clients call a router, here the API gateway, at a well-known location → it looks up available instances and load-balances across them
  • The gateway also gives each client a suitable API, aggregates calls and translates protocols
  • Single points of failure left after scaling instances
    • The shared databases → need high availability
    • The message broker → needs high availability
    • The gateway and registry must themselves be replicated
