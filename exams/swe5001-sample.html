Architecting + Platform: performance testing, messaging choice, domain-model critique, REST/RMM, NFR priority, metrics.

Question 1 Total: 25 marks

Refer to the case study in Appendix A and answer the following questions:

a.

One of the measures of success of a platform is how it grows its ecosystem by growing its reach with new types of interactions and number of users.

i.

During the testing of Phase 1 API request-response type of interactions for the ‘Verify Identity’ use case, the response time is expected to be less than 3 seconds for 90% of the requests for 100,000 voters.

Additional parameters of performance testing:

  1. API calls time frame: 30 seconds
  2. Maximum response time: < 5 seconds

A few testers had used some performance testing tools, e.g., Postman, to conduct the above test. It was however found that test results were varied and indeterministic, hence not a good proxy for the above performance criteria. Provide one possible reason for this observation. Propose one more reliable way to perform the test.

2 marksDiagnose an observationPlatformPerformance, testing and API architecture maturityArchValidating the design and documenting performanceArchSizing a system from a benchmark
Suggested answer and marking points (ours, not the official scheme)

Reason: an API client run from each tester's laptop cannot generate or control the specified load. It sends requests from one machine, mostly in sequence, over whatever network the tester is on. The client, its network and its warm-up state become the bottleneck, and every run has a different arrival pattern. The measurements describe the tester's set-up, not the system under 100,000 voters in 30 s.

More reliable test: a scripted load test run from distributed load generators placed near the system, against a production-like environment and data. Ramp to 100,000 virtual voters issuing Verify Identity inside the 30 s window and record the 90th percentile (< 3 s) and the maximum (< 5 s), not the average. Warm up first, repeat the run several times and compare.

Marking points

  1. 1 markA credible cause tied to the observation: uncontrolled or insufficient load from single client machines, network and cache noise, or no defined arrival profile.
  2. 1 markA reliable method with specifics: a load-generation tool with a scripted ramp and concurrency, distributed generators, a production-like environment, percentile measurement and repeated runs.

Trap: Saying ‘use a better tool’ with no reason. The mark is for explaining why the measurement was not a proxy for 100,000 concurrent voters.

ii.

The following interaction ‘Update Current Simplified/Detailed Results’ use case requires update of current simplified results should be completed within 1 minute on average while update of current detailed results should be completed within 3 minutes on average for the 100,000 concurrent voters planned for Phases 1 and 2. Furthermore, the results produced by the use case have to be deterministic and repeatable.

An aspiring Solution Architect had chosen to make use the message queue mechanism for triggering the above use case whenever a vote is concluded in the Conduct Vote use case. As the Lead Solution Architect, you strongly recommend the use of the event streaming mechanism instead. Provide two reasons to justify your recommendation.

2 marksDefend a choice against an alternativeArchCommunication styles and integration levelsCloud nativeLambda, Kappa, IoT, event-driven, multi-cluster, AICloud nativeEvent sourcing, service mesh and circuit breakerPlatformDomain events
Suggested answer and marking points (ours, not the official scheme)

1. Deterministic and repeatable: an event stream is a durable, ordered log, ordered per partition, so partition by poll. Consumers can replay it from any offset, and recomputing the tally from the same log always gives the same result. A queue deletes a message once it is consumed and gives no replay. With competing consumers it also gives no ordering guarantee, so a lost or failed tally cannot be rebuilt exactly.

2. One event, several independent consumers: the same VoteConcluded event must feed the simplified results (1-minute target), the detailed results (3-minute target) and, in Phase 2, Predict Trends. Each reads the stream at its own pace with its own offset, and the producer is unchanged. On a queue, consumers compete for messages: each vote reaches only one of them unless you add a queue per consumer. Partitions also let 100,000 voters be processed in parallel with windowed aggregation.

Marking points

  1. 1 markReplay and retention with per-partition ordering give deterministic, repeatable results (tied to the stated requirement).
  2. 1 markPublish/subscribe fan-out to multiple consumers with different latency targets, or partitioned throughput for 100,000 voters.

Trap: Generic ‘streaming is faster’. The paper hands you the requirement words (deterministic, repeatable, 1 and 3 minutes), so use them.

b.

With reference to the domain model found in Section 7 of the case study, analyze the following issues. For each issue, identify the most likely cause, propose an effective countermeasure (by revising the domain model) and suggest the major drawback(s) of the countermeasure, if any.

i.

The NotificationManager service is responsible for defining all kinds of notification used by the platform. The various kinds of notification are rather specific to the responsibilities of the other services of the platform. As the Lead Solution Architect, you are of the opinion that the current domain design does not facilitate the potential reuse of the NotificationManager service in other platforms. Significant cost saving could be realized if the NotificationManager service can be easily reused in other platforms without drastic adaptation.

5 marksIssue → cause → countermeasure → drawbackPlatformReusable assets in a platformPlatformBounded contexts and ubiquitous language in depthPlatformDecoupling services with context mappingsArchArchitecture styles and modifiability
Suggested answer and marking points (ours, not the official scheme)

Cause: NotificationManager holds the domain-specific subclasses PollingNotif, ProctoringNotif, ObservationNotif, VotingCompletionNotif, RejectionNotif and VerificationNotif. Each is associated with entities owned by other services (Poll, Voter, PollingRoom, Observer, User). The service speaks every other bounded context's language, so it is coupled to them. A new notification kind or a change to Poll forces a change in NotificationManager, and another platform would inherit e-voting concepts.

Countermeasure (revised model): make NotificationManager a generic, domain-agnostic context. Replace the subclasses with Notification (recipientRef, channel, templateId, parameters, status) and NotificationTemplate (owner, channel, body with placeholders). Add Channel (email now, SMS or push later) and DeliveryAttempt. Remove every association to Poll, Voter, PollingRoom and Observer, and refer to recipients by an opaque id or address. The owning services (VotingManager, ProctoringManager, PollManager) decide what to say: they register templates and either call a generic Send Notification API or publish domain events that a thin translator maps to notification requests (a published language or anti-corruption layer).

Drawbacks: the calling services take on composing content and managing templates. The payload loses type safety, so a wrong parameter is found at run time. Recipient data is copied into payloads, which spreads personal data and matters under GDPR. Existing code needs migrating.

Marking points

  1. 1 markCause: notification subclasses encode other contexts' concepts; associations to Poll, Voter, PollingRoom and others create tight coupling.
  2. 1 markWhy that blocks reuse: changes ripple into NotificationManager, and another platform would need e-voting entities.
  3. 2 marksRevised model: generic Notification, Template and Channel entities, no cross-context associations, owners supply templates and parameters or publish events.
  4. 1 markA real drawback: work moves to the callers, weaker validation, template governance, or PII spread in payloads.
ii.

As the Lead Solution Architect, you are pessimistic of the ability of the implemented platform in allowing the Observers in promptly viewing the updated CurrentSimplifiedResults of the Poll he/she is monitoring.

4 marksIssue → cause → countermeasure → drawbackPlatformAggregatesPlatformDomain eventsCloud nativeData store, CQRS and saga patternsArchCaching and precomputation
Suggested answer and marking points (ours, not the official scheme)

Cause: CurrentSimplifiedResults sits in ObservationManager but is aggregated by Poll in PollManager, while the votes (CastVote) live in VotingManager. Producing up-to-date results means ObservationManager queries or joins across PollManager and VotingManager on each view, or recounts votes. Nothing pushes changes to the observer either. With 100,000 voters and 1,000 observers this cannot meet ‘within 1 minute’.

Countermeasure: model the results as their own aggregate, for example PollResults with CandidateTally, owned by ObservationManager and referring to the poll by PollId only. Remove Poll's aggregation of the results. VotingManager publishes a VoteCast domain event, and ObservationManager updates the tally incrementally as a CQRS read model or materialised view. Observers subscribe to their poll's results, and changes are pushed to them (WebSocket or server-sent events).

Drawback: the results are eventually consistent: they lag by the processing window. Exact counts need idempotent, duplicate-safe event handling and a way to rebuild by replaying events. There is also extra infrastructure: the event stream and a read store.

Marking points

  1. 1 markCause: results are separated from the votes and owned through Poll in another service, so each view needs cross-service queries or recomputation, and there is no push.
  2. 2 marksRevised model: a results aggregate in ObservationManager, updated from VoteCast events (read model), referencing Poll by id, with observers subscribed and pushed.
  3. 1 markDrawback: eventual consistency, idempotency and replay complexity, or more infrastructure.

With reference to the interfaces provided above, answer the following questions:

  1. Do the above API interfaces comply with RMM Level 2? Provide the likely reason(s).
  2. Propose a better versioning solution/strategy to ensure API consumers are less implicated by API upgrades.
  3. There are redundant and/or missing inputs, outputs and possibly wrong HTTP verbs in the API interfaces. Reconstruct the above table to depict the corrected interfaces.
6 marksCritique and correct an artefactPlatformRichardson Maturity ModelPlatformResource naming, HTTP methods and idempotencyPlatformAPI versioning and security basicsCloud nativeAPI gateway, versioning and service discovery
Suggested answer and marking points (ours, not the official scheme)

1. Not Level 2. Level 2 means resources plus correct HTTP verbs and status codes. Both calls change state (admit a voter, switch a voter into voting mode) using GET, which must be safe and idempotent: caches, prefetchers and automatic retries could trigger admissions. The URIs also end in verbs (/invite, /start), which is RPC over HTTP, and they hang a voter's actions under votes, which is the wrong resource.

2. Versioning. Do not put minor versions in the URI: /v1.1 makes every consumer change URLs on each minor release. Use semantic versioning with only the major version exposed, in the path (/v1/) or in a header or media type (Accept: application/vnd.voteanywhere.v1+json). Make compatible changes additively within v1, run v1 and v2 side by side behind the gateway, and publish a deprecation window.

3. Corrected interfaces:

Marking points

  1. 1 markVerdict: not Level 2, because GET changes state (not safe or idempotent).
  2. 1 markSecond reason: verbs in URIs and the wrong resource (votes vs polling rooms, voters, ballots).
  3. 1 markVersioning: major version only (path or header or media type), semantic versioning, backward-compatible evolution and deprecation.
  4. 3 marksCorrected table: resource-style URIs, POST/PATCH, missing inputs added (room or poll id), redundant ones removed (voter list, voter id for invite), useful outputs and status codes.
d.

A team member has suggested that the usability of the system, particularly in enabling proctors to manage voting sessions effectively, is the most crucial non-functional requirement, especially considering the high volume of voters. Do you agree with this proposal, and if so, why? If not, what are your reasons for disagreement?

2 marksAgree or disagree with a teammateArchQuality attributes and the utility treeArchRequirements III: prioritise, detail, document and review
Suggested answer and marking points (ours, not the official scheme)

Disagree. The argument rests on ‘the high volume of voters’, and volume is a performance and scalability concern, not a usability one. The case's architecturally significant requirements are 100,000 concurrent voters, < 3 s for 90% of requests and results within 1 and 3 minutes. Beside them are security and integrity, given public mistrust of e-voting, and availability during the poll window. An easy-to-use proctor screen does not help if the platform cannot carry the load or cannot be trusted. Proctor usability still matters, since 1,000 proctors run the queues, but it ranks lower in the utility tree because it carries less architectural risk.

Marking points

  1. 1 markVerdict, with the volume argument reframed as scalability and performance (or security), using the case's numbers.
  2. 1 markPositions usability correctly: valid but lower priority in a utility tree because of lower risk and impact on the architecture.
e.

A team member has suggested monitoring the daily number of voters processed by the system as an application metric. The proposal argues that tracking this metric will help assess system scalability and usability, especially when the number is high. Do you agree with this proposal, and if so, why? If not, what are your reasons for disagreement?

4 marksAgree or disagree with a teammatePlatformMetricsArchWhat performance means: the core metricsArchNon-linearity: Amdahl's law and USL
Suggested answer and marking points (ours, not the official scheme)

Disagree. A daily count of voters is a volume or business metric. A high number shows that demand happened, not how the system behaved under it.

Not scalability: scalability is how throughput and response time hold up as load and resources grow. A daily total hides the peak (a poll is a short, bursty window) and says nothing about latency, saturation or the cost of extra capacity. Measure throughput (votes per second) against concurrency, p90/p99 response time at each load level, utilisation of the bottleneck, scaling efficiency as instances are added, and queue or consumer lag.

Not usability: many voters processed can coexist with confusing screens, long queues and abandoned sessions. Measure task success and completion time for Verify Identity and Conduct Vote, drop-off from the virtual queue, error rates and user satisfaction.

Keep the daily count for capacity trend planning and business reporting.

Marking points

  1. 1 markVerdict: it is a volume or business metric, and a high value does not demonstrate either quality.
  2. 1 markWhy it fails as a scalability measure: daily granularity hides peaks, and it has no latency, throughput or resource dimension.
  3. 1 markWhy it fails as a usability measure: it ignores task success, time, errors and abandonment.
  4. 1 markBetter metrics for each property (p90 latency vs load, votes/s, scaling efficiency; completion rate, drop-off).

Trap: Agreeing because ‘more voters means it scales’. This is the paper's classic metric trap.

Question 2 Total: 13 marks

With reference to the case study in Appendix A, answer the following questions based on the following context:

The cloud native engineering team decided to develop a smart frontend (Hinted but not limited to Phase 2 in the case study) and these improvements will be part of Vote Anywhere platform products. As a cloud native architect, you are responsible for a few architectural and design decisions involved in both Phases 1 and 2. Answer the following questions with the above-mentioned backdrop:

a.

Initially, your team created an initial architecture for its minimal viable product prototype as below.

Improve the above architecture by transforming the monolithic architecture into a hybrid reference architecture hosting relevant backend services needed by the voting platform (hint: you can consider using microservices, scheduled tasks, event/stream-driven services and serverless).

i.

Capture the essential components and their interactions from a cloud perspective in a reference architectural diagram. What are the additional components or managed services that are essential for such a multi-cloud environment?

ii.

In addition to external communication via API Gateway, how will the internal services communicate? Label the communication components in the diagram and explain the communication patterns preferred.

iii.

Identify any one out of the designed services that may need to remember state. Which state-management mechanism would suit the service you have identified?

iv.

Describe an overall deployment plan in terms of Kubernates cluster either using the k8s deployment diagram or as a paragraph.

10 marksDesign under constraints, then side effectsCloud nativeHybrid, multi-cloud and reference architecturesCloud nativeMonolithic vs distributed; microservicesCloud nativeInter-process communicationCloud nativeServerless architecture patternsCloud nativeState: pets vs cattleCloud nativeCloud native design on Kubernetes
Suggested answer and marking points (ours, not the official scheme)

i. Components. Clients (voter mobile app, web PWAs) reach the platform through global DNS/traffic management, then CDN + WAF, then the API gateway, which handles authentication with SingPass OIDC, throttling and routing. Behind it are microservices per bounded context: User, Poll, Proctoring, Voting, Results and Notification. A managed real-time video service carries the polling rooms. An event stream carries VoteCast and PollClosed. Scheduled tasks open and close polls and build reports. Serverless functions handle the bursty edges: bulk voter import triggered by a file upload, and sending email from a queue. Each service owns its database, and the results are an in-memory read model. Multi-cloud essentials: the same IaC and GitOps for each cloud's managed Kubernetes; global DNS/traffic manager; cross-cloud networking with a service mesh (mTLS); central identity, secrets and key management; central logs, metrics and traces; a replicated container registry; and a replication plan for the event stream and data.

ii. Internal communication. Synchronous REST/gRPC only where a caller needs an immediate answer (Proctoring checks a voter's eligibility with Poll), through Kubernetes service discovery and the mesh sidecars (mTLS, timeouts, retries, circuit breaking). Everything on the voting path is asynchronous: Voting publishes VoteCast to the stream (publish/subscribe, choreography). Results, Notification and Phase 2 Prediction subscribe independently. Point-to-point commands such as ‘send this email’ go on a queue with retries and a dead-letter queue. Async absorbs the burst and decouples the voting path from slow consumers.

iii. State. ProctoringManager has to remember each voter's place in the virtual queue and the live polling-room sessions. Keep its pods stateless (no sticky sessions) and externalise that state to a replicated in-memory key-value store with TTLs (a sorted set per room). Any replica can then serve the next request, and a pod restart loses nothing. Alternative: Results is a stateful stream processor whose running tallies sit in a checkpointed state store, rebuilt by replay.

iv. Kubernetes plan. One managed cluster per cloud and region, nodes spread across three zones, namespaces per domain (voting, proctoring, results, platform). Each service is a Deployment with at least 3 replicas, a PodDisruptionBudget and an HPA on requests per second or consumer lag, exposed through Services and an Ingress behind the API gateway. The stream runs as a StatefulSet with persistent volumes, or as a managed service. Config and secrets come from ConfigMaps and Secrets, network policies apply between namespaces, and GitOps handles delivery with canary releases. The cluster autoscaler is pre-scaled before each poll opens.

Marking points

  1. 3 marksi. Diagram decomposes the monolith into services per bounded context and shows gateway, event stream, scheduled jobs, serverless functions and data stores with interactions.
  2. 1 marki. Multi-cloud essentials named with purpose: IaC/GitOps, global traffic management, cross-cloud networking and mesh, central identity, secrets and observability.
  3. 2 marksii. Sync for immediate queries via discovery and mesh; async pub/sub for the vote flow and queues for commands, with the reason (decoupling, burst absorption).
  4. 2 marksiii. A genuinely stateful service and a fitting mechanism: externalised replicated store, StatefulSet or checkpointed stream state, with why the pods stay stateless.
  5. 2 marksiv. A coherent cluster plan: zones, namespaces, Deployments/StatefulSets, replicas, HPA, ingress, config, rollout.
b.

Observe the logical architecture diagram provided in Section 6.2 of the case study. As mentioned, the voters front end app needs native local storage back up facility. In the near future, the platform plans to expand in other countries with provision for physical voting booths involving additional IoT sensors and actuators. In such context, would you develop the proposed front-end using a native client or as a progressive web app? What are the design implications on the backend services.

3 marksA or B, with knock-on effectsCloud nativeProgressive Web Apps vs native appsCloud nativeLambda, Kappa, IoT, event-driven, multi-cluster, AICloud nativeAPI gateway, versioning and service discovery
Suggested answer and marking points (ours, not the official scheme)

Native (or cross-platform native) client for voters and booths. The proof-of-voting backup needs dependable native local storage: PWA storage can be evicted and is sandboxed. Physical booths need IoT sensors and actuators over Bluetooth, NFC or USB, secure key storage and kiosk mode, which a PWA reaches poorly or not at all. Proctoring video also benefits from native camera control. The cost is separate builds, app-store releases and slower fixes. The web apps for admins, observers and the public can stay PWAs for reach.

Backend implications: versioned, backward-compatible APIs, because old app versions stay in the field, ideally with a backend-for-frontend per client type (mobile, booth, web). Idempotent vote submission with client-generated keys, so offline retries cannot double-vote. Device registration and attestation (device certificates, mTLS) for booths. An IoT ingestion path (device gateway or broker, telemetry stream, device management). Push notifications. Plan for per-country data residency, since multitenancy is out of scope today but will be needed.

Marking points

  1. 1 markA choice justified by the case: native local storage and IoT device access point to native.
  2. 1 markThe trade-off acknowledged: release overhead, multiple code bases, or reach.
  3. 1 markBackend implications: API versioning or BFFs, idempotent sync, device identity, IoT ingestion, push.

c.

With reference to the domain model in Section 7 and the incomplete and potentially erroneous logical packaging cum deployment model in Figure 6 in Section 8, as the Lead Solution Architect, evaluate the logical architecture and identify two undesirable architectural decisions and propose the corrective actions. Justify your answer by explaining how the undesirable architectural decisions lead to the proposed corrective actions.

Hint: You may draw just the necessary parts of the diagram to illustrate your answers.

6 marksCritique and correct an artefactArchLogical architecture: overview and functional elementsArchLogical architecture: deployment, verify, validate, reviewArchSecure design principles and reference architecturesCloud nativeData store, CQRS and saga patterns
Suggested answer and marking points (ours, not the official scheme)

Any two of the following, each as decision → why it is undesirable → correction:

1. Voting Manager Control (VoteController) and Notification Manager Control are deployed to the voter's mobile device. The device is untrusted and sits on the Internet. Vote validation, the one-vote-per-voter rule, the update of results and email sending would all run where a tampered app can bypass them, and NotificationController would need Email Gateway credentials on every phone. This breaks complete mediation and least privilege. Correction: deploy only Voting Manager Presentation (VoteCastingScreen) and a local proof-of-voting store to the device. Move VoteController into the Voting service and NotificationController into the Notification service in the internal zone, reached through the API gateway.

2. Packaging crosses service boundaries. VotingCompletionNotif, a NotificationManager entity, is manifested by Voting Manager Data Access, and VoteController talks directly to Poll Manager Data Access. Two services sharing each other's data creates coupling and breaks database-per-service. Correction: VotingCompletionNotif moves to Notification Manager Data Access. VoteController gets poll and candidate data through PollManager's API (or a cached copy kept up to date by events) and publishes VoteCast. Notification reacts to that event.

3. The device lacks the local storage element the case requires, which keeps details of voting excluding the choice of candidate. Instead, server-side entities like CastVote (which contains the choice) and Voter are packaged with the device-side subsystems. Correction: add a device-side Local Proof-of-Voting Data Access holding only receipt details, and keep CastVote server-side so the choice never rests on the device.

Marking points

  1. 3 marksFirst undesirable decision identified, its consequence explained (security, integrity, coupling), and a concrete corrective packaging or deployment.
  2. 3 marksSecond undesirable decision, consequence and correction, with justification linking the problem to the fix.
d.

During performance testing, it was discovered that the system cannot handle the required 100,000 concurrent voters casting their votes within a 5-minute window due to a bottleneck in database write throughput. The current database setup includes one primary replica and one read replica. Please propose a comprehensive plan to scale up the database write throughput, including any necessary changes or impacts on software and infrastructure components. Additionally, identify at least two potential side effects of implementing this new design that the team should monitor closely.

6 marksDesign under constraints, then side effectsPlatformScaling databases: replication, sharding, cachingCloud nativeSharding, replication and eventual consistencyCloud nativeSharding strategiesArchPerformance tactics and load balancingArchNon-linearity: Amdahl's law and USL
Suggested answer and marking points (ours, not the official scheme)

Size it first: 100,000 votes in 300 s is about 333 writes/s on average. Bursts will be several times higher, and each vote also writes audit and notification rows. A read replica adds no write capacity: every write still lands on the one primary.

Plan:

  1. Level the load: Voting validates and appends each vote to a durable stream or queue and acknowledges with a receipt. Consumers batch-insert into the database at a rate it can sustain (queue-based load levelling). An outbox makes the vote write and its event atomic.
  2. Partition the writes: shard the vote store by hash of voter id (or poll and constituency) across N primaries, or move votes to a write-optimised distributed store (wide-column or NewSQL). Votes are append-only and keyed by voter, so the one-vote rule is a unique key within each shard.
  3. Take reads off the primaries: results come from the stream as a CQRS read model, so the write store serves almost no reads.
  4. Tune the write path: batch inserts, minimal indexes on the hot table, connection pooling, no shared counter row updated per vote, idempotency keys on every insert.
  5. Software and infrastructure changes: a shard-aware data access layer, idempotent consumers, ‘vote recorded’ receipts in the UX, more database nodes plus the stream cluster, per-shard monitoring, then repeat the 100,000-voter load test.

Side effects to monitor: (1) consumer and replication lag, which delays results against the 1-minute and 3-minute targets; (2) duplicate or lost votes from at-least-once delivery, so reconcile counts against receipts; (3) shard skew or hot partitions; (4) slower cross-shard queries for detailed results and reports; (5) more operational complexity and cost, and harder resharding.

Marking points

  1. 1 markDiagnosis: a single primary is the write bottleneck; replicas don't scale writes; rough sizing.
  2. 3 marksPlan elements: async load levelling, sharding or a write-scalable store, CQRS for reads, write-path tuning, with the software and infrastructure changes.
  3. 2 marksAt least two relevant side effects with what to watch (lag vs SLA, duplicates or consistency, hot shards, cross-shard queries, complexity).
