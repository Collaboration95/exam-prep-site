Day 1: What the Instructor Emphasised in Class

8 slides · about 15 min · open the deck · JSON

These classroom sketches connect architecture decisions, backlog work and hosting choices. Follow the same web application from on-premises tiers to cloud services and an orchestrated container design. Use the progression to explain why a component changes; the drawings are examples rather than requirements for every cloud-native system.

Big ideas

  • Architecture answers what (components and how they interact), where (data, infra, application, platform, security, enterprise viewpoints) and how (decisions driven by constraints, requirements and objectives).
  • Architecture is communicated human-to-human (diagrams) and human-to-machine / machine-to-machine (IaC, YAML, properties files).
  • Functional and non-functional requirements both feed the product backlog; skipped work becomes technical debt, a hidden 'secret list'.
  • Classic hosting: DNS, firewall, routers, API gateway and load balancers in front of web and app server tiers, with replicated databases (active-active or active-passive).
  • A one-to-one cloud migration swaps each on-prem box for an AWS service (CloudFront/IAM, API Gateway, ELB, ECS/EKS/EC2, RDS) without redesigning.
  • Cloud native: API gateway at ingress, Services and Deployments of pods on Kubernetes nodes, images from a container registry, service mesh (Istio) for service-to-service calls.
  • VMs and containers can run always-on or scheduled workloads; functions execute on demand under provider runtime constraints.
  • The classroom timeline links cloud infrastructure and platforms, Docker packaging, and Kubernetes orchestration; treat its dates as sketch annotations rather than verified launch dates.

Check yourself

A team hands in an architecture made of polished diagrams only. Infrastructure is still set up by hand from a wiki page. Using the instructor's framing, what is missing?
Architecture has two audiences: people, through diagrams and views, and machines, through IaC, YAML and properties files. In cloud native work, the provisioning code is part of the architecture, so without it the design can't be reproduced or checked against what is running. Add versioned IaC and config alongside the diagrams.
A messaging app and a video-streaming service are both being designed by the same team, and a manager wants one standard architecture and stack for both. Is that sensible?
Probably not. Different problem types lead to different architectures and stacks: messaging needs many long-lived connections and low-latency delivery, while streaming needs large content delivery and catalogue and recommendation workloads. Share platform tooling where it helps, but let each domain's constraints drive its design decisions.
To hit an MVP date, a team skips automated tests and hardcodes config, and records none of it. Six months later, every change breaks something. What went wrong, and what should they have done?
The shortcuts became hidden technical debt, which the instructor calls the 'secret list': future costs that stakeholders can't see or prioritise. Shortcuts can be a valid trade-off for an MVP, but each one should be recorded in the backlog with its consequence and a remediation item, next to the functional and non-functional requirements.

From on-prem to cloud to cloud native

The same web application in three stages: on-premise, a like-for-like migration to AWS, and a cloud-native Kubernetes design.

Three maturity stages, one web app

The same web application drawn at three maturity stages: a ready-made storyline for an exam answer on migration.

  1. On-premise
  2. One-to-one cloud mapping
  3. Cloud native on Kubernetes

On-premise

  • In front → DNS, firewall, routers, API gateway
  • Tiers → load-balanced web and app server tiers
  • Database pair for availability:
    • active-active → both serve
    • active-passive → standby takes over

One-to-one cloud mapping

Preserves the broad tiers.

  • Replaced with AWS services:
    • edge delivery
    • access control
    • gateways
    • load balancers
    • compute
    • databases
  • Match roles carefully:
    • CloudFront → CDN
    • Route 53 → DNS
    • IAM → controls access
  • Managed compute → can already provide scaling or replacement
  • Business-service decomposition → a separate change

Cloud native on Kubernetes

  • API gateway (firewall, throttling, IAM, monitoring) → fronts public endpoints and a service registry
  • Service → load-balances across a Deployment's pods on nodes
  • Images → from a container registry
  • Service mesh (Istio) → carries service-to-service calls (e.g. gRPC)
  • Backend deployment set (example) → one load balancer, five Tomcat copies, two MongoDB copies
Active-active / active-passive
Database replication where both nodes serve traffic, or one stands by to take over.
Pod
Smallest Kubernetes unit: one or more containers scheduled together on a node.
Kubelet
Agent on each Kubernetes node that runs the pods assigned to it.
Service mesh (Istio)
Infrastructure layer handling service-to-service traffic, security and observability.
Container registry
Store for container images, e.g. Amazon ECR, Docker Hub, Quay.

Check yourself

An on-premises three-tier app is moved one-to-one to cloud equivalents (managed DNS, CDN, load balancer, VMs or containers, managed database). What does this gain, and what doesn't it change?
It gains managed components, possibly with autoscaling and automatic replacement of failed instances, while keeping the broad tier structure. It doesn't create independently deployable business services, so release coordination and whole-app scaling stay the same. Redesign further only where a specific delivery or scaling problem justifies it.
The on-premises database pair must survive a server failure. Active-active or active-passive?
Active-passive if the goal is simple failover: a standby takes over when the primary fails, with straightforward consistency, but the standby's capacity is idle. Active-active if both nodes must serve load: better use of capacity and no failover delay, but concurrent writes need conflict handling or partitioning. Choose by write pattern and acceptable complexity.
In the cloud-native version, internal calls go through a service mesh using gRPC, and external traffic comes through an API gateway. Why split it this way rather than routing everything through the gateway?
The gateway handles north-south concerns at the edge: firewalling, throttling, identity and monitoring for public endpoints. The mesh handles east-west service-to-service traffic with consistent routing, encryption and telemetry, and gRPC is efficient for internal calls. Sending internal traffic through the gateway would add a hop and make it a bottleneck and single point of failure.

Packaging options and history

The three ways to wrap a solution and the history that led to Kubernetes.

Packaging vs operating schedule

Packaging does not force an operating schedule.

  • VMs → package a guest OS
  • Containers → package application dependencies while sharing a kernel
  • Functions → on-demand execution with a managed runtime
  • VMs and containers → can also run scheduled or short-lived jobs

Choose from execution needs

  • Always-on services → may favour containers or VMs
  • Sporadic event-driven work → often favours functions
  • Check → latency, startup, state, execution limits, cost
  • Don't assume a packaging choice decides them

Why Kubernetes emerged

  1. Cloud providers (AWS, Azure, GCP) → made VMs (IaaS) and SDK platforms (PaaS) mainstream
  2. Docker → made single containers easy
  3. Google's Borg/Omega experience → led to Kubernetes to schedule, scale and heal many containers
  4. By 2018 → the standard orchestrator with pluggable runtime, storage and networking interfaces
Serverless / function
Code run on demand per invocation, with no always-on server to manage.
Orchestrator
System (e.g. Kubernetes) that schedules, scales and heals containers across machines.
Borg / Omega
Google's internal cluster managers that inspired Kubernetes.

Check yourself

A component generates invoices once a night for 10 minutes, and another serves a 24/7 API. Function, container or VM for each?
The nightly job could be a function if it fits within execution limits, or a scheduled container job if it needs more time or runtime control, since containers can also run short jobs. The 24/7 API fits containers, or VMs if it needs OS-level control, because always-on load removes the pay-per-invocation advantage. Check startup, state and cost rather than assuming the packaging decides them.
A team runs 60 containers by hand on 8 machines with Docker. Failed containers stay down until someone notices. What does this show about why Kubernetes emerged?
Docker made it easy to build and run single containers, but running many across many machines needs scheduling, scaling and self-healing. Kubernetes, drawing on Google's Borg and Omega experience, provides that orchestration, with pluggable runtime, storage and networking. The cost is learning and operating the cluster.

Exam-style questions

Answer aloud or on paper before opening.

Plan how to evolve a three-tier on-premises web application (DNS, firewall, load-balanced web and app tiers, active-passive database) to a cloud-native architecture in stages. For each stage, say what it gains and what triggers the next one.
Stage 1, one-to-one mapping: managed DNS, CDN at the edge, cloud load balancers, VMs or containers for the tiers and a managed database. This gains managed operations and possibly autoscaling, with little application change. Stage 2, containerise the tiers and run replicas behind Kubernetes Services with images in a registry and IaC for everything. The trigger is a need for faster, repeatable deployments. Stage 3, extract business capabilities as services behind an API gateway, with a mesh for internal traffic, only where independent delivery or scaling is a real problem. Functions are added for event-driven parts. Each stage adds operational complexity, so take the next one only when its trigger appears.
For a new system with a 24/7 order API, a nightly reconciliation job and an image-thumbnail task triggered by uploads, compare VMs, containers and functions, and choose one for each component.
VMs include a guest OS and give OS control, containers share a kernel and package dependencies lightly, and functions run on demand with a managed runtime. Order API: containers for always-on load and portability. Nightly reconciliation: a scheduled container job, or a function if it fits execution limits. Thumbnails: functions, for short, sporadic, event-triggered work billed per invocation. Choose by duration, startup latency, state, runtime control and cost, not by packaging fashion.
You are asked to produce the architecture for a new cloud-native platform. Using the Day 1 framing (what, how, where, and two audiences), outline what the deliverable must contain and how you would keep it from going stale.
What: a reference architecture with layers, components and how they interact. How: decisions with the constraints, requirements and objectives behind each. Where: data, infrastructure, application, platform, security and enterprise viewpoints. Deliver diagrams for people and IaC, YAML and config for machines, so the running system is generated from the architecture. Keep functional and non-functional requirements and recorded technical debt in the backlog. Because the IaC is part of the architecture, changes to it go through review, which keeps the design and the system aligned.
