Application Architecture Styles (Archetypes)

48 slides · about 40 min · open the deck · JSON

Choose architecture styles from quality attributes, data needs and team capacity. Compare frontend options, monoliths, microservices, hexagonal design, serverless, and Lambda/Kappa data processing. The modern archetypes add decisions about blast radius, placement, ownership, offline work and repeatable operations; combine them only where their benefits justify the cost.

Big ideas

  • Every style is a trade-off: monoliths are simple and fast but hard to scale per component; distributed styles buy scalability and fault isolation at the cost of operational complexity.
  • Choose an architecture from drivers: domain, architecture characteristics, data, organisation and teams, and sync vs async communication.
  • Hexagonal architecture keeps the domain at the centre, reached only through ports and adapters, so it can be driven by users, tests or scripts and run on any infrastructure.
  • Lambda = batch + speed + serving layers (accurate but two pipelines); Kappa = one stream pipeline + serving (simpler, lower latency, harder reprocessing).
  • Event-driven is a principle applied across monoliths, microservices, serverless and data architectures for loose coupling and responsiveness.
  • AKF scale cube: x = replication (clones), y = functional decomposition (services/functions), z = data partitioning (sharding).
  • PWAs favour web reach and shared code; native integration can offer deeper platform capabilities. Verify offline, push and hardware needs on target devices.
  • Modern archetypes compose with classic ones; each answers a different question and has a stated 'do not use when'.

Check yourself

A team's code is well structured, but releases take two weeks because deployments are manual and the app runs on hand-built VMs. A teammate says 'architecture is about the code, the platform is ops' business'. Do you agree?

No: in a cloud native full stack, the platform is part of the design.

  • Packaging as containers or functions + delivery through Git-driven pipelines → shape scalability and delivery speed as much as the code does
  • Here the platform is the bottleneck
  • Fix: automated pipelines + a container or function platform → cuts the two-week cycle more than refactoring code would
A manager reads that AI-assisted engineering will soon make teams smaller and work 'specification-driven', and proposes cutting architecture reviews because 'the AI writes the code'. How do you respond?

Keep the reviews.

  • Forecasts, not settled facts: that is how the lecture presents them
  • Even if they come true → specifications and architectural constraints become the main input to AI-generated code
  • So clear quality attributes, review and verification matter more, not less

Cutting reviews removes the check on whether the generated code meets the constraints.

Progressive Web Apps vs native apps

Front-end delivery options: PWAs (broad reach, one codebase) versus native and cross-platform native apps (more capability), plus WebAssembly.

Reach vs required capability

  • PWA → web distribution; can add installation, offline caching, push and background work where the browser supports them
  • Native or cross-platform native → platform integration and app-store distribution, with extra platform-specific work

PWA vs cross-platform native

  • Choose a PWA for speed to market, low cost, broad reach, SEO, instant server-side updates
    • simple apps, e-commerce, news
    • e.g. Starbucks, Pinterest
  • Choose cross-platform native (React Native, Flutter) for feature-rich apps needing near-native performance, deep hardware access (camera, sensors) and app store presence
    • e.g. Instagram, UberEats

Check target devices and browsers

  • Vary by device/browser: installation, notifications, background work, hardware APIs
  • Offline operation requires deliberate caching, local data and synchronisation
  • A PWA label does not make every feature work offline

WebAssembly (Wasm)

  • Portable instruction format executed by a sandboxed runtime in browsers or other hosts
  • Supports compute-heavy modules and edge runtimes
  • The host determines which capabilities it can access
PWA
Progressive Web App: a website that behaves like an installable app (offline, push, home-screen icon).
Service worker
Browser background script that caches content so a PWA works offline.
WebAssembly (Wasm)
Portable binary instruction format executed by compatible sandboxed runtimes in browsers, servers or edge environments.
Cross-platform native
Shared application code targeting multiple native platforms, with framework-specific runtime and platform integrations.

Check yourself

A retailer wants a mobile shopping experience launched within 2 months, on a small budget, and found through search engines. PWA or native?

A PWA, not native.

  • One web codebase + instant server-side updates
  • Broad reach + search discoverability
  • → fits the deadline and budget
  • Check: the features it needs (push notifications, offline cart viewing) work on the target browsers

Native only justified if a required capability couldn't be delivered on the web.

Field inspectors must work for hours without signal, capture photos and read a Bluetooth sensor, and the app must be in the app stores. Native (or cross-platform native) or a PWA, and what does the choice mean for the backend?

Cross-platform native.

  • Why native
    • Deep hardware access (Bluetooth, camera)
    • Long offline operation with local storage
    • App-store presence
    • Browser support for these features varies
  • Backend: plan for synchronisation
    • APIs that accept batched, delayed uploads
    • Conflict handling and idempotent writes
    • API versioning, because installed app versions update slowly
A team says 'we built a PWA, so it works offline'. What would you check?

Check that offline behaviour was designed:

  • Which screens and data are cached
  • How local writes are stored
  • How they sync and resolve conflicts when the connection returns

A PWA can cache and work offline where the browser supports it, but the label doesn't make every feature offline-capable.

A web app needs to run a compute-heavy image filter in the browser, and the JavaScript version is too slow. What option does the lecture suggest, and what limits it?

WebAssembly.

  • Portable instruction format run by a sandboxed runtime
  • Suits compute-heavy modules in browsers or at the edge
  • Limit: its host decides what capabilities it can access

→ speeds up computation, but doesn't give the hardware access a native app has.

Choosing an architecture and architectural thinking

How an architect decides: factors to weigh, the shift from hand-off to collaboration, the four dimensions of architecture, characteristics and Attribute Driven Design.

Architecture drivers

Pick an architecture from drivers, not preference:

  • The domain
  • Architecture characteristics that affect structure
  • Data architecture
  • Organisational factors and team/ops knowledge
  • Domain-architecture isomorphism → the system's shape matches the problem's shape
  • Communication → whether services communicate synchronously or asynchronously

Four dimensions of architecture

  • Characteristics → the qualities to achieve, e.g. scalability, availability, testability
  • Decisions → long-term choices such as database type, number of services, how they communicate; they guide dev teams
  • Style → overall shape, like a building plan
  • Logical components → functional blocks such as inventory or payment

Hand-off vs collaboration

  • Traditional → architect fixed characteristics, style and components and threw them over a wall to developers
  • Modern → continuous collaboration; architect leads and mentors; feedback flows from code back into the architecture

Attribute Driven Design (ADD)

The method that ties it together.

  1. Take drivers:
    • purpose
    • primary functionality
    • quality attributes
    • constraints
    • concerns
  2. Apply design concepts:
    • reference architectures
    • tactics
    • patterns
    • external components
  3. Produce structures:
    • module views
    • component-and-connector views
    • allocation views (deployment, work assignment)
Architecture characteristics
The quality attributes (the '-ilities') the system must achieve.
Architectural style
The overall shape of the system, e.g. layered, microservices, event-driven.
Attribute Driven Design (ADD)
Method that turns drivers, especially quality attributes, into structures using tactics and patterns.
Domain/architecture isomorphism
How well the architecture's structure matches the shape of the problem domain.

Check yourself

In a design review, someone lists 'use a replicated NoSQL store' under the system's characteristics. What is wrong with that, and how would you rewrite it?

It's a decision, not a characteristic.

  • Characteristics = qualities to achieve, e.g. availability above 99.9%, tolerance of a zone failure
  • Decisions = long-term choices made to achieve them, e.g. the replicated store
  • Rewrite: write the characteristic first, then record the decision with the characteristic it serves

→ the decision can be revisited if the requirement changes.

An architect delivered a full design document 6 months ago, and the developers have since quietly worked around half of it. What went wrong, and what model would fix it?

Hand-off architecture → move to continuous collaboration.

  • What went wrong: the design was thrown over the wall → went stale as implementation realities appeared
  • Fix: the architect leads and mentors within the team
  • Feedback from code changes the architecture

Cost: the architect's ongoing time; but the design stays true to the code.

A team must design a new system using Attribute Driven Design but starts by choosing a microservices pattern. What step have they skipped, and what should ADD produce?
  • Skipped: the drivers → purpose, primary functionality, quality attributes, constraints, concerns
  • Design concepts (patterns, tactics, reference architectures) are chosen to satisfy those drivers
  • ADD outputs: structures
    • Module views
    • Component-and-connector views
    • Allocation views (deployment, work assignment)

Monolithic vs distributed; microservices

The core split between monolithic and distributed styles, a taxonomy of styles, and the pros and cons of monolith vs microservices using an e-commerce example.

Deployment boundary: the core distinction

  • Monolith → deploys as one application; may have well-separated modules
  • Microservices → deploy independently; own data through service boundaries
  • Distributed systems → broader than microservices; need not follow one database-per-service model

Monolith vs microservices

  • Monolith pros: simplicity and speed
    • no network hops
    • one thing to deploy
  • Monolith cons:
    • scales only by cloning everything
    • any fault can crash the whole process
    • changes ripple
    • technology is locked in
  • Microservices pros:
    • per-service scaling
    • fault isolation
    • independent updates
    • technology diversity
  • Microservices cons:
    • operational overhead
    • distributed-system problems (latency, data consistency)

Style taxonomy

  • Monolithic:
    • layered
    • batch pipeline
    • modular
    • microkernel
  • Anti-pattern → big ball of mud
  • Distributed:
    • event-driven
    • microservices
    • stream pipelines
    • AI services
    • serverless
    • space-based designs

Distribution can improve independent capacity and isolation but adds latency, partial failures and coordination.

Worked example: online shop

  • As a monolith bundles:
    • authorization
    • presentation
    • business logic
    • data access
    • integration
    • notification
  • As microservices:
    • Authorization
    • Order
    • Catalog
    • Cart (calls Catalog)
    • Payment
    • Shipping services

Rule of thumb: small teams and simple apps → (modular) monolith; large, complex, fast-scaling apps → microservices.

Big ball of mud
A monolith with no discernible structure (an anti-pattern).
Microkernel
Core system plus plug-in modules; listed as the IoT-style monolithic pattern.
Space-based architecture
Distributed style using replicated in-memory data grids to avoid database bottlenecks.
Modular monolith
A monolith organised into well-separated modules inside one deployable.

Check yourself

A startup with 4 developers is building an MVP whose features will change weekly. Monolith or microservices?

A modular monolith.

  • One thing to build, deploy and debug
  • No network hops
  • Team can't absorb microservices' operational overhead
  • Keep modules well separated → a part that later needs independent scaling can be extracted

Revisit when the team or load grows.

After moving to microservices, a crash in the recommendation service still makes the whole product page time out. Why didn't fault isolation help, and what would?
  • Why isolation didn't help: separate processes contain the crash, but the product page calls the recommendation service synchronously and waits → the failure spreads through the call
  • Fix: timeouts, a circuit breaker and graceful degradation, e.g. showing the page without recommendations

Isolation is a property you have to design for; it doesn't come from deployment alone.

A team splitting a monolith asks what it gives up by moving to microservices. Give the two biggest costs for an e-commerce shop where Cart calls Catalog.
  • Distributed-system problems
    • Cart's call to Catalog now adds network latency
    • It can fail partially
  • Data consistency becomes harder across separate stores
    • e.g. keeping prices in carts aligned with the catalogue
  • Also operational overhead grows: more deployments, monitoring and tracing

These costs are justified when independent scaling, releases and fault isolation are needed.

Hexagonal and serverless architectures

Two styles that move boundaries: hexagonal (ports and adapters around a pure domain) and serverless (event-triggered functions on provider-managed infrastructure).

Hexagonal (ports and adapters)

Protects the business domain.

  • Layers separated: Application, Domain, Infrastructure
  • Dependencies point inward to the Domain
  • Outside world (users, other systems, databases, tests, CI/CD) connects through adapters on ports
  • Payoff → driven equally by users, programs, tests or batch scripts; tested in isolation from real devices and databases

Serverless

Removes infrastructure management.

  • Event-triggered cloud functions (e.g. AWS Lambda) run on demand
  • Provider scales resources in real time, within configured and platform capacity limits
  • Pros:
    • pay per compute time
    • automatic scaling
    • low ops
  • Cons:
    • vendor lock-in
    • cold starts
    • less control
    • building serverless structures can be labour-intensive

Hexagonal vs serverless

  • Hexagonal → shielding the domain from infrastructure through interfaces
  • Serverless → outsourcing infrastructure
  • Combine well → e.g. a function whose core logic is a hexagon with adapters for triggers and stores
  • Serverless suits sporadic, event-driven load, not steady latency-critical work
Ports and adapters
Ports are interfaces the domain defines; adapters plug real technologies (UI, DB, queues, tests) into them.
Cold start
Extra latency when a serverless function is invoked with no warm instance ready.

Check yourself

A team's order logic can only be tested against a real database and a running message broker, so tests take 20 minutes. How would hexagonal architecture change this?
  • Domain core: the order logic depends only on ports (interfaces)
  • Adapters for the database and broker on the outside
  • Tests drive the domain through a test adapter; database and broker replaced with fakes
  • → business logic tested in seconds

Keep a smaller set of integration tests for the real adapters.

A payments API has steady traffic around the clock and a strict 50 ms latency target. A teammate proposes serverless functions. Do you agree?

No: long-running containers or VMs suit steady, latency-critical load.

  • Cold starts → threaten the latency target
  • Constant usage → the pay-per-use saving disappears
  • You also accept less control and lock-in

Serverless would fit sporadic, event-driven parts, such as sending receipts.

A team builds a function-based service and later wants to move part of it off that provider. How could combining hexagonal design with serverless have helped?
  • Function's business logic sits in a hexagonal core
  • Trigger and data stores = adapters
  • → to move providers or run in a container, only the adapters need rewriting
  • Serverless outsources infrastructure; hexagonal shields the domain from it

Together they reduce the lock-in cost of serverless.

Lambda, Kappa, IoT, event-driven, multi-cluster, AI

Data-centric and cross-cutting archetypes: the two big-data processing styles, IoT layering, event-driven design, multi-cluster deployments, AI archetypes, and how all archetypes relate.

Lambda vs Kappa (big-data trade-off)

  • Lambda → three layers:
    • batch layer: historical data, recomputing results such as ML models
    • speed layer: low-latency near-real-time
    • serving layer
  • Lambda pro → accurate, batch layer as source of truth; con → two pipelines to maintain
  • Kappa → one stream engine for real-time and reprocessing, plus a serving layer
  • Kappa pro → simpler, low latency; con → stateful processing and complex reprocessing are harder

Event-driven: a principle, not just a style

  • Built around events → significant state changes
  • Loose coupling
  • Independent horizontal scaling of consumers
  • Real-time responsiveness
  • Can be applied on top of any other architecture

Deployment and domain archetypes

  • IoT → smart things → networks/gateways → middleware (storage, analytics) → applications
  • Multi-cluster/hybrid cloud → spreads workloads across Kubernetes clusters for resilience, geo-distribution or compliance
  • AI → different architectures for:
    • predictive AI: classification, clustering, regression, detection
    • generative AI: LLMs, RAG

How the styles relate

  • Monoliths → small simple apps
  • Microservices → large complex apps
  • Serverless → event-driven or sporadic loads
  • Lambda/Kappa → data-centric work
  • They combine → microservices can be built from serverless functions; data pipelines often run on serverless functions
Lambda architecture
Batch + speed + serving layers combining accurate history and fast real-time results.
Kappa architecture
Single stream-processing pipeline plus serving layer; reprocess by replaying the stream.
Event-driven architecture
Components communicate by producing and reacting to events rather than direct calls.
Predictive vs generative AI
Predictive analyses and forecasts from existing data; generative produces new content.
Multi-cluster
Running workloads across several Kubernetes clusters, across clouds and on-premises.

Check yourself

A ride-hailing company needs surge prices updated within seconds and also retrains its pricing model on 3 years of trip history every night. Lambda or Kappa?

Lambda.

  • Speed layer: streams trip events → near-real-time surge prices
  • Batch layer: recomputes the model over full history
  • Serving layer: exposes both

Cost: maintaining two pipelines that must agree. Kappa would be simpler if retraining could be done by replaying the stream, but reprocessing years of history through one stream engine is harder.

A monolith needs to notify inventory, email and analytics when an order is placed, and each new consumer currently means editing the order code. Must the team move to microservices to fix this?

No: event-driven is a principle that can be applied on top of any style.

  • Monolith publishes an 'order placed' event; consumers subscribe
  • → loose coupling
  • → consumers scale independently
  • → new consumers added without editing order code

Cost: eventual consistency + the need to monitor event flows.

A company runs one Kubernetes cluster in one region and must now serve EU customers whose data must stay in the EU. Which archetype helps, and what does it cost?

Multi-cluster or hybrid deployment.

  • EU cluster keeps EU workloads and data in the EU
  • Puts compute closer to those users
  • Limits the impact of one cluster failing

Cost: operating several clusters consistently, routing users to the right cluster, and the reporting and data work across them.

Modern composables, scale cube and evolution

Why classic styles are not enough, the AKF scale cube, and the historical path from monoliths to packaged business capabilities.

Eight modern archetypes

Classic styles only answer 'how do I decompose logic?' Modern archetypes answer other questions:

  • Cell-based → blast radius
  • Edge-native → where compute runs
  • Micro-frontends → UI decomposition
  • Multi-runtime/sidecar → where distributed capabilities live
  • Data mesh/lakehouse → data ownership
  • Local-first → offline
  • MACH/PBC → business composition
  • Platform engineering → repeatable operation

They compose with, not replace, the classic styles.

AKF scale cube

Three independent ways to scale:

  • x = replication → clones behind a load balancer, replicated databases
  • y = functional decomposition → split into services or functions
  • z = data partitioning → shard by key, data per service

Diagnose the bottleneck, then pick the axis.

Evolution toward composable capabilities

Architecture evolved toward composable business capabilities:

  1. Monolith
  2. 2-tier
  3. 3-tier (UX/logic/data)
  4. SOA
  5. Web-scale services
  6. Software-defined microservices with outer and inner APIs, plus IoT
  7. Packaged services with edge computing

3-tier splits by technical layer; microservices split by business capability.

AKF scale cube
Three ways to scale: clone (x), split by function (y), split by data (z).
Sharding
Partitioning data across databases by a key (z-axis scaling).
SOA
Service-Oriented Architecture: coarse-grained shared services exposed via service APIs.

Check yourself

After adding app servers, the database becomes the bottleneck. Which scale-cube axis would you use next?

First identify the data-tier limit:

  • Reads → replicas or caching (x axis on the data tier)
  • Writes on independent records → shard by a suitable key (z axis)
  • Heavy workload → split it into its own service and store (y axis) → isolates it

None of these fixes a poorly designed slow query, so check that first.

A team describes its 3-tier app (web, logic, database) as 'already microservices because it has separate tiers'. What is the structural difference?
  • 3-tier: split by technical layer → one business change still touches every tier; tiers deploy together
  • Microservices: split vertically by business capability; each service owns its logic and data and deploys independently

The 3-tier app can scale tiers separately but not capabilities.

A SaaS's checkout path is overloaded during sales, but the search and account features are not. Which scale-cube axis fits, and why not just add more clones?

y axis (functional decomposition): split checkout into its own service.

  • → checkout scales on its own
  • Cloning the whole app (x axis) also scales search and accounts that don't need it → wastes capacity
  • Cloning doesn't isolate checkout failures

Cost: a new service boundary and its data ownership.

Appendix: cells, edge, micro-frontends, sidecars, data mesh

What, why, when and trade-offs for the first five modern composable archetypes.

Cell-based: bound the blast radius

  • Router assigns users or tenants to independent full-stack cells
  • No cross-cell runtime calls; cell-by-cell releases
  • Failure affects the assigned group: roughly 1/N only for equally sized cells
  • Costs:
    • duplicated capacity
    • a critical router
    • difficult cross-cell reporting
    • automation needed to operate many environments

Edge-native

Pushes compute and some state near users.

  • Runtime → V8 isolates or Wasm, millisecond cold starts
  • State → eventually consistent edge storage; origin as system of record
  • Use for tight latency or residency (auth, personalisation, A/B routing)
  • Avoid for heavy compute or strong consistency
  • Expect limited runtimes, hard debugging, lock-in

Micro-frontends and BFF

Extend team independence to the UI.

  • Teams own vertical slices (UI, API, data), composed at build, edge or run time
  • Backend-for-Frontend → each experience (web, mobile, kiosk) gets its own
  • Use when many teams share one UI, or replacing a legacy front end incrementally
  • Not for a single front-end team → duplicated payloads, design consistency and shared state costs

Sidecar / multi-runtime

Moves cross-cutting capability out of libraries.

  • Sidecar (service mesh, Dapr) provides discovery, mTLS, retries, circuit breaking, telemetry uniformly across languages
  • Effect → resilience and security become platform decisions
  • Costs → an extra hop, memory, a control plane
  • Rarely justified below about a dozen services in one language

Data mesh and lakehouse

Data mesh is the data-plane counterpart of microservices.

  • Data mesh principles:
    • domain ownership
    • data as a product
    • self-serve platform
    • federated governance
  • Central team → becomes a platform provider
  • Needs governance maturity first
  • Lakehouse → open table formats giving ACID, schema evolution, time travel on object storage; bronze/silver/gold medallion refinement
  • Lakehouse can be data mesh's technical base; not the same as Lambda's layers
Blast radius
How much of the system or user base a single failure affects.
Backend-for-Frontend (BFF)
A dedicated backend per client experience that aggregates and tailors downstream services.
Sidecar
Helper container beside a service handling cross-cutting concerns like mTLS and retries.
Data mesh
Decentralised data ownership where domains publish governed data products.
Medallion (bronze/silver/gold)
Progressive refinement layers from raw to cleaned to business-ready data in a lakehouse.

Check yourself

A bad deploy to a multi-tenant SaaS took down all 4,000 customers at once. Which archetype limits this, and what does it cost?

Cell-based architecture.

  • Router assigns tenants to independent full-stack cells
  • No cross-cell calls
  • Releases roll out cell by cell → a bad deploy hits one cell first
  • 10 equal cells → roughly 400 customers affected

Costs: duplicated capacity, a router that becomes critical, harder cross-cell reporting, and the automation to run many environments.

A team of five Java services proposes adding a sidecar service mesh for retries and telemetry. Would you approve it?

Probably not yet.

  • A mesh adds an extra network hop, memory per pod and a control plane
  • Lecture: rarely justified below about a dozen services in one language
  • There a shared library can give the same retries and telemetry

A requirement for uniform mTLS, or a move to several languages, would change the answer.

One front-end team builds a single web app and is considering micro-frontends to 'be modern'. What would you advise?

Don't.

  • Micro-frontends extend team independence to the UI
  • Pay off when many teams share one UI or a legacy front end is being replaced piece by piece
  • With one team → duplicated payloads, design-consistency work and shared-state problems, with no independence gained

A separate backend for each experience (BFF) may still help if web and mobile need different APIs.

A company bought a lakehouse and declared it has 'a data mesh'. What is missing?

Missing: domain ownership and governance maturity.

  • Lakehouse = a storage and processing base: open table formats with ACID, schema evolution and time travel on object storage
  • Data mesh = an operating model
    • Domain teams own their data as products with contracts and quality
    • On a self-serve platform
    • Under federated governance

Without them, it is still a central data platform.

A product team wants to run personalisation and A/B routing at the edge, and also move order checkout there for speed. Which part fits edge-native, and which doesn't?
  • Fits edge: personalisation and A/B routing → light, latency-sensitive, can tolerate eventually consistent edge storage
  • Keep at origin: checkout → needs strong consistency with the origin system of record

Edge also brings limited runtimes, harder debugging and lock-in → keep edge logic small.

Appendix: local-first, MACH, platform engineering, selection

The last three modern archetypes and a guide matching each archetype to its driving concern and anti-use-case.

Local-first

  • Completes suitable reads and writes on a local replica, then synchronises
  • CRDTs or operational transformation → merge supported concurrent edits
  • Suits collaboration and unreliable networks
  • Limit → merging cannot by itself protect global invariants (e.g. one seat sold once)
  • Can complement a PWA, rather than replace all PWA designs

MACH and PBC

Compose the business.

  • MACH =
    • Microservices
    • API-first
    • Cloud-native SaaS
    • Headless (one capability serves many channels)
  • Packaged Business Capability (PBC) → bundles the data and services of one capability (cart, pricing, tax), assembled from vendors and in-house parts
  • Integration becomes the architecture → needs a capability map with owners, or it becomes distributed procurement

Platform engineering

Decides which archetypes are affordable.

  • Internal developer platform (IDP) run as a product
  • Features → golden paths, self-service, templates, GitOps on Kubernetes
  • Measured by adoption and DORA metrics
  • Use when cognitive load limits delivery
  • Failure mode → the platform team becoming a gatekeeper

Selection guide (driver → archetype, not when)

  • Blast radius → cells (not small user bases)
  • Latency/residency → edge (not heavy compute or strong consistency)
  • Many teams on one UI → micro-frontends/BFF (not one team)
  • Uniform capability across polyglot services → sidecar (not few services)
  • Data ownership at scale → data mesh (not before governance)
  • Offline/collaboration → local-first (not global invariants)
  • Many vendors → MACH/PBC (not one stable channel)
  • Operability → platform/IDP (not small orgs)

Mature estates combine them.

CRDT
Conflict-free Replicated Data Type: data structure that merges concurrent edits automatically.
MACH
Microservices, API-first, Cloud-native SaaS, Headless.
Packaged Business Capability (PBC)
Self-contained, assemblable unit of one business capability's data and services.
Internal Developer Platform (IDP)
Self-service platform with golden paths so teams build and run services consistently.

Check yourself

A concert-ticketing app wants to be local-first so fans can pick seats offline. Where does local-first work here and where doesn't it?
  • Works for drafts: building a seat selection or a wishlist on the local replica
  • Can't guarantee a seat is sold only once: an offline replica doesn't know about other replicas' bookings
  • CRDT-style merging doesn't protect global invariants

Confirm the purchase through an authoritative coordination step before promising the seat.

A retailer composes its commerce stack from a vendor cart, a vendor tax engine, in-house pricing and a headless CMS (MACH). Two years in, nobody knows who owns checkout failures. What went wrong?

Integration became the architecture without a capability map that names owners → MACH turned into distributed procurement.

  • Each packaged business capability needs a clear owner and integration contracts
  • Integration, identity and cost across many vendors are routinely underestimated
A 12-developer company plans to build an internal developer platform with golden paths and self-service templates. Is it worth it?

Probably not yet.

  • Platform engineering pays off when cognitive load limits delivery across many teams
  • Must be run as a product, measured by adoption and DORA metrics
  • For 12 developers → shared templates and a simple pipeline may be enough

Risk at any size: the platform team becomes a gatekeeper instead of an enabler.

Exam-style questions

Answer aloud or on paper before opening.

A bank wants to modernise a 15-year-old monolithic loan system used by 300 branches while continuing to issue loans every day. Propose a target style and a migration approach, and name the two biggest trade-offs.
  1. Target style: microservices split by business capability
    • Application, credit check, disbursement, notification
    • Each owning its data
    • Hexagonal design inside services → testability
    • Events between them → loose coupling
  2. Migration: incremental, strangler approach
    • Route one capability at a time to new services
    • Not a big-bang rewrite, which would stop loan issuance
  3. Two biggest trade-offs
    • Distributed-system problems: latency, partial failures, consistency across stores
    • Operational overhead → invest in observability and platform automation before the number of services grows
Design a data architecture for a ride-hailing company that needs surge pricing within 5 seconds of demand changes and nightly retraining on 3 years of trips. Justify Lambda or Kappa, and say what would change your choice.

Lambda.

  • Speed layer: processes the trip-event stream → near-real-time surge prices
  • Batch layer: holds full history, retrains models nightly; remains the accurate source of truth
  • Serving layer: merges the results
  • Cost: two pipelines with logic that must stay consistent
  • What would change it → Kappa: if reprocessing can be done by replaying the stream within the nightly window; trades the second pipeline for harder stateful stream processing

Event-driven ingestion keeps producers decoupled either way.

A government services app must reach all citizens, including those on old phones. It needs form-filling that survives a dropped connection, and a later phase adds reading ID cards over NFC at kiosks. Native or PWA? Give the design implications for the backend services.

Start with a PWA; add a native kiosk app for the NFC phase.

  • PWA for citizens
    • Broad reach, no install barrier, one codebase, instant updates → suit a citizen service
    • Offline form drafts with local storage and sync
  • Native or cross-platform native kiosk app for NFC
    • Hardware access through browsers varies
    • The kiosks are controlled devices
  • Backend implications
    • APIs must accept delayed, batched submissions idempotently and handle conflicts
    • A separate backend for each experience (BFF) may serve web and kiosk clients
    • API versioning for installed kiosk apps
An e-commerce site handles normal traffic but fails on Black Friday at 12 times the load: the database's write capacity is exhausted and checkout slows everything else. Apply the AKF scale cube to the problem and name a side effect of each change.
  • x axis: load-balanced clones of the stateless web tier, plus read replicas
    • Side effect: replica lag → stale reads
  • y axis: split checkout into its own service and store → it scales and fails independently
    • Side effect: cross-service consistency for orders and inventory
  • z axis: shard orders by customer or region to spread writes → the fix for exhausted write capacity
    • Side effect: cross-shard queries and reporting become harder

Add a queue in front of order processing to level the peak.

A global SaaS needs sub-100 ms response for login and personalisation worldwide, must keep EU data in the EU, and had an outage last year where one bad deploy hit every tenant. Which modern archetypes would you combine, and what are their costs?
  • Cells per region and tenant group
    • Bound the blast radius
    • Keep EU tenants' data in EU cells
    • Releases rolled out cell by cell
  • Edge-native functions
    • Authentication checks and personalisation near users
    • The origin remains the system of record
  • Platform with GitOps → operates N cells consistently
  • Costs
    • Duplicated infrastructure
    • A critical cell router
    • Hard cross-cell reporting
    • Eventual consistency and limited runtimes at the edge
    • The investment in platform automation
A new product will have 3 developers at launch, sporadic traffic from 0 to 2,000 requests a minute, and a plan to grow to 6 teams in 2 years. Compare monolith, microservices and serverless, and recommend a path.

Recommend a modular monolith, or a few functions with a hexagonal core for the spiky parts.

  • Modular monolith: minimises deployment and network complexity for 3 developers, but scales as one unit
  • Microservices: independent scaling and releases, but bring partial failures, data coordination and operational overhead the team can't afford yet
  • Serverless: suits the sporadic load and costs little when idle, but brings cold starts, runtime limits and lock-in

Keep clear module boundaries so services can be extracted as the 6 teams arrive.
