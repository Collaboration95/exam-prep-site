Vendor Managed Services

12 slides · about 10 min · open the deck · JSON

Map an architectural need to a managed-service category, then to a provider example. Compare compute, storage, networking, data, messaging and security across AWS, Azure and Google Cloud. Similar categories help comparison, but service semantics and customer responsibilities still need checking.

Big ideas

  • Gartner Magic Quadrants evaluate vendors on weighted criteria; AWS, Microsoft Azure and Google Cloud are the main providers compared.
  • Compute comes in three managed flavours: VMs (EC2, Azure VM, Compute Engine), Kubernetes (EKS, AKS, GKE) and FaaS (Lambda, Azure Functions, Cloud Functions).
  • Storage comes as object (S3, Blob, Cloud Storage), block (EBS, Persistent Disk) and file (EFS, Azure Files, Filestore); pick by access pattern.
  • Networking building blocks: virtual network, DNS, load balancing and firewall, each with a managed equivalent on every major cloud.
  • Data services cover RDBMS, NoSQL, data warehouse, big data, AutoML and data catalogue/integration.
  • Messaging splits into streaming, event-driven, message queue and notification, each solving a different decoupling problem.
  • Monitoring, IaC, identity management and key encryption are managed too, so automation and security need not be built from scratch.

Vendor landscape and compute

How Gartner evaluates cloud platform and cloud database vendors, and the three kinds of managed compute.

Analyst reports: vendor viability, not fit

Gartner's Magic Quadrants weight criteria such as:

  • Cloud platforms → market responsiveness, overall viability, product strength
  • Cloud databases → offering strategy and innovation

Use them as one input alongside region, price and skills.

Managed compute: three levels of control

  1. VMs (EC2) → most control and most to operate
  2. Managed Kubernetes (EKS, AKS, GKE) → long-running containerised services, cross-cloud portability
  3. FaaS (Lambda) → short event-driven tasks, no function servers to operate, usage-based billing

Overlapping building blocks

Providers offer overlapping building blocks, not identical semantics.

  2. Then check the product's:
    • access model
    • supported regions
    • operating boundary
    • constraints

Check yourself

A CIO wants to pick the provider ranked highest in an analyst's Magic Quadrant and stop there. What does the ranking tell you, and what does it not?
It gives an independent view of vendor viability and capability using weighted criteria such as overall viability, market responsiveness and product strength. It doesn't tell you whether the vendor fits this workload. Also check the regions you need, pricing, your team's skills and how specific services behave, and treat the ranking as one input among several.
On the same provider, a team must run (a) a long-running order API that may later move to another cloud and (b) an image-resize task triggered a few hundred times a day. Managed Kubernetes, FaaS or VMs for each?
(a) Managed Kubernetes: long-running containerised services keep their packaging and orchestration portable across clouds. (b) FaaS: short, event-driven, no servers to operate, and billed only per use at this volume. VMs would give the most control but the most to operate, which is justified only if a workload needs OS-level control.
Two providers both list a 'managed message queue'. A teammate says they are interchangeable, so switching later will be easy. Do you agree?
No. Providers offer overlapping building blocks, not identical semantics. Ordering, delivery guarantees, message size limits, access model, regions and operating boundaries can differ. State the capability you need, check each product against it, and keep provider-specific calls behind your own interface if switching is a real requirement.

Storage and networking

The three storage types and when to use each, then the managed networking services.

Storage by access pattern

  • Object (S3) → unstructured data at scale: media, backups, archives
  • Block (EBS, Persistent Disk) → low-latency VM and database disks
  • File (EFS, Filestore) → shared file systems mounted by many VMs, often for lift-and-shift

Networking: distinct jobs

  • VPC/VNet → logical isolation
  • DNS → naming
  • Load balancing → distributing traffic; a load balancer helps availability only when healthy backend capacity remains
  • Network firewall rules → connections
  • WAF → HTTP-level filtering

Managed is not design-free

Managed reduces infrastructure work, not design responsibility.

  • Select capacity and availability options
  • Configure permissions and retention
  • Test recovery

A service being managed does not by itself satisfy an application SLA.

Object storage
Stores data as objects with metadata in a flat namespace; ideal for unstructured data at scale (S3, Blob, Cloud Storage).
Block storage
Raw disk volumes attached to VMs; used for OS disks and databases (EBS, Persistent Disk).
File storage
Shared network file system mounted by many VMs (EFS, Azure Files, Filestore).
WAF
Web Application Firewall that filters malicious HTTP traffic in front of web apps.

Check yourself

A media company must store millions of uploaded videos and serve them to users worldwide. Object, block or file storage, and why not the others?
Object storage: it scales cheaply for large unstructured files, is reached over HTTP APIs, and suits media, backups and archives, ideally with a CDN for global delivery. Block storage is a low-latency disk for one VM and doesn't scale as shared media storage. File storage is a shared filesystem for VMs, which the web and mobile clients don't need.
A lift-and-shift app on 8 VMs expects a shared directory, and its database needs a fast local disk. Which storage type for each?
File storage for the shared directory, since many VMs can mount it without the app changing, which is typical for lift-and-shift. Block storage for the database disk, for low-latency attached volumes. Moving the shared directory to object storage later would scale better but needs code changes.
A web app behind a managed load balancer went down when its only zone failed, and an attack sent malformed HTTP requests that the network firewall didn't block. What was missing in each case?
A load balancer only helps availability if healthy backend capacity remains, so the backends needed to be spread across zones. Network firewall rules filter connections, not HTTP content, so a WAF was needed to filter malicious HTTP requests. Being managed doesn't mean configured: capacity, placement and filtering are still design choices.

Data, messaging, performance and security

Managed data and analytics, streaming and messaging, and operations and security services.

Data services by shape and workload

  • Relational (RDS, Cloud SQL) → structured transactional data
  • NoSQL (DynamoDB, Cosmos DB) → flexible or high-scale access
  • Warehouse (BigQuery, Synapse, Redshift) → SQL analytics over huge data
  • Big-data engines (EMR, Dataproc) → Hadoop/Spark processing
  • Plus AutoML and data catalogue/integration services

Messaging patterns

Messaging separates distribution from work ownership.

  • Streams → retain ordered event data for processing and replay
  • Event routing → connects producers to interested consumers
  • Queue → distributes work among competing workers
  • Pub/sub → fans out to independent subscribers

Delivery may be repeated: design idempotent processing instead of assuming once-only business effects.

Managed operations and security

  • Monitoring → CloudWatch
  • Infrastructure as code → CloudFormation, reproducible environments
  • Identity management → IAM, access control
  • Key management → KMS, encryption

Automation, observability and security need not be built from scratch.

Message queue
Buffer distributing work among competing consumers; retries may deliver a task again.
Notification / pub-sub
Publish a message once and fan it out to many subscribers (e.g. SNS, Pub/Sub).
Infrastructure as Code
Defining cloud resources in versioned templates (CloudFormation, ARM, Deployment Manager) instead of manual setup.
KMS
Key Management Service: managed creation, storage and rotation of encryption keys.

Check yourself

An order event must be processed once by one of 10 worker instances, and also trigger an email, a loyalty update and an analytics record. Queue, pub/sub or both?
Both. A queue distributes the order work among competing workers so each order is handled by one. Pub/sub fans the event out to independent subscribers (email, loyalty, analytics), usually with one queue per consumer group. Delivery can repeat in either case, so consumers must be idempotent.
A queue redelivers a payment task after a worker times out, and the customer is charged twice. What is the fix, and why not simply ask for 'exactly-once' delivery?
Make the business operation idempotent, for example by recording a stable payment identifier with its result so a retry returns the recorded outcome instead of charging again. Redelivery after a timeout is normal in messaging, and you can't rely on once-only delivery to guarantee once-only business effects.
A team must replay the last 7 days of click events to rebuild a broken analytics view. Would a message queue or a stream suit this, and why?
A stream: it keeps ordered event data for a retention period, so consumers can reprocess and replay from an earlier point. A queue normally removes a message once it has been processed, so there would be nothing to replay. The cost of a stream is retention storage and managing consumer positions.
A team building on managed services plans to add monitoring, identity and encryption 'after launch'. Why is that risky, and what should be in place at launch?
Without identity management, access is likely too broad. Without managed key encryption, data protection depends on ad-hoc handling. Without monitoring, failures go unseen. Retrofitting each later is harder than defining them in IaC from day one. Use the provider's managed identity, key management and monitoring, provisioned through IaC, so they deploy consistently.

Exam-style questions

Answer aloud or on paper before opening.

Map a cloud-native e-commerce architecture (product browsing, carts, orders, product images, order processing, notifications) onto categories of managed services on one provider, justifying each, and name the decision that most increases lock-in.
Managed DNS and a load balancer with a WAF at the edge. Managed Kubernetes for the long-running services and FaaS for event handlers such as image resizing. A managed relational database for orders (ACID) and a NoSQL store for carts and sessions. Object storage with a CDN for images. A queue for order processing and pub/sub for notifications. Add monitoring, IaC, identity management and key management so operations and security are built in. The biggest lock-in usually comes from proprietary data and messaging services, because data and semantics don't move as easily as container images.
A company plans to run on three major providers 'for portability'. Using the idea of overlapping building blocks, assess what will be portable and what will not, and recommend whether to proceed.
Compare by capability categories such as managed Kubernetes, object storage and messaging, then check each service's semantics, regions and limits. Containers on Kubernetes keep packaging and orchestration portable. Data, identity, networking and proprietary managed-service APIs are not portable and need separate migration and integration work. Proceed only if a concrete benefit (regulation, resilience against a provider, a best-of-breed service) outweighs the cost of tripled skills and operations. Otherwise use one provider with an exit strategy.
A team must choose storage for VM boot disks, a database's data files, shared engineering files mounted by 20 VMs, and 5 years of backup archives. Recommend a type for each, and say what happens if the team puts everything on block storage to keep things simple.
Block storage for boot disks and database files, for low-latency attached volumes. File storage for the shared engineering files, since many VMs must mount them. Object storage for the backup archives, because it is cheap and durable at scale. With everything on block storage, the shared files can't easily be mounted by 20 VMs, and archives would cost much more than on object storage.
A CTO says: 'Use managed services everywhere, so availability and security are the provider's job.' Argue for and against, and state what remains the team's responsibility.
For: managed services offload patching, scaling, backups and much availability work, so teams can spend their effort on business code. Against: they increase lock-in through proprietary APIs, can cost more at scale, and tie you to the provider's SLA, which doesn't by itself meet an application SLA. The team still chooses capacity and availability options such as multi-zone placement, configures identity, permissions, encryption and retention, designs idempotent messaging, and tests recovery. Limit lock-in with open standards where it matters and keep an exit strategy.
