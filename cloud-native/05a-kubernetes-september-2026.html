Kubernetes: A Simple Introduction

38 slides · about 30 min · open the deck · JSON

Kubernetes schedules container workloads and reconciles them toward declared state. Learn the control-plane and worker roles, then connect Pods, Deployments, Services, Ingress, storage and configuration. Compare local and managed clusters, and distinguish the automation Kubernetes supplies from the availability and security choices you must design.

Big ideas

  • Kubernetes turns a group of machines into one container-oriented API: you declare the desired state and K8s schedules, heals and scales containers to match it.
  • Control plane = API server (front door), etcd (store of cluster state), scheduler (places pods), controller manager (drives actual state toward desired state); each node runs kubelet, kube-proxy and a container runtime.
  • A Pod is the smallest deployable unit: tightly coupled containers sharing IP, storage and lifecycle, always on a single node.
  • Deployments/ReplicaSets keep N replicas of a pod template running; Services give a stable virtual IP and DNS name with load balancing, selecting pods by label; Ingress routes external HTTP/HTTPS to many Services under one IP.
  • Kubernetes supplies orchestration primitives; choose and integrate databases, messaging, logging and monitoring around them.
  • Use Minikube for local learning and development; managed production options include GKE, EKS and AKS.
  • Container state is temporary: use PersistentVolumes/PVCs for data and ConfigMaps/Secrets for configuration so images stay immutable and reusable.

Why containers and Kubernetes

Why containers beat older deployment models, and what Kubernetes does and does not do.

  • Images standardise packaging; orchestration manages running instances. An image fixes the application and dependencies; a registry distributes it; a runtime starts isolated processes from it. Replacing versioned images supports repeatable releases and rollbacks, while host compatibility, configuration and data still affect behaviour.
  • Declare workloads; configure the automation they need. Kubernetes places Pods, maintains declared replicas, supports probes and rolling updates, and provides storage, configuration, discovery and access-control primitives. Autoscaling requires metrics and policy; uninterrupted updates require readiness, spare capacity and compatible releases.
  • Kubernetes vs PaaS: K8s is not a PaaS. It imposes no language or framework and supplies no databases, message queues or service marketplace, and you choose your own logging and monitoring. Platforms built on it (e.g. OpenShift) add those layers, so an architect must still select and integrate the surrounding services.
  • Why adopt it: developer velocity, declarative configuration, online self-healing, shared reusable tooling, scaling of software and teams, and abstraction from the underlying infrastructure.
Container image
Immutable binary package holding everything needed to run a program in a container.
Container registry
Repository that stores and distributes images, e.g. in the OCI standard format.
Orchestration
Automatically scheduling, healing and scaling containers across a cluster of machines.
Liveness / readiness check
Health probes: is the container alive (restart if not) and is it ready to receive traffic.

Check yourself

A release is rolled back by redeploying the previous image, but the app still fails. Why didn't image immutability make the rollback safe?
An immutable image restores the old application code exactly, but behaviour also depends on configuration and external data. If the new release ran a database migration the old code can't handle, a code-only rollback fails. Make schema changes backward-compatible, or plan a data recovery step alongside image rollbacks.
A team chose Kubernetes expecting it to give them a database, a message queue and logging out of the box, like their old PaaS. What do you tell them?
Kubernetes is not a PaaS. It schedules, heals, scales and networks containers, but it supplies no databases, queues, service marketplace or built-in logging stack. They must choose and integrate those, for example as managed services, or adopt a platform built on Kubernetes that adds them. The upside is freedom of language and framework.
A team turned on autoscaling in Kubernetes, but pods never scale during load spikes. What is likely missing?
Autoscaling needs metrics and a policy: a metrics source, resource requests or target metrics, and an autoscaler configured with sensible thresholds. Spare node capacity is also needed for new pods to be placed. Declaring replicas alone keeps a fixed count; Kubernetes only automates what has been configured.

Orchestration technologies

Kubernetes alongside the other orchestrators, Docker Swarm and Apache Mesos with Marathon.

  • The lecture compares Docker Swarm, Mesos/Marathon and Kubernetes. All illustrate cluster scheduling, but their scope differs: Swarm focuses on Docker services, Mesos allocates resources to frameworks, and Kubernetes integrates workload controllers and service objects. Treat this as a comparison of designs rather than a current product popularity ranking.
  • Swarm vs Mesos vs Kubernetes: Swarm is Docker's native, simple clustering driven by Compose files. Mesos is a general cluster resource manager (like an OS kernel, master/slave) where frameworks such as Marathon do the container scheduling. Kubernetes bundles scheduler, controllers, discovery and networking objects into one platform with managed offerings on every major cloud, which is why the course builds on it.
  • The name Kubernetes is Greek for pilot or helmsman, the one steering the ship of containers.
Apache Mesos
Cluster resource manager acting like a distributed OS kernel; frameworks like Marathon run containers on it.
Docker Swarm
Docker's built-in orchestrator that deploys Compose-described services across a cluster of Docker hosts.

Check yourself

A 3-person team runs 4 services on Docker Compose today and asks whether to move to Swarm or Kubernetes. What would you recommend, and what decides it?
Swarm is simpler and reuses their Compose files, which suits a small, stable Docker estate. Kubernetes has richer objects (Deployments, Services, Ingress, volumes, namespaces), managed offerings on every major cloud and a larger ecosystem, which matters if they expect to grow or need portability. The trade-off is learning and operating cost versus capability and future flexibility.
An organisation already runs big-data frameworks on a shared cluster and wants to add container scheduling. How do the Mesos and Kubernetes models differ for this?
Mesos is a general resource manager that offers cluster resources to frameworks, with Marathon doing container scheduling as one framework among others such as data-processing ones. Kubernetes builds its own scheduler and controllers into the control plane and focuses on container workloads. Mesos fits sharing one cluster across heterogeneous frameworks; Kubernetes gives a more integrated container platform.

Cluster architecture and components

The control-plane (master) components, node components and add-ons, and the core K8s objects.

  • A cluster splits into a control plane that decides and nodes that execute. Control plane: API server (the only front door, used by kubectl and all components), etcd (distributed key-value store holding all cluster state), scheduler (places pods on nodes) and controller manager (the brain that drives actual state toward desired state).
  • Each worker node runs three things: kubelet (agent that starts, stops and monitors the node's pods via the runtime), kube-proxy (network rules so Service traffic reaches pods) and a container runtime (a compatible container runtime, such as containerd or CRI-O). Add-ons include CoreDNS for service discovery, a dashboard, Metrics Server and cluster logging.
  • The declarative reconcile loop is the heart of K8s: you submit a spec via kubectl, the API server stores it in etcd, controllers compare desired vs actual state and act, the scheduler assigns new pods, and kubelets start them. This is what yields self-healing and scaling.
  • Core objects: Pod (containers sharing IP, storage, resources and lifecycle), ReplicaSet/Deployment (desired state: replicas, pod template, health checks), Service (stable virtual IP and DNS name for a group of pods), PersistentVolume/PVC (durable storage) and Label (key-value tags used to select objects). Minikube, kubeadm or a cloud can host the cluster.
API server
Front door of the control plane; every component and kubectl talks to the cluster through it.
etcd
Distributed key-value store that persistently holds all cluster configuration and state.
kubelet
Agent on each node that starts, stops and monitors the pods assigned to it.
kube-proxy
Per-node network proxy that maintains rules so traffic to a Service reaches its pods.
PV / PVC
PersistentVolume is a piece of storage; a PersistentVolumeClaim is a pod's request to use it.
Label
Key-value tag on objects, used by selectors to group pods for Services and Deployments.

Check yourself

You apply a Deployment with 3 replicas, and the pods stay 'Pending'. Trace where in the reconcile chain things stopped, and the likely cause.
The API server stored the spec in etcd, and the controller created pod objects, which is why they exist as Pending. The scheduler has not assigned them to nodes, most likely because no node has enough free resources for their requests or none matches their constraints. Check scheduling events, node capacity and the pod's resource requests.
A team runs a self-managed cluster with a single etcd member and no backups. What is the risk?
etcd holds all cluster state and configuration. Losing it means the control plane no longer knows desired or current state, and the cluster can't be managed or rebuilt as it was. Run etcd replicated across failure domains and back it up regularly. A managed control plane shifts this duty to the provider.
Pods on one node are running and healthy, but traffic sent to their Service never reaches them from other nodes. Which node component would you suspect first, and why not kubelet?
kube-proxy, which programs the network rules that route Service traffic to pod endpoints. kubelet manages pod and container lifecycles, and the pods are running, so it is doing its job. Also check that the Service's selector matches the pod labels, because a mismatch gives the same symptom.

Pods, Services and Ingress

The networking problems K8s solves and how Pods, Services, Namespaces and Ingress fit together, ending with the shape of a manifest.

  • Use distinct objects for distinct network concerns. Pods are replaceable workloads; Services discover and balance their endpoints; Ingress describes HTTP routing. Namespaces group resources for management and policy, but need RBAC and supported NetworkPolicies for access restrictions.
  • Pod design rules: a pod never spans nodes and gets its own routable IP; put only tightly coupled containers together (a main container plus helpers), one process per container, and split anything that need not share a machine so it can scale and fail independently.
  • Service vs Ingress: a typical Service offers a stable internal IP/DNS and selects ready Pod endpoints by label. An Ingress defines host/path routing to Services; an installed Ingress controller implements it. The controller may route directly to Pod endpoints, so this is a logical routing model rather than a claim about every packet hop.
  • Every K8s object is described declaratively in YAML: apiVersion, kind, metadata (name, namespace, labels), spec (desired state you declare) and status (actual state K8s reports). You hand K8s the descriptor and it pulls images and spreads containers across nodes, presenting the datacentre as one deployment platform.
Service
Stable virtual IP and DNS name that load-balances traffic to the pods matched by its label selector.
Ingress
HTTP/HTTPS host/path routing rules to Services, implemented by an installed Ingress controller.
Namespace
Logical grouping of cluster resources; access and network isolation require additional policies.
Label selector
Query on labels that decides which pods a Service or Deployment manages.
spec vs status
spec is the desired state you declare; status is the actual state K8s reports.

Check yourself

A team puts its web app, a log shipper, and the reporting service it calls into the same pod 'to keep things together'. Which belong together, and why?
The web app and the log shipper: the shipper is a tightly coupled helper that shares the app's lifecycle and storage. The reporting service should be its own pod, because containers in a pod share a node, IP and lifecycle, so they scale and fail together, and the reporting service needs to scale and update independently.
A frontend calls a backend by a pod IP copied from the console, and it breaks every few days. Why, and what is the fix?
Pods are ephemeral: they get new IPs when replaced or rescheduled. Put a Service in front of the backend pods. It gives a stable IP and DNS name and load-balances across whichever ready pods match its label selector.
Three web services must share one public domain with paths /shop, /blog and /api. Would you expose each Service directly or use an Ingress?
An Ingress: one external entry point with path-based routing to the three Services. Exposing each directly needs three external endpoints and gives no shared host or path routing. An Ingress needs an installed controller to implement its rules, which is one more component to run.
Two teams share a cluster in separate Namespaces, and a security review assumes their traffic is isolated. Is it?
No. Namespaces organise and scope resources but don't restrict traffic by themselves. Add NetworkPolicies (with a network plugin that supports them) to limit pod-to-pod traffic, RBAC to limit API access, and ResourceQuotas to stop one team starving the other.

Running K8s: Minikube, YAML and cloud

Running Kubernetes locally with Minikube, a Deployment manifest, and the managed offerings on GCP, AWS and Azure, plus config via ConfigMap.

  • Choose the cluster by operating purpose. The lecture’s single-node Minikube setup is for local learning and testing, not a production HA design. Self-managed clusters offer more control but require operation of the control plane, nodes, upgrades and recovery.
  • Managed offerings reduce cluster operations: GKE on Google Cloud, EKS on AWS and AKS on Azure. ECS is a separate AWS orchestrator rather than Kubernetes. Provider responsibilities vary by mode; worker capacity, workload security and application availability still require customer design. Treat the lecture’s pricing and setup commands as examples, not stable service guarantees.
  • A Deployment manifest ties it together: replicas say how many pods, the selector says how to find them by label, and the template says what a pod looks like. The selector must match the template labels or the Deployment cannot track its pods. Expose it with a Service (e.g. NodePort for local testing).
  • Separate configuration from the image. ConfigMaps hold ordinary settings; Secrets hold sensitive configuration with suitable access and encryption controls. Mounted configuration or environment injection supports one image across environments. Updating configuration may require reload logic or a Pod restart.
Minikube
Tool for local Kubernetes learning, development and testing; the lecture demonstrates a single-node VM setup.
kubectl
Command-line client that sends requests to the K8s API server.
GKE / EKS / AKS
Managed Kubernetes services on Google Cloud, AWS and Azure.
kops
CNCF tool to install, upgrade and manage production-grade K8s clusters on cloud VMs.
ConfigMap
K8s object storing non-secret configuration that pods consume, keeping config out of the image.
NodePort
Service type that exposes a service on a fixed port of every node.

Check yourself

A startup's production cluster is a single-node local setup like the one used in the lecture labs, because 'it works fine'. What would you tell them?
One machine is one failure domain: a host failure or upgrade takes everything down, and that setup is designed for learning and testing, not HA. Move to a managed or properly designed self-managed cluster with multiple nodes across zones, and test node and control-plane recovery.
A Deployment is applied but reports 0 of 3 pods available, even though pods with the app are running. What would you check first?
That the selector's matchLabels match the pod template's labels. The Deployment finds and counts its pods by label, so a mismatch means it can't track the pods it should own. Also check that the Service selector uses the same labels so traffic reaches them.
A team changed a value in a ConfigMap, but the app still uses the old value an hour later. Why, and what are the options?
The ConfigMap separates config from the image, but the running process may only read config at startup, and environment variables taken from a ConfigMap are not refreshed. Restart the pods through a rolling update, or mount the ConfigMap as a file and add reload logic. Sensitive values belong in Secrets with access and encryption controls.
Self-managed Kubernetes or a managed Kubernetes service for a team of 4 running 15 services? What should decide it?
Managed is the likely choice: the provider operates selected platform components, such as the control plane, so the small team avoids upgrades and control-plane recovery. Self-managed gives more control but leaves all cluster operations to the team. With either option, check the responsibility boundary: worker capacity, workload security and application availability still need the team's design.

Cloud native design on Kubernetes

Mapping distributed-system concerns and a typical cloud native application onto Kubernetes features and objects.

  • Kubernetes supports distributed-system design; it does not finish it. Configure replicas, placement, health checks, security and metrics. Spread a cluster across suitable zones where supported; use multiple clusters and explicit traffic/data recovery design for regional resilience.
  • A typical cloud native app maps onto K8s building blocks: Ingress and API gateway at the edge, CDN for static content, containerised stateless services and event-driven services, stateful services on persistent volumes, tiered data stores (SQL, NoSQL, object storage), monitoring via DaemonSets, and analytics workloads on the cluster.
  • Objects around a workload inside a Namespace: a Deployment replicates Pods; ConfigMaps and Secrets supply config; Volumes/PVCs supply storage; a ServiceAccount gives identity; a Service routes traffic; a NetworkPolicy restricts who can talk; a ResourceQuota caps consumption; Jobs/CronJobs run batch work.
  • Stateless vs stateful: stateless services scale freely as Deployments; stateful parts need persistent volumes or a managed data tier so data outlives pod restarts.
DaemonSet
Keeps a copy of a Pod on each eligible node, commonly for monitoring or logging agents.
NetworkPolicy
Rules controlling which pods may talk to which, i.e. network segmentation.
ResourceQuota
Caps the total resources a namespace can consume.
Job / CronJob
Runs pods to completion once, or on a schedule.

Check yourself

A cluster spans three zones in one region. A manager says the app is now 'resilient to anything'. What does it cover and what doesn't it?
Spreading replicas across zones covers the loss of a node or a zone, provided placement and spare capacity are configured. It doesn't cover a regional outage or a control-plane failure in that region. Regional resilience needs multiple clusters plus explicit traffic failover and data recovery design.
Map a stateless API, a nightly report, a per-node log collector and a database onto Kubernetes objects. Justify each.
Stateless API: a Deployment with several replicas behind a Service, because it scales freely. Nightly report: a CronJob, for scheduled batch work. Log collector: a DaemonSet, so one runs on every node. Database: a StatefulSet with PVCs, or a managed external database, which is usually the better default because the provider handles backups, replication and patching.
A compromised pod in one namespace could call the payment service and consumed all cluster CPU. Which objects around the workload would have limited this?
A NetworkPolicy restricting who can reach the payment service, a ResourceQuota capping the namespace's consumption (with resource limits on pods), and a dedicated ServiceAccount with only the permissions the workload needs. These are configured controls: Kubernetes supplies them, but they are off unless you set them.

Design patterns, state and traffic flow

Concluding takeaways, K8s design patterns, scaling, state management and how Ingress, Service and Deployment link via labels.

  • Red Hat's top-10 design patterns group into four levels: Foundational (Health Probe, Predictable Demands, Automated Placement), Structural (Init Container, Sidecar), Behavioural (Batch Job, Stateful Service, Service Discovery) and Higher-level (Controller, Operator). Sidecar vs Init Container: a sidecar helps the main container for the pod's whole life (logging, proxying); an init container finishes setup before the app starts.
  • State management: a container's own filesystem is temporary. Durable data goes through a PersistentVolumeClaim bound to a PersistentVolume; a pod-level volume can be shared by containers in the same pod.
  • Traffic and recovery use different mechanisms. Ingress rules identify a Service and its selected endpoints. A failed liveness probe can restart a container inside the same Pod; a lost Pod is replaced by its controller. Readiness determines traffic eligibility. A configured autoscaler changes replica count from metrics; none of these guarantees spare capacity or zero downtime.
  • Takeaway: K8s gives developer velocity, immutability, scaling, scheduling, storage, load balancing and monitoring, integrates with GCP, AWS and Azure, and is open source.
Sidecar
Helper container in the same pod that extends the main container, e.g. log shipping or proxying.
Init container
Container that runs to completion before the main containers start, for setup tasks.
Operator
Custom controller that encodes operational knowledge to manage a complex app automatically.
Horizontal pod autoscaling
Automatically changing the replica count based on a metric such as average CPU.

Check yourself

An API pod's liveness probe calls the database. During a 5-minute database slowdown, every API pod restarts repeatedly. What went wrong, and how should the probes be set?
Liveness failed because of a dependency, so restarts couldn't fix it and they added load during recovery. Liveness should detect only a process that needs a restart, such as a deadlock. Readiness should decide whether the pod can serve traffic, so dependency checks belong there, if anywhere.
Before an app starts, its database schema must be migrated, and throughout its life its logs must be shipped to a central store. Which pattern fits each?
An init container for the migration, because it runs to completion before the app container starts. A sidecar for log shipping, because it runs alongside the app for the pod's whole life and shares its storage. Neither requires changing the app's code. Make the migration safe to run more than once, because pods restart.
A stateful service writes data to its container filesystem, and the data disappears after a node failure. What is the fix, and what does a pod-level volume not solve?
A container's filesystem lives and dies with the container. Use a PersistentVolumeClaim bound to a PersistentVolume so the data outlives the pod, and a replacement pod can remount it. A pod-level volume lets containers in the same pod share files, but it is still tied to the pod's lifetime.
One of three replicas crashes during peak load and users see errors for a minute. Explain which mechanisms recover it, and why errors still happened.
Readiness removes the failed pod from Service endpoints, kubelet restarts a crashed container, and the controller replaces a lost pod. Errors still happen if requests were in flight, if the 2 remaining replicas lack the capacity for peak load, or if there was no spare node capacity for a replacement. None of these mechanisms guarantees zero downtime without headroom and graceful shutdown.

Exam-style questions

Answer aloud or on paper before opening.

A retailer's monolith has outages during sales peaks that are 15 times normal traffic. Propose a Kubernetes-based design, justify the main objects you would use, and say what Kubernetes will not solve for you.
Split the parts that peak, such as catalogue and checkout, into Deployments with several ready replicas spread across zones, Services for stable discovery, and an Ingress with an installed controller for external HTTP routing. Add autoscaling with metrics, resource requests and node headroom. Externalise state to a managed database and shared cache, and use readiness probes, graceful shutdown and rolling updates for deployments. Kubernetes won't supply the database, queue or monitoring stack, won't guarantee zero downtime without spare capacity, and won't fix a data tier that can't take the peak.
A new node joins a cluster and someone deletes a pod by accident at the same moment. Explain, component by component, how the control plane and nodes return the system to its desired state, and which single component's loss would be most serious.
The API server is the only entry point and records changes in etcd. The controller manager sees fewer replicas than declared and creates a replacement pod object. The scheduler places it on a node with capacity, possibly the new one. That node's kubelet starts it through the container runtime, and kube-proxy updates Service routing so traffic reaches it. Losing etcd would be most serious, because it holds all desired and current state, so it should be replicated and backed up.
Design the external access path for three web microservices (/products, /orders, /payments) under one domain. Explain the role of each object, and say what changes if /payments must be reachable only from the orders service internally.
Create a Deployment and a Service for each microservice, with selectors that match the pod labels, and one Ingress with path rules routing to the three Services, implemented by an installed Ingress controller. Services give stable backends, and the controller handles external HTTP routing. If /payments must be internal only, remove it from the Ingress, keep its Service internal, and add a NetworkPolicy that allows traffic only from the orders pods.
An organisation is choosing between a local single-node cluster, self-managed Kubernetes and a managed Kubernetes service for development and production of 20 services, with a 5-person platform team. Recommend a setup for each environment and justify it.
Use a local single-node cluster for developer learning and testing only. For production, use managed Kubernetes: the provider runs selected platform components such as the control plane, so the small team avoids upgrades and control-plane recovery. Self-managed would give more control but leave all cluster operations to 5 people. Check the provider's responsibility boundary, since worker capacity, workload security and application availability still need design, and plan multiple zones for production.
A team's Kubernetes design keeps database credentials in a ConfigMap, runs its database as a single pod with data on the container filesystem, and puts every team in one Namespace with no quotas. Critique the design and give corrected choices.
Credentials in a ConfigMap aren't protected, so move them to Secrets with access and encryption controls, or to an external secret store. A database writing to its container filesystem loses data when the pod is replaced, so use a StatefulSet with PVCs, or preferably a managed database. One shared Namespace without quotas gives no governance, so give each team its own Namespace with RBAC, ResourceQuotas and NetworkPolicies. Keep services stateless so they scale as Deployments, and use one image per release with config injected per environment.
