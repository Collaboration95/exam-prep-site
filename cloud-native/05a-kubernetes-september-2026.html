Kubernetes: A Simple Introduction

38 slides · about 30 min · open the deck · JSON

Kubernetes schedules container workloads and reconciles them toward declared state. Learn the control-plane and worker roles, then connect Pods, Deployments, Services, Ingress, storage and configuration. Compare local and managed clusters, and distinguish the automation Kubernetes supplies from the availability and security choices you must design.

Big ideas

  • Kubernetes turns a group of machines into one container-oriented API: you declare the desired state and K8s schedules, heals and scales containers to match it.
  • Control plane = API server (front door), etcd (store of cluster state), scheduler (places pods), controller manager (drives actual state toward desired state); each node runs kubelet, kube-proxy and a container runtime.
  • A Pod is the smallest deployable unit: tightly coupled containers sharing IP, storage and lifecycle, always on a single node.
  • Deployments/ReplicaSets keep N replicas of a pod template running; Services give a stable virtual IP and DNS name with load balancing, selecting pods by label; Ingress routes external HTTP/HTTPS to many Services under one IP.
  • Kubernetes supplies orchestration primitives; choose and integrate databases, messaging, logging and monitoring around them.
  • Use Minikube for local learning and development; managed production options include GKE, EKS and AKS.
  • Container state is temporary: use PersistentVolumes/PVCs for data and ConfigMaps/Secrets for configuration so images stay immutable and reusable.

Why containers and Kubernetes

Why containers beat older deployment models, and what Kubernetes does and does not do.

Images vs orchestration

Images standardise packaging; orchestration manages running instances.

  • Image → fixes the application and dependencies
  • Registry → distributes it
  • Runtime → starts isolated processes from it
  • Replacing versioned images → repeatable releases and rollbacks

Host compatibility, configuration and data still affect behaviour.

What Kubernetes does

Declare workloads; configure the automation they need.

  • Places Pods
  • Maintains declared replicas
  • Supports probes and rolling updates
  • Provides primitives for storage, configuration, discovery and access control
  • Autoscaling requires metrics and policy
  • Uninterrupted updates require readiness, spare capacity and compatible releases

Kubernetes vs PaaS

K8s is not a PaaS.

  • No language or framework imposed
  • Supplies no databases, message queues or service marketplace
  • Logging and monitoring: you choose your own
  • Platforms built on it (e.g. OpenShift) add those layers

An architect must still select and integrate the surrounding services.

Why adopt Kubernetes

  • Developer velocity
  • Declarative configuration
  • Online self-healing
  • Shared reusable tooling
  • Scaling of software and teams
  • Abstraction from the underlying infrastructure
Container image
Immutable binary package holding everything needed to run a program in a container.
Container registry
Repository that stores and distributes images, e.g. in the OCI standard format.
Orchestration
Automatically scheduling, healing and scaling containers across a cluster of machines.
Liveness / readiness check
Health probes: is the container alive (restart if not) and is it ready to receive traffic.

Check yourself

A release is rolled back by redeploying the previous image, but the app still fails. Why didn't image immutability make the rollback safe?
  • An immutable image restores the old application code exactly
  • Behaviour also depends on configuration and external data
  • If the new release ran a database migration the old code can't handle → a code-only rollback fails
  • Fix: make schema changes backward-compatible, or plan a data recovery step alongside image rollbacks
A team chose Kubernetes expecting it to give them a database, a message queue and logging out of the box, like their old PaaS. What do you tell them?

Kubernetes is not a PaaS.

  • It does: schedules, heals, scales and networks containers
  • It supplies no databases, queues, service marketplace or built-in logging stack
  • They must choose and integrate those, e.g. as managed services, or adopt a platform built on Kubernetes that adds them

Upside: freedom of language and framework.

A team turned on autoscaling in Kubernetes, but pods never scale during load spikes. What is likely missing?

Autoscaling needs metrics and a policy:

  • A metrics source
  • Resource requests or target metrics
  • An autoscaler configured with sensible thresholds
  • Spare node capacity so new pods can be placed

Declaring replicas alone keeps a fixed count; Kubernetes only automates what has been configured.

Orchestration technologies

Kubernetes alongside the other orchestrators, Docker Swarm and Apache Mesos with Marathon.

Three orchestrators compared

Docker Swarm, Mesos/Marathon and Kubernetes all illustrate cluster scheduling, but their scope differs:

  • Swarm → focuses on Docker services
  • Mesos → allocates resources to frameworks
  • Kubernetes → integrates workload controllers and service objects

A comparison of designs, not a current product popularity ranking.

Swarm vs Mesos vs Kubernetes

  • Docker Swarm → Docker's native, simple clustering, driven by Compose files
  • Mesos → general cluster resource manager, like an OS kernel (master/slave); frameworks such as Marathon do the container scheduling
  • Kubernetes → bundles scheduler, controllers, discovery and networking objects into one platform; managed offerings on every major cloud

That is why the course builds on Kubernetes.

The name Kubernetes

  • Greek for pilot or helmsman → the one steering the ship of containers
Apache Mesos
Cluster resource manager acting like a distributed OS kernel; frameworks like Marathon run containers on it.
Docker Swarm
Docker's built-in orchestrator that deploys Compose-described services across a cluster of Docker hosts.

Check yourself

A 3-person team runs 4 services on Docker Compose today and asks whether to move to Swarm or Kubernetes. What would you recommend, and what decides it?
  • Swarm → simpler and reuses their Compose files → suits a small, stable Docker estate
  • Kubernetes → richer objects (Deployments, Services, Ingress, volumes, namespaces), managed offerings on every major cloud and a larger ecosystem → matters if they expect to grow or need portability

Trade-off: learning and operating cost versus capability and future flexibility.

An organisation already runs big-data frameworks on a shared cluster and wants to add container scheduling. How do the Mesos and Kubernetes models differ for this?
  • Mesos → a general resource manager that offers cluster resources to frameworks; Marathon does container scheduling as one framework among others, such as data-processing ones
  • Kubernetes → builds its own scheduler and controllers into the control plane; focuses on container workloads

Mesos fits sharing one cluster across heterogeneous frameworks; Kubernetes gives a more integrated container platform.

Cluster architecture and components

The control-plane (master) components, node components and add-ons, and the core K8s objects.

Control plane components

A cluster splits into a control plane that decides and nodes that execute.

  • API server → the only front door, used by kubectl and all components
  • etcd → distributed key-value store holding all cluster state
  • Scheduler → places pods on nodes
  • Controller manager → the brain that drives actual state toward desired state

Worker node components

Each worker node runs three things:

  • kubelet → agent that starts, stops and monitors the node's pods via the runtime
  • kube-proxy → network rules so Service traffic reaches pods
  • Container runtime → a compatible container runtime, such as containerd or CRI-O
  • Add-ons:
    • CoreDNS for service discovery
    • dashboard
    • Metrics Server
    • cluster logging

Declarative reconcile loop

The heart of K8s.

  1. Submit a spec via kubectl
  2. API server stores it in etcd
  3. Controllers compare desired vs actual state and act
  4. Scheduler assigns new pods
  5. Kubelets start them

This is what yields self-healing and scaling.

Core objects

  • Pod → containers sharing IP, storage, resources and lifecycle
  • ReplicaSet/Deployment → desired state: replicas, pod template, health checks
  • Service → stable virtual IP and DNS name for a group of pods
  • PersistentVolume/PVC → durable storage
  • Label → key-value tags used to select objects

Minikube, kubeadm or a cloud can host the cluster.

API server
Front door of the control plane; every component and kubectl talks to the cluster through it.
etcd
Distributed key-value store that persistently holds all cluster configuration and state.
kubelet
Agent on each node that starts, stops and monitors the pods assigned to it.
kube-proxy
Per-node network proxy that maintains rules so traffic to a Service reaches its pods.
PV / PVC
PersistentVolume is a piece of storage; a PersistentVolumeClaim is a pod's request to use it.
Label
Key-value tag on objects, used by selectors to group pods for Services and Deployments.

Check yourself

You apply a Deployment with 3 replicas, and the pods stay 'Pending'. Trace where in the reconcile chain things stopped, and the likely cause.

The chain stopped at the scheduler.

  • API server stored the spec in etcd → done
  • Controller created pod objects → which is why they exist as Pending
  • Scheduler has not assigned them to nodes → stopped here
  • Likely cause: no node has enough free resources for their requests, or none matches their constraints
  • Check scheduling events, node capacity and the pod's resource requests
A team runs a self-managed cluster with a single etcd member and no backups. What is the risk?
  • etcd holds all cluster state and configuration
  • Losing it → the control plane no longer knows desired or current state; the cluster can't be managed or rebuilt as it was
  • Fix: run etcd replicated across failure domains and back it up regularly

A managed control plane shifts this duty to the provider.

Pods on one node are running and healthy, but traffic sent to their Service never reaches them from other nodes. Which node component would you suspect first, and why not kubelet?

Suspect kube-proxy first.

  • kube-proxy programs the network rules that route Service traffic to pod endpoints
  • Not kubelet: it manages pod and container lifecycles, and the pods are running → it is doing its job
  • Also check that the Service's selector matches the pod labels → a mismatch gives the same symptom

Pods, Services and Ingress

The networking problems K8s solves and how Pods, Services, Namespaces and Ingress fit together, ending with the shape of a manifest.

Distinct objects, distinct network concerns

  • Pods → replaceable workloads
  • Services → discover and balance their endpoints
  • Ingress → describes HTTP routing
  • Namespaces → group resources for management and policy; need RBAC and supported NetworkPolicies for access restrictions

Pod design rules

  • Never spans nodes; gets its own routable IP
  • Only tightly coupled containers together (a main container plus helpers)
  • One process per container
  • Split anything that need not share a machine, so it can scale and fail independently

Service vs Ingress

  • Service → stable internal IP/DNS; selects ready Pod endpoints by label
  • Ingress → defines host/path routing to Services
  • Ingress controller (installed) → implements it; may route directly to Pod endpoints

A logical routing model, not a claim about every packet hop.

Declarative YAML descriptor

Every K8s object is described declaratively in YAML:

  • apiVersion
  • kind
  • metadata → name, namespace, labels
  • spec → desired state you declare
  • status → actual state K8s reports

You hand K8s the descriptor; it pulls images and spreads containers across nodes, presenting the datacentre as one deployment platform.

Service
Stable virtual IP and DNS name that load-balances traffic to the pods matched by its label selector.
Ingress
HTTP/HTTPS host/path routing rules to Services, implemented by an installed Ingress controller.
Namespace
Logical grouping of cluster resources; access and network isolation require additional policies.
Label selector
Query on labels that decides which pods a Service or Deployment manages.
spec vs status
spec is the desired state you declare; status is the actual state K8s reports.

Check yourself

A team puts its web app, a log shipper, and the reporting service it calls into the same pod 'to keep things together'. Which belong together, and why?
  • Same pod: web app + log shipper → the shipper is a tightly coupled helper that shares the app's lifecycle and storage
  • Own pod: the reporting service
    • Containers in a pod share a node, IP and lifecycle → they scale and fail together
    • The reporting service needs to scale and update independently
A frontend calls a backend by a pod IP copied from the console, and it breaks every few days. Why, and what is the fix?

Pods are ephemeral: they get new IPs when replaced or rescheduled.

  • Fix: put a Service in front of the backend pods
  • → a stable IP and DNS name
  • → load-balances across whichever ready pods match its label selector
Three web services must share one public domain with paths /shop, /blog and /api. Would you expose each Service directly or use an Ingress?

An Ingress.

  • One external entry point with path-based routing to the three Services
  • Exposing each directly → needs three external endpoints and gives no shared host or path routing

Cost: an Ingress needs an installed controller to implement its rules → one more component to run.

Two teams share a cluster in separate Namespaces, and a security review assumes their traffic is isolated. Is it?

No. Namespaces organise and scope resources but don't restrict traffic by themselves.

  • NetworkPolicies (with a network plugin that supports them) → limit pod-to-pod traffic
  • RBAC → limit API access
  • ResourceQuotas → stop one team starving the other

Running K8s: Minikube, YAML and cloud

Running Kubernetes locally with Minikube, a Deployment manifest, and the managed offerings on GCP, AWS and Azure, plus config via ConfigMap.

Choose the cluster by operating purpose

  • Minikube (single-node, the lecture's setup) → local learning and testing, not a production HA design
  • Self-managed clusters → more control, but you operate the control plane, nodes, upgrades and recovery

Managed Kubernetes offerings

Reduce cluster operations.

  • GKE → Google Cloud
  • EKS → AWS
  • AKS → Azure
  • ECS → a separate AWS orchestrator, not Kubernetes
  • Provider responsibilities vary by mode; worker capacity, workload security and application availability still require customer design

Treat the lecture's pricing and setup commands as examples, not stable service guarantees.

Deployment manifest

  • replicas → how many pods
  • selector → how to find them by label
  • template → what a pod looks like
  • Selector must match the template labels, or the Deployment cannot track its pods
  • Expose with a Service (e.g. NodePort for local testing)

Configuration separate from image

  • ConfigMaps → ordinary settings
  • Secrets → sensitive configuration, with suitable access and encryption controls
  • Mounted configuration or environment injection → one image across environments
  • Updating configuration may require reload logic or a Pod restart
Minikube
Tool for local Kubernetes learning, development and testing; the lecture demonstrates a single-node VM setup.
kubectl
Command-line client that sends requests to the K8s API server.
GKE / EKS / AKS
Managed Kubernetes services on Google Cloud, AWS and Azure.
kops
CNCF tool to install, upgrade and manage production-grade K8s clusters on cloud VMs.
ConfigMap
K8s object storing non-secret configuration that pods consume, keeping config out of the image.
NodePort
Service type that exposes a service on a fixed port of every node.

Check yourself

A startup's production cluster is a single-node local setup like the one used in the lecture labs, because 'it works fine'. What would you tell them?
  • One machine is one failure domain: a host failure or upgrade takes everything down
  • That setup is designed for learning and testing, not HA
  • Move to a managed or properly designed self-managed cluster with multiple nodes across zones
  • Test node and control-plane recovery
A Deployment is applied but reports 0 of 3 pods available, even though pods with the app are running. What would you check first?

Check that the selector's matchLabels match the pod template's labels.

  • The Deployment finds and counts its pods by label → a mismatch means it can't track the pods it should own
  • Also check that the Service selector uses the same labels → so traffic reaches them
A team changed a value in a ConfigMap, but the app still uses the old value an hour later. Why, and what are the options?
  • Why: the ConfigMap separates config from the image, but the running process may only read config at startup
  • Environment variables taken from a ConfigMap are not refreshed
  • Options
    • Restart the pods through a rolling update
    • Mount the ConfigMap as a file and add reload logic

Sensitive values belong in Secrets with access and encryption controls.

Self-managed Kubernetes or a managed Kubernetes service for a team of 4 running 15 services? What should decide it?

Managed is the likely choice.

  • Managed: the provider operates selected platform components, such as the control plane → the small team avoids upgrades and control-plane recovery
  • Self-managed: more control, but leaves all cluster operations to the team
  • With either option, check the responsibility boundary: worker capacity, workload security and application availability still need the team's design

Cloud native design on Kubernetes

Mapping distributed-system concerns and a typical cloud native application onto Kubernetes features and objects.

K8s supports, doesn't finish, design

Kubernetes supports distributed-system design; it does not finish it.

  • Configure: replicas, placement, health checks, security, metrics
  • Zonal resilience → spread a cluster across suitable zones where supported
  • Regional resilience → multiple clusters plus explicit traffic/data recovery design

Typical cloud native app on K8s building blocks

  • Edge → Ingress and API gateway
  • CDN → static content
  • Containerised stateless services and event-driven services
  • Stateful services → persistent volumes
  • Tiered data stores → SQL, NoSQL, object storage
  • Monitoring → via DaemonSets
  • Analytics workloads → on the cluster

Objects around a workload (Namespace)

Inside a Namespace:

  • Deployment → replicates Pods
  • ConfigMaps and Secrets → supply config
  • Volumes/PVCs → supply storage
  • ServiceAccount → gives identity
  • Service → routes traffic
  • NetworkPolicy → restricts who can talk
  • ResourceQuota → caps consumption
  • Jobs/CronJobs → run batch work

Stateless vs stateful

  • Stateless → scale freely as Deployments
  • Stateful → persistent volumes or a managed data tier, so data outlives pod restarts
DaemonSet
Keeps a copy of a Pod on each eligible node, commonly for monitoring or logging agents.
NetworkPolicy
Rules controlling which pods may talk to which, i.e. network segmentation.
ResourceQuota
Caps the total resources a namespace can consume.
Job / CronJob
Runs pods to completion once, or on a schedule.

Check yourself

A cluster spans three zones in one region. A manager says the app is now 'resilient to anything'. What does it cover and what doesn't it?
  • Covers: spreading replicas across zones covers the loss of a node or a zone, provided placement and spare capacity are configured
  • Doesn't cover: a regional outage or a control-plane failure in that region
  • Regional resilience needs multiple clusters plus explicit traffic failover and data recovery design
Map a stateless API, a nightly report, a per-node log collector and a database onto Kubernetes objects. Justify each.
  • Stateless API → a Deployment with several replicas behind a Service: it scales freely
  • Nightly report → a CronJob: scheduled batch work
  • Log collector → a DaemonSet: one runs on every node
  • Database → a StatefulSet with PVCs, or a managed external database, usually the better default because the provider handles backups, replication and patching
A compromised pod in one namespace could call the payment service and consumed all cluster CPU. Which objects around the workload would have limited this?
  • NetworkPolicy → restricts who can reach the payment service
  • ResourceQuota → caps the namespace's consumption (with resource limits on pods)
  • Dedicated ServiceAccount → only the permissions the workload needs

These are configured controls: Kubernetes supplies them, but they are off unless you set them.

Design patterns, state and traffic flow

Concluding takeaways, K8s design patterns, scaling, state management and how Ingress, Service and Deployment link via labels.

Red Hat's top-10 design patterns

Grouped into four levels:

  • Foundational
    • Health Probe
    • Predictable Demands
    • Automated Placement
  • Structural
    • Init Container
    • Sidecar
  • Behavioural
    • Batch Job
    • Stateful Service
    • Service Discovery
  • Higher-level
    • Controller
    • Operator

Sidecar vs Init Container

  • Sidecar → helps the main container for the pod's whole life (logging, proxying)
  • Init container → finishes setup before the app starts

State management

  • Container's own filesystem → temporary
  • Durable data → PersistentVolumeClaim bound to a PersistentVolume
  • Pod-level volume → can be shared by containers in the same pod

Traffic vs recovery mechanisms

Traffic and recovery use different mechanisms.

  • Ingress rules → identify a Service and its selected endpoints
  • Failed liveness probe → restarts a container inside the same Pod
  • Lost Pod → replaced by its controller
  • Readiness → determines traffic eligibility
  • Configured autoscaler → changes replica count from metrics

None of these guarantees spare capacity or zero downtime.

Takeaway: what K8s gives

  • Developer velocity
  • Immutability
  • Scaling
  • Scheduling
  • Storage
  • Load balancing
  • Monitoring
  • Integrates with GCP, AWS and Azure
  • Open source
Sidecar
Helper container in the same pod that extends the main container, e.g. log shipping or proxying.
Init container
Container that runs to completion before the main containers start, for setup tasks.
Operator
Custom controller that encodes operational knowledge to manage a complex app automatically.
Horizontal pod autoscaling
Automatically changing the replica count based on a metric such as average CPU.

Check yourself

An API pod's liveness probe calls the database. During a 5-minute database slowdown, every API pod restarts repeatedly. What went wrong, and how should the probes be set?
  • What went wrong: liveness failed because of a dependency → restarts couldn't fix it and they added load during recovery
  • Liveness → detect only a process that needs a restart, such as a deadlock
  • Readiness → decide whether the pod can serve traffic → dependency checks belong there, if anywhere
Before an app starts, its database schema must be migrated, and throughout its life its logs must be shipped to a central store. Which pattern fits each?
  • Migration → an init container: it runs to completion before the app container starts
  • Log shipping → a sidecar: it runs alongside the app for the pod's whole life and shares its storage
  • Neither requires changing the app's code

Make the migration safe to run more than once, because pods restart.

A stateful service writes data to its container filesystem, and the data disappears after a node failure. What is the fix, and what does a pod-level volume not solve?
  • Cause: a container's filesystem lives and dies with the container
  • Fix: a PersistentVolumeClaim bound to a PersistentVolume → data outlives the pod, and a replacement pod can remount it
  • Pod-level volume → lets containers in the same pod share files, but is still tied to the pod's lifetime
One of three replicas crashes during peak load and users see errors for a minute. Explain which mechanisms recover it, and why errors still happened.
  • Recovery mechanisms
    • Readiness removes the failed pod from Service endpoints
    • kubelet restarts a crashed container
    • The controller replaces a lost pod
  • Why errors still happened
    • Requests were in flight
    • The 2 remaining replicas lacked the capacity for peak load
    • There was no spare node capacity for a replacement

None of these mechanisms guarantees zero downtime without headroom and graceful shutdown.

Exam-style questions

Answer aloud or on paper before opening.

A retailer's monolith has outages during sales peaks that are 15 times normal traffic. Propose a Kubernetes-based design, justify the main objects you would use, and say what Kubernetes will not solve for you.
  • Split the parts that peak, such as catalogue and checkout
    • Deployments with several ready replicas spread across zones
    • Services for stable discovery
    • An Ingress with an installed controller for external HTTP routing
  • Autoscaling with metrics, resource requests and node headroom
  • Externalise state to a managed database and shared cache
  • Readiness probes, graceful shutdown and rolling updates for deployments
  • Kubernetes won't
    • Supply the database, queue or monitoring stack
    • Guarantee zero downtime without spare capacity
    • Fix a data tier that can't take the peak
A new node joins a cluster and someone deletes a pod by accident at the same moment. Explain, component by component, how the control plane and nodes return the system to its desired state, and which single component's loss would be most serious.
  1. API server: the only entry point; records changes in etcd
  2. Controller manager: sees fewer replicas than declared → creates a replacement pod object
  3. Scheduler: places it on a node with capacity, possibly the new one
  4. kubelet on that node: starts it through the container runtime
  5. kube-proxy: updates Service routing so traffic reaches it

Most serious loss: etcd → it holds all desired and current state, so it should be replicated and backed up.

Design the external access path for three web microservices (/products, /orders, /payments) under one domain. Explain the role of each object, and say what changes if /payments must be reachable only from the orders service internally.
  • Per microservice: a Deployment and a Service, with selectors that match the pod labels → Services give stable backends
  • One Ingress with path rules routing to the three Services
  • An installed Ingress controller implements it and handles external HTTP routing
  • If /payments must be internal only
    • Remove it from the Ingress
    • Keep its Service internal
    • Add a NetworkPolicy that allows traffic only from the orders pods
An organisation is choosing between a local single-node cluster, self-managed Kubernetes and a managed Kubernetes service for development and production of 20 services, with a 5-person platform team. Recommend a setup for each environment and justify it.
  • Local single-node cluster → developer learning and testing only
  • Production → managed Kubernetes
    • The provider runs selected platform components such as the control plane → the small team avoids upgrades and control-plane recovery
    • Self-managed would give more control but leave all cluster operations to 5 people
    • Plan multiple zones for production
  • Check the provider's responsibility boundary: worker capacity, workload security and application availability still need design
A team's Kubernetes design keeps database credentials in a ConfigMap, runs its database as a single pod with data on the container filesystem, and puts every team in one Namespace with no quotas. Critique the design and give corrected choices.
  • Credentials in a ConfigMap aren't protected → move them to Secrets with access and encryption controls, or to an external secret store
  • Database writing to its container filesystem → loses data when the pod is replaced → a StatefulSet with PVCs, or preferably a managed database
  • One shared Namespace without quotas → no governance → give each team its own Namespace with RBAC, ResourceQuotas and NetworkPolicies
  • Keep services stateless → they scale as Deployments
  • One image per release with config injected per environment
