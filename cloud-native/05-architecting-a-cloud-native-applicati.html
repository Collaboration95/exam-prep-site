Architecting a Cloud Native Application

48 slides · about 40 min · open the deck · JSON

Design services for elasticity, resilience, automation and observable operation. Start with state placement and the 12-factor practices, then connect immutable delivery, external configuration and orchestration. Use the design checklists to test scaling, availability, security, operations and feasibility against actual requirements.

Big ideas

  • Cloud native = Platforms (clouds, managed services) + Properties (scalable, loosely coupled, resilient, manageable, observable) + Practices (automation, CD, DevOps).
  • Treat servers as cattle, not pets: keep instances stateless and push state to shared or external stores so any instance can die without losing user data.
  • The 12-factor app (codebase, dependencies, config, backing services, build/release/run, processes, port binding, concurrency, disposability, dev/prod parity, logs, admin processes) is the baseline recipe for cloud native services.
  • Config lives outside the artifact (environment variables), so the same immutable image runs in dev, test and prod.
  • Google's 5 principles: design for automation, be smart with state, favour managed services, practise defence in depth, always be architecting.
  • Cloud native vs traditional: speed over longevity, DevOps over silos, loosely coupled services over monoliths, horizontal on-demand scaling over vertical pre-provisioned scaling.
  • Maturity ladder: Cloud Ready, Cloud Friendly (12-factor), Cloud Resilient, Cloud Native (microservices, API-first).
  • Good design asks explicit questions on scalability, availability (SLAs are composite), security (data jurisdiction), manageability (monitoring, deployment) and feasibility (skills, cost, trade-offs).

What is cloud native?

Defines cloud native architecture and applications, and introduces the three Ps (Platforms, Properties, Practices) and the wider map of ideas around cloud native.

What cloud native means

Exploiting the cloud's very different constraints, not just hosting on it.

  • Goal qualities: scalable, portable, maintainable
  • Capabilities: resilient, scalable, observable, highly automated, easily updated
  • Practices: cooperation, integration and open governance between teams

The three Ps

Three Ps frame every answer.

  • Platforms → dynamic public, private or hybrid clouds and subscribed managed services
  • Properties → scalable, loosely coupled, resilient, manageable, observable, plus config and secrets
  • Practices → automation, continuous delivery, DevOps (frequent, predictable change)

Resilience, elasticity, portability

These need design.

  • Resilience: the ability to continue or recover after failure
  • Elasticity / autoscaling: adjusts capacity to demand
  • Portability / open standards: reduce some integration and switching costs
  • Lock-in still possible → provider-specific APIs and data dependencies

Typical topologies and CNCF

  • Containers
  • Orchestration (Kubernetes)
  • Serverless
  • CNCF: the foundation that curates this ecosystem

The goals they serve: speed, resilience, scale and cost.

Cloud native
Building and running apps to exploit cloud platforms: resilient, scalable, observable, automated and easily updated.
Three Ps
Platforms, Properties and Practices that together characterise a cloud native application.
Autoscaling
Applications automatically growing and shrinking to meet demand.
CNCF
Cloud Native Computing Foundation, which hosts Kubernetes and related projects.

Check yourself

A company moved its app onto Kubernetes on a public cloud, but releases still happen quarterly by hand and nobody watches metrics. Is it cloud native? Use the three Ps.

Only on the Platforms P.

  • Properties missing: observable, resilient, loosely coupled
  • Practices missing: automation, continuous delivery, DevOps
  • → it gets little of the speed, resilience or scale that cloud native aims for

Add CI/CD, monitoring and automated recovery before calling it cloud native.

A team says 'we use only open-standard containers, so we have no lock-in.' Do you agree?

Partly.

  • Open standards → tools easier to integrate, can lower switching costs
  • Lock-in also comes from provider-specific APIs, managed data services and operational dependencies
  • Check each managed service the app uses, and how its data would move, before claiming portability
During a zone failure, an app's autoscaler added capacity but users still saw errors for 20 minutes. Which cloud-native property was missing, and why isn't autoscaling enough?

Resilience was missing: the ability to continue or recover after failure.

  • Autoscaling adjusts capacity to demand only
  • It doesn't reroute traffic around a failed zone or replace dependencies that went down with it
  • Resilience needs design work: multi-zone placement, health checks, failover, bounded retries

Service models, stack and principles

Compares IaaS, CaaS, PaaS, FaaS and SaaS by who manages what, contrasts the cloud native stack with a traditional web app, and covers Google's five principles and the container workflow.

Service models: the operating boundary

Service models change the operating boundary.

  • IaaS → exposes VMs
  • CaaS → manages container-platform components
  • PaaS → manages the application runtime
  • FaaS → runs functions
  • SaaS → supplies a finished application

Exact duties vary by offering: managed Kubernetes does not necessarily remove worker-node operations, and data accountability remains with the customer.

CaaS vs FaaS

  • CaaS → long-running or portable containerised workloads where you want runtime control
  • FaaS → short event-driven work where the platform handles runtime and autoscaling

Splitting the layered monolith

Cloud native splits the traditional layered monolith.

  • Traditional web app → one server packs:
    • request processing
    • auth
    • caching
    • session management
    • validation
    • logging
    • workflows
  • Cloud native → pushes these into independently deployable services
  • Over a stack of:
    • container-optimised OS
    • registry
    • service mesh
    • orchestration
    • build/release tooling
  • Security and observability across the whole stack

Google's 5 principles

  • Design for automation
  • Be smart with state
  • Favour managed services: spend effort on business code, not operations
  • Practise defence in depth
  • Always be architecting: design is continuous

Container workflow (delivery mechanism)

  1. Write the app
  2. Package it as an image (app plus dependencies)
  3. Push to a registry
  4. Pull: a server pulls it
  5. Run: the container runtime starts it

Gives repeatable packaging on compatible platforms; configuration and backing services still affect behaviour.

CaaS
Containers as a Service: a provider manages container-platform components; worker and workload duties depend on the offering.
FaaS
Function as a Service (serverless): you deploy only functions; the platform handles runtime and autoscaling.
Container image
A packaged bundle of an app and its dependencies, stored in a registry.
Container runtime
Node software that pulls images and creates, starts, stops and deletes containers.

Check yourself

A new service processes uploaded documents within seconds of arrival, runs a few hundred times a day, and needs no special runtime. Another holds long-lived WebSocket connections. CaaS or FaaS for each?
  • Document processor → FaaS: short, event-driven work; the platform handles runtime and autoscaling; you pay only when it runs
  • WebSocket service → CaaS: long-running and needs runtime control, something functions handle poorly

Trade-off: FaaS gives up control and portability; CaaS keeps them but you operate more.

A team chose managed Kubernetes and says they no longer have any infrastructure work. Is that right?

Not necessarily.

  • CaaS manages the container platform components
  • Worker-node operations such as patching and scaling may still fall to the customer, depending on the offering
  • Data accountability always stays with the customer
  • Check the provider's actual responsibility split

'Favour managed services' moves effort to business code but doesn't remove all operations.

A container image passed every test in staging but fails in production with the same image tag. What is the most likely cause?
  • The image fixes the app and dependency versions only
  • Behaviour also depends on external configuration, platform features and backing services → these differ between staging and production
  • Compare environment config, secrets, service endpoints and platform versions

Keeping dev and prod sufficiently alike reduces this.

State: pets vs cattle

Explains why cloud native apps should be stateless, how sticky sessions differ from shared state, Kubernetes options for state, and VM-centric vs app-centric deployment.

Stateless instances

Stateless instances do not own durable user state.

  • Domain data → store in databases
  • Sessions → shared store, or suitable client-held tokens
  • Disposable caches possible, but correctness must not depend on one instance's memory

Losing an instance should not lose committed user data.

Pets vs cattle

An operating model, not a size or VM rule.

  • Pet → needs individual repair
  • Cattle → replaceable from automation
  • Sticky routing is fragile when session data exists only on that instance
  • VMs can also be disposable; containers can still be operated as pets

Where state goes on Kubernetes

  • StatefulSets → stable ordering and identity
  • Persistent Volumes and Claims → cluster storage and requests for it
  • Operators → custom resources encoding operational knowledge
  • External state stores → databases or queues outside the cluster (e.g. managed cloud databases)

In-cluster vs external state

  • In-cluster → control and portability, but you operate it
  • External managed store → offloads backups, replication and patching; keeps the cluster stateless

External is usually the better default.

Stateless application
Application instance whose durable correctness does not depend on local domain or session state; persistent state is kept elsewhere.
Sticky session
Load balancer routes a user to the same instance every time, tying their session to that server.
Pets vs cattle
Pets are hand-cared, irreplaceable servers; cattle are identical, disposable instances replaced automatically.
StatefulSet
Kubernetes workload object giving stateful pods ordering and uniqueness guarantees.
Kubernetes Operator
Extension using custom resources to encode and automate operational knowledge for an application.

Check yourself

A web tier uses sticky sessions with session data held in instance memory. During a scale-in event, users are logged out. Diagnose it and fix it.
  • Diagnosis: scale-in removed instances that held the only copy of some sessions → sticky routing sent users to sessions that no longer existed
  • Fix: move session state to a shared store, or use suitable client-held tokens → any ready instance can serve the next request

Cost: a shared store on the request path that must itself be available.

A team runs a database in Kubernetes with a StatefulSet. A reviewer suggests a managed external database instead. When is each right?
  • External managed database → usually the better default: the provider handles backups, replication and patching; the cluster stays stateless
  • StatefulSet, or an Operator that encodes operational knowledge → right when the store must run in the cluster for control or portability, and the team accepts operating it
A teammate says 'we're on containers, so our servers are cattle now.' What would show whether that is true?

Pets versus cattle is an operating model, not a technology.

  • Check: can any instance be deleted and recreated from automation without losing data or needing someone to fix it by hand?
  • Containers that are patched in place or hold unique local state → still pets
  • Disposable VMs can be cattle

The 12-factor app

The twelve practices that make a service suitable for cloud deployment.

The 12 factors

  1. Codebase: one tracked codebase, many deploys
  2. Dependencies: declared and packaged
  3. Config: in the environment
  4. Backing services: attached resources via URL
  5. Build/release/run: strictly separate stages
  6. Processes: stateless
  7. Port binding: self-contained service
  8. Concurrency: scale out via processes
  9. Disposability: fast start, graceful stop
  10. Dev/prod parity
  11. Logs: event streams
  12. Admin processes: one-off tasks

Separate build, release, run

  1. Build → one immutable artifact
  2. Release → artifact + environment-specific configuration
  3. Run → execute that release

Promoting the same tested artifact reduces drift. A rollback also needs compatible configuration and data/schema state.

Processes, concurrency, disposability

They work as a set.

  • Stateless shared-nothing processes → hold no local state, so can be duplicated freely
  • Scale-out concurrency → add more processes
  • Disposability → fast startup and graceful shutdown let the platform add, remove and replace them at will

Backing services, logs, parity

  • Backing services are configured dependencies → external addresses let deployments select compatible databases, queues or mail services without rebuilding
  • Caveat: a different protocol or data model can still require code changes
  • Logs → stream to central storage, because local files vanish with disposable instances
  • Dev/prod parity → keep dev and prod sufficiently alike to expose integration problems
12-factor app
Methodology of twelve practices for building portable, scalable services suited to cloud platforms.
Backing service
Any external resource (DB, queue, mail server) consumed over the network, attached via URL/config.
Shared-nothing
Processes keep no shared local state, so any can be added or removed freely.
Dev/prod parity
Keeping all environments as similar as possible to avoid late surprises.

Check yourself

A team rebuilds the image separately for test and for production with different config baked in. Which factors does this break, and what is the risk?

Breaks build/release/run separation and config in the environment.

  • Risk: the production artifact is not the one that was tested → builds can drift through dependency or build differences
  • Fix: build one immutable artifact, combine it with environment config at release, and promote the same artifact

A rollback still needs compatible config and schema state.

An autoscaler adds instances during a spike, but each takes 3 minutes to start and loses in-flight work when removed. Which factors are failing, and why do they matter together?

Disposability (fast start, graceful stop) and probably stateless processes.

  • Concurrency through scale-out only works if the platform can add and remove processes freely
  • Slow starts → capacity arrives after the spike
  • Abrupt stops → lose work
  • Fix
    • Speed up startup
    • Handle termination signals to finish or hand back work
    • Keep state in backing services
After an incident, engineers can't find the logs because the failed containers were already replaced. Which factor was ignored, and what is the fix?

Logs as event streams was ignored.

  • Instances are disposable → local log files vanish with them
  • Fix: write logs to stdout as a stream; the platform ships them to a central aggregator that can be searched across all instances

Cost: running or paying for the log pipeline and its storage.

Packaging, config and orchestration

Follows an app from code to a Kubernetes pod, covering the Kubernetes control plane, externalised configuration, the service mesh and application packages.

Code to cluster: chain of runtimes

  1. Built application → language runtime
  2. Container image → container runtime
  3. Pod → Kubernetes cluster

Orchestration, unlike running a container on one machine, spreads workloads across a cluster of nodes.

Kubernetes is declarative

  • Manifest states the desired state: apiVersion, kind, metadata, spec
  • Control plane (scheduling, scaling, self-healing) continuously reconciles reality to it
  • Worker nodes run the pods

Externalise configuration

So one artifact serves several environments.

  • Environment variables or mounted external configuration → avoid baking deploy-specific values into the image
  • Secrets → source from protected storage with restricted access
  • Caveat: environment variables alone do not make a secret secure

Service mesh vs API gateway

  • Both have a control plane and a data plane
  • API gateway → fronts external clients
  • Service mesh → manages service-to-service traffic (routing, resilience, observability, security) without changing service code

Application package vs container image

  • Application package → language-specific: program, same-language libraries, config
  • Container image → bundles the runtime environment too
Pod
Smallest deployable unit in Kubernetes; one or more containers scheduled together on a node.
Control plane
Management layer that schedules, scales and heals workloads (Kubernetes) or configures proxies (service mesh).
Manifest
Declarative file (apiVersion, kind, metadata, spec) describing the desired state of a Kubernetes object.
Service mesh
Pattern managing service-to-service communication: routing, resilience, observability, security.
External configuration
Settings kept outside the artifact, typically as environment variables.

Check yourself

A team puts its database password in an environment variable and calls it 'secure because it's not in the code'. Do you agree?

Not fully.

  • Externalising config is right → one artifact serves several environments
  • An environment variable alone doesn't protect a secret → it can leak through logs, dumps or anyone with access to the deployment spec
  • Fix: source it from protected secret storage with restricted access and inject it at runtime
Someone deletes a pod by mistake and it comes back a few seconds later. Explain why, and say what this means for how you change production.
  • The manifest declares a desired state (e.g. 3 replicas)
  • The control plane continuously reconciles the cluster to it → it recreated the pod
  • Change production by changing the declared state, not by editing live resources → reconciliation will undo manual fixes

This is also what gives self-healing.

A platform has 25 internal services with inconsistent retry and encryption behaviour, plus a public mobile API. Where do an API gateway and a service mesh each fit?
  • API gateway → the entry point for the mobile clients' external traffic: routing, authentication, rate limits
  • Service mesh → the 25 services' internal traffic: consistent routing, resilience, observability and encryption without changing service code
  • Both have a control plane and a data plane

The mesh adds operating cost, which is justified here by the inconsistency across 25 services.

Maturity, traditional vs cloud native, summary

A cloud native maturity model, a microservice retail example, traditional vs cloud native comparison, key attributes and design axes.

Cloud native maturity ladder

  1. Cloud Ready → no permanent disk access, self-contained, platform-managed ports and backing services
  2. Cloud Friendly → 12-factor, horizontally scalable, uses platform HA
  3. Cloud Resilient → fault tolerant, cloud-agnostic runtime, bundled metrics, proactive failure testing
  4. Cloud Native → microservices, API-first

Typical operating approaches contrasted

  • Traditional → long release cycles, server-centric capacity planning
  • Cloud native → frequent automated delivery, disposable horizontally scaled services

These are tendencies, not rules: monoliths and VMs can also use DevOps and autoscaling.

What a cloud native app is like

  • Predictable
  • OS-abstracted
  • Right-sized
  • Collaborative
  • Continuously delivered
  • Independent (small services)
  • Automatically scalable
  • Quick to recover

Together: microservices, loose coupling, resilience, agility, automation, self-healing and a DevOps culture.

Microservice retail example

  • Clients call an API gateway
  • Gateway fronts small services: search, cart, checkout, payments
  • Some services own their own databases
  • Integrates with back-end systems

Design axes

  • Cloud native services
    • building blocks
    • managed
    • advanced managed
  • Application-centric design
    • 12-factor
    • microservices
    • other aspects
  • Automation
    • deploy/config
    • monitoring/compliance/optimisation
    • AI/ML prediction
Cloud Native Maturity Model
Four levels: Cloud Ready, Cloud Friendly, Cloud Resilient, Cloud Native.
API gateway
Single entry point that routes client requests to back-end microservices.
API-first design
Designing the service's API contract first so services integrate through well-defined APIs.
Horizontal scaling
Adding more instances rather than making one machine bigger (vertical scaling).

Check yourself

A legacy app has been containerised but still writes to local disk and uses sticky sessions. Where is it on the maturity model, and what is the next step?

Not yet Cloud Ready.

  • Cloud Ready requires: no permanent disk access + a self-contained app using platform-managed backing services
  • First: move files and sessions to backing services
  • Then: adopt the 12 factors and horizontal scaling → Cloud Friendly

Containerising alone doesn't move it up the ladder.

An app is 12-factor and scales horizontally on platform HA, and a team wants to call it 'cloud native'. What would it still need?

That is Cloud Friendly.

  • Cloud Resilient adds: fault tolerance, a cloud-agnostic runtime, bundled metrics, proactive failure testing
  • Cloud Native adds: microservices and API-first design

Whether to go further depends on whether the business needs independent deployability and resilience that justify the cost.

A company adopted containers and microservices but kept separate dev and ops teams with handoffs, and releases are still slow. Why?
  • Short continuous delivery and fast recovery need collaborating teams and automation as well as the technical properties
  • Handoffs between silos → keep the release cycle long, whatever the architecture
  • Fix: pair the architecture with DevOps practices and shared ownership

Otherwise the speed-to-market benefit won't appear.

Design space, characteristics and guidelines

Levels of design abstraction, the characteristics to weigh when choosing a cloud, and guidelines for separation of concerns.

Choosing a cloud: multi-criteria decision

Start with the goal (productivity, ease of migration, or control), then weigh:

  • Integration
  • Data storage and location
  • Ecosystem and portfolio
  • Pricing model: fixed vs use-based
  • QoS: availability, DR, SLA
  • Security and privacy
  • Self-service
  • Elasticity
  • Vendor viability

Legacy migration vs new build

Weights the criteria differently.

  • Migration favours → backward compatibility, internal-network integration, data location
  • New product favours → productivity, elasticity, use-based pricing, rich managed-service portfolio

Separation of concerns

Keeps business rules portable.

  • Independent of frameworks, UI, database and external agencies
  • Testable without them
  • Organise code around the business problem, not generic folders

Levels of design abstraction

Design thinking spans levels of abstraction:

  1. Technologies and mechanisms
  2. Idioms and patterns
  3. Architecture
Separation of concerns
Keeping business rules isolated from UI, database, frameworks and external systems so each can change independently.
Vendor viability
The provider's commitment to cloud and ability to execute as a business.

Check yourself

Business rules for loan approval call the database driver and the web framework directly. The team now wants to change databases and unit-test the rules. What is the problem, and what would you change?
  • Problem: the rules are coupled to the database and framework → changing either means rewriting logic, and tests need a real database
  • Separate concerns: put the rules in code independent of frameworks, UI, database and external agencies
  • Reach the database through an interface

Cost: an extra layer of abstraction.

Two projects are choosing a cloud: migrating a legacy enterprise app with on-premises integrations, and building a new consumer product. Which characteristics should weigh most for each?
  • Legacy migration → weigh most: ease of migration, backward compatibility, integration with the internal network, data location
  • New product → weigh most: productivity, elasticity, use-based pricing, a rich managed-service portfolio

The same provider can win for one project and lose for the other → start from each project's goal.

Design considerations: scalability to feasibility

Checklists of questions an architect should answer on scalability, availability, security, manageability and feasibility.

Scalability

  • Ask: which layers must scale, how fast, can you scale down off-hours?
  • Persistence: check limits and partition data
  • Many small instances over few large ones
  • Level load with:
    • queues (producer and competing consumers)
    • async operations
    • load balancers

Availability and DR

  • Dependencies: identify those required for each request
  • Series estimate: for independent services in series, multiply availability probabilities; common failures and redundancy change the result
  • Design: failover, replication, bounded retries, circuit breakers
  • Backups protect against corruption as well as outages
  • Test restoration and idempotent replay

Security

  • Data residency: where data legally resides, including failover and metrics copies
  • Federated identity
  • Secured hybrid links
  • Access control for admin portal and database
  • Credential rotation
  • Multitenancy effects
  • Patching

Manageability

  • Monitor with usable, compliant storage of metrics and logs
  • Auditing vs logging: distinguish them
  • Adjust levels at runtime
  • Deployment: automated, verifiable, reversible, non-disruptive
  • Environments: a deliberate number of them

Feasibility

  • SLAs: can any provider meet them?
  • Skills, budget and time: do you have them?
  • Operating costs: what are they?
  • Trade-offs: what can be reduced (scope, SLAs, resilience) as an accepted trade-off
Composite SLA
End-to-end availability depends on the dependency structure; independent required services in series have multiplied availability probabilities.
Competing consumer pattern
Multiple consumers read from one queue so work is spread and load is levelled.
Circuit breaker
Pattern that stops calling a failing service for a while to avoid cascading failure and overload.
Idempotent
An operation that can be repeated (e.g. a replayed message) without changing the result beyond the first time.

Check yourself

A checkout request needs an API service, a payment service and a database in series, each at 99.9% availability. A manager promises 99.9% end-to-end. Is that realistic?

No. For independent components in series, availability multiplies.

  • 0.999 × 0.999 × 0.999 ≈ 99.7% → the path is less available than any single part
  • An estimate: shared failure modes and redundancy change it

To reach 99.9%: add redundancy or failover on the critical path, or reduce dependencies the request needs.

Order submissions spike tenfold at sale start, and the order processor falls over. How do queues help, and what must the consumers guarantee?
  • Queue between submission and processing → producers aren't blocked
  • Backlog levels the peak
  • Competing consumers scale out to drain it
  • Consumer fails → the message is delivered again → processing must be idempotent to avoid duplicate orders

Trade-off: users now get 'accepted' rather than 'completed' immediately.

The primary database is replicated to a second region, so the team drops nightly backups. What risk does this create?
  • Replication copies an accidental delete or a corrupting update to every replica → nothing earlier to recover
  • Backups keep recoverable earlier states
  • Keep backups, test restores against acceptable data loss and recovery time, and make replay idempotent
Customer data must stay in Singapore. The app's database is in Singapore, but failover is to another country's region and metrics go to a global monitoring service. Is the design compliant?

Probably not.

  • Data protection rules apply to every copy, including failover replicas and any customer data inside metrics or logs
  • Failover: choose an in-country location, or confirm the rules allow it
  • Telemetry: scrub personal data, or keep it in-region

Cost: may be weaker DR options.

Exam-style questions

Answer aloud or on paper before opening.

A retailer's monolithic web shop loses customers' carts whenever a server crashes and can't cope with sale-day spikes of 20 times normal traffic. Diagnose the causes and propose a cloud native redesign, naming one new risk it introduces.
  1. Diagnosis
    • Sticky sessions + in-memory carts → servers are pets
    • The single scaling unit can't grow fast enough
  2. Cloud native redesign
    • Stateless web tier, with carts in a shared store or managed database
    • Split hot areas such as checkout into services behind an API gateway
    • Run them as containers with horizontal autoscaling
    • Put order processing behind a queue → level peaks
    • Apply 12-factor practices and CI/CD
  3. New risks
    • Distributed failures and eventual consistency between services
    • → add observability, timeouts and idempotent consumers
Audit this service against the 12 factors: config is baked into images per environment, logs go to local files, the service takes 4 minutes to start, it writes uploads to local disk, and a database migration runs at every container start. Rank the gaps by operational risk and give the fix for each.

Ranked by operational risk:

  1. Uploads on local disk (highest risk)
    • Breaks stateless processes → data is lost when instances are replaced
    • Fix: move them to object storage
  2. Per-environment images
    • Breaks build/release/run and config → the tested artifact isn't the one deployed
    • Fix: build once and inject config at release, with secrets from protected storage
  3. 4-minute start
    • Breaks disposability → defeats autoscaling
  4. Migration at every container startup
    • Fix: a one-off admin process → avoids concurrent migrations
  5. Local logs (lowest)
    • They vanish with the instance
    • Fix: stream them to an aggregator
You must offer 99.95% availability for a service whose request path uses a gateway, a compute tier and a managed database, each with a 99.9% SLA. Explain why the target is at risk and propose design changes, with the cost of each.
  • Why the target is at risk
    • In series: 0.999³ ≈ 99.7%, below the target
    • Provider SLAs alone can't guarantee the end-to-end figure
  • Add redundancy on the path
    • Compute across zones behind health-checked load balancing
    • A database with a synchronous standby
    • Possibly a second region for the most critical path
  • Remove dependencies from the synchronous path using queues and caches
  • Bound retries and use circuit breakers → one slow dependency doesn't cascade

Cost: each step adds cost and complexity → check feasibility; if the budget or skills can't support it, renegotiate the SLA.

A bank's 20-year-old core app is released twice a year, runs on large VMs sized for peak, and is owned by separate dev and ops teams. A new digital-banking team wants weekly releases. Contrast the traditional and cloud-native approaches for each part, and say whether the core app should be converted.
  • Traditional
    • Long release cycles
    • Siloed teams
    • A tightly coupled monolith
    • Server-centric, vertical capacity pre-provisioned for peak
  • Cloud native
    • Continuous delivery
    • DevOps teams
    • Loosely coupled API-based services
    • Disposable, horizontally scaled containers
  • Digital team → should build cloud native
  • Core app: doesn't need to convert all at once
    • Expose it through APIs and modernise where business drivers justify it
    • These are tendencies → the core app can adopt automation and DevOps without a rewrite
You run 30 microservices on Kubernetes across dev, test and prod. Secrets are in plain manifests, retries differ per team, and an outage last month cascaded through internal calls. Propose how to manage configuration, secrets and service-to-service traffic.
  • Ordinary config → outside the image, per environment → the same artifact is promoted through all three
  • Secrets → protected secret storage with restricted access, injected at runtime → plain manifests or environment variables alone aren't protection
  • Declare everything in version-controlled manifests → the control plane reconciles drift
  • Service-to-service traffic → a service mesh, justified by 30 services and a cascading outage
    • Consistent timeouts, bounded retries, circuit breaking, encryption and tracing without code changes
    • An API gateway for external traffic

The mesh adds operational overhead and latency to manage.
