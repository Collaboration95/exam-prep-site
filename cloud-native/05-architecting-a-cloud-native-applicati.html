Architecting a Cloud Native Application

48 slides · about 40 min · open the deck · JSON

Design services for elasticity, resilience, automation and observable operation. Start with state placement and the 12-factor practices, then connect immutable delivery, external configuration and orchestration. Use the design checklists to test scaling, availability, security, operations and feasibility against actual requirements.

Big ideas

  • Cloud native = Platforms (clouds, managed services) + Properties (scalable, loosely coupled, resilient, manageable, observable) + Practices (automation, CD, DevOps).
  • Treat servers as cattle, not pets: keep instances stateless and push state to shared or external stores so any instance can die without losing user data.
  • The 12-factor app (codebase, dependencies, config, backing services, build/release/run, processes, port binding, concurrency, disposability, dev/prod parity, logs, admin processes) is the baseline recipe for cloud native services.
  • Config lives outside the artifact (environment variables), so the same immutable image runs in dev, test and prod.
  • Google's 5 principles: design for automation, be smart with state, favour managed services, practise defence in depth, always be architecting.
  • Cloud native vs traditional: speed over longevity, DevOps over silos, loosely coupled services over monoliths, horizontal on-demand scaling over vertical pre-provisioned scaling.
  • Maturity ladder: Cloud Ready, Cloud Friendly (12-factor), Cloud Resilient, Cloud Native (microservices, API-first).
  • Good design asks explicit questions on scalability, availability (SLAs are composite), security (data jurisdiction), manageability (monitoring, deployment) and feasibility (skills, cost, trade-offs).

What is cloud native?

Defines cloud native architecture and applications, and introduces the three Ps (Platforms, Properties, Practices) and the wider map of ideas around cloud native.

  • Cloud native is about exploiting the cloud's very different constraints, not just hosting on it. The goal qualities are scalable, portable and maintainable; the capabilities are resilient, scalable, observable, highly automated and easily updated, and the practices are cooperation, integration and open governance between teams.
  • Three Ps frame every answer. Platforms (dynamic public, private or hybrid clouds and subscribed managed services), Properties (scalable, loosely coupled, resilient, manageable, observable, plus config and secrets) and Practices (automation, continuous delivery, DevOps: frequent, predictable change).
  • Resilience, elasticity and portability need design. Resilience is the ability to continue or recover after failure; autoscaling adjusts capacity to demand. Open standards reduce some integration and switching costs, but provider-specific APIs and data dependencies can still create lock-in.
  • Containers, orchestration (Kubernetes) and serverless are the typical topologies, and the CNCF is the foundation that curates this ecosystem. The goals they serve are speed, resilience, scale and cost.
Cloud native
Building and running apps to exploit cloud platforms: resilient, scalable, observable, automated and easily updated.
Three Ps
Platforms, Properties and Practices that together characterise a cloud native application.
Autoscaling
Applications automatically growing and shrinking to meet demand.
CNCF
Cloud Native Computing Foundation, which hosts Kubernetes and related projects.

Check yourself

A company moved its app onto Kubernetes on a public cloud, but releases still happen quarterly by hand and nobody watches metrics. Is it cloud native? Use the three Ps.
Only on the Platforms P. The Properties (observable, resilient, loosely coupled) and the Practices (automation, continuous delivery, DevOps) are missing, so it gets little of the speed, resilience or scale that cloud native aims for. Add CI/CD, monitoring and automated recovery before calling it cloud native.
A team says 'we use only open-standard containers, so we have no lock-in.' Do you agree?
Partly. Open standards make tools easier to integrate and can lower switching costs, but lock-in also comes from provider-specific APIs, managed data services and operational dependencies. Check each managed service the app uses, and how its data would move, before claiming portability.
During a zone failure, an app's autoscaler added capacity but users still saw errors for 20 minutes. Which cloud-native property was missing, and why isn't autoscaling enough?
Resilience: the ability to continue or recover after failure. Autoscaling adjusts capacity to demand, but it doesn't reroute traffic around a failed zone or replace dependencies that went down with it. Resilience needs design work such as multi-zone placement, health checks, failover and bounded retries.

Service models, stack and principles

Compares IaaS, CaaS, PaaS, FaaS and SaaS by who manages what, contrasts the cloud native stack with a traditional web app, and covers Google's five principles and the container workflow.

  • Service models change the operating boundary. IaaS exposes VMs; CaaS manages container-platform components; PaaS manages the application runtime; FaaS runs functions; SaaS supplies a finished application. Exact duties vary by offering: managed Kubernetes does not necessarily remove worker-node operations, and data accountability remains with the customer.
  • CaaS vs FaaS: choose CaaS for long-running or portable containerised workloads where you want runtime control; choose FaaS for short event-driven work where the platform handles runtime and autoscaling.
  • Cloud native splits the traditional layered monolith. A traditional web app packs request processing, auth, caching, session management, validation, logging and workflows into one server; cloud native pushes these into independently deployable services over a stack of container-optimised OS, registry, service mesh, orchestration and build/release tooling, with security and observability across it.
  • Google's 5 principles: design for automation, be smart with state, favour managed services (spend effort on business code, not operations), practise defence in depth, always be architecting (design is continuous).
  • The container workflow is the delivery mechanism: write the app, package it as an image (app plus dependencies), push to a registry, a server pulls it and the container runtime starts it, giving repeatable packaging on compatible platforms; configuration and backing services still affect behaviour.
CaaS
Containers as a Service: a provider manages container-platform components; worker and workload duties depend on the offering.
FaaS
Function as a Service (serverless): you deploy only functions; the platform handles runtime and autoscaling.
Container image
A packaged bundle of an app and its dependencies, stored in a registry.
Container runtime
Node software that pulls images and creates, starts, stops and deletes containers.

Check yourself

A new service processes uploaded documents within seconds of arrival, runs a few hundred times a day, and needs no special runtime. Another holds long-lived WebSocket connections. CaaS or FaaS for each?
FaaS for the document processor: short, event-driven work, where the platform handles runtime and autoscaling and you pay only when it runs. CaaS for the WebSocket service, which is long-running and needs runtime control, something functions handle poorly. FaaS gives up control and portability; CaaS keeps them but you operate more.
A team chose managed Kubernetes and says they no longer have any infrastructure work. Is that right?
Not necessarily. CaaS manages the container platform components, but depending on the offering, worker-node operations such as patching and scaling may still fall to the customer, and data accountability always stays with the customer. Check the provider's actual responsibility split. 'Favour managed services' moves effort to business code but doesn't remove all operations.
A container image passed every test in staging but fails in production with the same image tag. What is the most likely cause?
The image fixes the app and dependency versions, but behaviour also depends on external configuration, platform features and backing services, which differ between staging and production. Compare environment config, secrets, service endpoints and platform versions. Keeping dev and prod sufficiently alike reduces this.

State: pets vs cattle

Explains why cloud native apps should be stateless, how sticky sessions differ from shared state, Kubernetes options for state, and VM-centric vs app-centric deployment.

  • Stateless instances do not own durable user state. Store domain data in databases; keep sessions in a shared store or use suitable client-held tokens. Disposable caches are possible, but correctness must not depend on one instance’s memory. Losing an instance should not lose committed user data.
  • Pets vs cattle is an operating model, not a size or VM rule. A pet needs individual repair; cattle are replaceable from automation. Sticky routing is fragile when session data exists only on that instance. VMs can also be disposable, and containers can still be operated as pets.
  • Where state goes on Kubernetes: StatefulSets (stable ordering and identity), Persistent Volumes and Claims (cluster storage and requests for it), Operators (custom resources encoding operational knowledge), or external state stores (databases or queues outside the cluster, e.g. managed cloud databases).
  • In-cluster vs external state: running state in-cluster gives control and portability but you operate it; an external managed store offloads backups, replication and patching and keeps the cluster stateless, which is usually the better default.
Stateless application
Application instance whose durable correctness does not depend on local domain or session state; persistent state is kept elsewhere.
Sticky session
Load balancer routes a user to the same instance every time, tying their session to that server.
Pets vs cattle
Pets are hand-cared, irreplaceable servers; cattle are identical, disposable instances replaced automatically.
StatefulSet
Kubernetes workload object giving stateful pods ordering and uniqueness guarantees.
Kubernetes Operator
Extension using custom resources to encode and automate operational knowledge for an application.

Check yourself

A web tier uses sticky sessions with session data held in instance memory. During a scale-in event, users are logged out. Diagnose it and fix it.
Scale-in removed instances that held the only copy of some sessions, so sticky routing sent users to sessions that no longer existed. Move session state to a shared store, or use suitable client-held tokens, so any ready instance can serve the next request. The cost is a shared store on the request path that must itself be available.
A team runs a database in Kubernetes with a StatefulSet. A reviewer suggests a managed external database instead. When is each right?
An external managed database is usually the better default: the provider handles backups, replication and patching, and the cluster stays stateless. A StatefulSet, or an Operator that encodes operational knowledge, is right when the store must run in the cluster for control or portability, and the team accepts operating it.
A teammate says 'we're on containers, so our servers are cattle now.' What would show whether that is true?
Pets versus cattle is an operating model, not a technology. Check whether any instance can be deleted and recreated from automation without losing data or needing someone to fix it by hand. Containers that are patched in place or hold unique local state are still pets. Disposable VMs can be cattle.

The 12-factor app

The twelve practices that make a service suitable for cloud deployment.

  • The 12 factors: codebase (one tracked codebase, many deploys), dependencies (declared and packaged), config (in the environment), backing services (attached resources via URL), build/release/run (strictly separate stages), processes (stateless), port binding (self-contained service), concurrency (scale out via processes), disposability (fast start, graceful stop), dev/prod parity, logs (event streams), admin processes (one-off tasks).
  • Separate build, release and run. Build one immutable artifact; combine it with environment-specific configuration to form a release; then execute that release. Promoting the same tested artifact reduces drift. A rollback also needs compatible configuration and data/schema state.
  • Stateless shared-nothing processes, scale-out concurrency and disposability work as a set: processes that hold no local state can be duplicated freely, and fast startup with graceful shutdown lets the platform add, remove and replace them at will.
  • Backing services are configured dependencies. External addresses let deployments select compatible databases, queues or mail services without rebuilding. A different protocol or data model can still require code changes. Stream logs to central storage because local files vanish with disposable instances; keep dev and prod sufficiently alike to expose integration problems.
12-factor app
Methodology of twelve practices for building portable, scalable services suited to cloud platforms.
Backing service
Any external resource (DB, queue, mail server) consumed over the network, attached via URL/config.
Shared-nothing
Processes keep no shared local state, so any can be added or removed freely.
Dev/prod parity
Keeping all environments as similar as possible to avoid late surprises.

Check yourself

A team rebuilds the image separately for test and for production with different config baked in. Which factors does this break, and what is the risk?
It breaks build/release/run separation and config in the environment. The production artifact is not the one that was tested, so builds can drift through dependency or build differences. Build one immutable artifact, combine it with environment config at release, and promote the same artifact. A rollback still needs compatible config and schema state.
An autoscaler adds instances during a spike, but each takes 3 minutes to start and loses in-flight work when removed. Which factors are failing, and why do they matter together?
Disposability (fast start, graceful stop) and probably stateless processes. Concurrency through scale-out only works if the platform can add and remove processes freely; slow starts mean capacity arrives after the spike, and abrupt stops lose work. Speed up startup, handle termination signals to finish or hand back work, and keep state in backing services.
After an incident, engineers can't find the logs because the failed containers were already replaced. Which factor was ignored, and what is the fix?
Logs as event streams. Instances are disposable, so local log files vanish with them. Write logs to stdout as a stream and have the platform ship them to a central aggregator that can be searched across all instances. The cost is running or paying for the log pipeline and its storage.

Packaging, config and orchestration

Follows an app from code to a Kubernetes pod, covering the Kubernetes control plane, externalised configuration, the service mesh and application packages.

  • Code to cluster is a chain of runtimes: built application (language runtime), container image (container runtime), pod (Kubernetes cluster). Orchestration, unlike running a container on one machine, spreads workloads across a cluster of nodes.
  • Kubernetes is declarative. You write a manifest (apiVersion, kind, metadata, spec) stating the desired state, and the control plane (scheduling, scaling, self-healing) continuously reconciles reality to it, running pods on worker nodes.
  • Externalise configuration so one artifact serves several environments. Environment variables or mounted external configuration avoid baking deploy-specific values into the image. Source secrets from protected storage with restricted access; environment variables alone do not make a secret secure.
  • Service mesh vs API gateway: both have a control plane and a data plane, but a gateway fronts external clients while the mesh manages service-to-service traffic (routing, resilience, observability, security) without changing service code.
  • An application package is language-specific (program, same-language libraries, config), whereas a container image bundles the runtime environment too.
Pod
Smallest deployable unit in Kubernetes; one or more containers scheduled together on a node.
Control plane
Management layer that schedules, scales and heals workloads (Kubernetes) or configures proxies (service mesh).
Manifest
Declarative file (apiVersion, kind, metadata, spec) describing the desired state of a Kubernetes object.
Service mesh
Pattern managing service-to-service communication: routing, resilience, observability, security.
External configuration
Settings kept outside the artifact, typically as environment variables.

Check yourself

A team puts its database password in an environment variable and calls it 'secure because it's not in the code'. Do you agree?
Not fully. Externalising config is right, because one artifact then serves several environments, but an environment variable alone doesn't protect a secret: it can leak through logs, dumps or anyone with access to the deployment spec. Source it from protected secret storage with restricted access and inject it at runtime.
Someone deletes a pod by mistake and it comes back a few seconds later. Explain why, and say what this means for how you change production.
The manifest declares a desired state (for example 3 replicas), and the control plane continuously reconciles the cluster to it, so it recreated the pod. Change production by changing the declared state, not by editing live resources, because reconciliation will undo manual fixes. This is also what gives self-healing.
A platform has 25 internal services with inconsistent retry and encryption behaviour, plus a public mobile API. Where do an API gateway and a service mesh each fit?
The gateway is the entry point for the mobile clients' external traffic (routing, authentication, rate limits). The mesh manages the 25 services' internal traffic, adding consistent routing, resilience, observability and encryption without changing service code. Both have a control plane and a data plane. The mesh adds operating cost, which is justified here by the inconsistency across 25 services.

Maturity, traditional vs cloud native, summary

A cloud native maturity model, a microservice retail example, traditional vs cloud native comparison, key attributes and design axes.

  • Cloud native maturity ladder: Cloud Ready (no permanent disk access, self-contained, platform-managed ports and backing services), Cloud Friendly (12-factor, horizontally scalable, uses platform HA), Cloud Resilient (fault tolerant, cloud-agnostic runtime, bundled metrics, proactive failure testing), Cloud Native (microservices, API-first).
  • The lecture contrasts typical operating approaches: long release cycles and server-centric capacity planning versus frequent automated delivery and disposable, horizontally scaled services. These are tendencies, not rules: monoliths and VMs can also use DevOps and autoscaling.
  • What a cloud native app is like: predictable, OS-abstracted, right-sized, collaborative, continuously delivered, independent (small services), automatically scalable and quick to recover. Together this means microservices, loose coupling, resilience, agility, automation, self-healing and a DevOps culture.
  • A typical microservice retail example has clients calling an API gateway that fronts small services (search, cart, checkout, payments), some with their own databases, integrating with back-end systems.
  • Design axes: cloud native services (building blocks, managed, advanced managed), application-centric design (12-factor, microservices, other aspects) and automation (deploy/config, monitoring/compliance/optimisation, AI/ML prediction).
Cloud Native Maturity Model
Four levels: Cloud Ready, Cloud Friendly, Cloud Resilient, Cloud Native.
API gateway
Single entry point that routes client requests to back-end microservices.
API-first design
Designing the service's API contract first so services integrate through well-defined APIs.
Horizontal scaling
Adding more instances rather than making one machine bigger (vertical scaling).

Check yourself

A legacy app has been containerised but still writes to local disk and uses sticky sessions. Where is it on the maturity model, and what is the next step?
Not yet Cloud Ready, which requires no permanent disk access and a self-contained app using platform-managed backing services. Move files and sessions to backing services first. Then adopt the 12 factors and horizontal scaling to reach Cloud Friendly. Containerising alone doesn't move it up the ladder.
An app is 12-factor and scales horizontally on platform HA, and a team wants to call it 'cloud native'. What would it still need?
That is Cloud Friendly. Cloud Resilient adds fault tolerance, a cloud-agnostic runtime, bundled metrics and proactive failure testing. Cloud Native adds microservices and API-first design. Whether to go further depends on whether the business needs independent deployability and resilience that justify the cost.
A company adopted containers and microservices but kept separate dev and ops teams with handoffs, and releases are still slow. Why?
Short continuous delivery and fast recovery need collaborating teams and automation as well as the technical properties. Handoffs between silos keep the release cycle long, whatever the architecture. Pair the architecture with DevOps practices and shared ownership, or the speed-to-market benefit won't appear.

Design space, characteristics and guidelines

Levels of design abstraction, the characteristics to weigh when choosing a cloud, and guidelines for separation of concerns.

  • Choosing a cloud is a multi-criteria decision. Start with the goal (productivity, ease of migration, or control), then weigh integration, data storage and location, ecosystem and portfolio, pricing model (fixed vs use-based), QoS (availability, DR, SLA), security and privacy, self-service, elasticity and vendor viability.
  • Legacy migration vs new build weights these differently: migration favours backward compatibility, internal-network integration and data location; a new product favours productivity, elasticity, use-based pricing and a rich managed-service portfolio.
  • Separation of concerns keeps business rules portable: independent of frameworks, UI, database and external agencies, and testable without them. Code should be organised around the business problem rather than generic folders.
  • Design thinking spans levels of abstraction, from technologies and mechanisms through idioms and patterns up to architecture.
Separation of concerns
Keeping business rules isolated from UI, database, frameworks and external systems so each can change independently.
Vendor viability
The provider's commitment to cloud and ability to execute as a business.

Check yourself

Business rules for loan approval call the database driver and the web framework directly. The team now wants to change databases and unit-test the rules. What is the problem, and what would you change?
The rules are coupled to the database and framework, so changing either means rewriting logic, and tests need a real database. Separate concerns: put the rules in code that is independent of frameworks, UI, database and external agencies, and reach the database through an interface. The cost is an extra layer of abstraction.
Two projects are choosing a cloud: migrating a legacy enterprise app with on-premises integrations, and building a new consumer product. Which characteristics should weigh most for each?
The legacy migration should weigh ease of migration, backward compatibility, integration with the internal network and data location most. The new product should weigh productivity, elasticity, use-based pricing and a rich managed-service portfolio. The same provider can win for one project and lose for the other, so start from each project's goal.

Design considerations: scalability to feasibility

Checklists of questions an architect should answer on scalability, availability, security, manageability and feasibility.

  • Scalability: ask which layers must scale, how fast, and whether you can scale down off-hours; check persistence limits and partition data. Prefer many small instances over few large ones, and level load with queues (producer and competing consumers), async operations and load balancers.
  • Availability and DR: identify dependencies required for each request. For independent services in series, multiply availability probabilities as an estimate; common failures and redundancy change the result. Design failover, replication, bounded retries and circuit breakers. Backups protect against corruption as well as outages; test restoration and idempotent replay.
  • Security: where data legally resides (including failover and metrics copies), federated identity, secured hybrid links, admin-portal and database access control, credential rotation, multitenancy effects and patching.
  • Manageability: monitor with usable, compliant storage of metrics and logs, distinguish auditing from logging, and adjust levels at runtime. Deployment should be automated, verifiable, reversible and non-disruptive, with a deliberate number of environments.
  • Feasibility: can any provider meet the SLAs, do you have the skills, budget and time, what are the operating costs, and what can be reduced (scope, SLAs, resilience) as an accepted trade-off.
Composite SLA
End-to-end availability depends on the dependency structure; independent required services in series have multiplied availability probabilities.
Competing consumer pattern
Multiple consumers read from one queue so work is spread and load is levelled.
Circuit breaker
Pattern that stops calling a failing service for a while to avoid cascading failure and overload.
Idempotent
An operation that can be repeated (e.g. a replayed message) without changing the result beyond the first time.

Check yourself

A checkout request needs an API service, a payment service and a database in series, each at 99.9% availability. A manager promises 99.9% end-to-end. Is that realistic?
No. For independent components in series, availability multiplies: 0.999 × 0.999 × 0.999 ≈ 99.7%, so the path is less available than any single part. This is an estimate, since shared failure modes and redundancy change it. To reach 99.9%, add redundancy or failover on the critical path, or reduce dependencies the request needs.
Order submissions spike tenfold at sale start, and the order processor falls over. How do queues help, and what must the consumers guarantee?
Put a queue between submission and processing so producers aren't blocked, the backlog levels the peak, and competing consumers scale out to drain it. If a consumer fails, the message is delivered again, so processing must be idempotent to avoid duplicate orders. Users now get 'accepted' rather than 'completed' immediately.
The primary database is replicated to a second region, so the team drops nightly backups. What risk does this create?
Replication copies an accidental delete or a corrupting update to every replica, so there's nothing earlier to recover. Backups keep recoverable earlier states. Keep backups, test restores against acceptable data loss and recovery time, and make replay idempotent.
Customer data must stay in Singapore. The app's database is in Singapore, but failover is to another country's region and metrics go to a global monitoring service. Is the design compliant?
Probably not. Data protection rules apply to every copy, including failover replicas and any customer data inside metrics or logs. Choose an in-country failover location, or confirm the rules allow it, and scrub personal data from telemetry or keep it in-region. The cost may be weaker DR options.

Exam-style questions

Answer aloud or on paper before opening.

A retailer's monolithic web shop loses customers' carts whenever a server crashes and can't cope with sale-day spikes of 20 times normal traffic. Diagnose the causes and propose a cloud native redesign, naming one new risk it introduces.
The diagnosis: sticky sessions and in-memory carts make servers pets, and the single scaling unit can't grow fast enough. Make the web tier stateless with carts in a shared store or managed database, split hot areas such as checkout into services behind an API gateway, run them as containers with horizontal autoscaling, and put order processing behind a queue to level peaks. Apply 12-factor practices and CI/CD. The new risks are distributed failures and eventual consistency between services, so add observability, timeouts and idempotent consumers.
Audit this service against the 12 factors: config is baked into images per environment, logs go to local files, the service takes 4 minutes to start, it writes uploads to local disk, and a database migration runs at every container start. Rank the gaps by operational risk and give the fix for each.
Highest risk: uploads on local disk (breaks stateless processes, so data is lost when instances are replaced); move them to object storage. Next, per-environment images (breaks build/release/run and config), meaning the tested artifact isn't the one deployed; build once and inject config at release, with secrets from protected storage. Then the 4-minute start (disposability), which defeats autoscaling. Then the migration at startup, which should be a one-off admin process to avoid concurrent migrations. Finally local logs, which vanish; stream them to an aggregator.
You must offer 99.95% availability for a service whose request path uses a gateway, a compute tier and a managed database, each with a 99.9% SLA. Explain why the target is at risk and propose design changes, with the cost of each.
In series, 0.999³ ≈ 99.7%, below the target, and provider SLAs alone can't guarantee the end-to-end figure. Add redundancy on the path: compute across zones behind health-checked load balancing, a database with a synchronous standby, and possibly a second region for the most critical path. Remove dependencies from the synchronous path using queues and caches. Bound retries and use circuit breakers so one slow dependency doesn't cascade. Each step adds cost and complexity, so check feasibility: if the budget or skills can't support it, renegotiate the SLA.
A bank's 20-year-old core app is released twice a year, runs on large VMs sized for peak, and is owned by separate dev and ops teams. A new digital-banking team wants weekly releases. Contrast the traditional and cloud-native approaches for each part, and say whether the core app should be converted.
Traditional: long release cycles, siloed teams, a tightly coupled monolith and server-centric vertical capacity pre-provisioned for peak. Cloud native: continuous delivery, DevOps teams, loosely coupled API-based services, and disposable, horizontally scaled containers. The digital team should build cloud native. The core app doesn't need to convert all at once: expose it through APIs and modernise where business drivers justify it, because these are tendencies and the core app can adopt automation and DevOps without a rewrite.
You run 30 microservices on Kubernetes across dev, test and prod. Secrets are in plain manifests, retries differ per team, and an outage last month cascaded through internal calls. Propose how to manage configuration, secrets and service-to-service traffic.
Keep ordinary config outside the image and per environment, so the same artifact is promoted through all three. Move secrets to protected secret storage with restricted access and inject them at runtime, because plain manifests or environment variables alone aren't protection. Declare everything in version-controlled manifests so the control plane reconciles drift. With 30 services and a cascading outage, a service mesh is justified for consistent timeouts, bounded retries, circuit breaking, encryption and tracing without code changes, with an API gateway for external traffic. The mesh adds operational overhead and latency to manage.
