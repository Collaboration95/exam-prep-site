Day 3 mock questions

Do these after all of today's topics. Give your choice, reason and trade-off before opening an answer.

Whole day

A 'microservices' system ships all 12 services in one container image, and every change needs a joint release. What would you change in its design and its Kubernetes deployment?
Find cohesive business boundaries and give each service stable contracts and private data ownership. Build a versioned image and a Deployment per service, with a Service for stable discovery and an Ingress or gateway for external routes. Kubernetes replicas only run more copies, so release coupling has to be removed in the application design and in each service's own pipeline.
An order platform on managed Kubernetes calls Payment, Inventory and Email synchronously. During a sale, Email slows down and checkout fails. Give the cause, a countermeasure and its drawback, and say whether a service mesh or managed messaging would help.
The cause is synchronous calls to a non-critical dependency: blocked threads in checkout spread Email's slowness. Publish an 'order placed' event to a managed queue or topic so Email processes asynchronously, keep a time-bounded synchronous call only to Payment, and add circuit breakers. The drawback is eventual consistency and the need for idempotent consumers. A mesh helps apply timeouts and breakers uniformly, but managed messaging is what removes the dependency from the checkout path.
A media company runs its upload API on Kubernetes, and a teammate wants to move the thumbnail generation (bursty, a few seconds per image) to functions and the video catalogue to a managed NoSQL database. Do you agree? Explain the knock-on effects.
Mostly yes. Bursty, short, event-triggered thumbnail work fits functions, which scale with uploads and cost nothing when idle, and the catalogue's flexible, keyed reads fit a document or key-value store. The knock-on effects: functions bring execution limits and cold starts, and can overwhelm downstream stores, so writes need to be idempotent. The managed database moves operations to the provider but adds lock-in through its API, and cross-entity queries become harder. Keep the always-on upload API on Kubernetes.

Kubernetes: A Simple Introduction

A retailer's monolith has outages during sales peaks that are 15 times normal traffic. Propose a Kubernetes-based design, justify the main objects you would use, and say what Kubernetes will not solve for you.
Split the parts that peak, such as catalogue and checkout, into Deployments with several ready replicas spread across zones, Services for stable discovery, and an Ingress with an installed controller for external HTTP routing. Add autoscaling with metrics, resource requests and node headroom. Externalise state to a managed database and shared cache, and use readiness probes, graceful shutdown and rolling updates for deployments. Kubernetes won't supply the database, queue or monitoring stack, won't guarantee zero downtime without spare capacity, and won't fix a data tier that can't take the peak.
A new node joins a cluster and someone deletes a pod by accident at the same moment. Explain, component by component, how the control plane and nodes return the system to its desired state, and which single component's loss would be most serious.
The API server is the only entry point and records changes in etcd. The controller manager sees fewer replicas than declared and creates a replacement pod object. The scheduler places it on a node with capacity, possibly the new one. That node's kubelet starts it through the container runtime, and kube-proxy updates Service routing so traffic reaches it. Losing etcd would be most serious, because it holds all desired and current state, so it should be replicated and backed up.
Design the external access path for three web microservices (/products, /orders, /payments) under one domain. Explain the role of each object, and say what changes if /payments must be reachable only from the orders service internally.
Create a Deployment and a Service for each microservice, with selectors that match the pod labels, and one Ingress with path rules routing to the three Services, implemented by an installed Ingress controller. Services give stable backends, and the controller handles external HTTP routing. If /payments must be internal only, remove it from the Ingress, keep its Service internal, and add a NetworkPolicy that allows traffic only from the orders pods.
An organisation is choosing between a local single-node cluster, self-managed Kubernetes and a managed Kubernetes service for development and production of 20 services, with a 5-person platform team. Recommend a setup for each environment and justify it.
Use a local single-node cluster for developer learning and testing only. For production, use managed Kubernetes: the provider runs selected platform components such as the control plane, so the small team avoids upgrades and control-plane recovery. Self-managed would give more control but leave all cluster operations to 5 people. Check the provider's responsibility boundary, since worker capacity, workload security and application availability still need design, and plan multiple zones for production.
A team's Kubernetes design keeps database credentials in a ConfigMap, runs its database as a single pod with data on the container filesystem, and puts every team in one Namespace with no quotas. Critique the design and give corrected choices.
Credentials in a ConfigMap aren't protected, so move them to Secrets with access and encryption controls, or to an external secret store. A database writing to its container filesystem loses data when the pod is replaced, so use a StatefulSet with PVCs, or preferably a managed database. One shared Namespace without quotas gives no governance, so give each team its own Namespace with RBAC, ResourceQuotas and NetworkPolicies. Keep services stateless so they scale as Deployments, and use one image per release with config injected per environment.

Vendor Managed Services

Map a cloud-native e-commerce architecture (product browsing, carts, orders, product images, order processing, notifications) onto categories of managed services on one provider, justifying each, and name the decision that most increases lock-in.
Managed DNS and a load balancer with a WAF at the edge. Managed Kubernetes for the long-running services and FaaS for event handlers such as image resizing. A managed relational database for orders (ACID) and a NoSQL store for carts and sessions. Object storage with a CDN for images. A queue for order processing and pub/sub for notifications. Add monitoring, IaC, identity management and key management so operations and security are built in. The biggest lock-in usually comes from proprietary data and messaging services, because data and semantics don't move as easily as container images.
A company plans to run on three major providers 'for portability'. Using the idea of overlapping building blocks, assess what will be portable and what will not, and recommend whether to proceed.
Compare by capability categories such as managed Kubernetes, object storage and messaging, then check each service's semantics, regions and limits. Containers on Kubernetes keep packaging and orchestration portable. Data, identity, networking and proprietary managed-service APIs are not portable and need separate migration and integration work. Proceed only if a concrete benefit (regulation, resilience against a provider, a best-of-breed service) outweighs the cost of tripled skills and operations. Otherwise use one provider with an exit strategy.
A team must choose storage for VM boot disks, a database's data files, shared engineering files mounted by 20 VMs, and 5 years of backup archives. Recommend a type for each, and say what happens if the team puts everything on block storage to keep things simple.
Block storage for boot disks and database files, for low-latency attached volumes. File storage for the shared engineering files, since many VMs must mount them. Object storage for the backup archives, because it is cheap and durable at scale. With everything on block storage, the shared files can't easily be mounted by 20 VMs, and archives would cost much more than on object storage.
A CTO says: 'Use managed services everywhere, so availability and security are the provider's job.' Argue for and against, and state what remains the team's responsibility.
For: managed services offload patching, scaling, backups and much availability work, so teams can spend their effort on business code. Against: they increase lock-in through proprietary APIs, can cost more at scale, and tie you to the provider's SLA, which doesn't by itself meet an application SLA. The team still chooses capacity and availability options such as multi-zone placement, configures identity, permissions, encryption and retention, designs idempotent messaging, and tests recovery. Limit lock-in with open standards where it matters and keep an exit strategy.

Application Architecture Styles (Archetypes)

A bank wants to modernise a 15-year-old monolithic loan system used by 300 branches while continuing to issue loans every day. Propose a target style and a migration approach, and name the two biggest trade-offs.
Target microservices split by business capability (application, credit check, disbursement, notification), each owning its data, with hexagonal design inside services for testability and events between them for loose coupling. Migrate incrementally with a strangler approach, routing one capability at a time to new services, rather than a big-bang rewrite that would stop loan issuance. The trade-offs are distributed-system problems (latency, partial failures, consistency across stores) and operational overhead, so invest in observability and platform automation before the number of services grows.
Design a data architecture for a ride-hailing company that needs surge pricing within 5 seconds of demand changes and nightly retraining on 3 years of trips. Justify Lambda or Kappa, and say what would change your choice.
Lambda: a speed layer processes the trip-event stream for near-real-time surge prices, a batch layer holds full history and retrains models nightly, and a serving layer merges the results. Batch remains the accurate source of truth. The cost is two pipelines with logic that must stay consistent. Choose Kappa instead if reprocessing can be done by replaying the stream within the nightly window, which trades the second pipeline for harder stateful stream processing. Event-driven ingestion keeps producers decoupled either way.
A government services app must reach all citizens, including those on old phones. It needs form-filling that survives a dropped connection, and a later phase adds reading ID cards over NFC at kiosks. Native or PWA? Give the design implications for the backend services.
Start with a PWA: broad reach, no install barrier, one codebase and instant updates suit a citizen service. Design offline form drafts with local storage and sync. For the NFC kiosks, use a native or cross-platform native kiosk app, because hardware access through browsers varies, and the kiosks are controlled devices. Backend implications: APIs must accept delayed, batched submissions idempotently and handle conflicts, a separate backend for each experience (BFF) may serve web and kiosk clients, and API versioning is needed for installed kiosk apps.
An e-commerce site handles normal traffic but fails on Black Friday at 12 times the load: the database's write capacity is exhausted and checkout slows everything else. Apply the AKF scale cube to the problem and name a side effect of each change.
x axis: add load-balanced clones of the stateless web tier, plus read replicas; side effect: replica lag gives stale reads. y axis: split checkout into its own service and store so it scales and fails independently; side effect: cross-service consistency for orders and inventory. z axis: shard orders by customer or region to spread writes, which is the fix for exhausted write capacity; side effect: cross-shard queries and reporting become harder. Add a queue in front of order processing to level the peak.
A global SaaS needs sub-100 ms response for login and personalisation worldwide, must keep EU data in the EU, and had an outage last year where one bad deploy hit every tenant. Which modern archetypes would you combine, and what are their costs?
Cells per region and tenant group bound the blast radius and keep EU tenants' data in EU cells, with releases rolled out cell by cell. Edge-native functions handle authentication checks and personalisation near users, with the origin remaining the system of record. A platform with GitOps operates N cells consistently. The costs are duplicated infrastructure, a critical cell router, hard cross-cell reporting, eventual consistency and limited runtimes at the edge, and the investment in platform automation.
A new product will have 3 developers at launch, sporadic traffic from 0 to 2,000 requests a minute, and a plan to grow to 6 teams in 2 years. Compare monolith, microservices and serverless, and recommend a path.
A modular monolith minimises deployment and network complexity for 3 developers but scales as one unit. Microservices give independent scaling and releases but bring partial failures, data coordination and operational overhead the team can't afford yet. Serverless suits the sporadic load and costs little when idle, but brings cold starts, runtime limits and lock-in. Recommend a modular monolith, or a few functions with a hexagonal core for the spiky parts, with clear module boundaries so services can be extracted as the 6 teams arrive.

Microservices Design

A retailer's monolithic e-commerce app slows down at sale peaks (search traffic rises 10 times, checkout 3 times), and releases take 6 weeks because 5 teams share one deployable. Propose a microservices design and an incremental migration plan, and name the main risk at each stage.
Decompose by business capability: Catalog/Search, Cart, Order, Inventory, Payment. Assign operations and define APIs, giving each service its own data, behind an API gateway with service discovery. Extract Search first: it has the biggest load difference, it is read-heavy and its data can be copied. Then extract Cart and Order. Risks: at first, data synchronisation between the new Search store and the monolith; later, consistency between Order, Inventory and Payment without distributed transactions. Independent deployment through CI/CD addresses the 6-week release cycle, but only if teams are reorganised around services.
A 6-person team with manual deployments, infrastructure-only monitoring and a moderately complex internal app is told to 'go microservices'. Argue whether they should, using the microservice premium and the maturity model, and say what would change your answer.
They shouldn't yet. The microservice premium (operations, monitoring, versioning, network latency, troubleshooting) pays off only when a system is too complex to manage as a monolith, and a moderately complex app for 6 people is unlikely to qualify. Low maturity on process and monitoring makes it worse, because they couldn't diagnose distributed failures. Build a modular monolith and raise DevOps maturity. Reconsider if the team grows, parts need very different scaling or availability, or release coordination becomes the bottleneck.
Design the communication between Order, Payment, Inventory and Notification services for a shop that must confirm payment to the user within 3 seconds and must never charge twice. Justify each synchronous or asynchronous choice.
Order calls Payment synchronously with a time limit under the 3-second budget, because the user needs the outcome, and passes an idempotency key so a retry never charges twice. After payment, Order publishes an 'order paid' event to a durable topic: Inventory reserves stock and Notification sends email asynchronously, so their outages don't fail checkout. Persist order and payment state and handle duplicate events in consumers. If inventory later fails, compensate by refunding or back-ordering instead of using a distributed transaction. gRPC can carry the internal calls.
A system has 40 services, a mobile app and a web app. Explain the roles of an API gateway, a service registry and a service mesh, say which traffic each handles, and say which you could do without if the platform is Kubernetes.
The gateway handles north-south traffic from the mobile and web apps: routing, composition, security, throttling, protocol translation and monitoring. It can be tailored per client type. The registry records where service instances live, for client-side or server-side discovery. The mesh manages east-west traffic between the 40 services: retries, encryption and telemetry. On Kubernetes, the platform's Services and DNS already provide discovery, so a separate registry is often unnecessary. The mesh is justified at 40 services if uniform policy is needed, at the cost of extra hops and a control plane.
A public pricing API is used by 200 external clients. The team must rename a field, add an optional discount field and fix a rounding bug. Plan the version numbers and the rollout so no client breaks.
Rounding fix: PATCH. Optional discount field: MINOR, provided omitting it keeps the old meaning and clients ignore unknown response fields, which should be tested with consumer contracts. Renaming a field is incompatible: MAJOR. Run V1 and V2 side by side, route by version at the gateway, document both contracts with OpenAPI, and retire V1 only after the 200 clients have migrated, tracked through gateway metrics. The cost is supporting two versions for the migration period.

What the Instructor Emphasised in Day 3: Kubernetes, Toolchains and Architecture Styles

Decompose a Netflix-like streaming platform into a cloud-native architecture: identify services and data stores, how viewing events reach recommendations, how it is deployed, and how it scales on each axis.
Services: search, profile, catalogue, recommendations and playback, each with a fitting store (search index, relational or key-value, document, precomputed fast reads, and key-value for resume position). Viewing events flow through a stream into recommendation processing, Kappa-style. Run stateless services as Kubernetes Deployments behind Services and an API gateway, using tokens or shared session state so any replica can serve. Scale by replication (more replicas), functional decomposition (hot services such as playback scale alone) and partitioning (shard user data by user ID). The costs are eventual consistency in recommendations and more services to operate.
Modernise a traditional web app that uses server-side sessions in memory, SOAP services, an ESB for workflows and a relational database. Decide what to keep, what to change and why.
Keep the relational database for transactional data and keep cookies, but move sessions to a shared store or tokens so replicas are replaceable. Expose SOAP functions through an API gateway with REST, rewriting services only where change justifies it. Move ESB workflows toward events or lightweight orchestration one flow at a time. Add observability and automated delivery (CI/CD or GitOps) first, because they make every later change safer. Don't swap in a vector store or agents unless a requirement calls for them.
Explain how Kubernetes provides high availability for both the control plane and the applications, and say why a large replica count alone doesn't guarantee availability to users.
Control plane: replicate API servers behind a load balancer, run controllers and schedulers with leader election, and keep etcd with quorum across failure domains. Applications: run ready replicas spread across zones, with health probes so kubelet restarts failed containers and controllers replace lost Pods, and persistent data with its own replication and recovery. Replica count alone doesn't help if replicas share one zone, lack capacity headroom, depend on a single database, or fail readiness together, so availability must be designed end to end.
A new product will start with one team and modest load but expects to grow. Choose between a singular and a distributed architecture, and explain how you would leave room to evolve.
Choose a singular, modular architecture: simplicity and low latency outweigh independent scaling at this size. Keep clear internal boundaries by business capability, make it stateless and containerised so replication works from day one, and keep data ownership per module so the parts can later be split into microliths or microservices. Real systems end up hybrid, so plan the first split around the module most likely to need independent scaling.
