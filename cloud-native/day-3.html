Day 3 mock questions

Do these after all of today's topics. Give your choice, reason and trade-off before opening an answer.

Whole day

A 'microservices' system ships all 12 services in one container image, and every change needs a joint release. What would you change in its design and its Kubernetes deployment?
  • Design
    • Find cohesive business boundaries
    • Give each service stable contracts and private data ownership
  • Kubernetes deployment
    • A versioned image and a Deployment per service
    • A Service for stable discovery
    • An Ingress or gateway for external routes

Kubernetes replicas only run more copies → release coupling must be removed in the application design and in each service's own pipeline.

An order platform on managed Kubernetes calls Payment, Inventory and Email synchronously. During a sale, Email slows down and checkout fails. Give the cause, a countermeasure and its drawback, and say whether a service mesh or managed messaging would help.
  • Cause: synchronous calls to a non-critical dependency → blocked threads in checkout spread Email's slowness
  • Countermeasure
    • Publish an 'order placed' event to a managed queue or topic → Email processes asynchronously
    • Keep a time-bounded synchronous call only to Payment
    • Add circuit breakers
  • Drawback: eventual consistency and the need for idempotent consumers
  • Mesh vs messaging
    • A service mesh helps apply timeouts and breakers uniformly
    • Managed messaging is what removes the dependency from the checkout path
A media company runs its upload API on Kubernetes, and a teammate wants to move the thumbnail generation (bursty, a few seconds per image) to functions and the video catalogue to a managed NoSQL database. Do you agree? Explain the knock-on effects.

Mostly yes. Keep the always-on upload API on Kubernetes.

  • Thumbnails → functions: bursty, short, event-triggered work; scale with uploads, cost nothing when idle
  • Catalogue → document or key-value store: fits its flexible, keyed reads
  • Knock-on effects
    • Functions: execution limits and cold starts; can overwhelm downstream stores → writes must be idempotent
    • Managed database: moves operations to the provider, but adds lock-in through its API
    • Cross-entity queries become harder

Kubernetes: A Simple Introduction

A retailer's monolith has outages during sales peaks that are 15 times normal traffic. Propose a Kubernetes-based design, justify the main objects you would use, and say what Kubernetes will not solve for you.
  • Split the parts that peak, such as catalogue and checkout
    • Deployments with several ready replicas spread across zones
    • Services for stable discovery
    • An Ingress with an installed controller for external HTTP routing
  • Autoscaling with metrics, resource requests and node headroom
  • Externalise state to a managed database and shared cache
  • Readiness probes, graceful shutdown and rolling updates for deployments
  • Kubernetes won't
    • Supply the database, queue or monitoring stack
    • Guarantee zero downtime without spare capacity
    • Fix a data tier that can't take the peak
A new node joins a cluster and someone deletes a pod by accident at the same moment. Explain, component by component, how the control plane and nodes return the system to its desired state, and which single component's loss would be most serious.
  1. API server: the only entry point; records changes in etcd
  2. Controller manager: sees fewer replicas than declared → creates a replacement pod object
  3. Scheduler: places it on a node with capacity, possibly the new one
  4. kubelet on that node: starts it through the container runtime
  5. kube-proxy: updates Service routing so traffic reaches it

Most serious loss: etcd → it holds all desired and current state, so it should be replicated and backed up.

Design the external access path for three web microservices (/products, /orders, /payments) under one domain. Explain the role of each object, and say what changes if /payments must be reachable only from the orders service internally.
  • Per microservice: a Deployment and a Service, with selectors that match the pod labels → Services give stable backends
  • One Ingress with path rules routing to the three Services
  • An installed Ingress controller implements it and handles external HTTP routing
  • If /payments must be internal only
    • Remove it from the Ingress
    • Keep its Service internal
    • Add a NetworkPolicy that allows traffic only from the orders pods
An organisation is choosing between a local single-node cluster, self-managed Kubernetes and a managed Kubernetes service for development and production of 20 services, with a 5-person platform team. Recommend a setup for each environment and justify it.
  • Local single-node cluster → developer learning and testing only
  • Production → managed Kubernetes
    • The provider runs selected platform components such as the control plane → the small team avoids upgrades and control-plane recovery
    • Self-managed would give more control but leave all cluster operations to 5 people
    • Plan multiple zones for production
  • Check the provider's responsibility boundary: worker capacity, workload security and application availability still need design
A team's Kubernetes design keeps database credentials in a ConfigMap, runs its database as a single pod with data on the container filesystem, and puts every team in one Namespace with no quotas. Critique the design and give corrected choices.
  • Credentials in a ConfigMap aren't protected → move them to Secrets with access and encryption controls, or to an external secret store
  • Database writing to its container filesystem → loses data when the pod is replaced → a StatefulSet with PVCs, or preferably a managed database
  • One shared Namespace without quotas → no governance → give each team its own Namespace with RBAC, ResourceQuotas and NetworkPolicies
  • Keep services stateless → they scale as Deployments
  • One image per release with config injected per environment

Vendor Managed Services

Map a cloud-native e-commerce architecture (product browsing, carts, orders, product images, order processing, notifications) onto categories of managed services on one provider, justifying each, and name the decision that most increases lock-in.
  • Edge → managed DNS and a load balancer with a WAF
  • Compute → managed Kubernetes for the long-running services; FaaS for event handlers such as image resizing
  • Data → a managed relational database for orders (ACID); a NoSQL store for carts and sessions
  • Images → object storage with a CDN
  • Messaging → a queue for order processing; pub/sub for notifications
  • Operations and security → add monitoring, IaC, identity management and key management so they are built in

Biggest lock-in: usually proprietary data and messaging services, because data and semantics don't move as easily as container images.

A company plans to run on three major providers 'for portability'. Using the idea of overlapping building blocks, assess what will be portable and what will not, and recommend whether to proceed.
  • Compare by capability categories such as managed Kubernetes, object storage and messaging, then check each service's semantics, regions and limits
  • Portable: containers on Kubernetes keep packaging and orchestration portable
  • Not portable: data, identity, networking and proprietary managed-service APIs → need separate migration and integration work

Proceed only if a concrete benefit (regulation, resilience against a provider, a best-of-breed service) outweighs the cost of tripled skills and operations; otherwise use one provider with an exit strategy.

A team must choose storage for VM boot disks, a database's data files, shared engineering files mounted by 20 VMs, and 5 years of backup archives. Recommend a type for each, and say what happens if the team puts everything on block storage to keep things simple.
  • Boot disks and database files → block storage: low-latency attached volumes
  • Shared engineering files → file storage: many VMs must mount them
  • Backup archives → object storage: cheap and durable at scale
  • Everything on block storage
    • The shared files can't easily be mounted by 20 VMs
    • Archives would cost much more than on object storage
A CTO says: 'Use managed services everywhere, so availability and security are the provider's job.' Argue for and against, and state what remains the team's responsibility.
  • For
    • Managed services offload patching, scaling, backups and much availability work
    • → teams spend their effort on business code
  • Against
    • Increase lock-in through proprietary APIs
    • Can cost more at scale
    • Tie you to the provider's SLA, which doesn't by itself meet an application SLA
  • Still the team's responsibility
    • The team chooses capacity and availability options such as multi-zone placement
    • Configures identity, permissions, encryption and retention
    • Design idempotent messaging
    • Test recovery

Limit lock-in with open standards where it matters and keep an exit strategy.

Application Architecture Styles (Archetypes)

A bank wants to modernise a 15-year-old monolithic loan system used by 300 branches while continuing to issue loans every day. Propose a target style and a migration approach, and name the two biggest trade-offs.
  1. Target style: microservices split by business capability
    • Application, credit check, disbursement, notification
    • Each owning its data
    • Hexagonal design inside services → testability
    • Events between them → loose coupling
  2. Migration: incremental, strangler approach
    • Route one capability at a time to new services
    • Not a big-bang rewrite, which would stop loan issuance
  3. Two biggest trade-offs
    • Distributed-system problems: latency, partial failures, consistency across stores
    • Operational overhead → invest in observability and platform automation before the number of services grows
Design a data architecture for a ride-hailing company that needs surge pricing within 5 seconds of demand changes and nightly retraining on 3 years of trips. Justify Lambda or Kappa, and say what would change your choice.

Lambda.

  • Speed layer: processes the trip-event stream → near-real-time surge prices
  • Batch layer: holds full history, retrains models nightly; remains the accurate source of truth
  • Serving layer: merges the results
  • Cost: two pipelines with logic that must stay consistent
  • What would change it → Kappa: if reprocessing can be done by replaying the stream within the nightly window; trades the second pipeline for harder stateful stream processing

Event-driven ingestion keeps producers decoupled either way.

A government services app must reach all citizens, including those on old phones. It needs form-filling that survives a dropped connection, and a later phase adds reading ID cards over NFC at kiosks. Native or PWA? Give the design implications for the backend services.

Start with a PWA; add a native kiosk app for the NFC phase.

  • PWA for citizens
    • Broad reach, no install barrier, one codebase, instant updates → suit a citizen service
    • Offline form drafts with local storage and sync
  • Native or cross-platform native kiosk app for NFC
    • Hardware access through browsers varies
    • The kiosks are controlled devices
  • Backend implications
    • APIs must accept delayed, batched submissions idempotently and handle conflicts
    • A separate backend for each experience (BFF) may serve web and kiosk clients
    • API versioning for installed kiosk apps
An e-commerce site handles normal traffic but fails on Black Friday at 12 times the load: the database's write capacity is exhausted and checkout slows everything else. Apply the AKF scale cube to the problem and name a side effect of each change.
  • x axis: load-balanced clones of the stateless web tier, plus read replicas
    • Side effect: replica lag → stale reads
  • y axis: split checkout into its own service and store → it scales and fails independently
    • Side effect: cross-service consistency for orders and inventory
  • z axis: shard orders by customer or region to spread writes → the fix for exhausted write capacity
    • Side effect: cross-shard queries and reporting become harder

Add a queue in front of order processing to level the peak.

A global SaaS needs sub-100 ms response for login and personalisation worldwide, must keep EU data in the EU, and had an outage last year where one bad deploy hit every tenant. Which modern archetypes would you combine, and what are their costs?
  • Cells per region and tenant group
    • Bound the blast radius
    • Keep EU tenants' data in EU cells
    • Releases rolled out cell by cell
  • Edge-native functions
    • Authentication checks and personalisation near users
    • The origin remains the system of record
  • Platform with GitOps → operates N cells consistently
  • Costs
    • Duplicated infrastructure
    • A critical cell router
    • Hard cross-cell reporting
    • Eventual consistency and limited runtimes at the edge
    • The investment in platform automation
A new product will have 3 developers at launch, sporadic traffic from 0 to 2,000 requests a minute, and a plan to grow to 6 teams in 2 years. Compare monolith, microservices and serverless, and recommend a path.

Recommend a modular monolith, or a few functions with a hexagonal core for the spiky parts.

  • Modular monolith: minimises deployment and network complexity for 3 developers, but scales as one unit
  • Microservices: independent scaling and releases, but bring partial failures, data coordination and operational overhead the team can't afford yet
  • Serverless: suits the sporadic load and costs little when idle, but brings cold starts, runtime limits and lock-in

Keep clear module boundaries so services can be extracted as the 6 teams arrive.

Microservices Design

A retailer's monolithic e-commerce app slows down at sale peaks (search traffic rises 10 times, checkout 3 times), and releases take 6 weeks because 5 teams share one deployable. Propose a microservices design and an incremental migration plan, and name the main risk at each stage.
  1. Design: decompose by business capability
    • Catalog/Search, Cart, Order, Inventory, Payment
    • Assign operations and define APIs; each service has its own data
    • Behind an API gateway with service discovery
  2. Incremental migration
    • Extract Search first: biggest load difference, read-heavy, and its data can be copied
    • Then extract Cart and Order
  3. Main risk per stage
    • At first: data synchronisation between the new Search store and the monolith
    • Later: consistency between Order, Inventory and Payment without distributed transactions

Independent deployment through CI/CD addresses the 6-week release cycle, but only if teams are reorganised around services.

A 6-person team with manual deployments, infrastructure-only monitoring and a moderately complex internal app is told to 'go microservices'. Argue whether they should, using the microservice premium and the maturity model, and say what would change your answer.

They shouldn't yet.

  • Microservice premium (operations, monitoring, versioning, network latency, troubleshooting) pays off only when a system is too complex to manage as a monolith
  • A moderately complex app for 6 people is unlikely to qualify
  • Maturity model: low maturity on process and monitoring makes it worse → they couldn't diagnose distributed failures
  • Instead: build a modular monolith and raise DevOps maturity

Reconsider if the team grows, parts need very different scaling or availability, or release coordination becomes the bottleneck.

Design the communication between Order, Payment, Inventory and Notification services for a shop that must confirm payment to the user within 3 seconds and must never charge twice. Justify each synchronous or asynchronous choice.
  • Order → Payment: synchronous
    • Time limit under the 3-second budget, because the user needs the outcome
    • Passes an idempotency key → a retry never charges twice
  • Order → Inventory, Notification: asynchronous
    • After payment, Order publishes an 'order paid' event to a durable topic
    • Inventory reserves stock; Notification sends email
    • → their outages don't fail checkout
  • Persist order and payment state; consumers handle duplicate events
  • If inventory later fails → compensate by refunding or back-ordering, not a distributed transaction
  • gRPC can carry the internal calls
A system has 40 services, a mobile app and a web app. Explain the roles of an API gateway, a service registry and a service mesh, say which traffic each handles, and say which you could do without if the platform is Kubernetes.
  • API gateway: north-south traffic from the mobile and web apps
    • Routing, composition, security, throttling, protocol translation, monitoring
    • Can be tailored per client type
  • Service registry: records where service instances live → for client-side or server-side discovery
  • Service mesh: east-west traffic between the 40 services
    • Retries, encryption, telemetry
  • On Kubernetes
    • The platform's Services and DNS already provide discovery → a separate registry is often unnecessary
    • The mesh is justified at 40 services if uniform policy is needed, at the cost of extra hops and a control plane
A public pricing API is used by 200 external clients. The team must rename a field, add an optional discount field and fix a rounding bug. Plan the version numbers and the rollout so no client breaks.
  • Rounding fix → PATCH
  • Optional discount field → MINOR, provided omitting it keeps the old meaning and clients ignore unknown response fields (test with consumer contracts)
  • Renaming a field → incompatible → MAJOR
  • Rollout
    • Run V1 and V2 side by side
    • Route by version at the gateway
    • Document both contracts with OpenAPI
    • Retire V1 only after the 200 clients have migrated, tracked through gateway metrics

Cost: supporting two versions for the migration period.

What the Instructor Emphasised in Day 3: Kubernetes, Toolchains and Architecture Styles

Decompose a Netflix-like streaming platform into a cloud-native architecture: identify services and data stores, how viewing events reach recommendations, how it is deployed, and how it scales on each axis.
  • Services and stores
    • Search → search index
    • Profile → relational or key-value
    • Catalogue → document
    • Recommendations → precomputed fast reads
    • Playback → key-value for resume position
  • Events: viewing events flow through a stream into recommendation processing, Kappa-style
  • Deployment: stateless services as Kubernetes Deployments behind Services and an API gateway, using tokens or shared session state so any replica can serve
  • Scaling axes
    • Replication: more replicas
    • Functional decomposition: hot services such as playback scale alone
    • Partitioning: shard user data by user ID

Costs: eventual consistency in recommendations and more services to operate.

Modernise a traditional web app that uses server-side sessions in memory, SOAP services, an ESB for workflows and a relational database. Decide what to keep, what to change and why.
  • Keep the relational database for transactional data
  • Keep cookies, but move sessions to a shared store or tokens → replicas are replaceable
  • SOAP → expose its functions through an API gateway with REST; rewrite services only where change justifies it
  • ESB workflows → move toward events or lightweight orchestration, one flow at a time
  • First: add observability and automated delivery (CI/CD or GitOps) → they make every later change safer

Don't swap in a vector store or agents unless a requirement calls for them.

Explain how Kubernetes provides high availability for both the control plane and the applications, and say why a large replica count alone doesn't guarantee availability to users.
  • Control plane
    • Replicate API servers behind a load balancer
    • Run controllers and schedulers with leader election
    • Keep etcd with quorum across failure domains
  • Applications
    • Run ready replicas spread across zones
    • Health probes → kubelet restarts failed containers and controllers replace lost Pods
    • Persistent data with its own replication and recovery
  • Why replica count alone doesn't help: replicas may
    • Share one zone
    • Lack capacity headroom
    • Depend on a single database
    • Fail readiness together

Availability must be designed end to end.

A new product will start with one team and modest load but expects to grow. Choose between a singular and a distributed architecture, and explain how you would leave room to evolve.

Choose a singular, modular architecture: simplicity and low latency outweigh independent scaling at this size.

  • Keep clear internal boundaries by business capability
  • Make it stateless and containerised → replication works from day one
  • Keep data ownership per module → the parts can later be split into microliths or microservices

Real systems end up hybrid, so plan the first split around the module most likely to need independent scaling.
