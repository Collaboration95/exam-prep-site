Whole-course questions

Try after all the days. Explain your choices before opening the answer.

A ticketing company must leave its data centre in 6 months. On-sale events push traffic to 30 times normal for 15 minutes, seat inventory must never be oversold, and card data falls under strict compliance rules. Outline a staged cloud design, justify the service model per component, and name two side effects to monitor after go-live.
  1. Stage 1: rehost or replatform the core
    • Onto IaaS and a managed relational database → meets the 6-month exit
  2. Stage 2: split out the components that spike
    • Event catalogue and queueing for seats → stateless containers or functions behind an API gateway
    • A queue to level the on-sale burst
  3. Seat inventory: keep seat reservation transactional (ACID) in the authoritative store → never oversold
  4. Compliance: tokenise card data; define everything in IaC with a clear shared-responsibility split
  5. Side effects to monitor
    • Queue depth and wait time (users' experience during the burst)
    • Database write contention on hot events, since scaling compute doesn't scale the inventory store
A logistics firm's monolith tracks parcels for 2 million deliveries a day. The team proposes rebuilding it as 40 microservices on Kubernetes across two clouds within a year. As the cloud architect, do you agree? Propose an alternative path and justify it with the drivers and the team's capacity.

Not as proposed. Diagnose the drivers first.

  • Drivers: if the pain is peak scaling and slow releases, the root cause is architecture and agility → rearchitecting the hot components fixes it at far lower risk than a full rebuild
  • Start small: a modular monolith or a few microliths for the parts that change or scale differently (tracking ingest, customer notifications)
  • Platform: one managed Kubernetes platform with CI/CD and observability
  • Add a second cloud only for a concrete reason: data, identity and managed-service dependencies aren't portable, and two clouds double operating skills
  • Grow the service count as maturity (DevOps, monitoring) and team size allow
A health-tech startup is building a patient app with offline symptom logging, a clinician dashboard, a GenAI assistant that answers from clinical guidelines, and a nightly analytics job. Data must stay in-country. Propose the reference architecture: front-end choice, compute per component, data stores, integration patterns and the main security controls.
  • Front end: PWA for broad reach
    • Designed offline storage and sync; native only if device features demand it
    • → Backend accepts delayed, idempotent submissions
  • Compute
    • Containers for the always-on patient and clinician APIs behind an API gateway
    • Functions for event-driven work
    • A scheduled job for nightly analytics
  • Data (all in an in-country region)
    • Relational store for patient records
    • Object store for attachments
    • Search or vector index of guidelines for RAG
    • Warehouse for analytics
  • Integration
    • Events for notifications and analytics feeds
    • Synchronous calls only where a user waits
  • Security
    • Classify data; encrypt with controlled key use
    • Least-privilege identities
    • Enforce the requester's permissions during retrieval
    • Keep audit trails
A team reports that its 'cloud-native' platform has 99.95% availability because every component has a 99.99% SLA. The request path crosses a gateway, three services in series and a database. Evaluate the claim and propose how to reach a real 99.95%, naming the cost of each change.

The claim holds only in the best case.

  • Series availability multiplies (independent components)
    • 0.9999 to the fifth power ≈ 99.95%
    • Shared failure modes and the application's own bugs push it lower
    • Provider SLAs don't add up to an application SLA
  • Events and caches: remove components from the synchronous path (cost: eventual consistency)
  • Spread replicas across zones with health probes and spare capacity (cost: more running capacity)
  • Timeouts and circuit breakers so one slow service doesn't cascade (cost: degraded responses)
  • Database standby with tested failover (cost: replication overhead)
  • Then measure availability end to end
