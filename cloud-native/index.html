Whole-course questions

Try after all the days. Explain your choices before opening the answer.

A ticketing company must leave its data centre in 6 months. On-sale events push traffic to 30 times normal for 15 minutes, seat inventory must never be oversold, and card data falls under strict compliance rules. Outline a staged cloud design, justify the service model per component, and name two side effects to monitor after go-live.
Stage 1: rehost or replatform the core onto IaaS and a managed relational database to meet the 6-month exit. Stage 2: split out the components that spike, such as the event catalogue and queueing for seats, as stateless containers or functions behind an API gateway, with a queue to level the on-sale burst. Keep seat reservation transactional (ACID) in the authoritative store, tokenise card data, and define everything in IaC with a clear shared-responsibility split. Monitor queue depth and wait time (users' experience during the burst) and database write contention on hot events, since scaling compute doesn't scale the inventory store.
A logistics firm's monolith tracks parcels for 2 million deliveries a day. The team proposes rebuilding it as 40 microservices on Kubernetes across two clouds within a year. As the cloud architect, do you agree? Propose an alternative path and justify it with the drivers and the team's capacity.
Not as proposed. Diagnose the drivers first: if the pain is peak scaling and slow releases, the root cause is architecture and agility, which rearchitecting the hot components fixes at far lower risk than a full rebuild. Start with a modular monolith or a few microliths for the parts that change or scale differently (tracking ingest, customer notifications), on one managed Kubernetes platform with CI/CD and observability. Add a second cloud only for a concrete reason, because data, identity and managed-service dependencies aren't portable and two clouds double operating skills. Grow the service count as maturity (DevOps, monitoring) and team size allow.
A health-tech startup is building a patient app with offline symptom logging, a clinician dashboard, a GenAI assistant that answers from clinical guidelines, and a nightly analytics job. Data must stay in-country. Propose the reference architecture: front-end choice, compute per component, data stores, integration patterns and the main security controls.
Front end: a PWA for broad reach, with designed offline storage and sync (native only if device features demand it), so the backend accepts delayed, idempotent submissions. Compute: containers for the always-on patient and clinician APIs behind an API gateway, functions for event-driven work, and a scheduled job for nightly analytics. Data: a relational store for patient records, an object store for attachments, a search or vector index of guidelines for RAG, and a warehouse for analytics, all in an in-country region. Integration: events for notifications and analytics feeds, synchronous calls only where a user waits. Security: classify data, encrypt with controlled key use, apply least-privilege identities, enforce the requester's permissions during retrieval, and keep audit trails.
A team reports that its 'cloud-native' platform has 99.95% availability because every component has a 99.99% SLA. The request path crosses a gateway, three services in series and a database. Evaluate the claim and propose how to reach a real 99.95%, naming the cost of each change.
The claim holds only in the best case: for independent components in series, availability multiplies (0.9999 to the fifth power is about 99.95%), and shared failure modes and the application's own bugs push it lower, because provider SLAs don't add up to an application SLA. Remove components from the synchronous path with events and caches (cost: eventual consistency). Spread replicas across zones with health probes and spare capacity (cost: more running capacity). Add timeouts and circuit breakers so one slow service doesn't cascade (cost: degraded responses). Use a database standby with tested failover (cost: replication overhead). Then measure availability end to end.
