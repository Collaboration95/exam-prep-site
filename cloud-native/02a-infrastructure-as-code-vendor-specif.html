Infrastructure as Code: Vendor-Specific Examples

13 slides · about 15 min · open the deck · JSON

IaC defines infrastructure in versioned files rather than manual clicks. Compare provisioning, configuration and orchestration, then apply them to AWS serverless, Azure microservices, a GCP pipeline and multi-cloud Kubernetes. GitOps keeps cluster desired state in Git and synchronises it through automation.

Big ideas

  • IaC = provisioning and managing infrastructure through scripts or config files instead of manual configuration.
  • IaC automates repeatable environments and records reviewed changes; reverting code still requires a safe infrastructure update.
  • IaC reference architecture has three components: infrastructure provisioning, configuration management, orchestration.
  • Best practices: modular design, environment segmentation (Dev/Test/Prod), and state management.
  • Vendor-native tools (AWS SAM/CloudFormation, Azure Bicep/ARM) suit a single cloud; Terraform is the cross-cloud tool.
  • Kubernetes IaC is declarative (desired state in YAML/JSON), stored in Git, and applied by GitOps automation with Git as the source of truth.

IaC concepts and reference architecture

What IaC is, its benefits and tools, the components and best practices of an IaC reference architecture, and the three example architectures.

IaC: repeatable environments in versioned files

  • Tools automate setup
  • Reduce manual differences
  • Record changes
  • Reuse modules while deliberately parameterising differences (production size, access, region)

Reference architecture: three components

  • Infrastructure provisioning → create VMs, containers, databases, networks
  • Configuration management → software configured as intended (e.g. Ansible, Chef)
  • Orchestration → workflows, deployments, scaling (e.g. Kubernetes, Terraform)

Three best practices

  • Modular design → reusable networking/compute modules
  • Environment segmentation → isolated Dev, Test, Prod
  • State management → track current infrastructure for smoother updates

Tool choice follows scope

  • One cloud → native tools: CloudFormation/SAM, Bicep, the GCP tooling illustrated in the lecture
  • Cross-cloud → Terraform
  • Kubernetes → Helm, Kustomize, Argo CD

Lecture examples

  • Serverless AWS app
  • Microservices on Azure AKS
  • Event-driven GCP pipeline
  • Multiple Kubernetes clusters across clouds
Infrastructure as Code (IaC)
Defining infrastructure in version-controlled files that tools apply automatically.
Configuration management
Keeping software on provisioned machines in the intended configuration (e.g. Ansible, Chef).
Orchestration
Coordinating deployments, workflows and scaling across many resources (e.g. Kubernetes, Terraform).
State management
Tracking what infrastructure currently exists so updates and scaling go smoothly.
Environment segmentation
Keeping Dev, Test and Prod isolated for safer deployments.

Check yourself

A change that passed in test fails in production, and the team finds production was hand-edited months ago. How would IaC have prevented this, and does it mean test must be identical to production?
  1. How IaC would have prevented it
    • the same reviewed modules build every environment and all changes go through code → the hand edit could not have drifted unnoticed
    • version history would show what changed
  2. Identical environments? No.
    • size, access and region should be explicit parameters

Drift only stays away if nobody makes manual changes outside the code.

VMs and databases are created correctly from templates, but an app fails because a library version on the VMs differs from the one expected. Which IaC component is missing, and which would not help?

Configuration management is missing.

  • Configuration management: makes sure the software on provisioned resources is set up as intended
  • Would not help: provisioning (only created the resources correctly) and orchestration (manages deployment workflows and scaling) → neither addresses what is installed on the VMs
  • Another way: bake the dependency into an immutable image
Three product teams each copy and edit the same 800-line network template, and a security fix had to be made in three places. Which IaC best practices would you apply?
  • Modular design: extract a reusable, versioned networking module that every team consumes with its own parameters → a fix is made once and rolled out
  • Environment segmentation: Dev, Test and Prod are isolated
  • State management: each apply knows the current infrastructure

Trade-off: changes to a shared module need versioning and testing, because one change now affects every team.

Two engineers run applies against the same environment at the same time and resources end up duplicated. Which best practice was missing, and why does it matter?

State management.

  • The tooling needs one tracked record of the current infrastructure, kept in one shared place that every apply reads and updates
  • Without it → each apply works from a different view of reality
  • → updates or scaling create duplicates or destroy resources unexpectedly

Vendor-native IaC: AWS SAM and Azure Bicep

Two worked examples using each provider's own IaC tooling: a serverless web app on AWS and a containerised microservices app on Azure.

Native templates describe the whole solution

Not just compute.

  • AWS serverless app → SAM template:
    • Lambda
    • API Gateway
    • DynamoDB
    • S3 for static content
    • permissions
    • CloudWatch logging
  • Deploy → sam build and sam deploy

Azure microservices app in Bicep/ARM

  • Resources:
    • AKS
    • Cosmos DB
    • VNet with Private Endpoints
    • Application Gateway with WAF
  • Azure Monitor logging
  • Role assignments so AKS reaches Cosmos DB securely
  • Deploy → az deployment group create

Security and observability in the template

  • Deployed identically every time
  • Rather than bolted on manually

SAM/CloudFormation vs Bicep/ARM

  • Same declarative idea on different clouds
  • Both single-provider
  • Everything on one provider → choose native tools
  • Spans clouds → choose Terraform
AWS SAM
Serverless Application Model: a simplified way to define serverless apps, used with CloudFormation.
AWS CloudFormation
AWS's native IaC service that provisions resources from YAML/JSON templates.
Azure Bicep
Azure's concise IaC language for deploying Azure resources; the alternative to ARM templates.
ARM template
Azure Resource Manager template, Azure's native JSON IaC format.
WAF
Web Application Firewall: filters malicious HTTP traffic in front of an app.

Check yourself

In one project, the function, API and table are defined in the IaC template, but permissions and logging are configured by hand in the console afterwards. What is the risk?

Security and observability settings are not versioned.

  • → a redeploy or a new environment can come up without them, or with different permissions
  • Lecture's serverless template: defines permissions and logging alongside the resources → they deploy the same way every time

Cost: a larger template that must be reviewed carefully.

A containerised app reaches its database over a public endpoint protected by IP firewall rules. A reviewer asks for private endpoints in the virtual network and a role assignment for the cluster instead. What does each change gain, and what does it cost?
  • Private endpoint → database traffic stays on the private network
    • the database is not exposed to the internet at all
    • firewall rules on a public endpoint can be misconfigured or bypassed by a compromised allowed address
  • Role assignment → identity-based access for the cluster
    • no secret has to be stored and rotated

Costs: more network design and harder access for tools outside the network.

A company is all-in on one cloud and is choosing between that provider's native declarative IaC and Terraform. What should decide it?
  • Everything on one provider → native tools are designed for its services and model them directly → favours them
  • Terraform → if the company expects to span clouds or wants one language and workflow across providers

Trade-off: depth on one cloud versus portability of skills and tooling.

Terraform, multi-cloud and Kubernetes GitOps

Terraform examples for a GCP event-driven pipeline and a multi-cloud Kubernetes deployment, then Kubernetes IaC principles: declarative config, version control and GitOps.

Terraform is the cross-cloud choice

  • One language and workflow, with a provider per platform
  • GCP event-driven pipeline provisioned this way:
    • Pub/Sub
    • Cloud Functions or Cloud Run
    • BigQuery
    • monitoring
  • IAM set per component → least privilege

Multi-cloud Kubernetes

Separate clusters with common provisioning.

  • Terraform modules create EKS, AKS and GKE
  • Need additional configuration:
    • connectivity
    • federated identity
    • workload placement
    • scaling
    • logging
  • GitOps can synchronise workload definitions
  • Example commands → initialise providers, then apply the declared resources

Kubernetes IaC is declarative

  • YAML/JSON describe desired state, not imperative steps
  • Live in Git → traceability, collaboration, rollback

GitOps: desired state vs live state

GitOps separates desired state from live state.

  1. Review a Git change
  2. Let automation synchronise the cluster
  3. Check convergence

Reverting a commit changes desired state; successful recovery still depends on compatible application versions, schemas and persistent data.

Terraform
Cloud-agnostic IaC tool that uses a provider per platform to provision resources across clouds.
Provider (Terraform)
Plugin that lets Terraform manage a specific platform such as AWS, Azure or Google.
Least privilege
Grant each component only the permissions it needs.
Declarative
You describe the desired end state and the tool works out how to reach it, versus imperative step-by-step commands.
GitOps
Operating model where Git holds the desired state and automation (e.g. Argo CD) applies it to clusters.

Check yourself

One Terraform configuration creates clusters on three providers. A manager says 'we now have one cross-cloud cluster'. Is that right?

No. It provisions separate clusters with a common tool and workflow.

  • Still to design and configure:
    • connectivity between them
    • federated identity
    • workload placement
    • scaling
    • logging
  • GitOps can keep workload definitions in sync

A common tool reduces the provisioning work but does not make the clusters one system.

An operator scales a Deployment by hand with a command during an incident. Ten minutes later it is back to its old size. Why, and what should they have done?
  • Why: under GitOps the declared state in Git is the source of truth → the sync tool reconciled the live cluster back to it
  • What they should have done:
    • make the change as a reviewed Git commit
    • or pause reconciliation deliberately during the incident, with the fix committed afterwards

This is the declarative model working as intended: imperative changes do not last.

A bad release is reverted in Git and the cluster syncs, but the app still fails. What does a Git rollback not undo?
  • Reverting a commit restores the desired configuration
  • Does not undo: persistent data or a database schema migration the new version already applied
  • Old version can't read the new schema → the rollback fails
  • Plan:
    • backward-compatible schema changes or a data recovery step
    • check that the cluster has actually converged before declaring recovery
In an event-driven pipeline, every component is provisioned with a single broad service identity because it was quicker. What would you change in the IaC, and why there?
  • Own identity per component with only the permissions it needs → e.g. publish-only for the producer, write-only to the analytics table for the processor
  • Why in IaC → applies the least-privilege policy the same way every time and keeps it under review

Cost: more identities and policies to manage, but a compromised component can no longer reach everything.

Exam-style questions

Answer aloud or on paper before opening.

A company's Dev, Test and Prod environments keep drifting apart, two engineers sometimes apply changes at the same time, and 30% of production deployments fail. Propose an IaC-based remedy and say what discipline it requires from the team.
  • Reusable, versioned modules in Git for all infrastructure
  • Environment segmentation: each environment is a separate, isolated set of parameters
  • One shared, tracked state → concurrent applies work from the same view
  • Apply only through a pipeline after review
  • Configuration management or immutable images → keep the software consistent too

Discipline: it only works if nobody changes infrastructure by hand; incident fixes must also go through code.

Choose IaC tooling for (a) a 5-person startup building only on one provider's serverless services and (b) an enterprise running Kubernetes on three providers. Justify each, and say what each choice gives up.
  1. (a) Startup: the provider's native declarative IaC
    • designed for that cloud's services
    • can define functions, APIs, tables, permissions and logging in one template
    • Gives up: portability if the startup later spans clouds
  2. (b) Enterprise: Terraform with a provider per cloud and reusable cluster modules, plus GitOps for the workloads
    • one language and workflow across clouds
    • Gives up: some native depth; connectivity and federated identity still have to be designed separately
Design the IaC for an event-driven pipeline: messages are ingested, processed by functions and written to an analytics store. A security review requires that a compromised processor cannot read or delete other data. Explain the security decisions in the template.
  • One declarative configuration provisions the topic, subscription, function and analytics tables, with monitoring and logging defined alongside
  • Own identity per component → the processor can only consume from its subscription and write to its table
  • Permissions defined in IaC → reviewed and applied the same way in every environment

Trade-off: more identities to manage, in exchange for a much smaller blast radius.

A team uses GitOps for its Kubernetes platform. A release that adds a database column fails, and an engineer proposes 'just revert the commit'. Explain what GitOps gives here and what the revert will and will not fix.
  • What GitOps gives: declared state in Git + automation reconciles the cluster to it → traceability, review and a quick way back to the previous configuration
  • Revert will fix: restores the old Deployment
  • Revert will not fix: the schema change has already been applied → if the old version can't work with the new column, the app still fails
  • Instead: backward-compatible migrations or a data recovery step, and verify convergence before calling it fixed
A reviewer compares two IaC designs for a containerised app and its database. Design A exposes the database on a public endpoint with IP allow-lists and stores a database password in the cluster. Design B places the database behind a private endpoint in the virtual network, puts a web application firewall at the edge, and grants the cluster a role assignment. Which would you approve, and what does B cost?

Approve B.

  • Private endpoint → removes public exposure of the database
  • WAF → filters malicious traffic at the edge
  • Identity-based role assignment → removes a long-lived secret that could leak
  • All defined in the template → the same controls present in every environment

B costs more network design, and tools outside the network can't reach the database without a controlled path.
