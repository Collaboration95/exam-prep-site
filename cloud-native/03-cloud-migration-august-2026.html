Cloud Adoption and Migration

58 slides · about 40 min · open the deck · JSON

Choose a migration approach by diagnosing the application’s business and technical problems. Compare VMs, containers, IaaS and PaaS, then apply the migration options and six modernisation drivers. Assess dependencies, risk and total cost, including the temporary cost bubble, before sequencing an incremental migration.

Big ideas

  • VMs include a guest OS; containers share a kernel and typically start faster with lower overhead. Image size and startup time vary.
  • Choose among Rehost, Replatform, Rearchitect, Rebuild and Replace; Retain, Retire and Encapsulate are alternatives. Their IaaS/PaaS/SaaS mapping is illustrative, not mandatory.
  • Lift-and-shift favours speed and low initial effort; lift-and-optimise can improve ongoing cost and return at greater migration effort.
  • Pick the approach per application by diagnosing it with the six drivers: business fit, innovation, agility (business) and cost, complexity, risk (IT).
  • The more you change (infrastructure, then platform, then code, then functionality), the higher the potential value, but also the cost, time and risk.
  • Expect a temporary migration bubble of extra cost (duplicate environments, training, consulting, lease penalties) before savings appear.
  • Start with a low-risk workload you can learn from, not the highest-ROI one; then rinse and repeat.
  • Decide sourcing (internal vs partner) and hosting (data centre/IaaS/PaaS/SaaS) with weighted criteria: differentiation, operational complexity, skills.

Recap: VMs, containers, managed services and IaaS

How VMs and containers package applications, what managed cloud services are, why IaaS emerged and which workloads suit it.

VMs vs containers: isolation boundaries

  • VM → boots a guest OS via a hypervisor
  • Container → starts isolated processes sharing the host kernel
  • Containers → usually less overhead, faster startup; image pulls and application initialisation still take time
  • VMs suit → different OS requirements or stronger kernel separation

IaaS: the raw-infrastructure layer

  • Grew out of successive waves of sharing:
    • networks
    • the web
    • grids
    • then services
  • Justified by:
    • elastic capacity
    • lower upfront investment
    • cheaper DR
    • easy seasonal scaling
    • freeing the business to focus on core work
  • Suits workloads:
    • analytics
    • ERP/CRM
    • collaboration
    • dev/test
    • backup/DR
    • general infrastructure

Managed cloud services

  • Hand part or all of cloud operations to a provider:
    • migration
    • configuration
    • optimization
    • security
    • maintenance
  • Usually on subscription
  • Contracted before migrating
  • Client gets cloud benefit with less internal time and cost

IaC and IaaS back end

  • IaC → infrastructure as machine-readable definition files, not manual setup → makes IaaS repeatable
  • An IaaS platform is run by three back-end systems:
    • resource management (VIM)
    • SLA management
    • billing
Managed cloud services
Partial or full management of a client's cloud resources by a provider, usually on subscription.
Infrastructure as Code (IaC)
Provisioning infrastructure from machine-readable definition files rather than manual setup.
VIM
Virtual Infrastructure Manager: the component that manages VMs and images in an IaaS cloud.

Check yourself

A team moved from VMs to containers to cut scale-out time, but new replicas still take 90 seconds to serve traffic. What is the likely cause, and what would you check?
  • Containers skip booting a guest OS because they share the host kernel
  • Likely cause: pulling a large image, loading dependencies and initialising the application can still dominate startup
  • Check: image size and pull time, and how long the application takes to warm up

Smaller images and lighter initialisation help more than changing the isolation boundary.

A legacy app needs a Windows kernel feature, and a second workload from a different tenant must run on the same hosts with strong separation. VMs or containers for each?

VMs for both.

  • Legacy app needs its own OS → a container sharing the host kernel cannot provide it
  • Hypervisor boundary → stronger separation between tenants than process-level isolation

You give up the lighter weight and faster startup of containers, which matter less for these two requirements.

A company with a 3-person IT team wants to migrate to the cloud this year but has no cloud skills. Should it run the migration itself or use a managed cloud service, and what is the catch?

A managed cloud service fits.

  • A provider takes on migration, configuration, optimisation, security and maintenance, usually on subscription
  • → the small team gets cloud benefits without building every skill first
  • Catch: the ongoing subscription cost and dependence on the provider
  • The contract must be in place before migrating

The company still owns its data and decisions.

OpenStack and Ansible (IaaS as code)

OpenStack as an open-source IaaS platform and Ansible as a way to provision it as code.

OpenStack: private IaaS cloud

Open-source suite that turns hardware into a private IaaS cloud.

  • Compute → Nova
  • Networking → Neutron
  • Object and block storage → Swift, Cinder
  • Identity → Keystone
  • VM templates → Glance
  • Dashboard → Horizon
  • Orchestration → Heat

Ansible: ordered YAML playbooks

  • Provisions and configures systems using ordered YAML playbooks
  • Modules can express intended resource state without a resident target agent
  • Heat uses its own YAML format, HOT, for OpenStack orchestration
  • A Heat template is not an Ansible playbook

The point: Infrastructure as Code

  • A playbook declares:
    • VM templates
    • servers
    • networks
    • security groups
  • Whole environment is versioned and re-runnable instead of hand-built
  • OpenStack-Ansible → a common way to install OpenStack itself
OpenStack
Open-source software suite for building a private IaaS cloud (Nova, Neutron, Swift, Cinder, Keystone, etc.).
Ansible playbook
A YAML file listing tasks Ansible runs to provision or configure systems.
HOT
Heat Orchestration Template: OpenStack's YAML template format for orchestration.

Check yourself

A university wants a private IaaS cloud on its own hardware and asks what a hypervisor alone would be missing. Using OpenStack's components, explain.

A hypervisor runs VMs, but an IaaS cloud needs more.

  • OpenStack supplies these on top of compute (Nova), for example:
    • networking (Neutron)
    • block storage (Cinder) and object storage (Swift)
    • identity (Keystone)
    • VM images (Glance)
    • a self-service dashboard (Horizon)
    • orchestration (Heat)
  • Without them → users still depend on administrators to wire each VM together → fails on-demand self-service
A security team won't allow extra agents on production servers but wants the servers' configuration managed as code. Does Ansible fit, and what does it still need?

Yes: Ansible is agentless.

  • No resident agent has to be installed on each target
  • Still needs:
    • a reachable management connection
    • credentials
    • whatever prerequisites its modules require on the target

The security team's concern then shifts to protecting those credentials and the control node.

An engineer calls an Ansible playbook a Heat template 'because both are YAML' and wants to feed the playbook to Heat. What is wrong?

YAML is only the file syntax.

  • Ansible runs a playbook's ordered tasks
  • Heat interprets HOT templates to orchestrate OpenStack resources
  • Each tool needs its own format

Either can describe infrastructure as code: choose by whether you need OpenStack-native orchestration or general provisioning and configuration across systems.

PaaS and containers vs VMs

Why PaaS emerged, what it gives, which workloads fit it, the CNCF ecosystem, and the VM vs container comparison.

PaaS reduces platform operations

  • Platform supplies deployment, scaling and runtime management for developers
  • Lecture's large labour, capital and delivery-time reductions → illustrative benefits, not guaranteed savings for every workload
  • Teams still configure access and secure their code

IaaS vs PaaS fit

  • PaaS → workloads consuming managed platform services:
    • databases
    • queues
    • APIs
    • rule engines
    • batch/ETL
    • CI/CD
    • mobile back-ends
  • IaaS → workloads needing server-level control:
    • application servers
    • backup
    • DR
    • storage

Compute abstraction moves up the stack

  1. Mainframe
  2. Client-server
  3. Web
  4. Now containers with edge devices

The CNCF (Linux Foundation) hosts the open-source projects behind cloud-native computing.

VM vs container: four contrasts

  • Virtualization → hardware-level vs OS-level
  • Isolation → machines vs processes
  • Resources → via hypervisor vs kernel namespaces and cgroups
  • Strength → hardware flexibility vs portability
  • VMs bring established management/security tools; containers bring lightness and speed
CNCF
Cloud Native Computing Foundation: Linux Foundation body hosting cloud-native projects such as Kubernetes.
Namespaces and cgroups
Linux kernel features that give containers isolated views of the system (namespaces) and resource limits (cgroups).
Hypervisor
Software (Type 1 or Type 2) that runs multiple VMs on one physical machine.

Check yourself

A team's API uses a managed database, a queue and CI/CD, and needs no OS changes. A second system is a backup server that needs custom storage drivers. Which fits PaaS and which IaaS?
  • API → PaaS: consumes managed platform services; the platform takes over deployment, scaling and runtime management
  • Backup server → IaaS: needs server-level control of drivers and storage

With PaaS the team still configures access and secures its own code.

A vendor pitch says moving to PaaS will 'cut delivery time from months to hours'. How would you treat this claim in a business case?

As an illustrative benefit, not a guaranteed saving.

  • PaaS removes server setup and platform operations → can shorten delivery a great deal
  • Real gain depends on how much of the current delay is infrastructure work rather than design, testing or approvals
  • Measure the current lead time and its causes before promising a figure
A multi-tenant SaaS platform plans to run every customer's code in containers on shared hosts. A security reviewer objects. What is the concern, and what are the options?
  • Concern: containers isolate processes through kernel namespaces and cgroups but share the host kernel → a kernel exploit can reach other tenants
  • VMs isolate at the hardware level through a hypervisor and come with established security tooling
  • Options:
    • VM-per-tenant → stronger isolation, more overhead
    • containers grouped onto VMs by tenant → keeps most of the containers' speed

Migration framework and strategy

How to think about migration: an on-prem to AWS example, the AWS migration roadmap, lift-and-shift vs lift-and-optimize, and Gartner's six drivers of modernization.

AWS migration roadmap

Migration is a decision process, not a single move.

  1. Discover and assess
  2. Choose a path per application:
    • do not move
    • decommission
    • vendor SaaS/PaaS
    • lift and shift
    • refactor
    • replatform/rearchitect/recode
  3. Plan and sequence
  4. Migrate and UAT
  5. Tune
  6. Sign off
  7. Cut over and operate

Alongside throughout: org/ops impact analysis and change management.

Lift-and-shift vs lift-and-optimise

Trades initial speed against later optimisation.

  • Lift-and-shift → moves largely unchanged apps quickly; may preserve inefficient resource use
  • Lift-and-optimise → adapts during migration; usually longer and costs more initially, for potential ongoing cost and ROI improvements
  • TCO → a cost to minimise
  • ROI → a return to improve

Gartner's six drivers (diagnose first)

  • Business drivers:
    • Business fit → no longer meets needs
    • Innovation → blocks opportunities
    • Agility → cannot keep pace with change
  • IT drivers:
    • Cost → too high for its value
    • Complexity → hard and risky to change
    • Risk → security, compliance, supportability, scalability, skills shortage

Diagnose before prescribing.

Method

  1. Understand each approach's scope and effect
  2. Run a cause-effect analysis with the six drivers → find the functional, architectural and technological problems
  3. Pick an approach per application with Gartner's framework

On-prem 3-tier app mapped to AWS

  • DNS
  • Load balancing
  • Auto-scaling web/app fleets across two AZs
  • Managed database
Lift-and-shift
Move an application to the cloud with minimal or no change.
Lift-and-optimize
Migrate and adapt the application to use cloud services at the same time.
Availability Zone
An isolated data-centre location within a cloud region; spreading across AZs gives resilience.

Check yourself

A firm must leave its data centre in 4 months and its apps are over-provisioned. Lift-and-shift or lift-and-optimise?

Lift-and-shift for most apps.

  • The deadline and low initial change matter most
  • It carries the over-provisioning into the cloud → budget for right-sizing and optimisation after cutover
  • Lift-and-optimise → lower ongoing TCO and improves ROI sooner, but takes longer and costs more up front

The 4-month window doesn't allow lift-and-optimise.

A business owner says 'our app is too expensive, let's rewrite it as microservices'. Using the six drivers, what would you check before agreeing?

Diagnose first.

  • Driver is cost (infrastructure too expensive for the value) → Rehost or Replatform may fix it far more cheaply
  • Rewrite justified when the drivers are business fit, innovation or agility → the app can't meet needs or change fast enough
  • Cause-effect analysis → shows whether the problem is functional, architectural or technological
  • The option should fix that cause
The migration roadmap lists 'do not move' and 'decommission' as paths alongside lift-and-shift and refactor. Why is it worth assessing every application before picking a default path?

Migration is a decision per application.

  • Some apps are better left in place or switched off → moving them wastes effort and adds cloud cost
  • Discover and assess each app first, then plan and sequence by dependency
  • → avoids migrating something only to retire it later

Cost: the time spent on discovery before anything moves.

Migration options I: Rehost and Replatform

The option spectrum against IaaS/PaaS/SaaS, and the two lightest-touch options with typical use cases.

Spectrum of increasing change

  1. Retire
  2. Rehost
  3. Replatform
  4. Rearchitect
  5. Rebuild
  6. Replace

Roughly: IaaS ≈ Rehost; PaaS ≈ Replatform through Rebuild; SaaS ≈ Replace.

Rehost (lift and shift, redeploy)

  • Moves the app to other infrastructure
  • No recompiling; no change to code, features or functions
  • Benefits are infrastructure-only:
    • scalability at peaks
    • less hardware upkeep
    • redundancy and availability
    • remote access
    • provider security and compliance posture

Replatform (lift, shape and shift)

  • Moves to a new runtime platform with minimal compatibility changes
  • Examples: managed cloud database, serverless, auto-scaling
  • No change to code structure or features
  • Typical gains:
    • better analytics or AI services
    • faster transactions
    • auto-scaling

Rehost vs Replatform

  • Rehost → changes only where it runs
  • Replatform → also swaps platform pieces (database, runtime); app stays functionally the same
Rehost
Redeploy unchanged to new infrastructure (lift and shift).
Replatform
Move to a new runtime platform with minimal code changes (lift, shape and shift).

Check yourself

A bank wants its transaction system on a managed cloud database but cannot touch the business logic. Rehost or Replatform?

Replatform.

  • Swaps the platform (the database) with minimal compatibility changes; code structure and features stay the same
  • Rehost would move the app with its existing self-managed database unchanged

Replatform adds testing for database compatibility in exchange for less database operations work.

After a Rehost, the business asks why the app's features and slow reports didn't improve. Is the migration a failure?

No, if the goal was infrastructure.

  • Rehost changes only where the app runs → its benefits are infrastructure ones
  • Rehost benefits:
    • scaling at peaks
    • less hardware upkeep
    • redundancy
    • remote access
    • the provider's security posture
  • Faster reports or new features → need Replatform (e.g. a managed analytics service) or deeper options

Set those expectations in the business case.

A retailer's app runs fine but the database can't cope with holiday peaks, and the code must not change. What option fits, and what would push you further along the spectrum?

Replatform onto a managed database and auto-scaling.

  • Addresses the peaks without touching code structure
  • What pushes further: the code itself blocks scaling (e.g. shared state in the app tier) → Replatform won't be enough → Rearchitect

Rearchitect comes at higher cost and risk.

Migration options II: Rearchitect to Encapsulate

The deeper-change options (Rearchitect, Rebuild) and the non-migrating or replacing options (Replace, Retain, Retire, Encapsulate).

Rearchitect (re-engineer, refactor)

  • Restructures code without changing external behaviour
  • Goal → remove technical debt, improve non-functional qualities
  • Often moves to:
    • microservices
    • serverless/event-driven
    • containers
    • CDN/caching
  • → components scale independently

Rebuild (rewrite, redesign)

  • Writes the application afresh, even as a like-for-like replacement
  • Usually cloud-native
  • Gains new capabilities:
    • mobile-first
    • IoT
    • AI
    • offline mode
    • microservices

Rearchitect vs Rebuild

  • Rearchitect → keeps behaviour, reshapes the existing code
  • Rebuild → may change functionality too; highest value, cost and risk

Replace and Retire

  • Replace (repurchase, drop and shop) → swaps the app for a COTS or SaaS product, taking new requirements into account
  • Retire → decommissions it, often as part of a Replace

Retain and Encapsulate

  • Retain → leave the app as is for now
  • Retain because:
    • modernization not worth the effort and risk
    • or it is nearing retirement
  • Encapsulate → exposes the app's data and functions as API services
  • Encapsulate extends its value while hiding the implementation
Rearchitect
Restructure code/architecture without changing external behaviour, e.g. to microservices or serverless.
Rebuild
Rewrite the application from scratch, often cloud-native.
Replace
Drop the app and buy COTS/SaaS instead.
Encapsulate
Wrap an existing app behind APIs so its functions can be reused as services.
COTS
Commercial off-the-shelf software.

Check yourself

An app's features are fine, but one module can't scale and every change is risky because of technical debt. A teammate proposes Rebuild. Do you agree?

Rearchitect is the better fit, not Rebuild.

  • Rearchitect: restructures the existing code without changing external behaviour → e.g. extract the bottleneck module so it scales independently
  • It reduces technical debt
  • Rebuild: rewrites everything, carries the highest cost and risk

Rebuild is justified only when new capabilities such as mobile-first, IoT or AI are needed.

A mainframe holds valuable pricing logic that a new mobile app needs, but the mainframe is too risky to change this year. Retain, Encapsulate or Rebuild?

Encapsulate.

  • Expose the pricing data and functions as APIs → the mobile app uses them without rewriting the internals
  • Plain Retain → leaves the logic inaccessible to the new app
  • Rebuild → the risk the business wants to avoid

Cost: the legacy system stays in place, and its performance and availability now limit the new app.

A department's expense tool is home-grown, offers nothing unique, and its developer has left. Which option fits, and what goes with it?

Replace with a COTS or SaaS product, and Retire the old tool as part of the move.

  • Take current requirements into account
  • Not a differentiator → owning code adds no value

Cost: users adapt to the product's workflow, and data has to be migrated before decommissioning.

Choosing the approach and planning

Gartner's comparison of what each option changes and its trade-offs, Gartner's migration stages, and the seven-step plan with eight classification criteria.

More change: more value, cost, risk

  1. Rehost → changes only infrastructure
  2. Replatform → adds platform/data layers
  3. Rearchitect → adds configuration and custom code
  4. Rebuild and Replace → can change everything, including business logic and UX

Gartner's ratings

  • Rehost → lowest overall
  • Rebuild → highest on change, value, cost and risk
  • Replace → most business disruption

Pick the lightest option that fixes the diagnosed drivers.

Gartner's four steps: mass migration to IaaS

  1. Choose the approach → lift-and-shift vs lift-and-optimize, weighing lock-in against unique cloud value
  2. Build the business case
  3. Prepare:
    • landing zone
    • cloud patterns
    • migration partner
    • cloud operations model
  4. Migrate and optimize → use cloud-native services sooner

The seven-step plan

  1. Identify desired outcomes
  2. Classify cloud candidates
  3. Define service and deployment criteria per workload (IaaS/PaaS/SaaS and public/private placement)
  4. Devise an iterative agile process → fails fast and learns fast
  5. Get buy-in
  6. Start simple → prioritize learning over ROI
  7. Rinse and repeat

Classify candidates on eight criteria

  • Architecture
  • Security
  • Availability
  • Performance
  • Scalability
  • Strategic importance
  • Future plans
  • Enthusiasm of the team

First project → low-risk and highly instructive, not the highest-ROI one: early success builds skills and buy-in.

Landing zone
A pre-configured, secure cloud environment and architecture set up before workloads are migrated.
Vendor lock-in
Dependence on one provider's unique services that makes switching costly.
Fail fast, learn fast
Agile migration mindset: small iterations that surface problems early.

Check yourself

Rebuild scores highest on value in Gartner's comparison. Why is it not the default answer?
  • Rebuild also has the highest cost of change, the highest risk and a long time to value
  • Diagnosed drivers only call for infrastructure or platform fixes → Rehost or Replatform give faster, cheaper, lower-risk results
  • Choose the lightest option that fixes the drivers

Keep Rebuild for when business logic or UX must change.

Leadership wants the first cloud migration to be the system with the biggest projected ROI, a customer-facing billing platform. How do you respond?

Push back.

  • Seven-step plan: start simple and prioritise learning over ROI
  • First project should be low-risk and highly instructive → early success builds skills and buy-in
  • Billing platform is strategically important and high-risk → a failure would set back the whole programme

Migrate it in a later wave, once the landing zone and operating model have been proven.

Two candidate first workloads score the same on architecture, security, availability and performance. One team is eager, the other was told to migrate. Which would you pick?

The eager team's workload.

  • Team enthusiasm is one of the eight classification criteria → migrations need the owning team's engagement
  • A willing team → an early success and useful lessons more likely
  • The other workload can follow once there is a proven pattern to copy

Application concerns and assessment

What to assess in each application, the migration planning framework, the migration cost bubble and TCO.

Assess each app across concern families

  • Performance → elasticity, latency, throughput
  • Architecture → complexity, data, life expectancy
  • Financial → operating cost, business value
  • Risk → business criticality, technical, contractual, audit
  • Operations → continuity, tooling, deployment
  • Security/compliance → jurisdiction, regulation, privacy, encryption; can rule out regions or providers

The planning framework

  1. Establish a baseline:
    • drivers
    • portfolio analysis assigning an R to each app
    • requirement recovery
  2. Design the target
  3. Follow a road map to migration complete

Supported by stakeholder buy-in, quality assurance, risk mitigation and a scope/schedule plan.

Budget for the migration bubble

Costs rise temporarily from:

  • Discovery
  • Duplicate environments
  • Training
  • Consultants
  • Tools
  • Lease penalties

Compare lifetime TCO with the baseline; retirement and optimisation may produce savings, but only the business case can establish whether and when they occur.

Migration bubble

Check yourself

Six months into migration, a CFO sees costs higher than before and wants to stop. What is the likely explanation, and what would you show?

The migration bubble.

  • Costs rise temporarily: duplicate environments, training, consultants, tools and lease penalties
  • → until old infrastructure is retired and optimisation starts
  • Show: lifetime TCO against the baseline, and the dates when on-premises costs stop

The CFO's concern is valid if the business case never showed savings, or retirement keeps slipping.

An app processes citizens' health records and must stay within national borders. The preferred provider has no local region. How does this assessment concern affect the plan?

Jurisdiction and regulation can rule out regions or providers → that provider is excluded for this app, no matter what else it offers.

  • Options:
    • another provider with a local region
    • a private or hybrid placement for the records
    • keep the app on premises (Retain)
  • Encryption and privacy controls are still needed, but they don't remove a data-location rule
A portfolio analysis assigns Rehost to an app with 2 years of remaining life and high audit risk. Which assessment concerns would make you question that choice?

Architecture (life expectancy) and risk (audit, contractual).

  • 2 years left → Retain or Retire may cost less than migrating
  • Audit risk → check compliance in the target environment before moving
  • The planning framework expects each app's R to come from these concerns, not from a default

Sourcing and hosting models

Deciding who should run each capability and where it should be hosted, using weighted criteria, then the overall assessment approach.

Two separate decisions per capability

  • Sourcing model → who operates it: internal team or a partner (e.g. MSP or cloud product partner)
  • Hosting model → where it runs: own data centre, IaaS, PaaS or SaaS

Sourcing factors

  • Level of differentiation → core stays internal; non-differentiators go to partners
  • Complexity of business processes → complex stays internal
  • Skills → common skills in-house; highly specialized skills outsourced

Core, complex, commonly skilled → lean internal; non-differentiating, simple, specialized → lean partner.

Weighted scoring (make it systematic)

  1. Rate each criterion 1-3 and weight it
  2. Example weights:
    • differentiation 60%
    • operational complexity 20%
    • skills 20%
  3. Skills scored inversely → 1 means highly specialized
  4. Combine into a composite classification
  5. Validate with stakeholders

Finish with options and proof

  1. Assess the portfolio:
    • dependencies
    • data type
    • coupling
    • compliance
    • audience
  2. Compare pros and cons of alternatives
  3. Use a proof of concept to reduce risk
Sourcing model
Who operates a capability: internal team or partner (MSP / product partner).
Hosting model
Where it runs: data centre, IaaS, PaaS or SaaS.
MSP
Managed Service Provider that runs operations for you.

Check yourself

A company's CRM is not a differentiator, has simple processes, and needs specialist skills it cannot hire. What sourcing and hosting model would you suggest?

Partner sourcing, most likely SaaS hosting → effectively a Replace decision.

  • All three sourcing factors point to a partner
  • Gives up: deep customisation and control of the roadmap

Acceptable for a non-differentiating capability.

A trading firm's pricing engine is its main differentiator and has complex logic, but it needs rare low-latency skills. The sourcing factors conflict. How do you decide?

Keep the engine internally sourced.

  • Differentiation carries the most weight (60% in the example) → outweighs skills pointing to a partner
  • Skills gap → hiring or training, or use a partner only for specialised infrastructure work

Validate with stakeholders: the weights are a decision aid, not a rule.

Using the example weights, a capability scores differentiation 3, complexity 2 and skills 1. What does the result suggest, and what should you do with it?
  1. Score: 3 × 0.6 + 2 × 0.2 + 1 × 0.2 = 2.4
  2. Result → leans toward internal sourcing in the example
  3. Skills is scored inversely → the 1 means highly specialised skills are needed → a real gap to plan for
  4. Validate against actual skills and constraints, and test risky choices with a proof of concept

Exam-style questions

Answer aloud or on paper before opening.

A hospital's 15-year-old on-premises patient scheduling system slows down at morning peaks. The code is stable and meets business needs, but the database server is end-of-life, and patient data must stay in the country. Recommend a migration option, justify it with the drivers, and name two risks to manage.

Replatform: move to a managed database and auto-scaling in an in-country region, with minimal code change.

  • Drivers: risk (end-of-life platform) and scalability, not business fit
  • Not Rebuild → would add cost and risk without fixing anything the business needs
  • Two risks to manage:
    • database compatibility → test on the new engine, ideally with a proof of concept
    • compliance → jurisdiction, privacy, encryption

Budget for the migration bubble while both environments run.

A firm must exit its data centre in 6 months, with 80 apps, many over-provisioned. The CFO expects savings in year one. Compare lift-and-shift and lift-and-optimise, recommend a mix, and respond to the CFO.
  • Lift-and-shift
    • needs the least initial change and fits the deadline
    • but carries over-provisioning and inefficiency
  • Lift-and-optimise
    • lowers ongoing TCO
    • but takes longer and costs more up front
  • Recommended mix
    • lift-and-shift for most apps, sequenced by dependency and risk
    • optimisation only for a few high-cost apps that can be done in time
    • right-sizing after cutover
  • To the CFO: year one includes the migration bubble
    • duplicate environments, training, lease penalties
    • savings depend on retirement and optimisation afterwards
Design a portfolio assessment for an organisation with 200 applications and a 2-year programme. How would you decide each app's R, and which app would you migrate first?
  1. Establish a baseline
    • the drivers
    • an inventory and dependency map
    • the application concerns: performance, architecture, financial, risk, operations, security and compliance
  2. Diagnose each app's problem with the six drivers
  3. Assign the lightest R that fixes it, using the sourcing and hosting scoring to decide who runs it and where
  4. Choose the first migration on the eight criteria: low-risk, instructive, with an enthusiastic team, not the highest ROI
  5. Iterate in waves and compare TCO against the baseline
An insurer's 30-year-old policy system holds valuable rules, is nearly impossible to change, and is due to be replaced by a SaaS product in 3 years. A new mobile app needs policy data now. Choose between Retain, Encapsulate and Rebuild, and say what changes if the SaaS project is cancelled.

Encapsulate: expose policy data and functions through APIs, hiding the internals.

  • The mobile app can use them now; the system stays in place until the planned Replace
  • Not Rebuild → would duplicate work the SaaS replacement will make redundant
  • Not plain Retain → would leave the mobile app without data
  • Risk: the legacy system's availability and performance now limit the mobile app
  • If the SaaS project is cancelled: revisit the drivers
    • a Rearchitect or Rebuild behind the same APIs becomes the long-term path
    • the APIs let you swap the implementation without breaking the app
A team migrating a 3-tier app proposes containers instead of VMs for the web and app tiers, keeping the database on a VM. Evaluate the proposal, including where containers would be the wrong choice.

Reasonable for stateless web and app tiers.

  • Containers: lighter, usually start faster, package the app consistently, and let each tier scale on its own
  • Database: keep it on a VM or move it to a managed database if it needs OS-level tuning or strong isolation
  • Wrong choice where a workload needs a different OS kernel or strong tenant separation → containers share the host kernel

Actual startup gains depend on image size and application initialisation.
