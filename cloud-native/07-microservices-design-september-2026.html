Microservices Design

67 slides · about 40 min · open the deck · JSON

Decompose services around business capabilities and define their APIs, data ownership and collaborations. Compare synchronous calls, messaging, REST and gRPC, then connect gateways, discovery, versioning and maintenance. Adopt the extra distributed-system complexity only where independent delivery or scaling provides enough benefit.

Big ideas

  • A monolith is one code base, one build, one deployable; microservices are small, independently deployable services that each own their data and talk over the network via language-agnostic APIs (REST or messaging).
  • Microservices are not a silver bullet: Fowler says only use them when a system is too complex to manage as a monolith, because they add the 'microservice premium' of operational overhead.
  • Key benefits: polyglot technology, selective scaling, substitution, fault isolation, coexisting versions, event-driven extensibility, and DevOps-friendly small teams.
  • Decompose in three steps: identify system operations, identify services (business capabilities or DDD subdomains), then define service APIs and collaborations.
  • Communication styles: synchronous request/response (simple but tightly coupled) vs asynchronous messaging/events (loosely coupled, resilient); start sync and refactor to async where it adds value.
  • An API gateway is the single entry point that routes, aggregates, secures and monitors calls (north-south traffic); a service mesh handles service-to-service (east-west) traffic; a service registry tells everyone where instances live.
  • Version APIs to signal compatibility, test existing consumer contracts, and retain old incompatible versions until clients migrate.
  • Costs of microservices: harder troubleshooting, extra network latency, operational complexity, and version management overhead.

Monolith vs microservices

What a monolith is and why it hurts at scale, what microservices are, and the principles each service should follow.

Monolith

One code base, one build, one deployable, usually over one shared database.

  • Simple at first
  • All-or-nothing choices:
    • scaling
    • availability
    • release coordination
    • library/technology choices
  • Bottleneck for innovation
  • Costly to maintain

Microservices

Small, independent processes that each do one thing.

  • Do one thing each
  • Own their data
  • Talk over the network via language-agnostic APIs (REST or messaging)

Monolith vs microservices

  • Data: one shared RDBMS vs a private store per service (any language, any DB)
  • Release: one release train vs independent deployment
  • Result → a modular system with a longer shelf life and faster development

Service principles support independence

  • One business responsibility within a clear context
  • Private data ownership
  • External configuration
  • Explicit contracts
  • Resilient error handling
  • Useful metrics
  • Stateless application instances → simplify scaling; the service can still own durable domain state in its store
  • Reactive processing → use when the concurrency workload warrants it
Monolith
Single code base, single build, single deployable binary, usually one shared database.
Bounded context
A boundary within which a domain model has one consistent meaning; service boundaries should align with it, without requiring exactly one service per context.
Externalized configuration
Config kept outside the code (e.g. a config server) so it varies per environment without rebuilding.

Check yourself

A team split its monolith into 6 separately deployed apps, but they still share one relational database, and every release still needs a joint change window. Why?
  • Shared tables → a schema change for one app can break the others
  • → releases must be coordinated → independent deployment is lost
  • Fix: give each service private ownership of its data; others reach it through the service's API or events

Cost: cross-service queries and consistency now need design.

In a monolith, ticket creation needs 10 times more capacity at peak, and the reporting module needs a newer library version that conflicts with the rest. Which monolith shortcomings are these, and how would microservices address them?
  • All-or-nothing scaling: the whole app must be cloned to scale one hot function → as a service, ticketing scales on its own
  • Library or technology lock-in: one dependency set for everything → as a service, reporting picks its own stack

Price: network calls, separate deployments and more to monitor.

A new microservice keeps its config in a file inside the image and holds user sessions in memory. Which service principles does it break, and why do they matter for independence?

Breaks external configuration and stateless instances.

  • Baked-in config → rebuilding to change environments → move config outside the image
  • In-memory sessions → instances can't be added or replaced freely → move sessions to a shared store

The service still owns its durable domain data in its own store.

When microservices fit and how to migrate

What a microservice looks like in a system, why microservices are not always the right choice, and how to migrate and decide where to split.

Not a silver bullet

  • Fowler's microservice premium: they add overhead
  • Overhead:
    • operations
    • monitoring
    • versioning
    • network calls
  • Pays off only when the system is too complex to manage as a monolith
  • Simple systems → a monolith is more productive

Organisational shift, not just technical

  • Monolith: one large interdependent application run by layer-based teams (UI, DBA, test, build, server)
  • Microservices: small autonomous, domain-driven services run by cross-functional teams owning a service end to end
  • The price: more moving parts
    • more archives
    • more config files
    • more registration/discovery code

Migrate incrementally

  • Lecture suggestion: extract heavily used functions
  • Better: choose a coherent business capability with a measurable scaling or change problem and manageable dependencies
  • Pitfall: splitting a busy but tightly coupled function too early → chatty services

Where to split: four pressures (AKF Partners)

  • Developer throughput
    • change frequency
    • reuse
    • team size
    • specialist skills
  • Availability and fault tolerance
    • required reliability
    • business criticality
    • failure risk
  • Scalability
    • of data
    • of services
    • of dependencies
  • Cost
Microservice premium
Fowler's term for the extra overhead microservices impose, worth paying only for complex systems.
Cross-functional team
A small team with all skills needed to own one service end to end.

Check yourself

A startup with 3 developers and a simple CRUD app asks whether to start with microservices. What is your advice?

Start with a monolith.

  • Low-complexity systems: the microservice premium (operations, monitoring, versioning, network calls) → lowers productivity
  • Keep the code modular
  • Split later when complexity, team size or scaling needs justify it
The most-called function in a monolith is 'get customer', which nearly every module uses. A teammate wants to extract it first because it is the busiest. Do you agree?

Not on usage alone.

  • Called by every module → tightly coupled
  • Extracting it first → in-process calls become many chatty network calls → latency everywhere
  • Extract first: a coherent business capability with a measurable scaling or change problem and dependencies you can separate

Heavy use is one signal, not the deciding one.

A company adopts microservices but keeps separate UI, DBA, test and server teams, and every feature now needs four teams. What is missing?

Missing: the organisational shift.

  • Microservices assume small cross-functional teams that own a service end to end
  • Layer-based teams → every change crosses team boundaries → independence is lost
  • Reorganise around services

Otherwise the system takes on microservice overhead without the delivery benefit.

Using the four AKF pressures, should a company split out its payment capability, which changes rarely but must stay available during catalogue outages?

Probably yes, driven by availability and fault tolerance.

  • Availability / fault tolerance: payment is business-critical → should not fail when the catalogue does
  • Developer throughput: little reason, since it changes rarely
  • Cost: a separate service adds operations
  • Scalability of its data and dependencies: weigh this too

Why adopt microservices: the benefits

The ten benefits taught in the lecture, with examples, and which well-known companies adopted the style.

Benefits come from independence

  • Polyglot → each service picks the right technology (e.g. an audit service on Kafka/HDFS beside MySQL services)
  • Experimentation → a new feature (hotel recommendation) plugs into an existing flow so you can fail fast
  • Substitution → a self-contained service (pricing) can be swapped for in-house or third-party
  • Organic growth → a monolith can be peeled apart step by step

Selective scaling (the classic example)

  • Monolith → scales by cloning the whole application behind a load balancer
  • Microservices → scale only the busy service (e.g. 3 Ticketing instances while Search and Catalog stay at 1)
  • Result → saving resources

Versions and technology debt easier

  • New services use current technology while old ones stay put
  • Migrating one small end-of-life service is far cheaper than upgrading a monolith
  • Each service packages its own runtime → V1 and V2 can coexist
  • Gateway routes by rule (e.g. one region to V2)

Events enable new consumers

New consumers without direct publisher calls.

  • Analytics service subscribes to an existing order topic without changing the publisher's code
  • Consumer must still understand:
    • event contracts
    • retention
    • authorisation
    • duplicate handling

A new consumer does not eliminate impact analysis.

Small services enable DevOps

  • Fast releases
  • Automated testing, provisioning and deployment
  • Teams aligned to service boundaries
  • Adopters → Netflix, Uber, Amazon, Twitter
Polyglot
Different languages or databases for different services, each fit for purpose.
Selective scaling
Scaling out only services under load rather than the whole app.
Event-driven architecture
Services publish events to topics; any interested service subscribes without the publisher knowing.
Technology debt
Accumulated cost of outdated technology that makes change expensive.

Decomposition, characteristics and building blocks

How to decompose an application into services, the key architectural characteristics, and the platform capabilities needed to host microservices.

Decompose in three steps

  1. Identify system operations from the requirements
  2. Identify services by business capability or DDD subdomain
  3. Define service APIs and collaborations by assigning each operation to a service

A service is a standalone, independently deployable component reachable only through its API.

Key architectural characteristics

  • Business-oriented: designed around business objectives, deployable or removable without affecting others
  • Design for failure: fault modelling, fault injection
  • Decentralised data: own DB per service, avoid distributed transactions, polyglot persistence
  • Discoverability: a registry
  • Inter-service communication: sync REST or async broker
  • Evolutionary design

ESB-centred SOA vs microservices

The lecture contrasts ESB-centred SOA with lightweight microservices.

  • Microservices → emphasise independent deployment and private data ownership
  • SOA → a broader service-oriented approach; does not inherently require a central ESB or shared database

Hosting: platform building blocks

  • API gateway (outside access)
  • Service discovery
  • Diagnosability/monitoring
  • Configuration and coordination
  • Microservice chassis for cross-cutting concerns
  • on a cloud-native platform

Capabilities: four groups

  • Core
    • listeners
    • implementation
    • storage
    • endpoints
  • Infrastructure
    • cloud
    • VMs
    • containers
    • lifecycle management
  • Supporting
    • gateway
    • load balancer
    • discovery
    • security
    • config
    • messaging
    • logging/monitoring
    • build
  • Process and governance
    • DevOps
    • automation
    • registry
    • documentation
    • templates
Business capability
Something the business does to create value (e.g. order management); a common basis for service boundaries.
Microservice chassis
Base framework handling cross-cutting concerns (config, discovery, health, logging).
Decentralised data management
Each service owns its database, avoiding shared schemas and distributed transactions.

Two services need to update an order and an inventory record together, and a teammate proposes a distributed transaction across both databases. What does the lecture's decentralised-data characteristic suggest?

Avoid distributed transactions.

  • Each service owns its database
  • Services coordinate through their APIs or events
  • Compensating actions if a step fails
  • → services stay independently deployable

Cost: eventual consistency + designing for failed or repeated steps.

An architect says 'our SOA already has services, so we have microservices'. The SOA routes everything through a central enterprise bus and several services share a database. What is the difference?
  • Microservices emphasise independent deployment, lightweight communication and private data ownership
  • This SOA: a central bus holding integration logic + a shared database → couples services in deployment and data
  • SOA doesn't require a central bus, but this one has one

To move toward microservices: move logic out of the bus and give each service its own data.

A team has deployed 8 services, but ops can't tell which one failed in an incident, and each service has its own way of reading config. Which platform building blocks are missing?
  • Diagnosability and monitoring: central logs, metrics, tracing
  • Configuration management
  • A microservice chassis for cross-cutting concerns would standardise both
  • Also needed: service discovery (finding services) and an API gateway (outside access)

These capabilities are what make many small services operable.

A team releases a risky change to a payment service. Should they use a canary release or blue-green, and what does each give up?

Canary: usually safer for a risky payment change.

  • Canary: a small slice of traffic to the new version first
    • Limits exposure, gives real-traffic evidence
    • Gives up: both versions run at once → they must be compatible
  • Blue-green: switches all traffic between two environments in one step
    • Fast, clean rollback
    • Gives up: needs double capacity, exposes everyone at once
A team on Kubernetes plans to install a separate service registry. What would you ask before approving it?

Ask: does the platform already provide discovery?

  • Kubernetes DNS and Services already resolve and load-balance service names
  • A separate registry adds another component that must stay highly available
  • Justified when services span environments outside the cluster or need registry features the platform lacks

Inter-process communication

Communication styles, protocol and format choices, RPC/gRPC, REST maturity, messaging, and how to choose sync vs async.

Communication styles

Communication style is the central design choice.

  • Synchronous blocking (caller waits) vs asynchronous non-blocking (caller carries on)
  • Request/response (expects a result) vs one-way notification vs publish/subscribe (one-to-many)
  • Event-driven → emitter doesn't know the consumers
  • Common data → a shared source, rarely a good idea
  • Synchronous request/response → simple but tightly couples services
  • Async messaging via queues or topics → decouples them and improves resilience, at the cost of complexity

Choose sync or async per interaction

  • Direct query → may need an immediate result (sync)
  • Deferred work → benefits from a durable queue or topic
  • Async introduces → ordering, retry and consistency questions
  • Reactive non-blocking code → changes how a process waits; does not remove downstream dependencies or guarantee delivery

Implementation options

  • RPC → call a remote method like a local one
  • REST → resources and standard HTTP verbs
  • GraphQL → consumer writes a custom query across services
  • Message brokers
  • Text formats (JSON, XML) → self-describing but verbose and slower to parse
  • Binary formats (Protocol Buffers, Avro) → compact

gRPC vs REST

  • gRPC → schema-defined messages + HTTP/2 + streaming for efficient cross-language calls
  • REST/JSON → often fits external web APIs
  • Check → browser/proxy support and client tooling; don't assume every JavaScript client or firewall has the same limitation

Richardson REST maturity

  1. Level 0: POST everything to one URL
  2. Level 1: resources exist but actions are still POSTed
  3. Level 2: proper HTTP verbs (GET/POST/PUT) → enables caching of GETs
  4. Level 3: HATEOAS → responses carry links to next actions
gRPC
Cross-language RPC framework using Protocol Buffers over HTTP/2 with streaming.
Protocol Buffers
Compact binary message format defined by an IDL schema.
HATEOAS
Responses carry links for next actions (REST level 3).
GraphQL
Query language letting clients request exactly the data they need, possibly from several services.
Publish/subscribe
One-to-many async messaging via a topic.

Check yourself

When an order is placed, the Order service calls Payment, Inventory and Notification synchronously, and an outage in Notification makes orders fail. Redesign the communication.
  • Synchronous, time-bounded call only where the order needs an immediate result, such as payment authorisation
  • Publish an 'order placed' event to a durable topic for notification and other deferred work
  • → a Notification outage delays emails instead of failing orders

Cost: eventual consistency + handling retries, ordering and duplicate events.

Internal services exchange large volumes of small messages, and JSON parsing is a measurable cost. A public partner API also exists. Would you use gRPC, REST/JSON or both?

Both.

  • gRPC for internal calls: schema-defined binary messages over HTTP/2 → compact and fast to parse across languages; supports streaming
  • REST/JSON for the partner API: self-describing, widely supported by web clients and tooling

Check proxy and browser support before using gRPC beyond internal traffic.

An API uses POST /api for every action, with the action name in the request body, and the team wonders why responses can't be cached. Which REST maturity level is this, and what would you change?

Level 0: one URL, everything POSTed.

  1. → Level 1: resources
  2. → Level 2: proper HTTP verbs → reads become GET requests that web infrastructure can cache; writes use POST, PUT or DELETE
  3. Level 3: links to next actions (HATEOAS) → helps discoverability, but optional for most internal APIs
A team switched to reactive, non-blocking code and says 'our services are now decoupled from their dependencies'. Is that right?

No.

  • Reactive code changes how a process waits → threads aren't blocked
  • The service still depends on its downstream calls succeeding and has no delivery guarantee
  • Decoupling comes from asynchronous messaging through a durable queue or topic, together with timeouts and fallbacks

API gateway, versioning and service discovery

Why clients need an API gateway and a service registry, semantic versioning, and client-side vs server-side discovery.

One front door, find services

Clients need one front door and a way to find services.

  • Monolith → one call sufficed and location was fixed
  • Many services → client would make many calls and need to know where each lives
  • API gateway → the single entry point that calls services and aggregates results
  • Service registry → stores where instances live

Gateway vs mesh

  • Gateway → north-south (client to service) traffic:
    • routing
    • transformation
    • throttling
    • security
    • metering
    • protocol translation
    • composition
    • caching
    • monitoring
  • Service mesh → east-west (service to service) traffic

Why a gateway helps

  • Separates consumers from providers
  • Each client type gets the API it needs
  • Orchestrates many calls into one → essential for mobile with latency and bandwidth limits
  • Centralises monitoring of API usage

Semantic Versioning

Signals compatibility.

  • MAJOR → incompatible changes
  • MINOR → compatible enhancements
  • PATCH → compatible fixes
  • Adding an optional field → compatible only if existing defaults and consumer behaviour remain valid
  • New required field or changed meaning → can still break clients

Client-side vs server-side discovery

  • Register then discover → services register with the registry (e.g. Eureka), then are discovered
  • Client-side → client queries the registry, load-balances itself, calls the instance directly; needs discovery code per language
  • Server-side → client calls a load balancer that queries the registry and routes; hides discovery from clients
  • Server-side cost → adds another highly available component unless the platform (Kubernetes) provides it
API gateway
Single entry point that routes, aggregates, secures, throttles and monitors requests.
Service registry
Database of service instances and locations, e.g. Eureka, Consul.
Service mesh
Infrastructure layer (Istio, Linkerd) for east-west traffic.
Semantic Versioning
MAJOR.MINOR.PATCH scheme signalling breaking vs compatible changes.

Check yourself

A mobile app's home screen makes 9 calls to different services and is slow on poor networks. What would you change?

Add an API gateway (or a backend for the mobile client).

  • It calls the services and composes one response tailored to the screen
  • → cuts round trips and payload size for limited mobile bandwidth

The gateway becomes a critical component: it must be highly available and must not accumulate business logic.

A polyglot estate (Java, Go, Python) uses client-side discovery with a registry library, and the Python library is unmaintained. What are the options?

Switch to server-side discovery.

  • Clients call a load balancer or platform service name that queries the registry
  • → no discovery code needed per language
  • Cost: another component that must be highly available, unless the platform, such as Kubernetes, already provides it

Client-side discovery saves a hop but needs library support in every language.

A team adds an optional request field and a new response attribute and calls it version 2.0.0. Is MAJOR right?

Usually not: this is MINOR.

  • MINOR if omitting the field keeps the old meaning and existing consumers ignore unknown response fields
  • A MAJOR bump wrongly signals a breaking change → can trigger unnecessary migrations
  • Test those consumer assumptions: a new required field or a changed meaning would be MAJOR

Maintenance, maturity and pros/cons

Practices for keeping microservices healthy, a maturity model, rules and workflows, and the summary of advantages and disadvantages.

Design recovery for each interaction

  • Preserve compatible APIs
  • Set client timeouts
  • Return useful errors
  • Monitor before restarting → a slow dependency is not always a failed process
  • Durable queue subscriptions → retain work for recovery, subject to retention, acknowledgement and retry policy
  • Make handlers idempotent

Maturity: five dimensions, Level 0 to 3

  • Application: monolithic → API-centric
  • Database: enterprise DB → data lake
  • Infrastructure: physical → containers
  • Monitoring: infra only → APM with central logs
  • Process: waterfall → DevOps

Low maturity is a warning sign for adopting microservices.

Rules and workflows

  • Simple rules local to a service → embedded rule engine
  • Complex or cross-domain rules → central rule repository
  • End-to-end processes mixing automation and people → composed with BPM or a dashboard

Advantages

  • Technology heterogeneity
  • Modularity
  • Simplicity per service
  • Selective scaling
  • Continuous delivery and DevOps
  • Fault isolation
  • Graceful degradation
  • Data segregation
  • Team alignment
  • Composability or easy replacement

Disadvantages

  • Harder troubleshooting → every network call can fail
  • Added latency
  • Operational complexity → hundreds of services to deploy, monitor and back up
  • Version management overhead
Failsafe design
Designing calls to fail gracefully, e.g. client timeouts and provider defaults or clear error codes.
Fault isolation
A failure in one service is contained and does not bring down others.

A downstream inventory service is often unavailable for minutes at a time, and the order service's threads pile up waiting. Give the cause, a countermeasure and the countermeasure's drawback.

    • Centralise logs and tracing

Exam-style questions

Answer aloud or on paper before opening.

A retailer's monolithic e-commerce app slows down at sale peaks (search traffic rises 10 times, checkout 3 times), and releases take 6 weeks because 5 teams share one deployable. Propose a microservices design and an incremental migration plan, and name the main risk at each stage.
  1. Design: decompose by business capability
    • Catalog/Search, Cart, Order, Inventory, Payment
    • Assign operations and define APIs; each service has its own data
    • Behind an API gateway with service discovery
  2. Incremental migration
    • Extract Search first: biggest load difference, read-heavy, and its data can be copied
    • Then extract Cart and Order
  3. Main risk per stage
    • At first: data synchronisation between the new Search store and the monolith
    • Later: consistency between Order, Inventory and Payment without distributed transactions

Independent deployment through CI/CD addresses the 6-week release cycle, but only if teams are reorganised around services.

A 6-person team with manual deployments, infrastructure-only monitoring and a moderately complex internal app is told to 'go microservices'. Argue whether they should, using the microservice premium and the maturity model, and say what would change your answer.

They shouldn't yet.

  • Microservice premium (operations, monitoring, versioning, network latency, troubleshooting) pays off only when a system is too complex to manage as a monolith
  • A moderately complex app for 6 people is unlikely to qualify
  • Maturity model: low maturity on process and monitoring makes it worse → they couldn't diagnose distributed failures
  • Instead: build a modular monolith and raise DevOps maturity

Reconsider if the team grows, parts need very different scaling or availability, or release coordination becomes the bottleneck.

Design the communication between Order, Payment, Inventory and Notification services for a shop that must confirm payment to the user within 3 seconds and must never charge twice. Justify each synchronous or asynchronous choice.
  • Order → Payment: synchronous
    • Time limit under the 3-second budget, because the user needs the outcome
    • Passes an idempotency key → a retry never charges twice
  • Order → Inventory, Notification: asynchronous
    • After payment, Order publishes an 'order paid' event to a durable topic
    • Inventory reserves stock; Notification sends email
    • → their outages don't fail checkout
  • Persist order and payment state; consumers handle duplicate events
  • If inventory later fails → compensate by refunding or back-ordering, not a distributed transaction
  • gRPC can carry the internal calls
A system has 40 services, a mobile app and a web app. Explain the roles of an API gateway, a service registry and a service mesh, say which traffic each handles, and say which you could do without if the platform is Kubernetes.
  • API gateway: north-south traffic from the mobile and web apps
    • Routing, composition, security, throttling, protocol translation, monitoring
    • Can be tailored per client type
  • Service registry: records where service instances live → for client-side or server-side discovery
  • Service mesh: east-west traffic between the 40 services
    • Retries, encryption, telemetry
  • On Kubernetes
    • The platform's Services and DNS already provide discovery → a separate registry is often unnecessary
    • The mesh is justified at 40 services if uniform policy is needed, at the cost of extra hops and a control plane
A public pricing API is used by 200 external clients. The team must rename a field, add an optional discount field and fix a rounding bug. Plan the version numbers and the rollout so no client breaks.
  • Rounding fix → PATCH
  • Optional discount field → MINOR, provided omitting it keeps the old meaning and clients ignore unknown response fields (test with consumer contracts)
  • Renaming a field → incompatible → MAJOR
  • Rollout
    • Run V1 and V2 side by side
    • Route by version at the gateway
    • Document both contracts with OpenAPI
    • Retire V1 only after the 200 clients have migrated, tracked through gateway metrics

Cost: supporting two versions for the migration period.
