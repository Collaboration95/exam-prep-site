Cloud Security: An Overview

47 slides · about 30 min · open the deck · JSON

Analyse a cloud threat by its affected security property, responsible party and relevant control. Apply shared responsibility across service models, then protect data, applications and identities through their lifecycle. Use the lecture’s historical cases to connect prevention with monitoring, audit and recovery rather than assuming a cloud model is inherently secure.

Big ideas

  • Shared responsibility: the provider secures the cloud itself, and the customer secures what they put in the cloud. The split shifts with IaaS, PaaS and SaaS.
  • Customers always remain responsible for data classification and accountability, even in SaaS.
  • The CSA 'Treacherous Twelve' threats (data breach, weak IAM, insecure APIs, system vulnerabilities, account hijacking, malicious insiders, APTs, data loss, insufficient due diligence, abuse of cloud services, DoS, shared technology vulnerabilities) can each be analysed with STRIDE and mapped to CSA domains.
  • Security components split into identity management (users), application security (apps) and data security (data).
  • Protect data across its lifecycle (create, store, use, share, archive, destroy) and in all states: at rest, in motion and in use.
  • Who holds the encryption key is the central encryption question; masking and tokenization protect sensitive data that must stay usable.
  • Access control decisions use actor, function, location and other attributes, enforced through IAM, federated identity and key management.
  • Manage cloud security by monitoring data and traffic (e.g. CloudWatch), gaining visibility via audit trails (e.g. CloudTrail), and managing access (IAM, SSO).

Security threats: motives, types, statistics

Why attackers attack, the main categories of attack, and statistics showing how frequent and costly breaches are.

Attacker motives

Know the attacker's motive, then the technique.

  • Stealing information for competitors
  • Financial gain
  • Espionage
  • Operational disruption

Attack techniques

  • Phishing → impersonated email
  • Malware
    • ransomware → blocks access
    • spyware → exfiltrates
    • worms/viruses → disrupt
  • Man-in-the-middle → intercepting a two-party exchange
  • Denial of service → flooding to exhaust resources
  • SQL injection → malicious input makes a SQL server leak data
  • DNS tunneling → smuggling data out over port 53

Map attack to the property it breaks

  • DoS → availability
  • Man-in-the-middle and spyware → confidentiality and integrity
  • Ransomware → availability of data

The quickest way to pick controls in a scenario.

Historical statistics

Cited by the lecture; not a current risk forecast.

  • Attacks every 39 seconds
  • 71% financially motivated
  • 25% espionage
  • Average breach cost USD 3.92 million
  • Only 5% of folders properly protected

Use the figures to motivate controls; prioritise actual assets and threats rather than treating these percentages as universal.

Detection and containment both matter

  • Cited 2019 averages → 206 days to identify; 314 days from breach to containment (the latter includes detection time)
  • Yahoo and Uber → illustrate the scale of historical incidents
  • Prevention alone is insufficient
  • Reduce the time an intrusion remains active:
    • retained logs
    • audit trails
    • alerting
    • response capability
Phishing
Impersonating a trusted sender, usually by email, to trick people into giving sensitive information.
Ransomware
Malware that blocks access to systems or data until a ransom is paid.
Man-in-the-middle
Attacker secretly intercepts communication between two parties.
SQL injection
Inserting malicious SQL into inputs so the database reveals or changes data.
DNS tunneling
Hiding non-DNS traffic inside DNS (port 53) to exfiltrate data.

Check yourself

A team's security budget goes entirely to preventive controls (firewalls, WAF, hardening), with no log retention or alerting. Using the lecture's figures on time to identify and contain breaches, critique this.
  • Cited figures: historical averages of about 206 days to identify and 314 days from breach to containment (which includes the 206)
  • → intrusions often stay active for months
  • Prevention alone: leaves no way to notice or investigate one
  • Fix: move some budget to retained, protected logs and audit trails, alerting, and an incident response process → shorten that window
An online store suffers two incidents: a flood of requests that makes checkout unavailable for an hour, and an attacker on public Wi-Fi intercepting and altering customers' sessions. Which property does each break, and which control addresses each?
  • Flood = denial of service → an attack on availability → DDoS protection, rate limiting, autoscaling headroom
  • Interception = man-in-the-middle → breaks confidentiality and integrity → enforce TLS end to end, with secure cookies and certificate validation

Naming the property first points to the right control.

The lecture's figures say most breaches are financially motivated. A startup concludes it should spend its whole security budget on encrypting its database. Is that the right inference?

Not by itself.

  • Financial motive → protect valuable data and the privileged credentials that reach it
  • Encryption at rest doesn't stop an attacker who steals an application or admin credential that can decrypt
  • Prioritise from the system's actual assets and risks
    • Least-privilege access
    • Credential protection
    • Then encryption and tokenisation where they cut exposure

Shared responsibility, enterprise concerns and CSA

Explains what changes in the cloud (shared responsibility by service model), lists what enterprises worry about, and introduces the Cloud Security Alliance and its 14-domain guidance.

Shared responsibility

The provider secures the cloud, the customer secures what is in it.

  • Cloud security → like on-premises security without owning facilities and hardware
  • Protect information flows with software-based tools

Responsibility shifts with service model

Responsibility shifts upward with the service model.

  1. IaaS → customer operates OS and applications
  2. PaaS → provider manages more runtime/host work
  3. SaaS → provider operates the application too

Data classification and access accountability stay with the customer. Joint controls still need both sides: the provider runs a firewall service, the customer sets appropriate rules.

Why enterprises hesitate

Even when the provider is secure:

  • Privacy
  • Ownership and control
  • Trust
  • Governance requirements
  • Regulation and legislation
  • Access to skills

CSA guidance: 14 domains

CSA guidance groups concerns rather than replacing a threat model. The lecture's chart lists:

  1. Cloud concepts/architecture
  2. Governance/risk
  3. Legal/contracts/e-discovery
  4. Compliance/audit
  5. Information governance
  6. Management plane/business continuity
  7. Infrastructure
  8. Virtualisation/containers
  9. Incident response
  10. Application security
  11. Data/encryption
  12. Identity/entitlement/access
  13. Virtualisation
  14. Security as a service

It repeats virtualisation in domains 8 and 13, so use the chart as the lecture's taxonomy rather than a definitive version-to-domain reference.

Shared responsibility model
Security duties are split between provider (security of the cloud) and customer (security in the cloud), varying by IaaS/PaaS/SaaS.
CSA
Cloud Security Alliance: non-profit setting cloud security best practices, guidance and certifications.

Check yourself

A company moves from IaaS VMs to a SaaS CRM. Which security duties does it stop doing, and which does it keep?
  • Stops: patching and operating the OS, middleware and application, which the SaaS provider now runs
  • Keeps: data classification, decisions about who gets access, account management, accountability for its data
  • Shared: endpoint and identity duties

Moving to SaaS shifts operations, not accountability.

A provider's firewall service worked as designed, but a rule allowing all inbound traffic exposed a database. Who is responsible, and what does this example show?

The customer.

  • Provider: responsible for the firewall service working
  • Customer: responsible for configuring its rules
  • → a joint control, where each side owns a different part

Audit and review rules as code to catch this kind of misconfiguration.

A provider passes every security audit, but a government agency still hesitates to move. Give two concerns that the provider's security can't resolve, and what would address each.
  1. Regulation and legislation about where data may live and who can access it → in-country regions or a hybrid placement, with contract terms
  2. Ownership, control and trust → key control, exit terms and audit rights in the contract

Another concern: lack of in-house cloud skills → training or a partner.

CSA Treacherous Twelve threats

The lecture’s historical CSA threat list and cases, analysed with STRIDE and linked to relevant security controls.

The Treacherous Twelve

The historical CSA threat list used in this course; use it as a checklist for threat analysis.

  • Analyse each threat with STRIDE:
    • Spoofing
    • Tampering
    • Repudiation
    • Information disclosure
    • Denial of service
    • Elevation of privilege
  • Map each to the CSA domains that address it

Identity and access threats

  • Data breach → BitDefender 2015: credentials stolen from an AWS-hosted app, USD 15,000 ransom demanded (information disclosure)
  • Insufficient identity, credential and access management → cloud credentials committed to GitHub were misused within 36 hours; possible consequences depend on the credential's permissions
  • Account hijacking → an Amazon XSS bug let attackers steal credentials
  • Malicious insiders → the 'privileged identity gap': rein in shared accounts and track user activity

Software and interface threats

  • Insecure interfaces and APIs → the IRS 'Get Transcript' API leaked over 300,000 records
  • System vulnerabilities → Heartbleed and Shellshock showed open-source software is not automatically safer
  • Shared technology vulnerabilities → VENOM, a QEMU floppy-controller buffer overflow, let one guest escape to the hypervisor and take over the host and its other tenants
  • Shared-platform risk → amplified by multi-tenancy, including private virtualised environments

Business and availability threats

  • Data loss → Code Spaces was hacked, most customer data destroyed, and the firm closed
  • Insufficient due diligence → Nirvanix went bankrupt and gave customers under two weeks to move data
  • Advanced persistent threats → stealthy, long-running espionage, e.g. hundreds of terabytes taken from 141 organisations
  • Abuse of cloud services → attackers rent capacity from providers who cannot vet everyone, and run DDoS for weeks
  • Denial of service → rising DDoS against providers

Breach vs data loss, hijacking vs insider

  • Breach → disclosure (confidentiality)
  • Data loss → destruction (availability/integrity)
  • Hijacking → an outsider taking over an account
  • Insider → already has legitimate access and abuses it
Treacherous Twelve
Historical CSA cloud-threat list used by the lecture for case-based analysis.
STRIDE
Threat model: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.
XSS
Cross-site scripting: injecting script into a web page to run in other users' browsers, e.g. to steal credentials.
APT
Advanced Persistent Threat: a long-running, stealthy, well-resourced intrusion, often state-backed.
DDoS
Distributed denial of service: many sources flood a target to make it unavailable.
Hypervisor escape
Breaking out of a guest VM to control the host hypervisor and the other tenants on it.

Check yourself

A developer commits a cloud access key to a public repository, and it is misused within 36 hours. Using STRIDE, what could happen, and what limits the damage?
  • STRIDE, depending on the key's permissions
    • Spoofing: acting as that identity
    • Tampering with or disclosing data
    • Denial of service by deleting or exhausting resources
    • Elevation of privilege if the role can grant more access
  • Least privilege → limits what the key can do
  • Short-lived credentials and rotation → limit how long
  • Audit trails → support investigation
  • Secret scanning in the pipeline → prevents the commit in the first place
A public API that returns tax records was abused to pull hundreds of thousands of records, as in the IRS 'Get Transcript' case. Which controls would have reduced the risk?

Treat the API as an attack surface:

  • Strong authentication and per-record authorisation
  • Input validation and application security testing
  • Rate limiting and monitoring for abnormal access patterns
  • A WAF
  • Incident response able to detect bulk extraction quickly

Any single control alone would have left gaps.

A company chooses a private virtualised cloud 'so we are safe from shared-technology vulnerabilities like VENOM'. Is that reasoning sound?

Only partly.

  • Multi-tenancy in public cloud amplifies the risk: a guest escape to the hypervisor can reach other customers' workloads
  • Private virtualised environments share the same class of risk across their own workloads
  • Still matter: patching hypervisors and separating high-sensitivity workloads
A small storage provider your firm depends on announces it is closing and gives customers two weeks to move their data. What should you have done beforehand?

This is the insufficient due diligence threat.

  • Due diligence on the provider's financial and operational stability
  • Exit and data-return terms in the contract and SLA
  • Backups held independently of the provider
  • A tested portability plan that avoids deep lock-in

The Nirvanix case shows how short the notice can be.

One incident: an outsider steals an admin's password through a phishing page and logs in. Another: a database administrator copies customer records before resigning. Classify each and give the most relevant control.
  • Phishing then login = account hijacking: an outsider takes over a legitimate account → strong multi-factor authentication and anomaly detection
  • DBA copying records = malicious insider, who already has legitimate access → least privilege, no shared admin accounts, activity monitoring, prompt deprovisioning

Both are breaches (disclosure), not data loss.

Data security and encryption

Splits cloud security into identity, application and data security, then covers data classification, the data lifecycle, encryption, masking and tokenization.

Security splits by layer

  • Identity management → users: transmission, authentication
  • Application security → access control
  • Data security → key management, encryption

In the cloud the focus shifts from infrastructure to data, because the customer always owns its data.

Three questions about data

What is it, where is it, how is it protected?

  • Type → confidential, public, sensitive
  • State → at rest, in motion, in memory
  • Protection → encrypt stored and transmitted data and manage keys (BYOK/KYOK)

Protect data across its lifecycle

  1. Create → classify
  2. Store → encrypt, access control, backup, monitor
  3. Use → DLP, DRM, database activity monitoring, WAF
  4. Share → DLP, DRM, HTTPS/TLS, VPN, SSH
  5. Archive → retention policy, encryption, access control, retrievability
  6. Destroy → secure disposal and crypto-shredding

Encryption: who holds the key

Encryption is applied per layer, but the key question is who holds the key.

  • In transit → TLS/VPN
  • At rest → file, volume, object and database encryption (transparent or application-level)
  • Provider holds keys → not all threats are covered
  • Consumer holds keys → it must protect them, and the provider may be unable to process encrypted data
  • RAM and moving data → add further weaknesses

Masking and tokenization

Reduce unnecessary exposure.

  • Masking → changes or hides values shown to a viewer or placed in a derived dataset
  • Tokenization → substitutes a token and protects its mapping or recovery mechanism separately
  • Complement → authorisation and encryption
  • Compliance effect → depends on the design

Deployment model vs sensitivity

Deployment model does not decide sensitivity by itself.

  • Lecture illustration → private placement for confidential systems, public placement for other workloads
  • In a design answer, test:
    • data location
    • access
    • provider duties
    • key access
    • recovery requirements

Public cloud is not inherently unsuitable for sensitive data.

Data at rest / in motion / in use
Stored data, data travelling over a network, and data being processed in memory.
BYOK / KYOK
Bring Your Own Key / Keep Your Own Key: customer-supplied or customer-retained keys; actual decryption authority depends on service integration and access policy.
DLP
Data Loss Prevention: tools that detect and block sensitive data leaving where it should be.
Crypto-shredding
Making encrypted data unreadable by destroying all usable copies of its encryption keys, subject to retained plaintext and backup copies.
Data masking
Showing altered values (e.g. XXX) to unauthorised viewers while keeping data usable.
Tokenization
Replacing sensitive values with tokens whose mapping is kept separately and securely.

Check yourself

Customer support staff need to verify the last 4 digits of a card, and a payments service needs to process refunds. Masking or tokenisation for each?
  • Support → masking: the screen shows only the last 4 digits, hiding the rest from viewers
  • Payments → tokenisation: systems store and pass a token; only the protected vault that holds the mapping can recover the real number

Both reduce exposure but still need access controls, and their compliance effect depends on the design.

A team says its data is safe 'because we use BYOK'. What should you check?

Check who can actually use the key to decrypt.

  • BYOK: the customer supplies the key, but the provider's service may still use it to process data → doesn't prove the provider can't decrypt
  • Check key-use permissions, recovery and revocation
  • Check whether customer-held keys are needed

Customer-held keys mean the provider may be unable to process the encrypted data.

Encrypted-at-rest customer data leaks through an application endpoint that returned other users' records. Why didn't encryption help, and what would have?
  • Why encryption didn't help: the running application is authorised to decrypt and read the data → encryption at rest protects stored media, not misuse by an authorised process
  • Needed: authorisation checks on each record, least-privilege data and key permissions, access monitoring

Encryption complements access control; it doesn't replace it.

A company relies on crypto-shredding to destroy a closed customer's data. What could make it fail?

Crypto-shredding works only if no usable decryption keys or plaintext copies remain.

  • Plaintext in backups, logs, caches or analytics exports → data still readable
  • A key that was replicated elsewhere → data still readable
  • Fix: apply the retention policy and key destruction across every copy

This is why classification at creation matters.

Application, user and access security

How to secure applications (scanning, DevSecOps), users (resource and network protection), the network and hardware layer, and how to make access-control decisions.

Classify first, then protect

  • Apps → mission-critical, infrastructure or business-function
  • Users → public, registered, or employees/developers/administrators

The class sets how strong the controls need to be.

Secure applications through the pipeline

  • Scan applications
  • Scan containers
  • Adopt DevSecOps → security built into delivery rather than added at the end

Defence in depth

  • Subnets → zone the network
  • Security groups → filter connections
  • Host firewalls → add local rules
  • VPN → protects hybrid connectivity
  • WAF → filters HTTP-level exploits and some application-layer abuse
  • Broader DDoS protection → addresses resource and network flooding
  • HSM → tamper-resistant key operations, not immunity to every attack

Access decision attributes

Access decisions use actor, function, location and other attributes.

  • Actor → who
  • Function → what action
  • Location
    • network (office, home, VPN)
    • machine (own vs company)
    • country (data export limits)
  • Others → group membership and time of day
  • Enforce with → key management, federated identity, IAM
DevSecOps
Building security checks (scanning, testing) into the DevOps pipeline rather than at the end.
Security group
Cloud virtual firewall rules controlling traffic to and from instances.
WAF
HTTP-layer firewall for web request filtering; broader network DDoS protection is a separate concern.
HSM
Hardware Security Module: tamper-resistant hardware for protected key generation, storage and cryptographic operations.

Check yourself

An employee tries to download the full customer database at 3 a.m. from a personal laptop in another country. Which access-control attributes should influence the decision, and what is a sensible outcome?
  • Actor: is this employee allowed this data?
  • Function: bulk download, not just viewing
  • Location: a personal rather than company machine, and a country that may break data-export rules
  • Time of day

Outcome: deny the request, or require step-up verification and limit it to viewing; enforce through IAM and federated identity, not ad-hoc checks.

A team protects its app with security groups only and asks why it would also need a WAF. What do you tell them?
  • Security groups: filter network connections by address and port → allow any request on an allowed port, including malicious HTTP payloads such as SQL injection
  • WAF: inspects HTTP content

Layer them with host firewalls and provider DDoS protection, because each covers a different boundary.

Security reviews happen only before release, and last quarter a vulnerable base image reached production. What would you change?

Adopt DevSecOps.

  • Scan application code and container images in the pipeline on every build
  • Fail builds on serious findings → security built into delivery rather than checked at the end
  • Mission-critical apps get stricter gates

Cost: slower pipelines and time spent triaging false positives.

A payments team must protect signing keys so that even a compromised admin can't copy them. Would an HSM meet the requirement, and what does it not guarantee?

Yes, for the copying concern.

  • HSM: keeps keys and cryptographic operations inside a tamper-resistant hardware boundary → keys can be used but not extracted
  • Not guaranteed: it doesn't stop a compromised identity from asking the HSM to sign

Access policy, key handling and monitoring of HSM use still matter.

Managing cloud security and conclusions

Ongoing security management has three steps (monitor, gain visibility, manage access), with AWS tools as examples, followed by the deck's concluding principles.

Ongoing security loop

  1. Monitor
  2. Gain visibility
  3. Manage access

Use the provider's native tooling for each.

Monitoring vs audit

They answer different questions.

  • CloudWatch-style → metrics/logs/alarms show health and behaviour
  • CloudTrail-style → audit events record supported identity and resource actions, helping reconstruct who did what
  • Verify → logging scope, retention, protection
  • Caveat → a log identity may itself have been compromised

IAM functions

The right people, the right resources, at the right times, for the right reasons.

  • Manage identities
  • Provision/deprovision
  • Authenticate
  • Authorise
  • Report
  • Single sign-on

Conclusions

  • SLA → the consumer-provider contract
  • Responsibility varies by service model
  • Providers supply → network, device, identity and encryption services
  • Focus shifts to data security
  • Secure data → in transit, at rest and in use
  • Access control follows classification across the whole data lifecycle
AWS CloudWatch
AWS monitoring service: metrics, logs, alarms and dashboards for resources.
AWS CloudTrail
AWS audit service recording supported account/resource activities; event coverage and retention depend on configuration.
IAM
Identity and Access Management: right people, right resources, right time, right reason.
SSO
Single Sign-On: one authentication grants access to multiple systems.

Check yourself

A production database was deleted overnight. Would you look in monitoring metrics or in audit events to find who did it, and what can't the record tell you?

Audit events.

  • Audit events: record identity and resource actions, such as a delete call and the role or user that made it
  • Monitoring metrics and logs: show the symptoms and timing
  • Limit: the record identifies the identity, not necessarily the person, because the credential may have been compromised

Audit logs must be retained and protected from tampering.

A contractor left 6 months ago, and their account was used last week to read sensitive files. Which IAM function failed, and what process would prevent it?

Deprovisioning: access wasn't removed when the person left.

  • Tie account removal to the HR offboarding process
  • Review access regularly
  • Prefer federated identity or single sign-on → disabling one identity removes access everywhere

Leftover accounts are an easy path for insiders and hijackers.

A CIO says: 'We moved to the cloud, so the provider handles security now.' Using the deck's conclusions, correct this.
  • Provider: secures the infrastructure and supplies network, device, identity and encryption services
  • Shared responsibility: the customer always owns its data and how it is accessed
  • Focus shifts to data security: classify data, protect it in transit, at rest and in use, and control access throughout its lifecycle
  • The SLA defines what the provider actually commits to

Exam-style questions

Answer aloud or on paper before opening.

A healthcare provider plans to move its patient records system to a public cloud PaaS. Patient data must stay in the country, and the regulator wants proof of who accessed which record. Propose the security architecture and say which duties remain the provider's.
  • Placement: classify patient data, use an in-country region, confirm the PaaS responsibility split
  • Encryption: TLS in transit and encrypt at rest; decide who holds and can use the keys, since BYOK and customer-held keys differ
  • Access: least-privilege identities for users and services; mask or tokenise identifiers in non-clinical views
  • Edge: a WAF and provider DDoS protection in front
  • For the regulator: retain protected audit events and database activity monitoring per record
  • Responsibility split
    • Provider keeps physical, host and platform runtime security
    • Classification, access decisions and accountability stay with the healthcare provider
A misconfigured storage bucket leaked customer data. The provider's service worked as documented. Using the shared responsibility model, explain who is accountable, then give a cause, a countermeasure and its drawback.

The customer is accountable.

  • Provider secures the storage service itself; the customer secures what is in it, including configuration, access control and data classification, just as with the firewall example
  • Cause: a public-access setting applied by hand
  • Countermeasure: define bucket policies in reviewed IaC, block public access by default, and alert on policy changes
  • Drawback: slower changes and friction for teams that legitimately publish public content
A microservices application exposes 30 public APIs, and its developers keep cloud keys in config files. Pick three Treacherous Twelve threats most relevant here, explain each through STRIDE, and give mitigations.
  1. Insecure interfaces and APIs (information disclosure, tampering)
    • Authenticate and authorise every call, validate input, rate-limit, add a WAF
  2. Insufficient identity, credential and access management (spoofing, elevation of privilege)
    • Move keys to a secrets manager and rotate them
    • Use least-privilege roles and scan repositories for secrets
  3. Denial of service (availability)
    • Provider DDoS protection, rate limits, autoscaling headroom and alarms

Throughout: run DevSecOps scanning of code and images, and keep audit trails to address repudiation.

Design data protection across the full lifecycle for a fintech's customer documents (ID scans, statements), including how deletion requests are honoured.
  1. Create: classify ID scans as sensitive
  2. Store: encrypt with controlled key use, restrict access, back up and monitor
  3. Use: DLP, database activity monitoring, and masking in support tools
  4. Share: TLS, VPN or SSH channels, and DLP or rights controls for external parties
  5. Archive: a retention policy with encryption and retrievability
  6. Destroy
    • Secure disposal or crypto-shredding with per-customer keys
    • Only works if backups, logs and analytics copies hold no plaintext and the keys are truly destroyed

Access follows classification at every stage.

A bank's board asks whether to use public, private or hybrid cloud 'for security'. Argue that the deployment model alone doesn't decide this, and recommend an approach.

The deployment model alone doesn't decide security.

  • Security depends on data location, access control, key management, provider duties and recovery, not on the label
  • Public cloud can meet sensitive requirements; private cloud still needs all of these controls
  • Hybrid if specific data must legally stay on premises: controlled, encrypted connectivity and tokenisation so public-cloud services handle tokens rather than raw data
  • Otherwise: public cloud with in-region placement and customer-controlled keys

Either way, the bank keeps responsibility for data classification and access.

Your organisation detected a breach only after 200 days, through a customer complaint. Diagnose the gaps and propose the monitoring, visibility and access capabilities you would add, with the main cost.
  • Gaps: no meaningful alerting, little audit coverage, and probably stale or over-broad access
  • Monitoring: continuous monitoring with alerts on unusual data movement and database access
  • Visibility: audit events for identity and resource actions with protected, long retention, and an incident response process
  • Access: review privileges and deprovision stale accounts

Main cost is ongoing: storing logs and triaging alerts needs staff, and noisy alerts get ignored, so tune them to the valuable data first.
