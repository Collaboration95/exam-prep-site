Whole day

A migration plan says 'use PaaS', but the architecture diagram shows your team patching VM operating systems, and the IaC creates VMs. What must you clarify before writing more IaC, and why does it matter?
Clarify the service model and responsibility split per component, since a solution can mix IaaS and PaaS. Agree who manages the OS, runtime, application and data, then make the diagram, migration plan and IaC match those decisions. It matters because the responsibility split decides patching, security and operating cost, and IaC that contradicts the plan turns the mismatch into running infrastructure.
A retailer has 120 on-premises applications and an 18-month data-centre exit. The CIO wants to start with the ERP 'because it gives the biggest saving' and to make everything cloud-native. Critique this plan and propose a first wave.
Starting with a critical, complex workload like ERP and treating cloud-first as cloud-native-everything are both listed strategy mistakes, and the biggest projected saving is not the right test for a first project. Assess each app with the drivers and assign the lightest R that fixes its problem: rehost most apps to meet the deadline, replatform where the database or runtime is the pain, and retain or retire the rest. Make the first wave a low-risk, instructive workload with an enthusiastic team, and build the landing zone in IaC. Budget for the migration bubble before savings appear.
A team rehosted its app onto cloud VMs, but the monthly bill is higher than on premises, and the app still can't scale down at night. Diagnose this, and say what to change and what it costs.
Lift and shift carries over-provisioning and the app's inability to scale, so the team pays for always-on peak capacity on usage-based pricing. Right-size the VMs, then partially refactor or replatform: make the web tier stateless so it can autoscale, and move the database to a managed service. The cost is refactoring effort and testing. Lift-and-optimise would have avoided some of this but would have taken longer up front.

Overview of Cloud Computing

A retailer runs a 6-week seasonal web shop. Evening traffic is 20 times the daytime level, the team is two developers, and there is no ops staff. Recommend a service model and a deployment model, and say what would make you choose IaaS instead.
PaaS on a public cloud, with SaaS for commodity parts such as payments or email: the provider runs the OS and runtime, and elasticity absorbs the evening peaks without the retailer owning peak capacity. Spend follows the 6-week season instead of a year-round investment. Choose IaaS only if the shop needs OS-level control or middleware the platform doesn't support, and accept that the two developers would then patch and scale servers themselves.
A regulated bank must keep customer records in its own data centre but wants elastic capacity for a new customer-facing app. Recommend a deployment model, and explain why a VPC alone is not enough.
Hybrid cloud: keep customer records in the on-premises private environment and run the elastic front end on public cloud, connected through controlled integration. A VPC gives logical isolation inside the provider's infrastructure but does not keep data on the bank's premises. The costs are governance, integration and co-existence work across two environments, plus the latency of calls back to on-premises data.
An enterprise wants its first cloud project to be moving its 15-year-old, heavily customised ERP. Advise on whether it should go first, and compare IaaS, PaaS and SaaS for it when it does move.
Advise against making it first: Gartner warns against starting with critical, complex, large workloads like ERP, so build skills on simpler workloads first. When it moves, IaaS (cloud-hosted lift and shift) keeps the customisation and needs the least change but keeps all the OS and middleware work. PaaS needs re-platforming. SaaS removes most of the operations but forces the business onto predefined settings, which may mean dropping years of customisation.
A proposal says: 'Move to the cloud to save money, and use two providers so disaster recovery is automatic.' Evaluate both claims and say what evidence you would want.
Both are listed myths or mistakes: cloud is not always cheaper, and multi-cloud does not by itself save money or improve DR; it adds cross-provider skills and operations. Ask for a workload-by-workload cost comparison, a prioritised list of benefits, and a tested DR design with recovery targets. Multi-cloud may still be justified for specific reasons, but it should come with an exit strategy rather than an assumed benefit.
An IT department rebrands its virtualisation cluster as 'our private cloud'. Developers can create VMs from a portal in minutes, but capacity is fixed at 200 VMs, adding hosts takes a 6-week purchase, and there is no usage reporting. Assess the claim against NIST and recommend what would close the gaps.
Partly justified: the portal gives on-demand self-service, and a shared cluster suggests resource pooling. It fails rapid elasticity, because the 200-VM cap and 6-week purchase stop capacity from growing quickly, and it fails measured service, because nothing is metered. Virtualisation alone is not a private cloud. To close the gaps, add per-team usage metering and either keep spare capacity or burst to public cloud (a hybrid model) so capacity can grow on demand.

Cloud Reference Architecture

A company runs a 10-year-old monolith on premises. The data-centre contract ends in 6 months, and the checkout module struggles at month-end peaks. Recommend a migration approach, and say what would justify a complete refactor.
Lift and shift to IaaS first to meet the 6-month deadline with minimal change, then partially refactor the checkout module, for example by extracting it as a stateless, autoscaled service. Leave the rest of the monolith alone until measured benefits justify more work. A complete refactor is justified only if long-term performance and operating-cost gains outweigh its higher cost, time and risk. Note that the lifted monolith may cost more to run than expected until it is optimised.
A platform team manages dev, test and prod by hand, and an outage last quarter took 3 days to recover. Justify Infrastructure as Code, explain how you would keep the environments consistent but deliberately different, and say what IaC will not solve.
Use shared, versioned IaC modules with explicit per-environment parameters (sizes, replica counts) and separate state. Changes go through Git review and are applied automatically, which reduces drift and documents the environment. A rebuild then takes minutes instead of days. IaC will not restore data, secrets or application configuration, so DR also needs backups or replication and a tested recovery runbook.
A regulated insurer must keep policyholder data on premises, wants elastic capacity for quote calculations, and its CTO also wants a second public cloud 'to avoid lock-in'. Design the strategy and judge the second cloud.
Hybrid: keep policyholder data in the private environment and run stateless quote calculation on public cloud, sending only the data it needs over a secured link. Add a second public cloud only for a concrete reason, such as a lock-in risk or a best-of-breed service. Containerising workloads on Kubernetes makes them portable (multi-cloud 2.0), but data, identity and managed-service dependencies still tie them to a provider. Every added environment increases integration, skills and management cost.
A startup runs 12 containerised microservices and has had two outages: one from a bad manual deployment and one from a retry storm between services. What components would you add to make the platform production-ready, and which outage does each address?
Add CI/CD with automated tests and rollback to address the bad manual deployment, plus orchestration that does rolling updates and health-checks containers. For the retry storm, add observability to see call chains, and either a service mesh or consistent client libraries for retry limits, timeouts and circuit breaking. At 12 services a mesh is defensible but adds operating cost. Also add an API gateway, secure images and config management, and test resilience with failure injection.
Design the architecture for an online game with spiky weekend traffic, global players downloading large assets, real-time leaderboards, and a target of surviving a full region outage. Explain each component's purpose.
Auto-scaled web and app tiers across two AZs behind a load balancer handle the spikes and zone failure. An in-memory cache holds sessions and leaderboards so servers stay stateless and reads are fast. Object storage and a CDN serve large assets close to players. A replicated database with a synchronous standby covers zone failure. For a region outage, copy snapshots to a second region and restore them with automation, accepting data loss back to the last snapshot and a restore delay.

Infrastructure as Code: Vendor-Specific Examples

A company's Dev, Test and Prod environments keep drifting apart, two engineers sometimes apply changes at the same time, and 30% of production deployments fail. Propose an IaC-based remedy and say what discipline it requires from the team.
Define all infrastructure in reusable, versioned modules in Git, with each environment as a separate, isolated set of parameters (environment segmentation). Keep one shared, tracked state so concurrent applies work from the same view, and apply only through a pipeline after review. Configuration management or immutable images keep the software consistent too. It only works if nobody changes infrastructure by hand; incident fixes must also go through code.
Choose IaC tooling for (a) a 5-person startup building only on one provider's serverless services and (b) an enterprise running Kubernetes on three providers. Justify each, and say what each choice gives up.
(a) The provider's native declarative IaC: it is designed for that cloud's services and can define functions, APIs, tables, permissions and logging in one template. It gives up portability if the startup later spans clouds. (b) Terraform with a provider per cloud and reusable cluster modules, plus GitOps for the workloads: one language and workflow across clouds. It gives up some native depth, and connectivity and federated identity still have to be designed separately.
Design the IaC for an event-driven pipeline: messages are ingested, processed by functions and written to an analytics store. A security review requires that a compromised processor cannot read or delete other data. Explain the security decisions in the template.
Provision the topic, subscription, function and analytics tables in one declarative configuration, with monitoring and logging defined alongside. Give each component its own identity: the processor can only consume from its subscription and write to its table. Because the IaC defines these permissions, they are reviewed and applied the same way in every environment. The trade-off is more identities to manage, in exchange for a much smaller blast radius.
A team uses GitOps for its Kubernetes platform. A release that adds a database column fails, and an engineer proposes 'just revert the commit'. Explain what GitOps gives here and what the revert will and will not fix.
GitOps keeps the declared state in Git and lets automation reconcile the cluster to it, which gives traceability, review and a quick way back to the previous configuration. Reverting restores the old Deployment, but the schema change has already been applied. If the old version can't work with the new column, the app still fails. Use backward-compatible migrations or a data recovery step, and verify convergence before calling it fixed.
A reviewer compares two IaC designs for a containerised app and its database. Design A exposes the database on a public endpoint with IP allow-lists and stores a database password in the cluster. Design B places the database behind a private endpoint in the virtual network, puts a web application firewall at the edge, and grants the cluster a role assignment. Which would you approve, and what does B cost?
Approve B. The private endpoint removes public exposure of the database, the WAF filters malicious traffic at the edge, and identity-based role assignment removes a long-lived secret that could leak. Defining all of this in the template means the same controls are present in every environment. B costs more network design, and tools outside the network can't reach the database without a controlled path.

Cloud Adoption and Migration

A hospital's 15-year-old on-premises patient scheduling system slows down at morning peaks. The code is stable and meets business needs, but the database server is end-of-life, and patient data must stay in the country. Recommend a migration option, justify it with the drivers, and name two risks to manage.
The drivers are risk (end-of-life platform) and scalability, not business fit, so Replatform: move to a managed database and auto-scaling in an in-country region, with minimal code change. Rebuild would add cost and risk without fixing anything the business needs. Manage database compatibility (test on the new engine, ideally with a proof of concept) and compliance (jurisdiction, privacy, encryption). Budget for the migration bubble while both environments run.
A firm must exit its data centre in 6 months, with 80 apps, many over-provisioned. The CFO expects savings in year one. Compare lift-and-shift and lift-and-optimise, recommend a mix, and respond to the CFO.
Lift-and-shift needs the least initial change and fits the deadline, but it carries over-provisioning and inefficiency. Lift-and-optimise lowers ongoing TCO but takes longer and costs more up front. Recommend lift-and-shift for most apps, sequenced by dependency and risk, with optimisation only for a few high-cost apps that can be done in time, and right-sizing after cutover. Tell the CFO that year one includes the migration bubble (duplicate environments, training, lease penalties), so savings depend on retirement and optimisation afterwards.
Design a portfolio assessment for an organisation with 200 applications and a 2-year programme. How would you decide each app's R, and which app would you migrate first?
Establish a baseline: the drivers, an inventory and dependency map, and the application concerns (performance, architecture, financial, risk, operations, security and compliance). Diagnose each app's problem with the six drivers, then assign the lightest R that fixes it, using the sourcing and hosting scoring to decide who runs it and where. Choose the first migration on the eight criteria: low-risk, instructive, with an enthusiastic team, not the highest ROI. Then iterate in waves and compare TCO against the baseline.
An insurer's 30-year-old policy system holds valuable rules, is nearly impossible to change, and is due to be replaced by a SaaS product in 3 years. A new mobile app needs policy data now. Choose between Retain, Encapsulate and Rebuild, and say what changes if the SaaS project is cancelled.
Encapsulate: expose policy data and functions through APIs so the mobile app can use them now, hiding the internals, while the system stays in place until the planned Replace. Rebuild would duplicate work the SaaS replacement will make redundant, and plain Retain would leave the mobile app without data. The legacy system's availability and performance now limit the mobile app. If the SaaS project is cancelled, revisit the drivers: a Rearchitect or Rebuild behind the same APIs becomes the long-term path, and the APIs let you swap the implementation without breaking the app.
A team migrating a 3-tier app proposes containers instead of VMs for the web and app tiers, keeping the database on a VM. Evaluate the proposal, including where containers would be the wrong choice.
Reasonable for stateless web and app tiers: containers are lighter, usually start faster, package the app consistently, and let each tier scale on its own. Keep the database on a VM or move it to a managed database if it needs OS-level tuning or strong isolation. Containers would be the wrong choice where a workload needs a different OS kernel or strong tenant separation, because they share the host kernel. Actual startup gains depend on image size and application initialisation.

Day 1: What the Instructor Emphasised in Class

Plan how to evolve a three-tier on-premises web application (DNS, firewall, load-balanced web and app tiers, active-passive database) to a cloud-native architecture in stages. For each stage, say what it gains and what triggers the next one.
Stage 1, one-to-one mapping: managed DNS, CDN at the edge, cloud load balancers, VMs or containers for the tiers and a managed database. This gains managed operations and possibly autoscaling, with little application change. Stage 2, containerise the tiers and run replicas behind Kubernetes Services with images in a registry and IaC for everything. The trigger is a need for faster, repeatable deployments. Stage 3, extract business capabilities as services behind an API gateway, with a mesh for internal traffic, only where independent delivery or scaling is a real problem. Functions are added for event-driven parts. Each stage adds operational complexity, so take the next one only when its trigger appears.
For a new system with a 24/7 order API, a nightly reconciliation job and an image-thumbnail task triggered by uploads, compare VMs, containers and functions, and choose one for each component.
VMs include a guest OS and give OS control, containers share a kernel and package dependencies lightly, and functions run on demand with a managed runtime. Order API: containers for always-on load and portability. Nightly reconciliation: a scheduled container job, or a function if it fits execution limits. Thumbnails: functions, for short, sporadic, event-triggered work billed per invocation. Choose by duration, startup latency, state, runtime control and cost, not by packaging fashion.
You are asked to produce the architecture for a new cloud-native platform. Using the Day 1 framing (what, how, where, and two audiences), outline what the deliverable must contain and how you would keep it from going stale.
What: a reference architecture with layers, components and how they interact. How: decisions with the constraints, requirements and objectives behind each. Where: data, infrastructure, application, platform, security and enterprise viewpoints. Deliver diagrams for people and IaC, YAML and config for machines, so the running system is generated from the architecture. Keep functional and non-functional requirements and recorded technical debt in the backlog. Because the IaC is part of the architecture, changes to it go through review, which keeps the design and the system aligned.
