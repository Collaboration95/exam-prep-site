Appendix: Cloud Patterns and Practices

68 slides · about 45 min · open the deck · JSON

Use this appendix to choose patterns by the problem they solve. It connects container helpers, event sourcing, circuit breakers, CQRS, sagas, sharding, tenancy, aggregation and workflow coordination. For each pattern, identify its boundary and failure behaviour as well as its benefits.

Big ideas

  • A pattern is a reusable, named solution to a recurring problem in a context; cloud patterns evolved from VM to containers to cloud native.
  • Event sourcing records authoritative state changes as events; the append can be atomic while asynchronously updated read models lag.
  • CQRS splits write (command) and read (query) models; a read-only view DB is kept up to date by subscribing to domain events.
  • Saga keeps data consistent across services with local transactions plus compensating transactions, coordinated by choreography (events) or orchestration (a central orchestrator).
  • Circuit breaker fails fast when a downstream service's error rate passes a threshold, stopping cascading failure and thread exhaustion.
  • Sharding splits data by lookup, range or hash strategy to beat single-server limits on storage, compute, bandwidth and geography.
  • Multi-tenancy is a continuum: isolating gives customization, security and control; sharing gives economy of scale and simpler management (separate DB vs separate schema vs shared schema).
  • Content can be aggregated at the client, the API gateway, a composite microservice, or the database (ODS), each trading latency, coupling and complexity.

What patterns are and where to find them

Defines architectural vs design patterns and surveys the main catalogues of cloud patterns an architect can borrow from.

What a pattern is

A named, reusable solution to a recurring problem in a context.

  • Architectural patterns → high-level ideas aimed at qualities like performance limits, availability and business risk
  • Design patterns → the more local, formalised best-practice templates
  • Benefit → lowers risk and gives the team a shared vocabulary

Cloud patterns evolved with the platform

  1. VM era → IaaS stack
  2. Container era → Kubernetes control plane and nodes
  3. Cloud native
    • customer-centric
    • agile
    • automated delivery
    • products not projects
    • heavy open source

Pattern catalogues

Several catalogues cover the same ground with different groupings.

  • Microsoft's A-Z cloud design patterns
    • Circuit Breaker, CQRS, Sharding, Sidecar, Strangler, Valet Key ...
  • Regrouped Fowler-style into:
    • Design and Implementation
    • Data Management and Performance
    • Availability and Resilience
  • Richardson's microservices.io → organises by application, application-infrastructure and infrastructure patterns
  • Erl's → by concern: scaling, reliability, data, security, monitoring

Practical use of catalogues

  1. Pick the catalogue that matches your problem category
  2. Quote the pattern's problem, mechanism and trade-offs when justifying a design

Give clients a restricted, time-limited token to access a resource (e.g. storage) directly.

Check yourself

In a design review, a teammate proposes a home-grown mechanism for letting clients upload files directly to storage with temporary access. You recognise it as a known pattern. Why does naming it matter?
It is the Valet Key pattern. Naming it gives the team a shared vocabulary and brings the pattern's known problem, mechanism and trade-offs, such as limiting the scope and lifetime of the key, so the design is easier to justify and review. A home-grown version risks rediscovering those trade-offs in production.
A team's problem is cascading failures between services. Which group of a cloud pattern catalogue would you search first, and what would you expect to find?
The Availability and Resilience group, where patterns such as Circuit Breaker, Retry, Bulkhead and Health Endpoint Monitoring address failing dependencies. Catalogues group the same patterns differently, so pick the one whose grouping matches the problem category. Then compare the candidates' trade-offs instead of applying the first match.

Container and microservice patterns

How cloud native layers good code, DDD, microservices and Kubernetes, plus container patterns (sidecar, adapter, ambassador, chain) and microservice/event-driven pattern families.

Cloud native is layered

  1. Clean code
  2. inside domain-driven design
  3. inside microservice principles → optimised for change
  4. inside Kubernetes patterns → automatable containers at scale

Allowing a polyglot world where each service chooses its own language and database.

A well-designed container

  • Single-concern
  • Disposable
  • Immutable
  • Self-contained
  • Small Linux process
  • API-driven
  • Observable

Immutability and disposability make scaling, rolling updates and self-healing safe.

Sidecar family

  • Sidecar → helper container in the same pod adds cross-cutting features (logging, proxying, config) without touching app code
  • Adapter → normalises the app's output (e.g. monitoring format)
  • Ambassador → proxies outbound connections (e.g. to the right DB per environment)
  • Container chain → fixes the start/stop order of sidecars and main app

Microservice pattern families

  • Decomposition
  • Database per service
  • Gateway/aggregation
  • Sync chains vs async pub/sub messaging
  • Shared data → an early decoupling stage
  • Event sourcing and CQRS
  • Erl's API/proxy/versioning patterns

Event-driven microservices

  • Coordinate through events on a broker (e.g. Kafka)
  • One service publishes, the next reacts
  • Event store feeds databases and analytics
  • Typical stack adds:
    • gateway
    • config server
    • discovery
    • circuit breaker with load balancing
    • a DB per service
    • messaging
    • central logging
Sidecar
Helper container alongside the main container in a pod adding cross-cutting features.
Ambassador
Sidecar that proxies the app's outbound connections to external services.
Adapter
Sidecar that converts the app's output into a standard format.
Container chain
Defined start/stop order for a pod's sidecar and main containers.

Check yourself

Twelve services in four languages must all ship logs in one format and route database connections per environment. Would you build this into each app, or use container patterns?
Container patterns: an adapter sidecar converts each app's log output to the standard format, and an ambassador sidecar proxies outbound database connections to the right target for each environment. Both work in any language without changing app code. The cost is extra containers per pod and a defined start and stop order (a container chain).
A team patches running containers in place to fix a bug, and the next autoscaling event brings back the bug. Which container properties were ignored?
Immutability and disposability. New instances start from the unchanged image, so in-place fixes are lost and instances drift apart. Build a new image with the fix and roll it out, so any instance can be killed and replaced by an identical one.
An order service must notify billing, shipping and analytics, and each team keeps asking the order team to add a new call. Which microservice pattern family helps?
Event-driven asynchronous pub/sub messaging: the order service publishes events to a broker, and each consumer reacts on its own, so new consumers subscribe without changing the order service. An event store can also feed databases and analytics. The cost is eventual consistency and the need for central logging and tracing to follow a flow.

Event sourcing, service mesh and circuit breaker

Event sourcing (state as events) with its pros and cons, then service mesh and circuit breaker as ways to make inter-service calls reliable.

Event sourcing

Makes the event history authoritative.

  • Append an OrderCreated or OrderApproved event atomically
  • Reconstruct state by replay
  • Lecture: the event store also exposes durable subscriptions → avoids a separate state-write and message-publish operation
  • Separate external broker → still needs reliable delivery integration

Event sourcing alone does not make unrelated systems commit atomically.

Write correctness vs read freshness

  • Event append → can be atomic
  • Projections and subscribers → catch up asynchronously
  • Audit history and replay → help recovery and analytics
  • Complexity → evolving events, rebuilding views, growing storage

Service mesh

Moves inter-service plumbing out of the app.

  • Requests flow through proxies
  • Dedicated infrastructure layer
  • Proxies run alongside each service as sidecars
  • Together → form a mesh network

Circuit breaker

Prevents cascading failure.

  • Problem → when a synchronous callee is down or slow, callers hold threads, exhaust resources and fail too
  • Proxy counts successes and failures
  • Past an error-rate threshold → trips so calls fail immediately
  • API gateway should protect itself this way
Event sourcing
Persist an entity as an append-only sequence of state-changing events; replay to get current state.
Event store
Database of events with APIs to append, read and subscribe.
Snapshot
Saved current state so only later events need replaying.
Service mesh
Infrastructure layer of sidecar proxies managing service-to-service traffic.
Circuit breaker
Proxy that stops calling a failing service once its error rate passes a threshold.

Check yourself

A service saves an order to its database and then publishes 'OrderCreated' to a broker. Sometimes the save succeeds but the publish fails. How does the lecture's event-sourcing design avoid this, and what doesn't it solve?
The event append is the state change: OrderCreated is written atomically to the event store, and subscribers read that committed history, so there is no separate save-then-publish step to fall out of sync. It doesn't make an external broker or a remote subscriber part of the same commit. Integrating with them still needs reliable delivery.
A team wants event sourcing for a simple product-catalogue service 'for the audit trail'. What would you weigh?
Benefits: full history for audit, replay for recovery and analytics. Costs: querying current state is hard, often needing CQRS read models; views are eventually consistent; event schemas must evolve over time; and storage grows because all history is kept. For a simple catalogue, an audit log table may give enough history at a fraction of the complexity.
When a recommendation service slows down, the product service's threads all wait on it, and the product pages fail too. Give the cause, a countermeasure and its drawback.
The cause is synchronous calls to a slow callee, which hold threads until resources are exhausted, so the failure cascades. A circuit breaker counts failures and, past an error-rate threshold, trips so calls fail immediately, with a fallback such as showing the page without recommendations. The drawback is that while the breaker is open, even requests that might have succeeded are rejected, so thresholds and recovery probes need tuning.

Data store, CQRS and saga patterns

Database-per-service vs shared database, then CQRS for cross-service queries and saga (choreography vs orchestration) for cross-service transactions.

Database per service vs shared database

  • Per service → data private behind an API → loose coupling and independent evolution
  • Per service cost → cross-service queries and transactions get hard
  • Shared DB → local ACID and easy joins, but couples services
  • If you share → do it within a domain boundary only

CQRS

Separates command and query models.

  • Lecture example → builds an Order History view from events published by owning services
  • Materialised view → makes cross-service reads efficient
  • Cost → can lag behind writes
  • Not required in every implementation → event sourcing or physically separate databases

CQRS plus event sourcing

  • Atomic operations
  • History for analytics
  • Separate scalable read and write models
  • Slim read DTOs
  • Cost → extra infrastructure, and complexity if models are poorly designed

Saga: cross-service transactions

  • Saga → a sequence of local transactions with compensating transactions on failure
  • Choreography → services react to each other's events (e.g. Order Created, then Credit Reserved or Credit Limit Exceeded), no controller
  • Orchestration → a central orchestrator sending commands (Reserve Credit)
  • Choreography suits → simple flows
  • Orchestration suits → many steps or branching

A saga is not one isolated ACID transaction: intermediate results can be visible, and compensation is a new business operation.

Database per service
Each service owns a private datastore accessed only via its API.
CQRS
Command Query Responsibility Segregation: separate write and read models; distinct stores and event-fed views are implementation options.
Saga
Sequence of local transactions across services, with compensating actions on failure.
Choreography
Saga coordination by services reacting to each other's events, no central controller.
Orchestration
Saga coordination where a central orchestrator sends commands to participants.

Check yourself

Order and Customer services each own their database, and a support screen needs 'all orders with customer names'. Joining across the databases is not allowed. What are the options?
API composition: a composer calls both services and joins the results in memory, which is simple but slow for large results. Or CQRS: build a read-optimised view from both services' events, which is fast but lags behind writes. Sharing tables would make the join easy but couples the services' releases.
An order flow has 7 steps with branching for credit checks, stock and fraud review. Choreography or orchestration for the saga?
Orchestration: with many steps and branches, a central orchestrator keeps the flow in one place where it can be followed, monitored and changed. Choreography suits simple flows with few participants, because each service reacting to events avoids a coordinator but scatters the logic. The orchestrator must itself be durable and must not take over the services' business logic.
A saga charges a card, then stock reservation fails, so the saga issues a refund. A teammate calls this 'a rollback'. Why is that misleading?
The charge was committed and may already have been seen by the customer or the bank. A refund is a new business action with its own outcome and possible failure, not an erasure of history. Intermediate states are visible because a saga isn't one isolated ACID transaction. Persist saga progress and make each step and compensation safe to retry.
A team uses CQRS without event sourcing, updating the read view from the write database's changes. Is that valid?
Yes. CQRS only separates the command and query models; it doesn't require event sourcing or separate physical databases in every implementation. Event sourcing pairs well with CQRS because the event store is poor at queries and supplies events to project. Without it, the team must still handle view lag and rebuilding the view.

Sharding strategies

Why one data server is not enough and the three ways to split data across shards.

Why shard

A single data server runs into limits:

  • Storage
  • Compute under concurrent queries
  • Network bandwidth
  • Geography → legal, compliance or latency reasons to keep data near users

Sharding splits data across servers.

Three strategies, by access pattern

  • Lookup → a map routes by shard key (e.g. tenant ID); tenants can be placed or moved → good for multi-tenancy and residency
  • Range → sequential keys keep related data together (orders by month) → good for range queries but prone to hotspots
  • Hash → a hash of the key spreads distinct keys, can reduce hotspots → but range queries touch many shards

Balance by actual traffic

Not by record counts alone.

  • One very hot key can still dominate a hash shard
  • Consider:
    • key distribution
    • tenant growth
    • rebalancing
    • cost of cross-shard queries
Shard key
Attribute deciding which shard a record lives in.
Hotspot
A shard receiving a disproportionate share of load.

Check yourself

An orders table is sharded by order month, and every December the current shard is overloaded while the others sit idle. Diagnose this and propose a change.
Range sharding on a sequential key puts all current writes on the newest shard, creating a hotspot. Hash sharding by order or customer ID would spread writes across shards. The cost is that queries by date range now fan out to every shard. Keep a separate date-indexed read view if month reports are frequent.
A multi-tenant SaaS has a few very large tenants and must keep EU tenants' data in the EU. Which sharding strategy fits, and why?
Lookup sharding with tenant ID as the shard key: the map can place each tenant on a specific shard, in the right region for residency, and move a large tenant onto a dedicated shard. The cost is that the lookup map becomes a critical component and tenant moves need careful migration.
After hash sharding, one shard is still overloaded. Records are evenly spread. What is the likely cause?
A hot key: one very busy tenant or item sends most of the traffic to its shard, and hashing spreads distinct keys, not the traffic on a single key. Balance by actual traffic, for example by moving that tenant to its own shard with a lookup or adding caching for it.

Multi-tenancy models

The isolate-vs-share continuum for architecture, schema, storage and deployment, plus SaaS managed-service capabilities and maturity levels.

Multi-tenancy

Shares application or infrastructure resources among tenants while keeping their data and access logically separated.

  • One codebase serves many customers with tenant-specific configuration
  • Isolation and sharing vary by layer
  • Choose the mix from:
    • cost
    • customisation
    • security
    • control requirements

Applies at every layer

  • Architecture (ordered):
    • physical
    • VM
    • runtime
    • application
    • storage
    • sub-tenancy (everything shared)
  • Deployment:
    • bare-metal/VM → most isolation
    • VM images
    • containers sharing one OS → simplest management

Schema options

  • Separated DB → a DB per tenant
    • easy, strongest isolation
    • but few tenants per server and cost rises fast
    • use when tenants need isolation and will pay
  • Separated schema → one DB, a schema per tenant
  • Shared schema → TenantID column with predefined custom fields
    • maximises tenants per server
    • but gives sparse tables
    • use when co-mingling is acceptable and custom fields are predictable

Choosing a data store

Hinges on:

  • Structured vs unstructured
  • Query needs → key/value is weak for complex queries
  • Aggregation
  • Scale-out
  • Transactions
  • Backup/DR
  • Security/audit

SaaS operations

  • Providers need:
    • business support (billing, contracts, price plans)
    • provisioning/metering/SLA
    • portability
  • SaaS maturity climbs:
    • level 0 → outsourcing
    • ASP stages
    • single-app SaaS
    • level 5 → dynamic business apps-as-a-service
Multi-tenancy
Multiple customer groups share a service or infrastructure with deliberate tenant isolation and potentially different configurations.
Separated schema
One database with a separate schema per tenant.
Shared schema
All tenants share tables, distinguished by a tenant ID column.
Polyglot persistence
Using different data store types for different needs in one system.

Check yourself

A bank-grade client of a SaaS product demands strict isolation and will pay extra. Which schema option, and why not the cheaper ones?
Separated database per tenant: strongest isolation, security and room for customisation, with the higher cost and fewer tenants per server covered by the premium. A separated schema shares a database engine, and a shared schema co-mingles rows by TenantID, which may not meet the client's isolation demand.
A SaaS for small shops has 20,000 tenants, mostly on the same plan, and a few need extra fields. Which schema option fits, and what problem should you expect?
A shared schema with a TenantID column maximises tenants per server, and predefined custom fields fit if the extra fields are predictable. If the design reserves generic custom columns that most tenants leave empty, tables become sparse. Co-mingled data also means every query must filter by tenant, so access control and testing must be strict.
A SaaS provider wants enterprise tenants on isolated infrastructure and small tenants sharing everything, all from one codebase. Is that a contradiction?
No. Multi-tenancy is a continuum applied at each layer: deployment (bare-metal or VM versus shared containers), runtime, application and storage. One codebase with tenant-specific configuration can serve shared and isolated tiers. Moving toward isolation gives more security, control and customisation at higher cost, and moving toward sharing gives economies of scale.

Content aggregation patterns

Four places to combine data from many microservices for one screen: client, API gateway, composite microservice, or database.

Where to assemble one screen's data

One screen's data from many services:

  1. Client
  2. API gateway
  3. Composite microservice
  4. Database

Each moves the logic further from the UI and adds cost.

Client vs API aggregation

  • Client-side calls → can render parts of a screen as each result arrives, but expose coordination to the client
  • Gateway aggregation → reduces external round trips and hides internals
  • Complete combined response → may wait for its slowest required backend
  • Mitigation → deliberate timeouts or partial results where the experience allows them

Microservice ('business tier')

  • Composite service applies real-time business logic during aggregation
  • Pros → finer control, less gateway dependence
  • Cost → extra hop, more code, more failure points, reactive/callback code for parallel calls

Database ('data tier')

  • Pre-aggregate into an operational data store (often a document DB)
  • Most flexible, analytics-enriched views → such as customer 360
  • Cost → complexity, duplicated data, ETL or change data capture
Bounded context
DDD boundary within which one model and its service/DB apply.
Operational data store (ODS)
Central store of pre-aggregated operational data, often a document DB.
Change data capture (CDC)
Capturing changes from a source database to propagate elsewhere.

Check yourself

A mobile app on slow networks needs a dashboard built from 5 services. Client or gateway aggregation?
Gateway aggregation: one request instead of five suits limited bandwidth and weak devices, and it hides the internal services. The combined response waits for the slowest required service, so set timeouts and return partial results where the screen allows. Client aggregation would let parts render as they arrive, but it costs five round trips on a slow network.
While a dashboard is aggregated, a discount must be calculated from loyalty tier and basket contents. Should that logic live in the gateway?
No. Real-time business logic during aggregation belongs in a composite microservice in the business tier, not in the gateway, which should stay focused on routing and cross-cutting concerns. The composite service costs an extra hop, more code and more failure points, and parallel calls need reactive or callback code.
A customer-360 view needs orders, support tickets and churn scores from analytics, and must load in under a second. Which aggregation pattern fits, and what does it cost?
Database aggregation: pre-aggregate into an operational data store, often a document database, so the view loads with one read and can include analytics. It costs duplicated data, extra storage and ETL or change-data-capture pipelines, and the view is only as fresh as the last sync.

Microservice coordination and design checklist

Capabilities needed to coordinate multi-service flows and the closing cloud-native design checklist and summary map.

Coordinating multi-service flows needs

  • State management → outputs kept in a persistent store safe from failure
  • Transaction control
  • Post-call coordination → collect each call's success or failure and decide the next step
  • Timeout handling → a per-microflow timer raising an event on the event bus
  • Configurability of timers and compensations

2PC vs saga

Choose coordination from the invariant.

  • 2PC → coordinates an atomic distributed commit, but can hold locks and block during failures; participants must support the protocol
  • Saga → local commits and business compensations, reducing synchronous coordination, at the cost of intermediate states and recovery logic

Neither choice is universally best.

Cloud-native design checklist

  • App design and tenancy model
  • Scale and zero-downtime upgrades
  • Data store → redundancy, partitioning, caching
  • Security → encryption, token auth, auditing, SSO
  • Integration formats and per-tenant SLAs
  • Middleware → config, queues, discovery, monitoring

Overall: software services rest on

  • Economics → cost and revenue models
  • Service Architecture → multi-tenancy, capacity, data/service/security patterns
  • Operational Structure → monitoring, billing, deployment, SLA, compliance, risk
Compensating transaction
New business action that semantically reverses or offsets an earlier committed step; it can also fail and need recovery.
Two-phase commit (2PC)
Distributed transaction protocol where all participants prepare then commit together.
Microflow
Short coordinated flow of service calls managed by a composite service.

Check yourself

A payment call from a composite service times out. A developer retries by creating a new payment. What could go wrong, and what is the safe approach?
The timeout doesn't prove the payment failed: the provider may have charged before the response was lost, so a new payment can charge twice. Reuse a stable operation identifier and query or reconcile the original result before retrying or compensating. The coordination layer should keep that state in a persistent store safe from failure.
Two services in different teams must both commit or both abort a transfer. One proposes 2PC, the other a saga. What decides it?
The invariant and the participants. 2PC gives an atomic distributed commit, but it holds locks, can block when a participant fails, and every participant must support the protocol. A saga uses local commits with business compensations, which reduces synchronous coupling but exposes intermediate states. If brief intermediate states are acceptable to the business, a saga usually fits independent services better.
A composite flow calls 4 services, and one never responds. The flow hangs forever. Which coordination capabilities are missing?
Timeout handling (a timer for each flow that raises an event when it expires), post-call coordination (collecting each call's success or failure and deciding the next step), and state management so progress survives a crash. Timers and compensations should also be configurable, because different steps need different limits.

Exam-style questions

Answer aloud or on paper before opening.

Design order processing on microservices where placing an order must reserve customer credit in a separate Customer service. A teammate proposes a shared database to keep it simple. Evaluate that, then design the consistency mechanism and say what users may see.
A shared database gives local ACID and easy joins, but it couples the two services' schemas and releases, so keep data private. Use a saga: Order creates a pending order, Customer reserves credit in its own local transaction, and Order approves or rejects. Choreograph it through events for this two-step flow, or orchestrate if steps will grow. Persist progress, use stable command identifiers and timeouts, and compensate (cancel the order) if credit fails. Users may briefly see a 'pending' order, because a saga exposes intermediate states.
A SaaS provider serves 5,000 small businesses and 4 regulated enterprise clients, two of which require in-country data. Propose a multi-tenancy, schema and sharding strategy, and state the trade-offs.
Use a mixed position on the isolation-sharing continuum. Small tenants share a schema (TenantID with predefined custom fields) for economies of scale. Regulated tenants get a separated database, or VM-level isolation, charged as a premium tier. Use lookup sharding by tenant ID to place each tenant, including the in-country ones in local regions, and to move a large tenant to its own shard. Trade-offs: possibly sparse shared tables and strict tenant filtering on one side, higher infrastructure and operating cost for isolated tenants on the other, and a critical lookup map.
An order-history page must show data from Order, Kitchen, Delivery and Accounting services within 300 ms. API composition is too slow. Design the read side, and decide whether event sourcing is needed.
Use a CQRS read model: an Order History view updated from the four services' domain events, so the page reads one pre-joined store. Explain that the view can lag writes, so a just-placed order may briefly be missing, and handle duplicate and out-of-order events and rebuilding the view. Event sourcing is optional. Adopt it only if authoritative event history for audit and recovery justifies the modelling and infrastructure cost; otherwise, publish events from each service's normal writes.
A slow downstream service took down an entire platform last month: gateway threads were exhausted and every API failed. Explain the failure, then design protection at the gateway and between services, naming one drawback.
Synchronous calls to a slow callee held threads until the gateway ran out, so one dependency's slowness became everyone's outage. Add timeouts on every call, and a circuit breaker at the gateway and in callers that trips past an error-rate threshold so calls fail fast, with fallbacks or partial responses. Apply it consistently through sidecars or a service mesh rather than per-app code. Drawback: an open breaker rejects some requests that would have succeeded, and badly tuned thresholds can trip too often.
A customer portal home page combines profile, orders, recommendations, support tickets and a churn score. Users are on mobile and desktop. Compare the four aggregation patterns for this page and recommend a combination.
Client aggregation renders parts as they arrive on desktop but costs round trips on mobile and exposes coordination in the UI. Gateway aggregation gives mobile one request and hides internals, but waits for the slowest service. A composite microservice can apply business logic, such as ranking recommendations, at the cost of a hop and more failure points. Database aggregation (an operational data store) suits analytics-enriched data like the churn score, at the cost of duplication and ETL or CDC. Recommend gateway aggregation for mobile, with timeouts and partial results, and pre-aggregate the churn score and ticket summary in the data store.
A global app's data store has hit single-server limits on write throughput, and EU users' data must stay in the EU. Recommend a sharding approach and name two operational side effects to plan for.
First confirm the limit: write compute, storage, bandwidth or geography. Use lookup sharding by region or tenant for EU residency, and within a region hash by customer ID to spread writes and avoid the hotspots that range sharding on dates would create. Side effects: cross-shard queries and reports get slower and more complex, and rebalancing when shards fill or a hot key appears needs data migration. Balance by actual traffic, not record counts.
