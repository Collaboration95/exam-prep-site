Day 4 mock questions

Do these after all of today's topics. Give your choice, reason and trade-off before opening an answer.

Whole day

A private support assistant uses RAG over internal documents and a managed model API. What security work remains with the company, and when would the design need an agent rather than retrieval alone?
Enforce the requester's permissions during retrieval, protect stored documents, embeddings and credentials, and monitor access. A managed model API still leaves application and data responsibilities with the customer under shared responsibility. RAG only supplies context. Actions such as changing an order need an agent with tools, each with separate authorisation, limits and validation.
A RAG assistant gives accurate answers using documents the requester should not be allowed to see. A manager says the design is fine because the answers are correct and the data is encrypted. Do you agree?
No. Accuracy and encryption don't replace authorisation: the running application can decrypt, so it leaked data the user wasn't entitled to, which is an information-disclosure breach. Filter retrieval by the requester's permissions and apply the same checks to any tool calls. Keep audit evidence of what was retrieved for whom.
An event-driven serverless pipeline processes uploaded invoices: a function extracts fields with a GenAI model, another writes to a database, and failures are retried automatically. Name two security risks and two reliability risks, with a control for each.
Security: over-broad function roles (give each function least-privilege access to only its bucket and table) and sensitive invoice data sent to an external model (classify the data, confirm the provider's terms and data location, or self-host an open-weight model). Reliability: retries creating duplicate records (idempotent writes keyed on the invoice ID) and bursts of scaled-out functions overwhelming the database (cap concurrency or put a queue in front). Also log and audit model calls, because generated extractions can be wrong and need validation.

Serverless Architecture

A startup's image-upload service is idle at night and gets bursts of 5,000 uploads a minute during campaigns. Should it use serverless? Design it and name two limits or side effects to plan for.
Yes. An upload to object storage triggers a stateless function that resizes the image and writes results back to object storage, with metadata in a key-value database. It scales with bursts, bills per invocation and has no idle servers at night. Plan for execution time and memory limits for large images, and for the burst of concurrent writes to the metadata store. Also plan for retries producing duplicate work, so make writes idempotent.
An order system is being designed. A teammate argues for 'pure FaaS, one function per operation'; another wants microservices on containers. Compare the options, recommend one, and explain how they could combine.
Microservices choose deployment boundaries (Order, Payment, Inventory as independently deployed capabilities). FaaS chooses how handlers execute. One function per operation maximises granularity but adds deployment, monitoring and coordination overhead, and cold starts on latency-sensitive paths. Recommend capability-sized services, implemented as a few functions where load is spiky and event-driven (notifications, receipts) and as containers where load is steady or latency-critical (checkout). Assess state, latency, limits and coordination cost, not function count.
Design a serverless back end that lets a mobile app use a legacy SOAP order system that handles at most 50 requests a second. Explain how you would protect the legacy system and secure the functions.
Put an API gateway in front of the mobile app with REST routes, each invoking a function that translates to SOAP/XML and back. Handle authentication at the gateway or through a managed identity service. To protect the legacy system, throttle at the gateway, cache read responses, and send non-urgent writes through a queue that a function drains at a controlled rate. Give each function an execution role limited to what it calls. The trade-off is that queued writes are confirmed later, not immediately.
A team asks when serverless is the wrong choice. Give three workload characteristics that argue against it, and for each say whether a redesign could still make functions work.
Continuous long-running processing beyond execution limits: functions still work if the work can be split into short steps with state persisted between them, otherwise use containers. Tight latency budgets that cold starts would break: a long-running service is usually the simpler answer. Steady high load where sustained-use cost exceeds always-on compute: compare costs, and the honest answer is often containers. Stateful work that depends on one instance's memory can be redesigned with external durable state.
Design a serverless real-time analytics pipeline for 20,000 click events a second with dashboards updated within 10 seconds, and say what happens when a downstream database slows down.
Events enter a stream service partitioned for throughput. Functions consume batches, transform and aggregate them, and write to a database or storage that the dashboards query, while raw events also go to object storage for later reprocessing. It scales with volume without servers. If the database slows, function retries and consumer lag grow and the dashboards fall behind. Cap function concurrency, batch writes, and monitor lag, accepting that the dashboards may briefly exceed 10 seconds rather than overloading the database.

Integrating Generative AI Tools into Cloud Native Applications

Design a GenAI customer-support assistant for a cloud-native e-commerce platform that must answer from current product and policy documents and also check order status. Choose plain LLM, RAG or agent, and say how it fits into the existing microservices.
Use RAG for answers, retrieving current product docs, FAQs and policies from an index such as a vector store, so responses are grounded without retraining. Extend it to an agent with tools for order status, calling the order service's existing API with the customer's own authorisation, and keep refunds behind human approval. Run the assistant as its own service behind the API gateway, using a hosted foundation model through an API or a self-hosted open-weight model. Monitor retrieval quality and answer support, because retrieval doesn't guarantee correctness.
Explain the layers of the GenAI tech stack, and advise a 10-person cloud-native team on where to invest and where to buy.
Bottom up: hardware (GPUs/TPUs), cloud platforms (scalable compute, storage, AI services), foundation models (closed through an API, or open-weight), customisation (prompt engineering, RAG, fine-tuning), and end-to-end applications. Buy the bottom three: pre-training is high-cost and existing models are reusable. Invest in customisation and the application, where the team's data and domain knowledge create value. Choose closed versus open weights by data constraints and operating capacity.
An enterprise wants GenAI for expense processing: answer staff questions about the policy, read receipt images and submit claims. Compare a plain LLM, RAG and an agent for this, and design the safeguards for the part that acts.
A plain LLM can interpret text but doesn't know the company's current policy. RAG adds the retrieved policy, which is enough for staff questions. Extracting receipt data and submitting claims needs an agent with tools calling the expense system's API. Safeguards: tools act only with the employee's permissions, limits route claims above a threshold to human approval, every action is logged, and the agent can only prepare or submit within defined integrations. The patterns combine, but an answer is not a permitted business action.
A product manager asks why chat responses get slower as answers get longer, even though 'Transformers are parallel'. Explain using the RNN-to-Transformer change, and give one design implication for a cloud-native chat service.
Transformers replaced step-by-step recurrence with self-attention, which lets training run in parallel over known inputs and links distant context directly. That is what made large-scale training possible. Generation is still autoregressive: each token is predicted from the tokens so far, so a longer answer takes longer to generate. Design implication: stream tokens to the client as they are generated, and set timeouts and capacity by expected output length.
A global marketing organisation proposes three GenAI features: personalised video per customer segment, first-draft product copy in 8 languages, and AI-generated ad music. Assess each for business value and risk, and say what process control is needed across all three.
Personalised video increases engagement at scale, but it is the costliest to generate and carries the most likeness and brand risk. Multilingual draft copy gives the clearest time saving, with translation errors as the main risk. Ad music is cheap content at scale, but its usage terms must permit commercial use. The common business value is content at scale, personalisation and faster delivery. Across all three, require human review and approval before publication, and track the usage terms of each generated asset.

Cloud Security: An Overview

A healthcare provider plans to move its patient records system to a public cloud PaaS. Patient data must stay in the country, and the regulator wants proof of who accessed which record. Propose the security architecture and say which duties remain the provider's.
Classify patient data, use an in-country region, and confirm the PaaS responsibility split. Encrypt in transit with TLS and at rest, and decide who holds and can use the keys, since BYOK and customer-held keys differ. Enforce least-privilege identities for users and services, mask or tokenise identifiers in non-clinical views, and put a WAF and provider DDoS protection in front. For the regulator, retain protected audit events and database activity monitoring per record. The provider keeps physical, host and platform runtime security, while classification, access decisions and accountability stay with the healthcare provider.
A misconfigured storage bucket leaked customer data. The provider's service worked as documented. Using the shared responsibility model, explain who is accountable, then give a cause, a countermeasure and its drawback.
The customer is accountable: the provider secures the storage service itself, and the customer secures what is in it, including configuration, access control and data classification, just as with the firewall example. The cause is a public-access setting applied by hand. The countermeasure is to define bucket policies in reviewed IaC, block public access by default, and alert on policy changes. The drawback is slower changes and friction for teams that legitimately publish public content.
A microservices application exposes 30 public APIs, and its developers keep cloud keys in config files. Pick three Treacherous Twelve threats most relevant here, explain each through STRIDE, and give mitigations.
Insecure interfaces and APIs (information disclosure, tampering): authenticate and authorise every call, validate input, rate-limit, and add a WAF. Insufficient identity, credential and access management (spoofing, elevation of privilege): move keys to a secrets manager, rotate them, use least-privilege roles, and scan repositories for secrets. Denial of service (availability): provider DDoS protection, rate limits, autoscaling headroom and alarms. Run DevSecOps scanning of code and images throughout, and keep audit trails to address repudiation.
Design data protection across the full lifecycle for a fintech's customer documents (ID scans, statements), including how deletion requests are honoured.
Create: classify ID scans as sensitive. Store: encrypt with controlled key use, restrict access, back up and monitor. Use: DLP, database activity monitoring, and masking in support tools. Share: TLS, VPN or SSH channels and DLP or rights controls for external parties. Archive: a retention policy with encryption and retrievability. Destroy: secure disposal or crypto-shredding with per-customer keys, which only works if backups, logs and analytics copies hold no plaintext and the keys are truly destroyed. Access follows classification at every stage.
A bank's board asks whether to use public, private or hybrid cloud 'for security'. Argue that the deployment model alone doesn't decide this, and recommend an approach.
Security depends on data location, access control, key management, provider duties and recovery, not on the label: public cloud can meet sensitive requirements, and private cloud still needs all of these controls. Recommend hybrid if specific data must legally stay on premises, with controlled, encrypted connectivity and tokenisation so public-cloud services handle tokens rather than raw data. Otherwise use public cloud with in-region placement and customer-controlled keys. Either way, the bank keeps responsibility for data classification and access.
Your organisation detected a breach only after 200 days, through a customer complaint. Diagnose the gaps and propose the monitoring, visibility and access capabilities you would add, with the main cost.
The gaps were no meaningful alerting, little audit coverage, and probably stale or over-broad access. Add continuous monitoring with alerts on unusual data movement and database access, audit events for identity and resource actions with protected, long retention, and an incident response process. Review privileges and deprovision stale accounts. The main cost is ongoing: storing logs and triaging alerts needs staff, and noisy alerts get ignored, so tune them to the valuable data first.
