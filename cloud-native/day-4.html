Day 4 mock questions

Do these after all of today's topics. Give your choice, reason and trade-off before opening an answer.

Whole day

A private support assistant uses RAG over internal documents and a managed model API. What security work remains with the company, and when would the design need an agent rather than retrieval alone?
  • Security work that remains with the company
    • Enforce the requester's permissions during retrieval
    • Protect stored documents, embeddings and credentials
    • Monitor access
  • Shared responsibility: a managed model API still leaves application and data responsibilities with the customer
  • Agent vs retrieval: RAG only supplies context
    • Actions such as changing an order need an agent with tools
    • Each tool with separate authorisation, limits and validation
A RAG assistant gives accurate answers using documents the requester should not be allowed to see. A manager says the design is fine because the answers are correct and the data is encrypted. Do you agree?

No. Accuracy and encryption don't replace authorisation.

  • Encryption: the running application can decrypt → it leaked data the user wasn't entitled to
  • Information-disclosure breach
  • Fix: filter retrieval by the requester's permissions; apply the same checks to any tool calls
  • Audit evidence: keep a record of what was retrieved for whom
An event-driven serverless pipeline processes uploaded invoices: a function extracts fields with a GenAI model, another writes to a database, and failures are retried automatically. Name two security risks and two reliability risks, with a control for each.
  • Security risks
    • Over-broad function roles → give each function least-privilege access to only its bucket and table
    • Sensitive invoice data sent to an external model → classify the data, confirm the provider's terms and data location, or self-host an open-weight model
  • Reliability risks
    • Retries creating duplicate records → idempotent writes keyed on the invoice ID
    • Bursts of scaled-out functions overwhelming the database → cap concurrency or put a queue in front

Also log and audit model calls: generated extractions can be wrong and need validation.

Serverless Architecture

A startup's image-upload service is idle at night and gets bursts of 5,000 uploads a minute during campaigns. Should it use serverless? Design it and name two limits or side effects to plan for.

Yes.

  • Design
    • An upload to object storage triggers a stateless function
    • It resizes the image and writes results back to object storage
    • Metadata in a key-value database
  • Why it fits: scales with bursts, bills per invocation, no idle servers at night
  • Limits and side effects to plan for
    • Execution time and memory limits for large images
    • The burst of concurrent writes to the metadata store
    • Retries producing duplicate work → make writes idempotent
An order system is being designed. A teammate argues for 'pure FaaS, one function per operation'; another wants microservices on containers. Compare the options, recommend one, and explain how they could combine.
  • Microservices choose deployment boundaries (Order, Payment, Inventory as independently deployed capabilities)
  • FaaS chooses how handlers execute
  • One function per operation → maximises granularity, but adds deployment, monitoring and coordination overhead and cold starts on latency-sensitive paths
  • Recommend capability-sized services, combining both
    • A few functions where load is spiky and event-driven (notifications, receipts)
    • Containers where load is steady or latency-critical (checkout)

Assess state, latency, limits and coordination cost, not function count.

Design a serverless back end that lets a mobile app use a legacy SOAP order system that handles at most 50 requests a second. Explain how you would protect the legacy system and secure the functions.
  • API gateway in front of the mobile app with REST routes, each invoking a function that translates to SOAP/XML and back
  • Authentication at the gateway or through a managed identity service
  • Protect the legacy system
    • Throttle at the gateway
    • Cache read responses
    • Send non-urgent writes through a queue that a function drains at a controlled rate
  • Secure the functions: give each an execution role limited to what it calls

Trade-off: queued writes are confirmed later, not immediately.

A team asks when serverless is the wrong choice. Give three workload characteristics that argue against it, and for each say whether a redesign could still make functions work.
  1. Continuous long-running processing beyond execution limits
    • Redesign: functions still work if the work can be split into short steps with state persisted between them
    • Otherwise use containers
  2. Tight latency budgets that cold starts would break
    • A long-running service is usually the simpler answer
  3. Steady high load where sustained-use cost exceeds always-on compute
    • Compare costs; the honest answer is often containers
  4. Stateful work that depends on one instance's memory → can be redesigned with external durable state
Design a serverless real-time analytics pipeline for 20,000 click events a second with dashboards updated within 10 seconds, and say what happens when a downstream database slows down.
  • Pipeline
    • Events enter a stream service partitioned for throughput
    • Functions consume batches, transform and aggregate them, and write to a database or storage that the dashboards query
    • Raw events also go to object storage for later reprocessing
    • Scales with volume without servers
  • When the database slows down
    • Function retries and consumer lag grow → the dashboards fall behind
    • Cap function concurrency, batch writes, monitor lag

Accept that the dashboards may briefly exceed 10 seconds rather than overloading the database.

Integrating Generative AI Tools into Cloud Native Applications

Design a GenAI customer-support assistant for a cloud-native e-commerce platform that must answer from current product and policy documents and also check order status. Choose plain LLM, RAG or agent, and say how it fits into the existing microservices.

RAG for answers, extended to an agent for order status.

  • RAG: retrieve current product docs, FAQs and policies from an index such as a vector store → responses grounded without retraining
  • Agent tools: order status by calling the order service's existing API with the customer's own authorisation
  • Refunds stay behind human approval
  • Fit with microservices: run the assistant as its own service behind the API gateway, using a hosted foundation model through an API or a self-hosted open-weight model
  • Monitor retrieval quality and answer support

Retrieval doesn't guarantee correctness.

Explain the layers of the GenAI tech stack, and advise a 10-person cloud-native team on where to invest and where to buy.
  • Layers, bottom up
    • Hardware: GPUs/TPUs
    • Cloud platforms: scalable compute, storage, AI services
    • Foundation models: closed through an API, or open-weight
    • Customisation: prompt engineering, RAG, fine-tuning
    • End-to-end applications
  • Buy the bottom three
    • Pre-training is high-cost
    • Existing models are reusable
  • Invest in customisation and the application
    • Where the team's data and domain knowledge create value

Choose closed versus open weights by data constraints and operating capacity.

An enterprise wants GenAI for expense processing: answer staff questions about the policy, read receipt images and submit claims. Compare a plain LLM, RAG and an agent for this, and design the safeguards for the part that acts.
  • Plain LLM: can interpret text but doesn't know the company's current policy
  • RAG: adds the retrieved policy → enough for staff questions
  • Agent with tools calling the expense system's API: needed for extracting receipt data and submitting claims
  • Safeguards for the part that acts
    • Tools act only with the employee's permissions
    • Limits route claims above a threshold to human approval
    • Every action is logged
    • Agent can only prepare or submit within defined integrations

The patterns combine, but an answer is not a permitted business action.

A product manager asks why chat responses get slower as answers get longer, even though 'Transformers are parallel'. Explain using the RNN-to-Transformer change, and give one design implication for a cloud-native chat service.
  • RNN → Transformer: step-by-step recurrence replaced by self-attention
  • Training: runs in parallel over known inputs and links distant context directly → made large-scale training possible
  • Generation: still autoregressive; each token predicted from the tokens so far → a longer answer takes longer to generate
  • Design implication: stream tokens to the client as they are generated; set timeouts and capacity by expected output length
A global marketing organisation proposes three GenAI features: personalised video per customer segment, first-draft product copy in 8 languages, and AI-generated ad music. Assess each for business value and risk, and say what process control is needed across all three.
  • Personalised video
    • Value: increases engagement at scale
    • Risk: costliest to generate; most likeness and brand risk
  • Multilingual draft copy
    • Value: clearest time saving
    • Main risk: translation errors
  • Ad music
    • Value: cheap content at scale
    • Risk: its usage terms must permit commercial use
  • Common business value: content at scale, personalisation, faster delivery

Process control across all three: human review and approval before publication, and track the usage terms of each generated asset.

Cloud Security: An Overview

A healthcare provider plans to move its patient records system to a public cloud PaaS. Patient data must stay in the country, and the regulator wants proof of who accessed which record. Propose the security architecture and say which duties remain the provider's.
  • Placement: classify patient data, use an in-country region, confirm the PaaS responsibility split
  • Encryption: TLS in transit and encrypt at rest; decide who holds and can use the keys, since BYOK and customer-held keys differ
  • Access: least-privilege identities for users and services; mask or tokenise identifiers in non-clinical views
  • Edge: a WAF and provider DDoS protection in front
  • For the regulator: retain protected audit events and database activity monitoring per record
  • Responsibility split
    • Provider keeps physical, host and platform runtime security
    • Classification, access decisions and accountability stay with the healthcare provider
A misconfigured storage bucket leaked customer data. The provider's service worked as documented. Using the shared responsibility model, explain who is accountable, then give a cause, a countermeasure and its drawback.

The customer is accountable.

  • Provider secures the storage service itself; the customer secures what is in it, including configuration, access control and data classification, just as with the firewall example
  • Cause: a public-access setting applied by hand
  • Countermeasure: define bucket policies in reviewed IaC, block public access by default, and alert on policy changes
  • Drawback: slower changes and friction for teams that legitimately publish public content
A microservices application exposes 30 public APIs, and its developers keep cloud keys in config files. Pick three Treacherous Twelve threats most relevant here, explain each through STRIDE, and give mitigations.
  1. Insecure interfaces and APIs (information disclosure, tampering)
    • Authenticate and authorise every call, validate input, rate-limit, add a WAF
  2. Insufficient identity, credential and access management (spoofing, elevation of privilege)
    • Move keys to a secrets manager and rotate them
    • Use least-privilege roles and scan repositories for secrets
  3. Denial of service (availability)
    • Provider DDoS protection, rate limits, autoscaling headroom and alarms

Throughout: run DevSecOps scanning of code and images, and keep audit trails to address repudiation.

Design data protection across the full lifecycle for a fintech's customer documents (ID scans, statements), including how deletion requests are honoured.
  1. Create: classify ID scans as sensitive
  2. Store: encrypt with controlled key use, restrict access, back up and monitor
  3. Use: DLP, database activity monitoring, and masking in support tools
  4. Share: TLS, VPN or SSH channels, and DLP or rights controls for external parties
  5. Archive: a retention policy with encryption and retrievability
  6. Destroy
    • Secure disposal or crypto-shredding with per-customer keys
    • Only works if backups, logs and analytics copies hold no plaintext and the keys are truly destroyed

Access follows classification at every stage.

A bank's board asks whether to use public, private or hybrid cloud 'for security'. Argue that the deployment model alone doesn't decide this, and recommend an approach.

The deployment model alone doesn't decide security.

  • Security depends on data location, access control, key management, provider duties and recovery, not on the label
  • Public cloud can meet sensitive requirements; private cloud still needs all of these controls
  • Hybrid if specific data must legally stay on premises: controlled, encrypted connectivity and tokenisation so public-cloud services handle tokens rather than raw data
  • Otherwise: public cloud with in-region placement and customer-controlled keys

Either way, the bank keeps responsibility for data classification and access.

Your organisation detected a breach only after 200 days, through a customer complaint. Diagnose the gaps and propose the monitoring, visibility and access capabilities you would add, with the main cost.
  • Gaps: no meaningful alerting, little audit coverage, and probably stale or over-broad access
  • Monitoring: continuous monitoring with alerts on unusual data movement and database access
  • Visibility: audit events for identity and resource actions with protected, long retention, and an incident response process
  • Access: review privileges and deprovision stale accounts

Main cost is ongoing: storing logs and triaging alerts needs staff, and noisy alerts get ignored, so tune them to the valuable data first.
