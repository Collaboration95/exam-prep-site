Serverless Architecture

36 slides · about 25 min · open the deck · JSON

Serverless shifts function-server operations to a provider while the application still needs sound state, error and security design. Choose it for suitable event-driven work, and compare function, gateway, queue, stream and legacy-proxy patterns. Learn the Lambda configuration and invocation model without treating the lecture’s pricing details as permanent limits.

Big ideas

  • Serverless offloads server operations and supports usage-based scaling; application resilience still needs failure and dependency design.
  • Monolith/microservices describe application boundaries; FaaS describes execution. A microservice may use one or more functions.
  • Serverless designs can compose events, streams and elastic compute; configure application timeouts, retries and failure handling explicitly.
  • Design with single-purpose stateless functions, push-based event pipelines, thicker front ends and third-party services.
  • Best fits: application back ends, data processing, real-time analytics, legacy API proxies, scheduled jobs and bots.
  • Functions, events, tasks, scheduling and services are the compute building blocks; storage, key-value, query and pipelines are the data blocks.
  • An API Gateway exposes Lambda functions as a RESTful web API and can hide legacy services behind it.
  • A Lambda function is configured with memory, timeout and an IAM role; billing is per invocation and execution time scaled by memory.

What serverless is

The definition, the monolith to FaaS progression, and the platform features that define serverless.

What serverless means

You stop managing servers, not that servers vanish.

  • Architectural approach → small independent functions on transient servers in an elastic runtime

Four shared platform traits

  • No OS to configure
  • Pay-per-invocation billing
  • Automatic scaling
  • Built-in availability and fault tolerance

Decomposition vs hosting

Decomposition and hosting are separate choices.

  • Lecture contrast:
    • one application API
    • separate domain APIs
    • individual action functions
  • A microservice can be implemented with functions
  • Moving to FaaS is not a compulsory next maturity stage
  • More functions ≠ better design → no such promise

Event-driven composition, elastic compute

Serverless supports event-driven composition and elastic compute.

  • Streams → ordered processing within their supported ordering scope; may retain events for replay
  • Configure as needed → queues, retries, timeouts, circuit breakers
  • Function platform does not automatically protect every downstream dependency

Why it matters

  • Well-planned serverless design → reduces and organises complexity
  • Makes future change easier
  • Matters for long-lived applications
FaaS
Functions as a Service: deploy individual functions that run on demand.
Event-driven
Components react to published events rather than direct calls.
Stream
Ordered sequence of events that can be processed later, replayed and fanned out.

Check yourself

A manager says 'we went serverless, so we no longer need to think about failures or state'. Correct this.

Serverless = the provider operates the servers, OS and scaling; servers and failures don't vanish.

  • Team still designs durable state in external stores
  • Team still designs retries, timeouts and protection for downstream dependencies
  • Team still configures each function's access and limits

Built-in availability covers the platform, not the application's own logic or the services it calls.

A team plans to turn its 8 microservices into 120 single-action functions 'because FaaS is the next maturity stage'. Do you agree?

No.

  • Decomposition (one app, domain services, individual actions) and hosting (servers, containers, functions) are separate choices
  • Moving to FaaS is not a required next stage
  • A microservice can be implemented with one or a few functions behind its API
  • 120 functions → deployment, monitoring and coordination overhead

Split further only where an action has different scaling, timing or ownership needs.

A function processes a stream of account events and must apply each account's events in order. What should the team check, and what doesn't the platform guarantee?
  • Ordering scope: streams usually keep order within a partition or shard → events must be partitioned by account ID
  • Retry behaviour: a failing batch can block or reorder processing
  • Not guaranteed: the platform doesn't automatically protect downstream dependencies → configure retries, timeouts and failure handling as needed

Design principles and when to use serverless

The guiding design principles, the situations where serverless pays off, and typical use cases.

Five principles

  • Run code on demand in a stateless compute service
  • Single-purpose stateless functions → more testable, robust, fewer side effects
  • Push-based, event-driven pipelines → the most flexible designs
  • Thicker, more powerful front ends → fewer hops, lower latency, better perceived performance
  • Embrace third-party services rather than building everything

When to use it

  • Focus on code and design rather than infrastructure
  • Reduce layers and code
  • Easier scalability and high availability with fairer pricing
  • Parallel processing problems → using stateless scalable compute

Typical use cases

  • Application back end (web, mobile, IoT)
    • authentication
    • device registry
    • shadowing
    • rules engine
  • Data processing and transcoding
  • Real-time analytics on logs, events and clicks
  • Legacy API proxy → gateway plus functions translating formats
  • Scheduled services
  • Bots and skills

Prefer a fit, not a blanket rule

  • Short event-triggered work → natural function fit
  • Long-running processes, in-memory durable state, tight latency budgets → may need a different runtime or extra design
  • Stateful applications → can still use stateless functions with durable external stores
  • Steady high load → needs a cost comparison
Stateless function
Function keeping no state between invocations; state lives in external stores.
Device shadow
Persistent copy of a device's state kept in the cloud.
Thick front end
Client does more work and calls services directly, reducing hops.

Check yourself

A single function validates an order, charges the card, updates stock and sends an email. What principle does this break, and what would you change?

Breaks single-purpose functions.

  • One function doing four things → harder to test, fails as a unit
  • Its side effects are hard to reason about (a charge without an email)
  • Fix: split into a push-based pipeline in which each step triggers the next through events

Cost: coordinating the steps and handling a failure part-way through.

A video platform transcodes uploads that arrive in bursts of hundreds after events, with nothing in between. Is serverless a good fit, and why?

Yes: data processing and transcoding is a typical use case.

  • Work is triggered by events
  • Can run in parallel on stateless compute
  • Pay only during bursts

Check the platform's execution time and memory limits against the longest video; very long transcodes may need a container or batch service instead.

An order workflow can take hours while waiting for warehouse confirmation. Must one function stay running throughout?

No.

  • Persist workflow state in a durable store
  • Use events or scheduled steps to invoke short functions as each piece of work becomes ready

A long-running service is justified only if the work truly needs continuous execution or the orchestration overhead outweighs its benefit.

A latency-critical API runs at a steady 3,000 requests a second all day. A teammate argues serverless will be cheaper and faster. Evaluate this.

Doubtful on both counts.

  • Cheaper? Steady high load → the pay-per-invocation advantage shrinks → compare sustained-use cost against always-on containers
  • Faster? Cold starts and runtime restrictions can threaten tight latency budgets

Serverless still fits the sporadic parts around this API, such as scheduled reports or file processing.

Layers of abstraction and serverless compute and data services

Where serverless sits in the stack and the types of service it is composed from.

Four layers of increasing abstraction

  1. Physical infrastructure → actual servers, networks
  2. Virtual infrastructure → virtualised servers and networking
  3. Serverless infrastructure → compute and data services
  4. Serverless applications (on top) → websites, API/RPC services, simple data pipelines

Each layer hides the one beneath.

Serverless compute services

  • Functions → small code handling a cloud event or HTTP request
  • Services → like functions but containerised and reachable by HTTP
  • Events → broadcast information to one or more components
  • Tasks → reliably send a message to a single component
  • Scheduling → repeating jobs triggered by other components

Serverless data services

  • Blob storage
  • Key-value database
  • Big-data query engine
  • Big-data transform pipeline

So storage and analytics also need no server management.

Provider categories, not one-to-one APIs

  • AWS → Lambda, DynamoDB, S3, Athena, Kinesis
  • Google → Cloud Functions, Cloud Run, Firestore, BigQuery, Dataflow
  • Azure → Azure Functions, Table Storage, Event Hub

These offer examples in these categories; check each product's execution and delivery semantics.

Event vs task
Event broadcasts to many consumers; task reliably delivers to one.
Blob storage
Object storage for unstructured files.
Key-value database
Simple store for lookup by key (e.g. DynamoDB).

Check yourself

When an order is placed, three components must react (email, analytics, loyalty), and one invoice job must be handed to exactly one worker reliably. Which serverless compute services fit each?
  • Events → the order notification: they broadcast information to one or more interested components
  • Tasks → the invoice job: they reliably deliver a message to a single component

Swapped: events for the invoice risk several workers processing it; tasks for the notification mean sending one task per consumer.

A team needs a containerised HTTP service with a library that won't run in the function runtime, but it doesn't want to manage servers. What serverless compute option fits?

Serverless services.

  • Like functions, but containerised and reachable over HTTP
  • Team controls the runtime in the image; the platform handles servers and scaling

Trade-off: a larger deployable and possibly slower starts than a function.

A small analytics team wants to run SQL over files in object storage once a week without running any servers. How do serverless data services help, and what should they check?
  • Blob storage for the files
  • A serverless big-data query engine runs SQL over them
  • → nothing runs between queries; billing follows usage
  • Check: the cost model and file formats
  • Compare providers by category and semantics, not by one-to-one product names

Serverless architecture patterns

Four reusable patterns showing how functions combine with gateways, queues, streams and servers.

Application back end

  • API Gateway → presents a RESTful interface and hides functions
  • Functions (e.g.)
    • save profile
    • calculate cost
    • submit job
    • process job
  • Functions talk to → storage, databases and a message pipeline
  • Direct calls → clients can often call services such as authentication or search directly instead of relaying through the gateway

API proxy for legacy systems

  • Gateway fronts legacy SOAP or XML services
  • Convert-and-invoke function per route → translates request and response formats
  • Benefit → modern clients use legacy systems without changing them

Real-time streams

  • Events flow into a stream service (e.g. Kinesis)
  • Functions pull batches and write to storage or a database
  • Suited to → data-intensive real-time reporting and analytics

Hybrid serverless and server-based

  • Fan out through notification topics into queues
  • Queues consumed by both functions and EC2 instances, with a database behind
  • Not all-or-nothing → mix it where it fits

Assess the whole path

  • Triggers → objects, queues, HTTP or data changes
  • Operational savings can be substantial
  • Account for, before concluding cheaper:
    • downstream capacity
    • retry behaviour
    • latency
    • data durability
    • integration cost
API proxy
Gateway plus functions translating between modern clients and legacy services.
Fan-out
One message distributed to many queues or consumers.
Kinesis
AWS streaming ingestion service, a canonical example.

Check yourself

A mobile app must use a legacy SOAP service that can't be changed. How would you expose it with serverless components, and what remains a risk?
  • API gateway in front → presents a REST interface
  • A function per route: converts the request to SOAP/XML, calls the legacy service, converts the response
  • The legacy system stays unchanged

Risk: its capacity and latency now limit the mobile app, because functions scale far faster than it can → add throttling or caching at the gateway.

Clickstream events arrive at 20,000 a second for real-time dashboards. Sketch a serverless pipeline and name one thing to monitor.

Pipeline (it scales with event volume without servers):

  1. Events go into a stream service
  2. Functions pull batches, transform them and write to storage or a database
  3. The dashboards query that store

Monitor: consumer lag and the write capacity of the target store, because fast-scaling functions can overwhelm a database downstream.

An architect insists the whole system must be serverless, including a steady, stateful matching engine. What would you propose instead?

A hybrid: serverless doesn't have to be all or nothing.

  • Fan out events through notification topics into queues
  • Queues consumed by functions for spiky, event-driven work
  • ... and by server-based instances for the steady, stateful matching engine
  • A shared database behind

Put each part where it is cheapest and fits best.

A business case claims moving an upload workflow to functions will 'cut costs by 60%' based only on compute prices. What is missing from the assessment?

Missing: the whole path.

  • Downstream capacity: can the database absorb the scaled-out writes?
  • Retry behaviour and duplicate processing
  • Added latency
  • Data durability
  • Integration cost

Operational savings can be real, but compute price alone can't establish them → model the full request path at expected and peak load.

AWS Lambda in practice

How Lambda functions are configured, invoked and exposed as a web API.

Lambda configuration

Configure code/handler, memory, timeout and execution role.

  • Timeout → bounds execution
  • IAM role → limits accessible resources
  • Network configuration → can provide access to private resources
  • Lecture's billing model → invocation count + duration weighted by memory
  • 100 ms example is historical → use the model rather than memorising a billing increment

Invocation dimensions

Invocation has more than one dimension.

  • Input → function receives event input and runtime context
  • Synchronous invocation → waits for a result
  • Asynchronous invocation → accepts an event for later processing
  • Event sources → may push events or be polled by platform mappings

Event-triggered is not a synonym for asynchronous invocation.

Lambda as a web API

  • Integrate a function with an API Gateway method
  • Pass HTTP parameters through
  • Format the function output as the HTTP response
  • URL = domain + stage (prod, test, dev) + resource paths
  • Each HTTP verb mapped to a function

Request flow (GET /greeting)

  1. Client request
  2. Method request (auth)
  3. Integration request to Lambda
  4. Function execution
  5. Integration response
  6. Method response → HTTP 200 with JSON

Logs (print output) go to CloudWatch Logs; testing uses a query string to inspect response, latency and logs.

Exam tip: tuning knobs

  • Memory
  • Timeout
  • IAM role
  • Memory also determines → cost and CPU share
Event (Lambda)
JSON input passed to the function.
Context (Lambda)
Runtime information about the execution environment.
IAM role
Permissions the function has on resources.
Stage
Named deployment of an API (prod, test, dev).

Check yourself

A function that resizes images runs at 128 MB memory and takes 8 seconds, often timing out. A teammate says raising memory will only raise cost. Do you agree?

Not necessarily.

  • On function platforms, memory also sets the CPU share → more memory can make the function finish much faster
  • Billing = invocations + duration weighted by memory → a shorter run at higher memory may cost about the same or less
  • Test a few memory sizes; set the timeout from the measured duration
A function's execution role has full access to every storage bucket and database 'to avoid permission errors'. What is the risk, and what should the role grant?
  • Risk: if the function's code or a dependency is compromised, the attacker gets all of that access
  • Grant only the resources and actions the function needs, e.g. read from one bucket and write to one table

The execution role and the timeout are the main controls on what a function can touch and how long it can run.

A function is triggered by messages from a queue, and a teammate calls it 'asynchronous, so the caller never waits'. Is that the right way to classify it?

Not quite: classify the invocation by its actual delivery and retry contract.

  • Queue: the platform often polls the source and invokes the function in batches → a different contract
  • Synchronous call: the caller waits for the result
  • Asynchronous call: an event is accepted for later execution

That contract decides error handling and duplicate processing.

A function exposed through an API gateway logs a successful run, but clients still get an error response. Using the request flow, where would you look?

Flow: method request → integration request → function execution → integration response → method response.

  • The function ran → likely fault in the integration response or method response
  • The function's output wasn't mapped to a valid HTTP response, e.g. a missing status code or wrong body format
  • Check the function's logs and output format; test the stage endpoint directly

Exam-style questions

Answer aloud or on paper before opening.

A startup's image-upload service is idle at night and gets bursts of 5,000 uploads a minute during campaigns. Should it use serverless? Design it and name two limits or side effects to plan for.

Yes.

  • Design
    • An upload to object storage triggers a stateless function
    • It resizes the image and writes results back to object storage
    • Metadata in a key-value database
  • Why it fits: scales with bursts, bills per invocation, no idle servers at night
  • Limits and side effects to plan for
    • Execution time and memory limits for large images
    • The burst of concurrent writes to the metadata store
    • Retries producing duplicate work → make writes idempotent
An order system is being designed. A teammate argues for 'pure FaaS, one function per operation'; another wants microservices on containers. Compare the options, recommend one, and explain how they could combine.
  • Microservices choose deployment boundaries (Order, Payment, Inventory as independently deployed capabilities)
  • FaaS chooses how handlers execute
  • One function per operation → maximises granularity, but adds deployment, monitoring and coordination overhead and cold starts on latency-sensitive paths
  • Recommend capability-sized services, combining both
    • A few functions where load is spiky and event-driven (notifications, receipts)
    • Containers where load is steady or latency-critical (checkout)

Assess state, latency, limits and coordination cost, not function count.

Design a serverless back end that lets a mobile app use a legacy SOAP order system that handles at most 50 requests a second. Explain how you would protect the legacy system and secure the functions.
  • API gateway in front of the mobile app with REST routes, each invoking a function that translates to SOAP/XML and back
  • Authentication at the gateway or through a managed identity service
  • Protect the legacy system
    • Throttle at the gateway
    • Cache read responses
    • Send non-urgent writes through a queue that a function drains at a controlled rate
  • Secure the functions: give each an execution role limited to what it calls

Trade-off: queued writes are confirmed later, not immediately.

A team asks when serverless is the wrong choice. Give three workload characteristics that argue against it, and for each say whether a redesign could still make functions work.
  1. Continuous long-running processing beyond execution limits
    • Redesign: functions still work if the work can be split into short steps with state persisted between them
    • Otherwise use containers
  2. Tight latency budgets that cold starts would break
    • A long-running service is usually the simpler answer
  3. Steady high load where sustained-use cost exceeds always-on compute
    • Compare costs; the honest answer is often containers
  4. Stateful work that depends on one instance's memory → can be redesigned with external durable state
Design a serverless real-time analytics pipeline for 20,000 click events a second with dashboards updated within 10 seconds, and say what happens when a downstream database slows down.
  • Pipeline
    • Events enter a stream service partitioned for throughput
    • Functions consume batches, transform and aggregate them, and write to a database or storage that the dashboards query
    • Raw events also go to object storage for later reprocessing
    • Scales with volume without servers
  • When the database slows down
    • Function retries and consumer lag grow → the dashboards fall behind
    • Cap function concurrency, batch writes, monitor lag

Accept that the dashboards may briefly exceed 10 seconds rather than overloading the database.
