Gartner: Choosing the Right Approach for Application Modernization and Cloud Migration

14 slides · about 20 min · open the deck · JSON

This July 2024 supplementary note selects modernisation approaches by root cause. Diagnose the six business and IT drivers, identify whether technology, structure or functionality needs change, then compare rehost, replatform, rearchitect, rebuild and replace. Retain, encapsulate and retire remain valid alternatives; apply choices incrementally by component.

Big ideas

  • Five main approaches, in rising scope: rehost (lift and shift), replatform (lift and reshape), rearchitect (refactor), rebuild (rewrite), replace (buy COTS/SaaS).
  • Alternatives when modernizing isn't worth it: retain (leave as is), encapsulate (wrap in an API), retire (decommission).
  • Each approach changes different layers: rehost/replatform fix technology; rearchitect fixes technology and architecture; rebuild/replace can also change functionality.
  • Diagnose first using six drivers: business fit, innovation and agility (business); cost, complexity and risk (IT).
  • Map drivers to root cause: cost, complexity and risk point to technology; business fit and innovation point to functionality; agility and complexity point to architecture.
  • Pick the approach that fixes the causing layer with acceptable value, time to value, disruption, cost of change and risk; don't expect replatforming to improve business fit.
  • Modernize incrementally, component by component, not as a big bang; different components may need different approaches.

Why the choice of approach matters

States the note's key findings and recommendations, gives survey evidence that modernization spending is rising, and explains why picking the wrong approach is costly.

Pick from the problem, not fashion

  • Common mistake → leaders modernize or migrate without establishing why the app obstructs the business
  • Result → the chosen approach misses the root cause
  • Wrong choices lead to:
    • budget overruns
    • late delivery
    • little benefit
    • process disruption
    • unmaintainable code
    • a cancelled programme

Portfolios decay, spend is rising

  • Apps lose → business fit, innovation support, agility
  • Apps get → costlier, more complex, riskier
  • 2023 CIO survey:
    • 46% planned more modernization spend
    • 50% more cloud-platform spend
    • 47% less legacy-infrastructure spend

No one-size-fits-all fix

Gartner's method:

  1. Cause-effect analysis using six drivers
  2. Evaluation framework to choose per application

Modernization ≠ cloud migration

Modernization is not always cloud migration; most efforts involve cloud, but:

  • COBOL app → rearchitected to Java and stays on the mainframe
  • Or replaced by an on-premises COTS package
Application modernization
Improving an existing application's technology, architecture or functionality so it better supports the business.
COTS
Commercial off-the-shelf software bought from a vendor rather than built.

A CIO launches a 'move everything to cloud' modernisation programme because competitors are doing it. Eighteen months later, costs are up and the business sees no benefit. What did Gartner's note warn about?
  • Warning: choosing an approach from fashion without first diagnosing why each application obstructs the business
  • → the chosen approach misses the root cause → overruns, late delivery, little benefit or a cancelled programme
  • Fix: a cause-effect analysis per application using the six drivers before picking an approach
A bank's COBOL system must be modernised, but the mainframe contract runs for 8 more years. A teammate says modernisation is impossible until they can move to cloud. Do you agree?

No. Modernisation is not always cloud migration.

  • Rearchitect the COBOL code to Java and stay on the mainframe
  • Or replace the app with an on-premises COTS package

Pick the approach from the drivers, and treat the hosting location as a separate decision.

A board member cites a survey showing CIOs plan more spending on modernisation and cloud and less on legacy infrastructure, and asks to fund all applications equally. What is the flaw?
  • The trend explains why portfolios need attention: apps lose fit and agility while growing costlier and riskier
  • But it doesn't say which apps need what
  • No one-size-fits-all fix → fund by application after diagnosis
  • Some will need rebuilding, some only replatforming, and some should be retained or retired

The five approaches and what each can change

Defines the five approaches, covers which application layers each can change, lists the three alternatives for legacy apps, and introduces the two diagnostic questions.

Five approaches, different scopes

  • Rehost → moves infrastructure
  • Replatform → changes runtime with minimal compatibility edits
  • Rearchitect → restructures existing code while preserving behaviour
  • Rebuild → rewrites it, possibly like-for-like
  • Replace → adopts COTS or SaaS

Compare the affected layer before comparing implementation cost.

Match approach to layer

  • Rehost, replatform → change technology only
  • Rearchitect → changes technology and architecture; limited value for functional problems
  • Rebuild, replace → can change functions and features, and also technology and architecture

Three alternatives to modernization

When modernization is not worth it, usually decided in a portfolio assessment.

  • Retain → leave as is for now (too much effort or risk, or near retirement)
  • Encapsulate → expose data and functions as services through an API while hiding the internals
  • Retire → decommission, often as part of a replace

Rehost vs rebuild in one line

  • Rehost → cheapest and least risky, but changes almost nothing
  • Rebuild → most flexibility, but costs the most and carries the most risk
Rehost
'Lift and shift': redeploy to other infrastructure without changing code or features.
Replatform
'Lift and reshape': move to a new runtime platform with minimal code changes for compatibility, but no structural or feature changes.
Rearchitect
Re-engineer/refactor: restructure the code without changing external behaviour, to remove technical debt and improve non-functional qualities.
Encapsulate
Wrap a legacy app's data and functions behind an API so they can be reused without changing the internals.
Retain / Retire
Retain: leave as is for now. Retire: decommission the application.

Check yourself

An app's code and features are fine, but it runs on middleware that is going out of support. Which approach fits, and why not rebuild?

Replatform.

  • The problem is in the technology layer → replatforming changes it with minimal code edits
  • Rebuilding would also change architecture and functionality that don't need fixing → adds cost, time and risk for no extra benefit
A legacy claims engine is valuable and stable, but changing it is very risky, and a new mobile app needs its data. Modernise or one of the alternatives?

Encapsulate.

  • Expose its data and functions as services through an API → the mobile app can use them
  • The implementation stays hidden and untouched
  • Extends the app's value cheaply

The engine's limits remain, so revisit it later if business fit or agility becomes the driver.

A team proposes rearchitecting an app into microservices because 'users say it is missing features'. Will rearchitecting fix that?

Probably not.

  • Rearchitecting changes technology and architecture while preserving behaviour → limited value for functional problems
  • Missing features point to functionality → rebuild or replace can change it
  • Rearchitect only if the real complaint is the speed or risk of adding features, which is an agility problem

Six drivers, root cause and the selection framework

Describes the three business and three IT drivers of modernization, maps them to the application layer most likely causing the problem, and presents Gartner's framework rating each approach.

Six drivers define the issue

  • Business drivers
    • Business fit → no longer meets requirements
    • Innovation → blocks new opportunities
    • Agility → cannot keep pace with change at acceptable cost and risk
  • IT drivers
    • Cost → too high relative to value
    • Complexity → hurts maintainability and the cost and risk of change
    • Risk → security, compliance, supportability, scalability, skills shortage on old platforms

Usually a mix of both tips the decision.

Drivers suggest a cause

Investigate before selecting.

  • Technology → often contributes to cost, complexity or risk
  • Functionality → business fit or innovation
  • Architecture → agility or complexity
  • Probable links, not a one-to-one diagnosis
  • Evidence may reveal more than one layer

Choose the approach that changes that layer

  • Technology faults → rehost, replatform or rearchitect
  • Architecture faults → rearchitect (or rebuild)
  • Functionality faults → rebuild or replace

Gartner's framework ratings

Each approach rated on value, time to value, disruption, cost of change and risk.

  • Rehost → low on all of them
  • Rebuild → most flexible but highest cost and risk
  • Replace → high value with the greatest business disruption
Six drivers of modernization
Business fit, innovation, agility (business) plus cost, complexity, risk (IT).
Technical debt
Accumulated shortcuts and outdated design that make an application costly and risky to change.

Check yourself

A system can't support a new digital sales channel. What must you diagnose before choosing an approach?

Diagnose: missing business functionality, or missing access to existing functions?

  • Functionality missing → rebuild or replace the component that needs it
  • Functions exist but can't be reached by the new channel → encapsulating them behind APIs or integrating at the architecture level may be enough

Rehosting alone won't add the capability.

Releases of a core app take months and often break unrelated features. Rearchitect or rebuild?

Rearchitect is the likely fit.

  • Slow, risky change points to agility and complexity → usually from the architecture
  • Rearchitecting fixes architecture and technology at lower cost, risk and disruption than a rebuild

Rebuild is justified only if the functionality must also change or the code can't be restructured.

Running costs of an app are too high for its value, but users are happy with it. Which drivers and layer does this point to, and which approaches would you shortlist?
  • Driver: IT cost
  • Layer: most likely technology, such as expensive licences or over-provisioned infrastructure
  • Shortlist: rehost or replatform → low on cost, risk and disruption
  • Not rebuild or replace: would add disruption and risk to fix functionality that already works

Check the evidence: drivers suggest a cause but don't diagnose it one-to-one.

A sponsor prefers replacing an in-house HR system with SaaS because it has 'the highest value'. What does the framework add to that view?
  • Replace: can change all layers and offers high value, but causes the greatest business disruption → processes redesigned, users retrained
  • Rehost: low on value, cost, risk and disruption, but changes little

Choose replace only if business fit or innovation is the driver and the business accepts the disruption.

Weighing consequences and the incremental approach

Lists the considerations to weigh when shortlisting approaches and recommends modernizing component by component.

Weigh five consequences

Before committing:

  • Potential business value → often overestimated (e.g. expecting a replatform to improve business fit)
  • Time to value
  • Business disruption → retraining, process redesign; SaaS replacement is high
  • Cost of change
  • Execution risk

Agree scope with stakeholders

  1. Shortlist approaches that address the actual problem
  2. Compare → outcomes, disruption, time, cost, execution risk
  3. Choose a proportionate change rather than the most extensive one

Modernize incrementally

  • Target can be a component rather than a whole app
  • Gartner recommends → component by component rather than big bang
  • Different components, different approaches → some a rebuild, others just a replatform
Time to value
How long before the modernization starts delivering business benefit.
Incremental modernization
Modernizing an application component by component rather than all at once (big bang).
Replace ('drop and shop')
Retire the app and repurchase the capability as COTS or SaaS.

Check yourself

A large app needs a new customer workflow, but its stable reporting module only needs a supported runtime. Must the whole app be rebuilt?

No. Gartner recommends modernising component by component.

  • Workflow component → rebuild or replace, where functionality must change
  • Reporting module → replatform, where only the runtime is the problem
  • Confirm dependencies and sequence the work → each change delivers its benefit and risk stays contained
A sponsor expects replatforming the ERP to make it fit the business better. How do you respond?
  • Replatforming changes only the technology layer → won't improve business fit, which is a functionality problem
  • Gartner: potential value is often overestimated in this way
  • Set expectations: if business fit is the driver, rebuild or replace is needed, with their higher cost, risk and disruption
Two approaches both fix an app's diagnosed problem: replatform (3 months) and rebuild (14 months, more flexibility). The business wants value this year. Which, and why?

Replatform.

  • Fixes the actual problem with shorter time to value
  • Lower cost of change and less execution risk
  • Choose a proportionate change, not the most extensive one

Rebuild's extra flexibility is worth it only if a near-term need for functional change is expected.

Exam-style questions

Answer aloud or on paper before opening.

A government agency's 20-year-old COBOL benefits system costs too much to run, is hard to change, and its COBOL staff retire within 3 years. The benefit rules themselves still meet policy. Recommend a modernisation approach using the drivers and root-cause layers.

Rearchitect, for example to Java, possibly staying on the current platform.

  • Drivers: cost, complexity, agility and risk (a skills shortage on an old platform)
  • Root-cause layers: technology and architecture, not functionality, since the rules still fit
  • Rearchitecting preserves behaviour while addressing these problems
  • Rebuild only if restructuring isn't viable
  • Execution: modernise component by component; encapsulate stable parts behind APIs where new channels need them
  • Before committing: compare time to value, cost, risk and disruption

The skills deadline sets the order of the work.

An on-premises web application has three complaints: hardware is ageing, the database needs constant hand-tuning, and features take months to ship. Compare rehost, replatform and rearchitect for moving it to cloud, and say which complaint each one fixes.
  • Rehost (lift and shift onto cloud VMs) → fixes ageing hardware
    • Quickly, cheaply and with the least risk
    • Changes nothing else
  • Replatform (e.g. a managed database or managed runtime, minimal code changes) → also fixes database operations
    • Gains some managed-service benefits
  • Rearchitect (e.g. refactoring into services) → the only one that fixes slow feature delivery
    • An architecture and agility problem
    • At higher cost, time and risk

Sensible plan: replatform now and rearchitect the slowest-changing components later.

A company wants to replace its 12-year-old custom CRM with a SaaS product. The sales team is attached to custom workflows. Using Gartner's framework, what should it consider before deciding?
  • Check the drivers are business fit or innovation: replace is justified for functional gaps, not for technology problems that replatforming could fix more cheaply
  • Replace: high value but the greatest business disruption → sales processes redesigned, users retrained, custom workflows may be lost
  • Weigh time to value, cost and execution risk with stakeholders
  • Plan data migration and the retirement of the old CRM
Describe a structured method for selecting modernisation approaches across a 150-application portfolio, and show how it would avoid the failures Gartner describes.
  1. Portfolio assessment: decide whether each app is retained, retired, encapsulated or modernised
  2. For candidates: define the issues with the six drivers; trace each to its likely root-cause layer (technology, architecture or functionality), checking the evidence
  3. Shortlist approaches that can change that layer
  4. Weigh value, time to value, disruption, cost and risk with stakeholders
  5. Execute incrementally per component

Avoids fashion-driven choices that miss the root cause (→ overruns and little benefit), and avoids big-bang rewrites.
