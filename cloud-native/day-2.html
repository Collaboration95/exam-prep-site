Whole day

Autoscaling fixes high CPU on a shop's web tier, but carts still disappear when instances are replaced and order retries create duplicate orders. Which design decisions remain, and which 12-factor principles do they relate to?
Keep session and cart state out of replaceable instances, in a durable shared store (stateless processes, backing services). Protect order writes with the required transaction rules and make retryable operations idempotent, for example with a stable order identifier. Ensure fast start and graceful stop so scale-in doesn't drop in-flight work (disposability). Scaling compute solves capacity, not state management or correctness.
A transfer commits successfully, but a read replica briefly shows the old balance, and the customer calls support. Has ACID failed? Decide which reads must be served from where.
No. The authoritative transaction committed atomically, and asynchronous replication is lagging. Serve balance checks right after a transfer, and anything used for further transfers, from the primary, or require read-your-writes. Let statements, analytics and activity feeds use replicas that tolerate staleness. Specify the freshness each operation needs rather than one policy for the whole app.
A product team plans a relational database for orders, a document store for the catalogue, a key-value cache for sessions, a graph store for recommendations and object storage for images, all for an MVP with 3 developers. Evaluate the plan against the 12 factors and the cost of polyglot persistence.
Each choice matches an access pattern, but polyglot persistence adds programming and operational cost for every store, which a 3-person MVP may not afford. Keep the relational database for orders and possibly the catalogue, the cache for sessions and object storage for images. Defer the graph store and compute recommendations in batch. Treat every store as an attached backing service configured from the environment, so adding one later doesn't need code changes.

Cloud Persistence

Design the persistence strategy for a cloud-native e-commerce platform with a catalogue (varying attributes), carts that must survive a cache failure, orders, recommendations and product images. Justify each store and say which one you would drop if the team were only 4 people.
Orders: a managed relational database for ACID transactions. Catalogue: a document store for flexible attributes read as whole items. Carts: a durable key-value store, or the relational database, with a cache in front, since carts must survive cache loss. Recommendations: a graph store for traversal. Images: object storage served through a CDN. With 4 people, drop the graph store and compute recommendations in batch from the order database, and consider keeping the catalogue relational, because each extra store adds programming and operational complexity.
A regional retailer's single relational database can't keep up with growing order writes across Singapore and Malaysia. A teammate proposes read replicas. Evaluate that, then propose how to scale the data tier and name two side effects to monitor.
Read replicas won't fix a write bottleneck, because all writes still go to one leader. Shard orders by country so each node serves its own reads and writes, and replicate the shared, read-heavy product list to both nodes with single-leader replication. Keep payment data under ACID and accept eventual consistency only where the business allows. Monitor replica lag on the product list (stale prices) and cross-shard query cost for regional reports.
Recommend data stores for a global banking ledger and for a social media status feed, and explain why the SQL versus NoSQL label alone doesn't settle the choice.
The ledger needs transactional invariants and durability, so a relational or NewSQL store fits, weighing distributed coordination cost against scale needs. The feed tolerates briefly stale replicas and needs high write and read scale, so a distributed NoSQL store with eventual consistency fits. The label doesn't settle it, because NoSQL products vary in transaction scope and relational systems can distribute. Decide from per-operation consistency requirements, access patterns and coordination cost.
A manager says 'NoSQL replaced relational databases, so all new systems should be NoSQL.' Using the V's of big data and the web-search example, explain why NoSQL emerged and argue whether the claim holds.
NoSQL emerged because variety needed flexible schemas, volume needed scale-out on commodity servers, and velocity needed distributed throughput. The web-search lookup needed none of the joins or multi-record transactions that relational systems provide. The claim doesn't hold: relational databases remain the natural fit for constraints, joins and ACID transactions. Polyglot persistence uses each model where it fits and accepts the complexity only when the benefit is larger.
An image-processing service has 10 worker VMs. Choose storage for temporary processing scratch space, the job database's data files, configuration shared by all workers, and finished images served to web and mobile apps. Then say what breaks if the shared configuration is put on one VM's block volume.
Scratch: ephemeral instance disk, since it can be regenerated. Database files: a persistent block volume with retention and backups, or a managed database. Shared configuration: a network file system. Finished images: object storage reached through its API by both apps. A block volume is normally attached to one VM, so the other 9 workers couldn't read the configuration, and that VM's failure would take the configuration with it.

Architecting a Cloud Native Application

A retailer's monolithic web shop loses customers' carts whenever a server crashes and can't cope with sale-day spikes of 20 times normal traffic. Diagnose the causes and propose a cloud native redesign, naming one new risk it introduces.
The diagnosis: sticky sessions and in-memory carts make servers pets, and the single scaling unit can't grow fast enough. Make the web tier stateless with carts in a shared store or managed database, split hot areas such as checkout into services behind an API gateway, run them as containers with horizontal autoscaling, and put order processing behind a queue to level peaks. Apply 12-factor practices and CI/CD. The new risks are distributed failures and eventual consistency between services, so add observability, timeouts and idempotent consumers.
Audit this service against the 12 factors: config is baked into images per environment, logs go to local files, the service takes 4 minutes to start, it writes uploads to local disk, and a database migration runs at every container start. Rank the gaps by operational risk and give the fix for each.
Highest risk: uploads on local disk (breaks stateless processes, so data is lost when instances are replaced); move them to object storage. Next, per-environment images (breaks build/release/run and config), meaning the tested artifact isn't the one deployed; build once and inject config at release, with secrets from protected storage. Then the 4-minute start (disposability), which defeats autoscaling. Then the migration at startup, which should be a one-off admin process to avoid concurrent migrations. Finally local logs, which vanish; stream them to an aggregator.
You must offer 99.95% availability for a service whose request path uses a gateway, a compute tier and a managed database, each with a 99.9% SLA. Explain why the target is at risk and propose design changes, with the cost of each.
In series, 0.999³ ≈ 99.7%, below the target, and provider SLAs alone can't guarantee the end-to-end figure. Add redundancy on the path: compute across zones behind health-checked load balancing, a database with a synchronous standby, and possibly a second region for the most critical path. Remove dependencies from the synchronous path using queues and caches. Bound retries and use circuit breakers so one slow dependency doesn't cascade. Each step adds cost and complexity, so check feasibility: if the budget or skills can't support it, renegotiate the SLA.
A bank's 20-year-old core app is released twice a year, runs on large VMs sized for peak, and is owned by separate dev and ops teams. A new digital-banking team wants weekly releases. Contrast the traditional and cloud-native approaches for each part, and say whether the core app should be converted.
Traditional: long release cycles, siloed teams, a tightly coupled monolith and server-centric vertical capacity pre-provisioned for peak. Cloud native: continuous delivery, DevOps teams, loosely coupled API-based services, and disposable, horizontally scaled containers. The digital team should build cloud native. The core app doesn't need to convert all at once: expose it through APIs and modernise where business drivers justify it, because these are tendencies and the core app can adopt automation and DevOps without a rewrite.
You run 30 microservices on Kubernetes across dev, test and prod. Secrets are in plain manifests, retries differ per team, and an outage last month cascaded through internal calls. Propose how to manage configuration, secrets and service-to-service traffic.
Keep ordinary config outside the image and per environment, so the same artifact is promoted through all three. Move secrets to protected secret storage with restricted access and inject them at runtime, because plain manifests or environment variables alone aren't protection. Declare everything in version-controlled manifests so the control plane reconciles drift. With 30 services and a cascading outage, a service mesh is justified for consistent timeouts, bounded retries, circuit breaking, encryption and tracing without code changes, with an API gateway for external traffic. The mesh adds operational overhead and latency to manage.
