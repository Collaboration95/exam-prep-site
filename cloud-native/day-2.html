Day 2 mock questions

Do these after all of today's topics. Give your choice, reason and trade-off before opening an answer.

Whole day

Autoscaling fixes high CPU on a shop's web tier, but carts still disappear when instances are replaced and order retries create duplicate orders. Which design decisions remain, and which 12-factor principles do they relate to?
  • Session and cart state out of replaceable instances, in a durable shared store (stateless processes, backing services)
  • Order writes: protect with the required transaction rules; make retryable operations idempotent, e.g. with a stable order identifier
  • Fast start and graceful stop so scale-in doesn't drop in-flight work (disposability)

Scaling compute solves capacity, not state management or correctness.

A transfer commits successfully, but a read replica briefly shows the old balance, and the customer calls support. Has ACID failed? Decide which reads must be served from where.

No. The authoritative transaction committed atomically; asynchronous replication is lagging.

  • From the primary (or require read-your-writes): balance checks right after a transfer, and anything used for further transfers
  • From replicas: statements, analytics and activity feeds, which tolerate staleness

Specify the freshness each operation needs rather than one policy for the whole app.

A product team plans a relational database for orders, a document store for the catalogue, a key-value cache for sessions, a graph store for recommendations and object storage for images, all for an MVP with 3 developers. Evaluate the plan against the 12 factors and the cost of polyglot persistence.

Each choice matches an access pattern, but polyglot persistence adds programming and operational cost for every store, which a 3-person MVP may not afford.

  • Keep: relational database for orders (and possibly the catalogue), the cache for sessions, object storage for images
  • Defer the graph store; compute recommendations in batch
  • 12 factors: treat every store as an attached backing service configured from the environment → adding one later doesn't need code changes

Cloud Persistence

Design the persistence strategy for a cloud-native e-commerce platform with a catalogue (varying attributes), carts that must survive a cache failure, orders, recommendations and product images. Justify each store and say which one you would drop if the team were only 4 people.
  • Orders → managed relational database: ACID transactions
  • Catalogue → document store: flexible attributes read as whole items
  • Carts → durable key-value store, or the relational database, with a cache in front → carts must survive cache loss
  • Recommendations → graph store: traversal
  • Images → object storage served through a CDN
  • With 4 people
    • Drop the graph store → compute recommendations in batch from the order database
    • Consider keeping the catalogue relational

Each extra store adds programming and operational complexity.

A regional retailer's single relational database can't keep up with growing order writes across Singapore and Malaysia. A teammate proposes read replicas. Evaluate that, then propose how to scale the data tier and name two side effects to monitor.
  1. Read replicas? No
    • Won't fix a write bottleneck → all writes still go to one leader
  2. Scale the data tier
    • Shard orders by country → each node serves its own reads and writes
    • Replicate the shared, read-heavy product list to both nodes with single-leader replication
    • Keep payment data under ACID; accept eventual consistency only where the business allows
  3. Two side effects to monitor
    • Replica lag on the product list (stale prices)
    • Cross-shard query cost for regional reports
Recommend data stores for a global banking ledger and for a social media status feed, and explain why the SQL versus NoSQL label alone doesn't settle the choice.
  • Ledger → a relational or NewSQL store fits: needs transactional invariants and durability; weigh distributed coordination cost against scale needs
  • Feed → a distributed NoSQL store with eventual consistency: tolerates briefly stale replicas, needs high write and read scale
  • Why the label doesn't settle it
    • NoSQL products vary in transaction scope
    • Relational systems can distribute

Decide from per-operation consistency requirements, access patterns and coordination cost.

A manager says 'NoSQL replaced relational databases, so all new systems should be NoSQL.' Using the V's of big data and the web-search example, explain why NoSQL emerged and argue whether the claim holds.
  • Why NoSQL emerged
    • Variety → needed flexible schemas
    • Volume → needed scale-out on commodity servers
    • Velocity → needed distributed throughput
  • Web-search lookup: needed none of the joins or multi-record transactions that relational systems provide
  • Claim doesn't hold: relational databases remain the natural fit for constraints, joins and ACID transactions
  • Polyglot persistence: use each model where it fits

Accept the complexity only when the benefit is larger.

An image-processing service has 10 worker VMs. Choose storage for temporary processing scratch space, the job database's data files, configuration shared by all workers, and finished images served to web and mobile apps. Then say what breaks if the shared configuration is put on one VM's block volume.
  • Scratch → ephemeral instance disk: it can be regenerated
  • Database files → persistent block volume with retention and backups, or a managed database
  • Shared configuration → network file system
  • Finished images → object storage, reached through its API by both apps
  • Shared config on one VM's block volume
    • A block volume is normally attached to one VM → the other 9 workers couldn't read the configuration
    • That VM's failure would take the configuration with it

Architecting a Cloud Native Application

A retailer's monolithic web shop loses customers' carts whenever a server crashes and can't cope with sale-day spikes of 20 times normal traffic. Diagnose the causes and propose a cloud native redesign, naming one new risk it introduces.
  1. Diagnosis
    • Sticky sessions + in-memory carts → servers are pets
    • The single scaling unit can't grow fast enough
  2. Cloud native redesign
    • Stateless web tier, with carts in a shared store or managed database
    • Split hot areas such as checkout into services behind an API gateway
    • Run them as containers with horizontal autoscaling
    • Put order processing behind a queue → level peaks
    • Apply 12-factor practices and CI/CD
  3. New risks
    • Distributed failures and eventual consistency between services
    • → add observability, timeouts and idempotent consumers
Audit this service against the 12 factors: config is baked into images per environment, logs go to local files, the service takes 4 minutes to start, it writes uploads to local disk, and a database migration runs at every container start. Rank the gaps by operational risk and give the fix for each.

Ranked by operational risk:

  1. Uploads on local disk (highest risk)
    • Breaks stateless processes → data is lost when instances are replaced
    • Fix: move them to object storage
  2. Per-environment images
    • Breaks build/release/run and config → the tested artifact isn't the one deployed
    • Fix: build once and inject config at release, with secrets from protected storage
  3. 4-minute start
    • Breaks disposability → defeats autoscaling
  4. Migration at every container startup
    • Fix: a one-off admin process → avoids concurrent migrations
  5. Local logs (lowest)
    • They vanish with the instance
    • Fix: stream them to an aggregator
You must offer 99.95% availability for a service whose request path uses a gateway, a compute tier and a managed database, each with a 99.9% SLA. Explain why the target is at risk and propose design changes, with the cost of each.
  • Why the target is at risk
    • In series: 0.999³ ≈ 99.7%, below the target
    • Provider SLAs alone can't guarantee the end-to-end figure
  • Add redundancy on the path
    • Compute across zones behind health-checked load balancing
    • A database with a synchronous standby
    • Possibly a second region for the most critical path
  • Remove dependencies from the synchronous path using queues and caches
  • Bound retries and use circuit breakers → one slow dependency doesn't cascade

Cost: each step adds cost and complexity → check feasibility; if the budget or skills can't support it, renegotiate the SLA.

A bank's 20-year-old core app is released twice a year, runs on large VMs sized for peak, and is owned by separate dev and ops teams. A new digital-banking team wants weekly releases. Contrast the traditional and cloud-native approaches for each part, and say whether the core app should be converted.
  • Traditional
    • Long release cycles
    • Siloed teams
    • A tightly coupled monolith
    • Server-centric, vertical capacity pre-provisioned for peak
  • Cloud native
    • Continuous delivery
    • DevOps teams
    • Loosely coupled API-based services
    • Disposable, horizontally scaled containers
  • Digital team → should build cloud native
  • Core app: doesn't need to convert all at once
    • Expose it through APIs and modernise where business drivers justify it
    • These are tendencies → the core app can adopt automation and DevOps without a rewrite
You run 30 microservices on Kubernetes across dev, test and prod. Secrets are in plain manifests, retries differ per team, and an outage last month cascaded through internal calls. Propose how to manage configuration, secrets and service-to-service traffic.
  • Ordinary config → outside the image, per environment → the same artifact is promoted through all three
  • Secrets → protected secret storage with restricted access, injected at runtime → plain manifests or environment variables alone aren't protection
  • Declare everything in version-controlled manifests → the control plane reconciles drift
  • Service-to-service traffic → a service mesh, justified by 30 services and a cascading outage
    • Consistent timeouts, bounded retries, circuit breaking, encryption and tracing without code changes
    • An API gateway for external traffic

The mesh adds operational overhead and latency to manage.
