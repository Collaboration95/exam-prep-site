Whole day

A system uses TLS, but an administrator account exports confidential records with no business need. Trace the risk and propose two different kinds of control.
  • Trace the risk
    • Asset: the confidential records
    • Threat: misuse of privileged access
    • Vulnerability: excessive permissions and no monitoring
    • Assess likelihood and impact, then treat
  • Least privilege and role-based access (technical, preventive)
  • Audit logging with alerts on bulk exports (technical, detective)
  • Backed by regular access reviews (administrative, detective)

TLS protects data in transit; it does not decide who should read the records.

A telehealth service runs video consultations and stores consultation notes. TLS terminates at a load balancer in the DMZ, clinicians log in with a password, and a vendor supports the video servers remotely. Identify the top three risks and choose a control for each, stating its type and category.
  1. Stolen clinician passwords → access to patient notes (spoofing, authenticity)
    • Control: MFA (technical, preventive)
  2. Plaintext at the DMZ load balancer → exposes notes if it is compromised (information disclosure)
    • Control: encrypt the notes for the back end, or terminate TLS deeper, and harden the load balancer (technical, preventive)
  3. Vendor's remote access → becomes a stepping stone
    • Control: an MFA-protected, logged jump host on a segregated admin network (technical, preventive and detective)

Add IDS and log review so the design is not only preventive, and record the residual risk.

A pharmacy chain's online prescription portal serves 200,000 patients. The web tier in the DMZ reads a records database, a vendor has remote support access, and the budget covers three new controls this year. (a) Identify a crown jewel and a stepping stone. (b) Write two risk scenarios and rate them. (c) Choose a treatment for each and three controls, justifying the mix of types and categories. (d) State the residual risk.
  1. (a) Crown jewel and stepping stones
    • Crown jewel: patient prescription records
    • Stepping stones: the DMZ web server and the vendor's remote access path
  2. (b) Risk scenarios
    • 'An attacker exploits the vendor's remote access to reach the records database and disclose prescriptions': medium likelihood, high impact
    • 'An attacker exploits a web-tier flaw and pivots to the database': medium likelihood, high impact
  3. (c) Treatment: mitigate both. Controls:
    • MFA-protected, logged vendor access through a jump host: technical, preventive and detective
    • Segmentation with an inner firewall allowing only required web-to-database traffic: technical, preventive
    • Centralised log review with alerting: administrative and technical, detective
  4. (d) Residual risk: unknown application flaws and insider misuse
    • Record them, accept within tolerance, and revisit next year
Threat-model a mobile banking transfer: phone app, then API gateway, then transfer service, then core banking system. For each of three trust boundaries, give the most likely STRIDE threat, the objective it breaks and a control.
  1. Phone → gateway: spoofing (authenticity)
    • Using stolen credentials
    • Control: MFA and device binding
  2. Gateway → transfer service: tampering (integrity)
    • Altering the amount or payee in transit
    • Control: TLS on each hop plus signed transfer requests, which also give non-repudiation
  3. Transfer service → core banking: elevation of privilege (authorisation)
    • Through an over-privileged service account
    • Control: least privilege and authorising each operation

Across all three, protected audit logs counter repudiation.

A bank's control list for online banking is: TLS, a web application firewall, MFA, a password policy and data-centre locks. An auditor calls it unbalanced. Classify the controls, find the gaps and fill them.

Everything prevents; nothing detects or corrects.

  • Classify
    • TLS, web application firewall, MFA: technical, preventive
    • Password policy: administrative, preventive
    • Data-centre locks: physical, preventive
  • Add detective: an IDS, log review, CCTV in the data centre
  • Add corrective: tested backups, incident response, access revocation

Check every major risk against a grid of type (technical, administrative, physical) by category (preventive, detective, corrective).

Design how a web login protects a password from browser to the final consumer, when TLS terminates at a DMZ proxy. Discuss the limits of TLS.
  • TLS limit: protects each connection only between its own endpoints → if it ends at the DMZ proxy, the password is plaintext there, even if the next hop also uses TLS
  • Field-level encryption: encrypt the password field for the final consumer with its public key, plus a nonce checked against replay
  • Protect that private key
  • Forward secrecy: authenticated ephemeral key agreement on each connection
  • Inspection proxies: any proxy that decrypts traffic sees plaintext → include it in the trust boundary
A small company runs its app server and database on one flat network. The app server's account is a database superuser, admins use their everyday laptops to manage servers, and permissions are cached at login for a day. Apply the four secure design principles.
  1. Defence in depth
    • Zones (DMZ, internal) with firewalls between them, encryption of sensitive data, and an IDS
    • → one breach doesn't expose everything
  2. Least common mechanism
    • Administration and logging get their own out-of-band network and dedicated admin devices
    • Separate keys per purpose
  3. Least privilege
    • App server account gets only the table reads and writes it needs, never superuser
  4. Complete mediation
    • Check authorisation on every request instead of caching it for a day → revocations take effect immediately

Each fix adds cost or latency → prioritise them by the risks they reduce.

In a DMZ-based architecture, decide where you would use an IDS and where an IPS, and how you would handle false positives.
  • Inline IPS at the internet edge: blocking obvious attacks is worth the occasional false block
  • NIDS sensors at internal zone boundaries (e.g. between the DMZ and the internal network) → alert without blocking business traffic
  • HIDS on critical hosts like the database, which encrypted traffic would otherwise hide
  • False positives
    • Tune signatures
    • Start new rules in alert-only mode
    • Review alerts

A passive IDS sees copied traffic and cannot stop an attack → pair it with a response process.
