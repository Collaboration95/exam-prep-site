Architect the Solution Architecture (Assets)

88 slides · about 40 min · open the deck · JSON

This topic is the architect's toolbox of reusable assets: architecture styles (structural and communication), reference architectures (web, mobile, broker, SOA, microservices, cloud, serverless) and the way an architecture is described through views and viewpoints (IEEE 42010, UML, 4+1). The idea is that you rarely start from a blank page; you reuse proven patterns and choose among them by quality attributes. For the exam, expect to pick and justify styles and reference architectures for a scenario and to describe the architecture with the right views.

Big ideas

  • Architectural assets = reference patterns (idioms, design patterns, architecture styles) + reference architectures, used to produce an architecture and its architectural description.
  • Similar systems lean mostly on reuse; innovative systems lean more on method and intuition.
  • Structural styles: client-server, tiered (3-tier/n-tier), peer-to-peer. Network zoning uses DMZ, reverse proxy (hides servers) and forward proxy (hides clients).
  • During a network partition, CAP forces a trade-off between strict consistency and availability. ACID consistency means preserving database rules; it is a different use of the word consistency.
  • Communication styles: data flow (file or database level), call and return (presentation or application level, SOAP/REST), event-based (point-to-point queue, publish/subscribe).
  • Reference architectures bundle many patterns for a domain: web, mobile, broker/ESB, SOA layers, microservices (scale cube, discovery, API gateway), cloud, serverless; avoid spaghetti.
  • Microservices scale cube: X = clone, Y = functional decomposition, Z = data partitioning.
  • Describe architecture with multiple views: 4+1 (logical, process, development, physical + scenarios) and viewpoints tied to stakeholders and concerns.

Architectural assets and the metamodel

Why architects reuse assets, and how reference patterns, reference architectures and architectural description relate.

Derivation depends on the system

How you derive an architecture depends on the system:

  • Similar system (built before) →
    • leans mainly on reuse of known solutions
    • method/assets and intuition as supporting inputs
  • Innovative system →
    • relies more heavily on method and assets
    • reuse is a smaller (but still present) input

Metamodel from the lecture

  • An architecture uses → reference patterns and reference architectures
  • An architecture is documented by → an architectural description

These reusable assets capture earlier solutions; check their fit to the current requirements.

Reference patterns break down into

  • Idioms
  • Design patterns
  • Architecture styles → the coarse-grained ones this topic focuses on
  • Analysis patterns → also listed among them in the lecture's summary
Reference pattern
Reusable proven solution: idiom, design pattern or architecture style.
Reference architecture
Domain-specific architecture that bundles many patterns.
Architectural description
The documented description of the architecture (views and viewpoints).

Your firm has built five online-banking portals and is asked for a sixth, for a new bank. Separately, it is asked to architect a first-of-its-kind drone-delivery control system. How does your approach differ?
  • Sixth portal → lean heavily on reuse

  • Drone system → no close precedent

    • Intuition backed by more validation

The risk differs: reuse risks carrying over assumptions that no longer fit; an innovative design risks unproven decisions.

A team adopts a published retail e-commerce reference architecture for a B2B procurement system with multi-level approvals. What do they gain, and what must they check?
  • Gain: a proven structure that bundles many patterns → cuts logical design effort
  • Check fit: a reference architecture is tied to its domain → B2B approval workflows and integration with buyers' systems may not appear in a retail reference at all
  • Adapt: keep what fits, add patterns for the gaps, and record where you departed from the reference

Structural styles and deployment components

Client-server and tiered styles, the network zones and proxies used to deploy them, and the server component types.

Client-server

  • Server offers services through well-defined interfaces
  • Clients use them → browser, applet, mobile app
  • Design questions:
    • thick or thin client
    • application layer design
    • state management
    • authentication and authorisation

Tiered computing

  • Several tiers cooperate → 3-tier, n-tier
  • Each tier acts as server to its caller and client to the next
  • Decide:
    • segregate by layers, features or organisation structure
    • plus state management
    • authentication

Network zoning

  • Example in the lecture → public web reverse proxy in a DMZ
  • Separated from internal application and database servers by an inner firewall
  • Some supporting servers also appear in its DMZ
  • Placement is an example, not a rule for all deployments
  • Permit only required traffic between zones

Reverse vs forward proxy

  • Reverse proxy → sits in front of internal servers, serving internet users, hides the servers' identity
  • Forward proxy → provides internet access to firewall-restricted internal clients, hides the clients' identity

Server component categories

  • Service execution → application servers
  • B2C integration → portal servers
  • Service and B2B integration → API gateway, ESB, BPM suites, B2B gateways
  • Management and governance → MDM, MAM, service registry
  • Data persistence → SQL, NoSQL
DMZ
Network segment separating a purely internal network from an external network.
Reverse proxy
Server in front of internal servers facing internet users; hides server identity.
Forward proxy
Server giving restricted internal clients internet access; hides client identity.
ESB
Enterprise Service Bus: service and B2B integration component.
n-tier
Architecture of several computational tiers, each server to the one above and client to the one below.

Check yourself

Staff on the internal network need controlled internet access, and internet customers need to reach the company's web servers. Which kind of proxy fits each, and what does each hide?
  • Staff → forward proxy: gives firewall-restricted internal clients internet access; hides the clients' identity
  • Customers → reverse proxy: typically in the DMZ, fronts the internal servers; hides theirs

Using one for the other's job would expose the wrong side.

A design puts the web server, application server and database all in the DMZ 'to keep latency low'. Critique it.
  • Problem: everything is exposed in the outer zone → compromising the web server gives direct reach to the application and the data
  • DMZ: keep only the internet-facing reverse proxy or web tier there
  • Inner firewall: put the application and database servers behind it
  • Permit only the traffic each needs

Cost: an extra network boundary and more firewall rules to manage → buys a much smaller blast radius.

A field-inspection app must keep working in areas with no mobile signal and sync later. Thick or thin client, and what design questions does that raise?

Thick client: it needs local logic and storage to work offline. That raises the client-server design questions:

  • Logic split: how to split logic between client and server
  • State: how to manage state and reconcile changes made offline
  • Security: how to authenticate and authorise without a live connection

You give up easy updates and accept more data on devices, which must be protected.

SQL vs NoSQL, CAP, ACID vs BASE, peer-to-peer

Data persistence trade-offs a structural style forces: relational vs NoSQL, the CAP theorem, ACID vs BASE, and the peer-to-peer style.

SQL vs NoSQL

They describe data models, not guaranteed scaling or consistency.

  • Relational (SQL) → tables and declared schemas (MySQL, Postgres, Oracle)
  • NoSQL stores →
    • key-value (DynamoDB)
    • document (MongoDB)
    • wide-column (Cassandra)
    • graph (Neo4j)
  • Scaling → lecture contrasts typical vertical SQL and horizontal NoSQL scaling
  • Actual capabilities depend on the product and configuration

CAP applies during a network partition

  • Consistency → operations behave like one up-to-date copy
  • Availability → every request to a non-failing node receives a response
  • Partition → if nodes cannot communicate, a distributed store cannot guarantee both

This is not a general instruction to pick any two properties for normal operation.

ACID transactions

  • Atomicity → all or none
  • Consistency → preserve database rules
  • Isolation → control interference between concurrent transactions
  • Durability → committed changes survive

ACID consistency differs from CAP consistency. An ACID label alone does not describe partition behaviour.

BASE

  • Basically available
  • Soft state
  • Eventual consistency → replicas may temporarily disagree and converge later

Describes an approach to distributed state, not a promise that every NoSQL store lacks transactions or durability.

Apply CAP per operation

  • Persist carts
  • Browsing and cart updates → may tolerate stale data to remain available
  • Checkout and payment → need coordinated, correct updates; may wait or reject requests during a partition

State the acceptable staleness and failure behaviour rather than choosing solely by database label.

Peer-to-peer

  • Peers act as both clients and servers and communicate directly
  • Lecture examples → Napster, BitTorrent, games, Bitcoin
  • May still use supporting discovery services
  • Consider → consistency, authentication and authorisation
CAP theorem
During a network partition, a distributed shared-data system cannot guarantee both strict consistency and availability.
ACID
Atomicity, Consistency, Isolation, Durability.
BASE
Basically Available, Soft state, Eventual consistency.
Peer-to-peer
Peers can each act as client and server and communicate directly; supporting coordination may still exist.

Check yourself

A ride-hailing platform runs in two data centres. During a network partition between them, which operations would you let answer with possibly stale data, and which would you make wait or reject: showing nearby drivers, updating a profile photo, charging the rider's card?
  • Nearby drivers, profile photos → favour availability: slightly stale data is acceptable and reconciles later
  • Charging the card → favour consistency: wait or fail rather than risk a double or lost charge

CAP is applied per operation during a partition → state the acceptable staleness for each one rather than choosing by database label.

A teammate says: 'Our database is ACID, so it stays consistent even when the two regions lose contact.' Do you agree?

No.

  • ACID consistency: a transaction preserves the database's rules
  • CAP consistency: all nodes behave like one up-to-date copy during a partition
  • An ACID label says nothing about what the system does when regions cannot communicate

Check the product's replication and partition behaviour, and decide per operation whether to reject requests or serve stale data.

A team picks a NoSQL document store for an invoicing system 'because NoSQL scales horizontally and SQL doesn't'. Invoices need atomic updates across customer, invoice and ledger records. Critique the choice.

The reasoning uses a label, not the requirement.

  • Tendencies, not guarantees: the lecture presents horizontal NoSQL and vertical SQL scaling as tendencies
  • Deciding need: coordinated multi-record updates → a relational ACID store supports them directly
  • Check: the expected volume and each product's actual transaction and scaling options

If volume were huge and the data naturally document-shaped, the balance could change.

A company must push 2 GB software updates to 20,000 branch PCs over thin WAN links. Would a peer-to-peer style fit, and what concerns would you raise?

It can fit: peers act as both clients and servers, so branches share pieces locally instead of all downloading from the centre (the BitTorrent pattern). Concerns to raise:

  • Authenticating and authorising peers
  • Consistency: keeping updates consistent and untampered across peers
  • Discovery service: peers still rely on it

If the links could handle a central download, a simpler client-server distribution avoids those problems.

Communication styles and integration levels

The three communication styles (data flow, call and return, event-based), the integration level at which each is used and the technologies behind them.

Data flow

  • Data enters and passes through components one at a time to a final destination
  • Suits batch integration (ETL)
  • Concerns → error handling, acceptable processing time, one- vs two-way replication
  • File level →
    • FTP
    • large scheduled batches
    • legacy integration with few technology options
  • Database level (views, federation, replication) →
    • single customer view
    • enterprise data inventory
    • real-time reporting and dashboards
    • updating common information across sources

Call and return

  • Component runs when it receives control and returns control when done (OSI layers, OS layers)
  • Concerns → discovering the target, error handling, timeouts
  • Presentation level (URL access, screen scraping) →
    • extending legacy systems to the web without source code
    • or across technology domains
  • Application level (RPC, SOAP/REST web services) →
    • B2B transactions
    • integrating existing systems in a process

Point-to-point messaging

  • Queue routes each message to one consumer for processing
  • Producer need not wait for the business operation to finish
  • Decide:
    • persistence
    • acknowledgement
    • ordering
    • retry behaviour
    • push versus pull
    • broker redundancy

Asynchrony does not by itself guarantee delivery.

Event-based (publish/subscribe)

  • Subscribers register interest; publisher sends to any number of them
  • Examples → forum subscriptions, push notifications
  • Concerns → asynchrony, durable vs non-durable, single point of failure

Choosing a communication style

Match it to the required qualities and coupling.

  • Synchronous call and return → simple, but couples caller and callee in time
  • Event-based → decouples and handles load, but adds complexity

Haze-information scenario

  • Public needs → availability, performance, usability for rich graphics
  • Data already sits in a sensor system
  • So → database-level data flow or web-service call and return can feed a web front end
ETL
Extract-Transform-Load: typical data flow batch integration.
Database federation
Integrating several databases through a single virtual view.
Screen scraping
Presentation-level integration by reading a legacy system's user interface.
SOAP / REST
Web service styles for application-level call and return.
Publish/subscribe
Publisher announces events to any number of registered subscribers.

Check yourself

An order service must (a) hand each payment job to exactly one of several payment workers and (b) tell inventory, email and analytics that an order was placed. Which messaging style suits each?
  1. (a) Point-to-point queue: each message goes to one consumer → workers share the jobs
  2. (b) Publish/subscribe: each subscriber gets the event → new subscribers can be added without changing the order service

In both, delivery depends on configuration: use persistent messages, acknowledgements and durable subscriptions if consumers can be offline.

Management wants a near-real-time sales dashboard combining three regional databases. An engineer proposes nightly FTP exports. Do you agree?

No.

  • File-level data flow suits large scheduled batches and legacy systems with few options
  • Real-time reporting and dashboards = a database-level use case (views, federation or replication)
  • Trade-off: database-level integration couples you to the source schemas and needs database access

If the regions can only export files, you are forced to file level and must accept stale data.

A 25-year-old application has no API, its source code is lost, and the business wants its data on a new web portal next quarter. What integration do you choose, and what are the risks?

Presentation-level integration (screen scraping) is the realistic choice: it suits extending a legacy system to the web without source code.

  • Fragile: any screen change breaks it
  • Slow
  • Limited to what the screens show

If its database turns out to be accessible, database-level data flow would be more robust.

Checkout calls fraud check, inventory, loyalty points and email synchronously, one after another. The loyalty service is often slow, and checkout times out. What would you change?
  • Keep call-and-return: fraud check and inventory → the checkout result depends on them
  • Move to event-based messaging: loyalty and email → a slow service no longer holds checkout
  • Why: synchronous calls couple the caller to the callee in time, while events decouple them

Cost: extra complexity and loyalty points that update a little later → add retries and failure handling for the asynchronous path.

Reference architectures: web and mobile

What a reference architecture is, the web architecture and its AWS mapping, and the shift to client-centric mobile architecture.

What a reference architecture is

  • Belongs to a domain and bundles many patterns
  • Deck covers → web, mobile, broker, SOA and microservices, cloud and serverless
  • Anti-example → spaghetti 'architecture': components tangled with no structure

Web architecture on AWS

Each concern maps to a service:

  • DNS routing → Route 53
  • Content delivery at the nearest edge location for low latency → CloudFront
  • Static content storage → S3
  • Load balancing across instances
  • Web and application servers → dynamic content
  • Auto scaling → adjust capacity up or down
  • Multi-AZ managed database

E-commerce version adds

  • Persistent session store → the cart
  • Volatile session store and cache → the catalogue
  • Search
  • Secure SSL checkout
  • Log-based recommendations

Client-centric architecture

  • Moves rendering and some application logic to a browser or native app that calls backend APIs
  • Server-side services still enforce business rules and protect data

The shift concerns where presentation and interaction run.

Mobile reference architecture

  • Choices driven by decision drivers the deck leaves open (e.g. native vs hybrid vs web)
  • IBM and AWS both publish mobile reference architectures
  • Combine device app, API/backend services and enterprise integration
Reference architecture
Domain-level architecture combining many patterns as a reusable template.
Client-centric architecture
App runs on the client and consumes APIs and services rather than receiving server-rendered pages.
Edge location
Content delivery point close to users for low latency.

Check yourself

A news site's application servers run at 90% CPU, mostly serving images and scripts, and readers abroad see slow page loads. What would you change, following the web reference architecture?

Move static content to object storage and serve it through a content delivery network.

  • Offload: takes static load off the application servers → left for dynamic content
  • Latency: serves readers from the nearest edge location

It does not speed up slow dynamic pages, and updated content must reach the edge copies.

An e-commerce site keeps shopping carts in web-server memory. During a scale-in event, customers lose their carts. Diagnose and fix.
  • Diagnosis: the cart state lives in the instance that was removed
  • Fix, as in the e-commerce reference: put carts in a persistent session store that survives instance loss
  • Fast in-memory store: for volatile session data and catalogue caching

Cost: another component to run and a network hop per cart access → in return any instance can serve any customer.

A bank moves from server-rendered pages to a single-page app calling APIs. A developer proposes moving the transfer-limit check into the browser to save a round trip. Do you agree?

No.

  • Client-centric architecture: rendering and interaction move to the client
  • Server-side services must still enforce business rules and protect data → client code can be bypassed

A browser-side check is fine for quick feedback, as long as the server repeats it.

Broker, SOA and microservices

Broker/ESB event channels, the five-layer SOA reference architecture and the microservices style with its scale cube, discovery and API gateway.

Broker architecture

  • Events go into event channels, handled by independent event processors (modules)
  • Examples (ESBs) → WebSphere ESB, Apache Camel, Mule
  • Process orchestration sits on top (e.g. BizTalk)
  • Consider:
    • integration need
    • number of systems
    • orchestration complexity
    • the broker's own single-point-of-failure and bottleneck risk

SOA layers (Open Group)

  1. Consumer → portal
  2. Integration and Business Process
  3. Services
  4. Component
  5. Operational Systems → runtime, legacy and packaged back ends

SOA loan example (from the deck)

  1. Portal on top
  2. Process orchestration beneath
  3. Services supporting the process
  4. Components implementing services
  5. Systems running them

Microservices

  • Split the system into vertical slices instead of horizontal layers
  • Each owns its own data store
  • Cost → hundreds of services form a dense web of dependencies
  • So the style demands → service discovery, gateways and automation

Scale cube (3 dimensions)

  • X axis → horizontal duplication (scale by cloning)
  • Y axis → functional decomposition (scale by splitting different things, i.e. microservices)
  • Z axis → data partitioning (scale by splitting similar things, i.e. sharding)

Service discovery and API gateway

  • Service discovery → needed because instances are ephemeral:
    • clients call a router at a well-known location
    • router queries a service registry
    • forwards to an available instance
  • API gateway → the single entry point that routes, aggregates and shields clients from the service layout
  • On AWS, microservices run either:
    • traditionally on application servers on EC2
    • or serverless with Lambda
Event channel
Broker pathway through which events flow to event processors.
Service registry
Directory of live service instances queried during discovery.
API gateway
Single entry point for clients that routes to microservices.
Scale cube
X cloning, Y functional decomposition, Z data partitioning.
Vertical slice
A service aligned to a business capability, owning its logic and data rather than sharing horizontal technical layers.

Check yourself

A retail system's search service is overloaded at peak, its order table has grown to 2 billion rows, and the promotions and payments teams keep blocking each other's releases. Which scale-cube axis addresses each problem?
  • Search load → X axis: clone more identical instances behind a load balancer
  • Huge order table → Z axis: partition data (for example by customer) so each instance handles a subset
  • Team collisions → Y axis: split by function into separate services
  • Each has a cost
    • X needs stateless instances
    • Z complicates queries across partitions
    • Y adds distributed operations
A team lists service instance addresses in configuration files. After auto-scaling is switched on, calls fail intermittently. Diagnose and fix.
  • Diagnosis: instances are now ephemeral → new ones are missing from the files and removed ones are still being called
  • Fix: service discovery → clients call a router at a well-known location, which looks up available instances in a service registry

The registry then becomes critical infrastructure and needs its own high availability.

All 40 integrations in a bank flow through one ESB instance, and an ESB upgrade took every channel offline for an evening. What risk did this expose, and what would you consider?

The broker style's main risk: the central broker is a single point of failure and a potential bottleneck.

  • Make the broker redundant and upgradable without an outage
  • Move integrations that need no central orchestration to direct or event-based links

You give up some central governance in exchange for resilience.

A 10-person team with one product and weekly releases is told to split its layered monolith into 30 microservices. Do you agree?

Probably not yet.

  • Microservices give: independently deployable, scalable vertical slices
  • Cost: a dense web of dependencies; needs service discovery, gateways and automation
  • One team, manageable release pace → operational cost likely outweighs the benefit

Modularise the monolith first; split out a service when a part needs independent scaling or more teams join.

Cloud, serverless and reactive

Cloud reference architecture, service and deployment models, VMs vs containers, multitenancy and elasticity, serverless, and the Reactive Manifesto.

Cloud reference architecture (IBM)

  • Wrapped by → governance and security, resiliency, performance, consumability
  • Three roles → service creator, consumer, provider
  • Provider's common cloud management platform → supplies operational and business support services
  • Over cloud services at IaaS, PaaS, SaaS and BPaaS levels

Deployment models (NIST)

  • Private → on-site or outsourced
  • Community → on-site or outsourced
  • Public
  • Hybrid

VMs vs containers

  • VM → each includes a guest OS
  • Container → shares a host kernel, packages the app with its dependencies
  • A hosted hypervisor is one arrangement

The key distinction is the guest OS boundary versus a shared kernel.

Multitenancy and elasticity

  • Multitenancy → isolation of independent organisations' workloads in a shared environment
  • Elasticity → provisioning resources in proportion to changing demand, up or down

Serverless

  • e.g. Lambda
  • You supply functions; the platform runs and scales them
  • You do not manage servers
  • Complements microservices

Reactive Manifesto

  • Responsive → consistent response times with reliable upper bounds
  • Elastic → stay responsive under varying workload
  • Resilient → stay responsive in the face of failure
  • Asynchronous message passing → gives loose coupling, isolation and location transparency
Multitenancy
Isolating independent organisations' workloads in a shared environment.
Elasticity
Provisioning resources in proportion to changing needs, up or down.
Container
Lightweight packaged app sharing the host OS kernel via a container engine.
Hybrid cloud
Combination of private and public cloud (NIST deployment model).
Reactive system
Responsive, resilient, elastic and message-driven system.

Check yourself

You must run 200 small instances of the same Linux service, and also host a legacy application that needs its own OS kernel version. Containers or VMs for each?
  • 200 instances → containers: share the host kernel and package only the application and its dependencies → lighter and denser
  • Legacy application → VM: it needs its own guest OS

The trade-off is isolation: a VM has a guest OS boundary, while containers share one kernel.

A SaaS payroll provider hosts 300 client companies on shared infrastructure, and load spikes at each month end. Which cloud property addresses which concern?
  • Multitenancy → sharing: each company's workloads and data must stay isolated in the common environment
  • Elasticity → the spike: resources are provisioned up for month end and back down afterwards

They interact: elastic capacity without good tenant isolation lets one tenant's spike degrade the others.

An image-thumbnail job runs a few hundred times a day, with occasional bursts of several thousand. Serverless functions or always-on containers?

Serverless fits.

  • You supply the function; the platform runs and scales it
  • No servers to manage
  • No paying for idle capacity between bursts

You give up control over the runtime environment. If the load became steady and high, re-examine whether always-on instances are better value.

A service blocks one thread per request while calling a slow partner API. Under peak load it stops responding entirely. What would the Reactive Manifesto suggest?

Use asynchronous message passing, so a slow partner does not tie up a thread per request.

  • Loose coupling and isolation
  • Elastic: keeps the service responsive under varying load
  • Resilient: responsive when the partner fails

Cost: a more complex programming and failure-handling model.

Architectural description: views and viewpoints

How architecture is documented: IEEE 42010 metamodel, UML, the 4+1 view model and further viewpoints aimed at specific stakeholders.

ISO/IEC/IEEE 42010

Standard for architecture description (building on IEEE 1471). Key idea:

  • Stakeholders have concerns
  • A viewpoint addresses those concerns with modelling techniques
  • A view is the viewpoint applied to the system

UML

  • General-purpose standard notation
  • Structure and behaviour diagram types
  • Examples → class, component, package, deployment, sequence, activity, state

4+1 view model

Several concurrent views tied to scenarios (view → stakeholder: concerns):

  • Logical → end user: functionality
  • Process → integrator: performance, security, throughput
  • Development → programmer: coding, testing
  • Physical → system engineer: topology, delivery, installation, telecommunication
  • +1 Scenarios → tie the four together

Other viewpoints

Each has stakeholders, concerns and techniques (viewpoint → techniques):

  • Organization → block diagram
  • Business Function → block diagram
  • Business Process → block, BPMN, BPEL, UML activity
  • Application Structure → layering, UML package, component
  • Application Behaviour → sequence, collaboration, state
  • Infrastructure → network, package, block (concerns: security, stability, cost)
  • Deployment → UML package, deployment diagrams (mapping logical components to physical artifacts)
  • Information Structure → UML class, ER

Takeaway

  • Metamodel → reference patterns, reference architectures, architectural description
  • Reference patterns include → architecture styles, analysis patterns, design patterns, idioms
  • Choosing the right style and architecture depends on the architect's knowledge and experience

The right choice is critical to achieving the required qualities.

Viewpoint
Conventions for a kind of view: which stakeholders, concerns and modelling techniques.
View
Representation of the system from one viewpoint.
4+1 model
Logical, process, development and physical views tied by scenarios.
UML
Unified Modeling Language, standard visual notation for software design.
BPMN
Business Process Model and Notation, used for business process viewpoints.

Check yourself

An architect presents one large diagram mixing classes, servers, network zones and business process steps. Operations staff and developers both say it doesn't answer their questions. What would you change?

Split it into views aimed at each stakeholder's concerns, as ISO/IEC/IEEE 42010 suggests:

  • Physical or deployment view → operations
  • Development view → programmers
  • Logical view → functionality
  • Process view → performance
  • Key scenarios → tie them together

Cost: keeping several views consistent, which the scenarios help with.

Three concerns are raised: an integrator asks about throughput between concurrent processes; a system engineer asks how components are installed across sites; programmers ask how code modules are organised for testing. Which 4+1 view answers each?
  • Integrator → process view: performance, throughput, concurrency
  • System engineer → physical view: topology, installation, delivery
  • Programmers → development view: code organisation, testing
  • Scenarios: check that the three views describe the same system
A team defines a deployment viewpoint but supplies no deployment view. What is missing?
The viewpoint sets the conventions and concerns; the view applies them to this system. The team still needs the actual mapping of components and artifacts to nodes, with the relevant connections.
A security auditor asks which components run in the DMZ and which can talk to the database. Which viewpoint and notation would you use?
  • Deployment viewpoint: UML deployment diagrams → map logical components to physical nodes
  • Infrastructure viewpoint: a network diagram → zones and permitted connections

A logical component diagram alone cannot answer it, because it doesn't say where anything runs.

Exam-style questions

Answer aloud or on paper before opening.

A retailer's legacy inventory system offers only a nightly CSV export and read access to its database. A new web shop needs stock levels no more than 1 minute old, synchronous order placement, and order notifications to email, SMS and analytics. (a) Choose a communication style and integration level for each need. (b) The inventory team then forbids direct database access. What changes?
  1. (a) Style and level per need
    • Stock → database-level data flow (replication or a view): 1-minute freshness rules out the nightly file
    • Orders → application-level call and return through a web service: the customer needs an immediate result
    • Notifications → publish/subscribe: email, SMS and analytics subscribe independently; new channels need no change to the order service
    • Structurally: a tiered client-server design with a reverse proxy in the DMZ
  2. (b) No database access → only the file export remains
    • Either negotiate an application-level interface on the inventory system
    • Or accept stale stock data and show availability as approximate
    • Document this as a constraint-driven decision with its business impact
A concert-ticketing platform runs in two regions. During an on-sale for 20,000 seats, the regions lose contact for 2 minutes. Which operations favour availability and which favour consistency? What does the customer see, and does an ACID database settle the question?
  • Favour availability: browsing events and seat maps → accept briefly stale seat maps
  • Favour consistency: seat reservation and payment → otherwise two regions could sell the same seat
  • During the partition: those operations wait or are refused in the region that cannot coordinate → the customer sees a 'try again' or queue message
  • When the link returns: reconcile holds
  • ACID doesn't settle it: ACID transactions guarantee rules within a transaction but say nothing about partition behaviour → check the replication design separately
A five-year-old monolith: during sales the catalogue gets 50 times the traffic of checkout; three teams work on it; a nightly report reads every table. Propose a decomposition using the scale cube and name two side effects to monitor.
  • Y axis: split by business capability (catalogue, checkout, accounts), each service owning its data → teams deploy independently
  • X axis: clone the catalogue service heavily for sales peaks without scaling checkout
  • Z axis: partition order data later if it grows too large
  • Add an API gateway and service discovery
  • Nightly report: can no longer read every table → feed it from events or replicas
  • Side effects to monitor
    • Cross-service consistency (orders referring to changed catalogue data)
    • Latency and failures across the new network call chains → need tracing and timeouts
Compare two organisations. A bank has 15 legacy core systems, and loan approval is a long process orchestrated across six of them. A start-up has one product, two teams and frequent releases. Would you lean towards broker/SOA or microservices for each, and why?
  • Bank → SOA with a broker
    • Layered services over the existing operational systems
    • Process orchestration in the integration layer, reusing enterprise services
    • Make the broker redundant: it is a single point of failure and a bottleneck risk
  • Start-up → modular monolith now, microservices later
    • Independent vertical slices with their own data favour agility
    • But only once the team can support discovery, gateways and automation

Deciding factors: the number of systems to integrate, the complexity of orchestration and the team's operational maturity.

A new payments platform is reviewed by an auditor (where card data flows and who can reach it), operations (servers, sites, failover) and developers (module structure, build). How would you document the architecture, and how do you keep the views consistent?

Follow 42010: list the stakeholders and their concerns, then choose viewpoints.

  • Auditor: an information-structure view (class or ER model) for card data, plus deployment and infrastructure views showing zones and permitted connections
  • Operations: the physical or deployment view, with nodes, sites and failover paths
  • Developers: the development view and an application-structure view (packages, components)
  • Process view: for throughput and concurrency
  • Consistency: tie the views together with key scenarios such as 'authorise a card payment', and trace each scenario through every view
An exam-results portal is idle most of the year, then 200,000 students log in during the first hour of results day. The results are personal data under strict regulation. Which reference-architecture options would you weigh, and what do you give up with each?

The demand profile calls for elasticity: capacity that scales up for one hour and back down.

  • Public cloud, elastic
    • Containers on an elastic platform
    • Or serverless functions for the read-heavy results lookup, which scale without managed servers
    • Give up: serverless gives up runtime control
  • Private or hybrid deployment: data sensitivity pushes the other way
    • Keep the results store in a controlled environment
    • Put only the elastic front end in public cloud
    • Give up: private hosting gives up elasticity, forcing you to provision for the peak

Judge the options by availability on results day, security, cost and responsiveness under the spike, the Reactive goal.
