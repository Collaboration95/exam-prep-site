Day 4 mock questions

Do these after all of today's topics. Give your choice, reason and trade-off before opening an answer.

Whole day

Two app servers replace one, but the database and network remain shared. Peak-time latency still fails its target. What should you inspect before adding a third?
Measure response time, queueing, throughput and per-resource utilisation to find the real bottleneck: if the shared database is saturated, a third app server adds load to it without adding throughput. Map required dependencies and shared failure points too, because two app servers do nothing for a database or network failure. Add app servers only if that tier is the limit; otherwise scale or offload the database (caching, read replicas, fewer visits per request).
Two app servers in parallel, 99% available each, run at 70% CPU during peak. A teammate claims the tier is now 99.99% available. Do you agree?
Not at peak. The 99.99% figure assumes either server can carry the full load alone, but if one fails, the survivor would need 140% of its capacity, so it saturates, queues grow without bound and the service is effectively down. Either size so that one server can carry the peak (each below about 50% at peak, preferably lower to keep response times acceptable) or add a third server. Then the parallel calculation is justified, provided failover works and failures are independent.
Search works from cache during a database outage, but checkout fails. Is the system available?
Judge each function against its own requirement: cached search is available, and checkout is not. If the agreed service counts checkout as critical, the service is unavailable for that purpose, whatever the search page shows. A circuit breaker and cache provide graceful degradation, but checkout availability needs a redundant data tier or a degraded mode, such as holding orders for later confirmation, if the business accepts it.

Designing Highly Available Architecture

A web system has an active/passive load balancer pair (99% each), two web servers in parallel (99% each), one application server (99%), an active/passive database pair (99% each) and one firewall (98%). The target is 99.9%. Calculate end-to-end availability, say whether it meets the target, and recommend improvements with their assumptions.
Each pair gives 1 - 0.01^2 = 0.9999. In series: 0.9999^3 x 0.99 x 0.98 = 96.99%, which misses 99.9% badly because of the single application server and firewall. Replicating both gives 0.9999^4 x (1 - 0.02^2) = 99.92%, which just meets the target. This assumes independent failures, working failover and enough capacity in the survivors. Shared power, storage or a common software fault would lower the real figure, so test failover and check for shared failure domains.
A monthly SLA promises 99.95% over a 30-day, 24-hour service month. This month had a 15-minute unplanned outage and a 20-minute planned maintenance window. Does the service meet the SLA? What changes the answer, and what would you change in the design?
The month has 43,200 minutes, so 99.95% allows 21.6 minutes of downtime. The outage alone is 15 minutes (99.965%), which passes. If planned maintenance counts, the total is 35 minutes (99.919%), which fails. The answer depends on whether the agreed service time excludes the maintenance window. Design changes: rolling or blue/green deployments, so maintenance needs no downtime, and faster detection and failover to shorten unplanned outages.
Service A receives 100 requests/s and has 200 worker threads. Each request calls service B with a 30 s timeout. B slows from 50 ms to 10 s per call. Explain what happens to A, and design the containment.
By Little's Law, A needs 100 x 10 = 1,000 requests in flight but has 200 threads, so the pool is exhausted within about 2 seconds. A stops responding and its own callers fail: a cascading failure, made worse by retries. Containment: a short timeout (1 s would keep about 100 requests in flight), a circuit breaker that fails fast with a fallback once B is unhealthy, a bulkhead so calls to B use their own limited pool and cannot take every thread, and bounded retries with backoff. Validate it by injecting latency into B in a chaos experiment.
An e-commerce site needs 99.99% availability for checkout. The data tier is the weak point. Compare two database redundancy models and recommend one, stating what you would monitor.
Active/passive with shared disk is simple failover, but the shared storage is a single point of failure unless the array itself is redundant. Shared-nothing replication (a primary with replicas, or multi-node replication) gives each node its own storage, avoiding that, but needs promotion rules and risks losing unreplicated writes at failover. For 99.99%, prefer shared-nothing replication across failure domains, with automated, tested promotion and enough capacity in the survivors, plus RAID and tested backups for recovery. Monitor replication lag, failover time and data loss in failover tests, and calculate end-to-end availability rather than trusting the topology label.
A database holds 2 TB. A full backup takes 5 hours, the nightly window is 2 hours, daily changes are about 50 GB, and the recovery-time target is 3 hours. Compare full, differential and incremental backup and recommend a scheme.
A nightly full backup is impossible (5 hours against a 2-hour window). Weekly full plus nightly incrementals copies only about 50 GB a night, but a restore late in the week needs the full plus up to six incrementals in order, which is the slowest and most fragile option. Weekly full plus nightly differentials grows to about 300 GB by day six, which must still fit the window, and a restore needs only the full plus one differential. Recommend the differential scheme if day-six differentials fit the window. Then test whether a 2 TB full restore can finish within 3 hours. If it cannot, backups alone cannot meet the target, and you need a standby replica.
Choose a RAID level for an array of four 3 TB disks that must tolerate any two simultaneous disk failures, and state its cost against the alternatives.
RAID 6 guarantees any two disk failures with at least four disks. Two disks' worth of capacity holds parity, so four 3 TB disks provide 6 TB usable. Parity updates add write overhead, and actual speed depends on workload and implementation. RAID 10 gives the same 6 TB but guarantees only one failure (two only if they are in different mirrors). RAID 5 gives 9 TB with one-failure tolerance, and RAID 0 has no protection.

Design for Performance in Architecture

A request passes a firewall (5 ms wait, 45 ms service, 10 tps capacity), a reverse proxy (10, 90, 16 tps), an app server (50, 550, 6 tps) and a database (30, 300, 20 tps), with 200 ms of network latency. (a) Find the response time and throughput. (b) You add a second app server. What is the new throughput, and what is the next bottleneck?
(a) Response time = 50 + 100 + 600 + 330 = 1080 ms, plus 200 ms latency, giving 1280 ms. Throughput = min(10, 16, 6, 20) = 6 tps, limited by the app server. (b) Two app servers give about 12 tps, so throughput becomes min(10, 16, 12, 20) = 10 tps, and the firewall is now the bottleneck. Each request's service time is unchanged, so response time improves only through less queueing at the app tier. To go beyond 10 tps, scale the firewall as well.
Each job needs 5 s of CPU, 80 I/Os on storage A (50 ms each) and 100 I/Os on storage B (30 ms each). Storage A is observed at 15.70 I/Os per second. Find the system throughput, the utilisations and the bottleneck. What would it take to double throughput?
Forced Flow: λ_0 = 15.70 / 80 = 0.196 jobs/s. Demands: CPU 5 s, A 4 s, B 3 s. U = λ_0 x D gives CPU 98%, A 78.4%, B 58.8%; the CPU is the bottleneck, and maximum throughput is 1 / 5 = 0.2 jobs/s. To double to about 0.39 jobs/s, every demand must fall below about 2.56 s. Halving CPU demand alone leaves A as the limit at 1 / 4 = 0.25 jobs/s, so storage A, and storage B (3 s), also need faster devices, fewer visits or more parallel units. Bottlenecks move as you fix them.
A shop receives 20 requests an hour, and one server handles 30 an hour. Compute the utilisation and average time in system. Then, at 2 requests per minute with a 1.5-minute service time and a target of queueing under 3 minutes, a faster server is not possible: how many servers do you need with separate queues, and with one shared queue?
For 20/hour arrivals and 30/hour capacity, U = 2/3 and R = 6 minutes including service. For λ = 2/min and S = 1.5 minutes, the offered load is 3, so ρ = 3/c. Waiting under 3 minutes means R < 4.5. Separate queues need c = 5; the lecture's approximate shared-queue model gives c = 4. Both need ρ < 1. Validate the chosen model with measured data and add headroom for a server failure.
1000 players each trigger an event every 3 s (think time). Server time is 50 ms and the round trip is 200 ms. What load must the server handle, and how many requests are in flight?
Assuming one outstanding request per player and no queueing, the rate is 1000 / (3 + 0.05 + 0.2) = 307.7/s. Work in the server averages 307.7 x 0.05 = 15.4 requests. Including network time, 307.7 x 0.25 = 76.9 requests are in flight. State the boundary you are counting; the remaining players are thinking.
A product-detail lookup takes 50 ms from the database. A cache would take 5 ms. Measured access is uniform across the catalogue, and a cache the size you can afford gives a 20% hit ratio. A teammate says to add the cache. Argue for or against, and say what would change your mind.
Expected time = 0.2 x 5 + 0.8 x 55 = 45 ms against 50 ms: a 10% gain for the cost of the cache memory and an extra component, which is weak. It stops paying at all if cache access reaches 10 ms or the hit ratio falls. With uniform access, a larger cache raises hits only in proportion to its size. What would change the decision: a power-law access pattern, where a small cache catches most requests; precomputing the expensive part of the page; or a source that is much slower than 50 ms. Measure before buying.
A web tier runs at 85% utilisation with 4 s average response time against a 2 s target, and 40% of requests fetch the same home-page data. Which tactics would you apply, in what order, and how would you verify them before building?
First reduce demand: cache or precompute the home-page data, removing up to 40% of the work and lowering utilisation and queueing. Then manage resources: add servers behind a load balancer (shared queue) so per-server utilisation falls well below 85%, and fix any algorithmic or database bottleneck the measurements show. If needed, throttle or deprioritise non-interactive load. Verify with a queueing model or simulation (for example JMT) and an instrumented prototype benchmark under the real request mix, repeating until the 2 s target holds with headroom.
