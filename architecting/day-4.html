Day 4 mock questions

Do these after all of today's topics. Give your choice, reason and trade-off before opening an answer.

Whole day

Two app servers replace one, but the database and network remain shared. Peak-time latency still fails its target. What should you inspect before adding a third?
  • Find the real bottleneck: measure response time, queueing, throughput and per-resource utilisation
  • Shared database saturated? → a third app server adds load to it without adding throughput
  • Map required dependencies and shared failure points: two app servers do nothing for a database or network failure
  • Decision: add app servers only if that tier is the limit; otherwise scale or offload the database (caching, read replicas, fewer visits per request)
Two app servers in parallel, 99% available each, run at 70% CPU during peak. A teammate claims the tier is now 99.99% available. Do you agree?

Not at peak.

  • Assumption: the 99.99% figure assumes either server can carry the full load alone
  • At 70% CPU: if one fails, the survivor would need 140% of its capacity → it saturates, queues grow without bound, service effectively down
  • Fix
    • Size so one server can carry the peak (each below about 50% at peak, preferably lower to keep response times acceptable)
    • Or add a third server

Then the parallel calculation is justified, provided failover works and failures are independent.

Search works from cache during a database outage, but checkout fails. Is the system available?

Judge each function against its own requirement: cached search is available, checkout is not.

  • Agreed service: if it counts checkout as critical, the service is unavailable for that purpose, whatever the search page shows
  • Circuit breaker and cache → graceful degradation
  • Checkout availability needs a redundant data tier or a degraded mode, such as holding orders for later confirmation, if the business accepts it

Designing Highly Available Architecture

A web system has an active/passive load balancer pair (99% each), two web servers in parallel (99% each), one application server (99%), an active/passive database pair (99% each) and one firewall (98%). The target is 99.9%. Calculate end-to-end availability, say whether it meets the target, and recommend improvements with their assumptions.

96.99%: misses 99.9%; replicating the app server and firewall gives 99.92%.

  1. Each pair: 1 - 0.01^2 = 0.9999
  2. In series: 0.9999^3 x 0.99 x 0.98 = 96.99% → misses 99.9% badly because of the single application server and firewall
  3. Replicate both: 0.9999^4 x (1 - 0.02^2) = 99.92% → just meets the target
  4. Assumes: independent failures, working failover and enough capacity in the survivors

Shared power, storage or a common software fault would lower the real figure → test failover and check for shared failure domains.

A monthly SLA promises 99.95% over a 30-day, 24-hour service month. This month had a 15-minute unplanned outage and a 20-minute planned maintenance window. Does the service meet the SLA? What changes the answer, and what would you change in the design?

Passes if planned maintenance is excluded; fails if it counts.

  1. Month = 43,200 minutes; 99.95% allows 21.6 minutes of downtime
  2. Outage alone: 15 minutes (99.965%) → passes
  3. Planned maintenance counts: total 35 minutes (99.919%) → fails
  4. What changes the answer: whether the agreed service time excludes the maintenance window
  5. Design changes
    • Rolling or blue/green deployments → maintenance needs no downtime
    • Faster detection and failover → shorter unplanned outages
Service A receives 100 requests/s and has 200 worker threads. Each request calls service B with a 30 s timeout. B slows from 50 ms to 10 s per call. Explain what happens to A, and design the containment.
  • What happens to A: a cascading failure
    • Little's Law: A needs 100 x 10 = 1,000 requests in flight but has 200 threads
    • → pool exhausted within about 2 seconds
    • → A stops responding and its own callers fail, made worse by retries
  • Containment
    • Short timeout: 1 s would keep about 100 requests in flight
    • Circuit breaker: fails fast with a fallback once B is unhealthy
    • Bulkhead: calls to B use their own limited pool, so they cannot take every thread
    • Bounded retries with backoff
  • Validate: inject latency into B in a chaos experiment
An e-commerce site needs 99.99% availability for checkout. The data tier is the weak point. Compare two database redundancy models and recommend one, stating what you would monitor.

Prefer shared-nothing replication across failure domains for 99.99%.

  • Active/passive with shared disk: simple failover, but the shared storage is a single point of failure unless the array itself is redundant
  • Shared-nothing replication (a primary with replicas, or multi-node replication): each node has its own storage → avoids that, but needs promotion rules and risks losing unreplicated writes at failover
  • Recommendation
    • Automated, tested promotion and enough capacity in the survivors
    • Plus RAID and tested backups for recovery
  • Monitor
    • Replication lag
    • Failover time and data loss in failover tests

Calculate end-to-end availability rather than trusting the topology label.

A database holds 2 TB. A full backup takes 5 hours, the nightly window is 2 hours, daily changes are about 50 GB, and the recovery-time target is 3 hours. Compare full, differential and incremental backup and recommend a scheme.

Weekly full + nightly differentials, if day-six differentials fit the window.

  • Nightly full: impossible (5 hours against a 2-hour window)
  • Weekly full + nightly incrementals: copies only about 50 GB a night, but a late-week restore needs the full plus up to six incrementals in order → slowest and most fragile
  • Weekly full + nightly differentials: grows to about 300 GB by day six, which must still fit the window; restore needs only the full plus one differential
  • Then test whether a 2 TB full restore can finish within 3 hours

If it cannot, backups alone cannot meet the target → you need a standby replica.

Choose a RAID level for an array of four 3 TB disks that must tolerate any two simultaneous disk failures, and state its cost against the alternatives.

RAID 6.

  • Tolerance: guarantees any two disk failures, with at least four disks
  • Capacity: two disks' worth holds parity → four 3 TB disks provide 6 TB usable
  • Cost: parity updates add write overhead; actual speed depends on workload and implementation
  • Alternatives
    • RAID 10: same 6 TB but guarantees only one failure (two only if they are in different mirrors)
    • RAID 5: 9 TB with one-failure tolerance
    • RAID 0: no protection

Design for Performance in Architecture

A request passes a firewall (5 ms wait, 45 ms service, 10 tps capacity), a reverse proxy (10, 90, 16 tps), an app server (50, 550, 6 tps) and a database (30, 300, 20 tps), with 200 ms of network latency. (a) Find the response time and throughput. (b) You add a second app server. What is the new throughput, and what is the next bottleneck?
  1. (a) Response time and throughput
    • Response time = 50 + 100 + 600 + 330 = 1080 ms
    • Plus 200 ms latency → 1280 ms
    • Throughput = min(10, 16, 6, 20) = 6 tps, limited by the app server
  2. (b) Second app server
    • Two app servers give about 12 tps
    • Throughput = min(10, 16, 12, 20) = 10 tps → the firewall is now the bottleneck
    • Each request's service time is unchanged → response time improves only through less queueing at the app tier

To go beyond 10 tps, scale the firewall as well.

Each job needs 5 s of CPU, 80 I/Os on storage A (50 ms each) and 100 I/Os on storage B (30 ms each). Storage A is observed at 15.70 I/Os per second. Find the system throughput, the utilisations and the bottleneck. What would it take to double throughput?
  1. Forced Flow: λ_0 = 15.70 / 80 = 0.196 jobs/s
  2. Demands: CPU 5 s, A 4 s, B 3 s
  3. U = λ_0 x D: CPU 98%, A 78.4%, B 58.8%
  4. Bottleneck: the CPU; maximum throughput = 1 / 5 = 0.2 jobs/s
  5. To double to about 0.39 jobs/s: every demand must fall below about 2.56 s
    • Halving CPU demand alone leaves A as the limit at 1 / 4 = 0.25 jobs/s
    • So storage A, and storage B (3 s), also need faster devices, fewer visits or more parallel units

Bottlenecks move as you fix them.

A shop receives 20 requests an hour, and one server handles 30 an hour. Compute the utilisation and average time in system. Then, at 2 requests per minute with a 1.5-minute service time and a target of queueing under 3 minutes, a faster server is not possible: how many servers do you need with separate queues, and with one shared queue?
  1. Part 1: 20/hour arrivals, 30/hour capacity
    • U = 2/3
    • R = 6 minutes including service
  2. Part 2: λ = 2/min, S = 1.5 minutes
    • Offered load is 3 → ρ = 3/c
    • Waiting under 3 minutes → R < 4.5
    • Separate queues need c = 5
    • The lecture's approximate shared-queue model gives c = 4
    • Both need ρ < 1

Validate the chosen model with measured data and add headroom for a server failure.

1000 players each trigger an event every 3 s (think time). Server time is 50 ms and the round trip is 200 ms. What load must the server handle, and how many requests are in flight?

Assuming one outstanding request per player and no queueing:

  1. Rate = 1000 / (3 + 0.05 + 0.2) = 307.7/s
  2. Work in the server averages 307.7 x 0.05 = 15.4 requests
  3. In flight, including network time: 307.7 x 0.25 = 76.9 requests

State the boundary you are counting; the remaining players are thinking.

A product-detail lookup takes 50 ms from the database. A cache would take 5 ms. Measured access is uniform across the catalogue, and a cache the size you can afford gives a 20% hit ratio. A teammate says to add the cache. Argue for or against, and say what would change your mind.

Against: the gain is weak.

  • Expected time = 0.2 x 5 + 0.8 x 55 = 45 ms against 50 ms → a 10% gain
  • Cost: the cache memory and an extra component
  • Stops paying at all if cache access reaches 10 ms or the hit ratio falls
  • Uniform access → a larger cache raises hits only in proportion to its size
  • What would change the decision
    • A power-law access pattern, where a small cache catches most requests
    • Precomputing the expensive part of the page
    • A source that is much slower than 50 ms

Measure before buying.

A web tier runs at 85% utilisation with 4 s average response time against a 2 s target, and 40% of requests fetch the same home-page data. Which tactics would you apply, in what order, and how would you verify them before building?
  1. First reduce demand: cache or precompute the home-page data → removes up to 40% of the work, lowering utilisation and queueing
  2. Then manage resources
    • Add servers behind a load balancer (shared queue) → per-server utilisation falls well below 85%
    • Fix any algorithmic or database bottleneck the measurements show
  3. If needed, throttle or deprioritise non-interactive load
  4. Verify before building
    • A queueing model or simulation (for example JMT)
    • An instrumented prototype benchmark under the real request mix
    • Repeat until the 2 s target holds with headroom
