Design for Performance in Architecture

107 slides · about 48 min · open the deck · JSON

This topic covers how to define, measure and design for performance in an architecture. It builds from the core metrics (response time, throughput, utilization, load) through queueing theory and its laws (utilization, forced flow, Little's, general response time, M/M/1 and multi-server models) to tactics such as load balancing, caching, precomputation and flow control, and finally validation by modelling, prototyping and documentation. In the exam expect numeric questions using these formulas plus scenarios asking you to find bottlenecks and justify tactics.

Big ideas

  • Response time includes service, queueing and communication within a stated boundary. Serial visit times add; concurrent branches that must all finish contribute their maximum plus coordination overhead.
  • Serial pipeline capacity is limited by the bottleneck. Independent load-balanced replicas can add capacity when work is distributed and no shared bottleneck intervenes.
  • For a stable single resource, utilization U = X S, where X is its throughput; if no work is lost, X equals arrival rate λ. Forced flow accounts for repeated visits: X_i = X_0 V_i.
  • Little's Law n = λR; General Response Time Law R = sum of R_i V_i.
  • M/M/1: R = S/(1-U) = 1/(µ-λ); response time explodes as utilization nears 100%, so keep utilization below the knee.
  • Shared-queue M/M/c and separate c(M/M/1) use different models. Both require per-server utilization ρ = λS/c < 1; the lecture’s M/M/c response-time formula is approximate.
  • Tactics: control demand, manage resources, load balance, cache (weighted hit/miss), precompute, lower algorithmic complexity, remove bottlenecks.
  • Validate early by simulation and prototyping; document major components, big messages and high-frequency calls.

What performance means: the core metrics

Performance is useful work done accurately, efficiently and quickly, and it is judged through a handful of metrics: response time, throughput, utilization, load, latency and think time.

Choose measurable goals

  • Specify response time, throughput and resource use
  • ...for a stated workload
  • Low utilization alone is not proof of good performance: an idle system may simply be doing little work
  • Use metrics together

Response time components

Response time = service time + waiting time + transmission time

  • Service time: how long the work itself takes
  • Waiting (queue) time: how long the request sits behind others
  • Transmission time: moving the request and reply

For finer analysis each piece can be split further (network, rendering, processing).

Throughput vs load

  • Throughput = rate of completed work; load = rate of incoming work
  • Arrival rate (input rate, load) → counts requests coming in per period
  • Response rate (output rate, throughput) → counts responses going out
  • Throughput is a better indicator of system performance than clock speed or disk seek time, because it reflects all components together

Utilization

  • Utilization = used capacity / total capacity
  • = the share of time a component is busy
  • Busy CPU or disk cannot take other work → pending requests wait
  • High utilization is what creates queueing

Define “load”

  • May mean request rate, throughput or utilization: write the units
  • Stable, loss-free system → arrival and completion rates match
  • End-to-end latency vs network latency are different boundaries: specify which is being measured

Think time

  • Think time = the user's pause between actions
  • Does not measure the system
  • But it changes utilization and throughput calculations
  • → matters for performance testing and capacity planning
Response time
Elapsed time from a request until its response: service + waiting + transmission.
Throughput
Number of responses completed per unit time (output rate).
Utilization
Used capacity divided by total capacity; share of time busy.
Latency
Minimum time to send data from one component to another.
Think time
Time a user spends between successive actions.

Check yourself

A vendor offers a server with a 30% faster CPU clock. Your application spends 70% of each request waiting on the database. Will throughput rise by 30%?

No.

  • Throughput reflects the whole system → here the database dominates
  • A faster CPU speeds up only the small CPU share of the work
  • Measure throughput under your own workload before paying for clock speed

Upgrading the bottleneck resource (the database, or how it is used) is what raises throughput.

A dashboard shows CPU at 20%, and the team concludes performance is fine. Users report 8-second responses. What is wrong with the conclusion?

Low utilisation is not proof of good performance.

  • Time spent waiting on another resource: database locks, disk, a slow dependency, the network
  • Or the CPU may be idle because work is stuck elsewhere
  • Look together at response time, throughput and the utilisation of each resource → find where the time goes
A load test fires requests back-to-back from 500 virtual users with zero think time. Real users pause about 10 s between actions, and responses take about 1 s. What does the test misrepresent?

The load.

  1. No think time: 500 users generate about 500 requests/s
  2. 10 s pause: 500 / (10 + 1) → roughly 45 requests/s
  3. → the test therefore models a far heavier load than 500 real users

Set realistic think times and arrival rates, or the results won't map to the requirement.

Average response time rose from 300 ms to 2 s while service time stayed at 250 ms. Where did the extra time go, and how would you confirm it?

Response time = service time + waiting time + transmission time.

  • Service unchanged → the growth is almost certainly waiting in queues caused by higher utilisation
  • Or possibly transmission
  • Confirm: check queue lengths, utilisation and network timings at each tier

Combining components: serial vs parallel, load vs throughput

How response time and throughput combine across components in series and in parallel, how throughput saturates as load grows, and worked exercises on a burger shop, a game server and a four-tier stack.

Serial composition

  • Add response times along the request path
  • Pipeline capacity is limited by the lowest stage capacity (when each request visits each stage once)
  • Repeated visits → compare service demand per system request instead

Two meanings of parallel

  • Concurrent branches of one request → contribute their maximum time when all results are required
  • Load-balanced replicas → process different requests and can add capacity
  • Assumptions behind these results:
    • independent work
    • adequate distribution
    • no additional shared bottleneck
  • Include coordination overhead where relevant

Single-worker burger example

  • 1 minute to prepare + 0.5 minute to pack = 1.5 minutes of work
  • → capacity 40 burgers/hour
  • Halving that service time doubles this worker’s capacity

This does not establish that any reduction in end-to-end response time doubles system throughput.

Below vs at saturation

  • Below saturation: a stable system completing one response per accepted request → throughput = arrival rate
  • Capacity 20/s, arrivals 22/s → completion rate cannot exceed 20/s; the excess queues or is rejected
  • At or above capacity: an unbounded queue has no finite steady-state waiting time

Ideal vs real throughput curve

  • Ideal: throughput rises linearly then flattens at capacity
  • Real interactive systems fall short of the ideal curve: co-ordination overhead keeps them below that ceiling
  • Congestion penalty → a badly behaved system's throughput actually falls as load keeps increasing

Closed population example

1000 players, each waits 3 seconds after a response.

  • 50 ms server time, 200 ms round-trip network time
  • Assumes enough parallel capacity, no queueing, one outstanding request per player
  • Rate = 1000 / (3 + 0.05 + 0.2) = 307.7/s
  • If response time already includes network time, do not add latency again

Four-tier worked example

Per-tier wait + service:

  1. Firewall: 5+45 = 50 ms
  2. Reverse proxy: 10+90 = 100 ms
  3. App server: 50+550 = 600 ms
  4. DB: 30+300 = 330 ms
  5. Sum 1080 ms + 200 ms network latency = 1280 ms
  6. Throughput (one server per tier) = min(10, 16, 6, 20) = 6 tps, set by the app server
Serial
Required stages on a request path: add visit times; the capacity bottleneck limits throughput.
Parallel
Concurrent branches or replicated workers; identify which before combining times or capacities.
Saturation
Point at which load reaches maximum throughput; extra load only queues.

Three tiers in series take 50, 100 and 600 ms per request and have capacities of 40, 12 and 25 requests/s. Which tier do you work on to cut response time, and which to raise throughput?
  • Response time → the 600 ms tier, which is the largest share of the 750 ms total

Four tiers have throughputs 10, 16, 6 and 20 tps in series. What is system throughput, and what happens if you double the DB?
System throughput is min = 6 tps (app server). Doubling the DB changes nothing because the app server remains the bottleneck.
A system can complete at most 20 requests/s and receives 22/s for an hour. What happens to throughput and response time?

Throughput stays at 20/s, its capacity.

  • Excess 2 requests/s → either queue or are rejected
  • Unbounded queue → about 7,200 requests waiting after an hour
  • Response time keeps climbing → no steady state

Add capacity or shed or throttle load; waiting it out does not help.

A page calls three services in parallel, taking 120, 300 and 80 ms, and needs all three results. A teammate estimates 500 ms for the page. Do you agree?

No: the page takes about 300 ms plus coordination overhead.

  • Branches that run concurrently contribute their maximum
  • Speed up the 300 ms service; improving the other two changes nothing

If the calls were sequential, the teammate's sum would be right.

Queueing theory notation and the operational laws

Queueing theory models jobs, servers and waiting; the operational laws (utilization, forced flow, bottleneck) hold on observed measurements regardless of distribution.

Queueing theory basics

  • Queueing theory = mathematical basis for response time, throughput and utilization
  • → and so for performance analysis and capacity planning
  • A population generates arrivals at rate λ → jobs wait → c servers each take service time S
  • Jobs in the system = jobs in queue + jobs in service

Notation

  • λ: arrival rate
  • S: mean service time
  • µ = 1/S: per-server service capacity
  • X: actual throughput
  • c: server count
  • ρ = λ/(cµ): mean utilization per identical server under stable, balanced load
  • L/L_q: count jobs in system/queue; W/W_q: their residence/wait times
  • P_n: probability of n jobs; K: the capacity limit

Operational laws vs queueing models

  • Operational laws are measurement identities: independent of arrival and service distributions
  • Keep units, observation interval and system boundary consistent; account for losses
  • Queueing-model predictions need extra assumptions: steady state, exponential service, Poisson arrivals

Utilization Law

  • U = X S for one service resource
  • Stable loss-free system: X = λ → U = λS = λ/µ
  • Example: 20 orders/hour x 1.5 minutes/order = 30 busy minutes/hour = 50%
  • Example: 125 packets/s x 0.002 s = 25%

Forced Flow Law

  • λ_i = λ_0 V_i
  • A component's load = system load x its visit ratio V_i
  • V_i = average visits to it per system request

Service demand and bottleneck

  • D_i = V_i S_i
  • Single resources: U_i = X_0 D_i → the highest demand saturates first (bottleneck)
  • Component with c_i equivalent parallel workers → compare D_i/c_i and effective capacity instead
  • Do not ignore different worker counts

Worked example: CPU and storage

Each instruction needs 5 s of CPU, 80 I/Os to storage A (50 ms each), 100 I/Os to storage B (30 ms each); storage A throughput observed as 15.70/s.

  1. λ_0 = λ_A / V_A = 15.70 / 80 = 0.196 job/s
  2. Service demands:
    • D_CPU = 5 s
    • D_A = 80 x 0.05 = 4 s
    • D_B = 100 x 0.03 = 3 s
  3. → the CPU is the bottleneck
  4. Utilizations:
    • U_CPU = 0.196 x 5 = 98%
    • U_A = 0.196 x 4 = 78.4%
    • U_B = 0.196 x 3 = 58.8%
λ (lambda)
Mean arrival rate of requests.
µ (mu)
Mean service capacity of one server, 1/S; actual throughput can be lower.
Visit ratio V_i
Average number of visits to component i per system request.
Service demand D_i
V_i x S_i: total service time component i spends per system request.

Check yourself

Each request uses 40 ms of application CPU and makes 3 database calls of 20 ms each. At 15 requests/s, which resource saturates first, and at what request rate?

The database saturates first, at about 16.7 requests/s.

  1. Service demand: CPU 40 ms; database 3 x 20 = 60 ms
  2. At 15 requests/s: database 15 x 0.06 = 90% busy; CPU 60%
  3. Saturation: database at 1 / 0.06 → about 16.7 requests/s

Cutting database visits per request (for example by batching or caching) raises that limit more than a faster CPU would.

A gateway forwards 125 packets/s, taking 2 ms each. What is its utilisation, and at what rate does it saturate?
U = 125 x 0.002 = 25%. It saturates at 1 / 0.002 = 500 packets/s. Response time will rise sharply well before that point because of queueing, so don't plan to run it near 100%.
A colleague says you cannot apply the Utilization Law because the arrivals are bursty, not Poisson. Do you agree?

No.

  • Operational laws are identities over measured quantities → U = XS holds for the observed interval, whatever the arrival distribution
  • What does need distribution assumptions is predicting queueing delay, as in M/M/1
  • Keep the units, interval and system boundary consistent

Little's Law and the General Response Time Law

Little's Law links jobs in the system to arrival rate and response time; the General Response Time Law sums component times weighted by visits.

Little’s Law

  • n = λR
  • For stable long-run averages with consistent boundaries
  • n counts requests both waiting and in service
  • R includes all time within that same boundary
  • Use the accepted arrival/completion rate; account for rejected work

Lecture burger estimate

  • 15 customers/hour = 0.25/min
  • 1.6 burgers/customer x 1.5 minutes/burger = 2.4 minutes of work
  • → n = 0.6 customers if queueing is ignored
  • With measured waiting, add it to residence time before using Little’s Law

Service time is not generally total time in the shop.

Little's Law backwards: component response times

From the CPU/storage example:

  1. λ_B = λ_0 V_B = 0.196 x 100 = 19.6/s
  2. λ_CPU = λ_0 V_CPU = 0.196 x 181 = 35.47/s (CPU visits = 80 + 100 + 1)
  3. Observed jobs n = 8.88, 3.19, 1.40 at CPU, A and B
  4. R = n / λ:
    • R_CPU = 8.88/35.47 = 0.250 s
    • R_A = 3.19/15.70 = 0.203 s
    • R_B = 1.40/19.6 = 0.071 s

General Response Time Law

  • R = sum over i=1..M of R_i V_i
  • Total response time = sum of each component's response time per visit x its visits
  • Example: 0.250 x 181 + 0.203 x 80 + 0.071 x 100 = about 68.6 s
  • Equivalently 13.47 jobs / 0.196 job/s via Little's Law
Little's Law
n = λR: jobs in system = arrival rate x response time.
General Response Time Law
R = sum of R_i V_i over all M components.

Check yourself

A server has a pool of 40 threads. Requests arrive at 100/s and spend 0.3 s each in the server. Is the pool big enough, and what if a slow dependency raises the time to 0.6 s?
  1. At 0.3 s: by Little's Law, n = 100 x 0.3 = 30 requests in the server → fits within 40 threads
  2. At 0.6 s: n = 60 → more than the pool
    • Requests queue for threads → response time climbs further
    • The failure can cascade upstream

Protects against this: a timeout on the dependency, or a larger pool.

Measured per-visit response times: CPU 0.25 s over 181 visits, storage A 0.203 s over 80 visits, storage B 0.071 s over 100 visits. Which contributes most to the 68.6 s job time, and what does that suggest?

By the General Response Time Law:

  1. CPU: 0.25 x 181 → about 45.3 s
  2. Storage A: 0.203 x 80 → about 16.2 s
  3. Storage B: 0.071 x 100 → about 7.1 s
  4. → the CPU dominates, mostly because of its visit count

Reduce the CPU's visits or its per-visit time before tuning storage.

A shop serves 15 customers an hour, and you observe an average of 3 customers inside. How long does a customer spend in the shop?
R = n / λ = 3 / 0.25 per minute = 12 minutes. That includes both waiting and service, because n counted everyone inside. Use the same boundary for n and R.

Queues and the M/M/1 response time curve

Even when average capacity exceeds average load, random or bursty arrivals create queues; M/M/1 gives response time as S/(1-U), which explodes as utilization nears 100%.

Queues appear even at 75% utilization

  • Burger shop: a customer every 2 min on average, service 1.5 min → U = 75%
  • Yet arrivals are random and bursty (e.g. 30 customers in the last 5 minutes after 55 idle minutes) → queues form

Averages hide bursts, which is why queueing models are needed.

Kendall notation A/B/C/K/N/D

  • Specifies arrival distribution, service distribution, servers, capacity, population and discipline
  • M = Markovian assumptions; D = deterministic; Ek = Erlang; G = general; PH = phase-type
  • Disciplines: FIFO, LIFO, round robin, processor sharing, priority
  • Distinguish:
    • one queue/server
    • separate queues
    • one shared queue feeding c servers

M/M/1 model

  • Assumes Poisson arrivals and independent exponential service times
  • One server, stable rate λ < µ
  • Mean response R = S/(1-U) = 1/(µ-λ)
  • Example: 20 orders/hour, capacity 30/hour → S = 2 minutes, U = 2/3, R = 6 minutes (including 4 minutes waiting)

Queueing rises non-linearly

At S = 1 second, M/M/1 predicts:

  • 50% utilization → R = 2 seconds
  • 70% → 3.33
  • 90% → 10

These are model outputs, not a universal safe-utilization threshold. Use the workload, measured curve and response target to choose headroom.

Reducing utilization reduces response time

U_i = λ_0 V_i S_i; with the same arrival rate:

  • Lower S_i → faster service
  • Lower V_i → fewer visits
  • Or reduce the arrival rate to the system → throttling, spreading load
M/M/1
One-server queue with Poisson arrivals and exponential service; steady-state formulas need λ < µ.
Kendall notation
A/B/C/K/N/D: arrival, service, servers, capacity, population, discipline.
Knee
Utilization/load at which response time starts to climb sharply.

Check yourself

Orders arrive at 20 an hour, and one server completes 30 an hour, giving a 6-minute average time in system. The target is under 3 minutes. Would a server that completes 45 an hour meet it?

Yes: 2.4 minutes.

  1. M/M/1: R = 1 / (µ - λ) = 1 / (45 - 20) hours = 2.4 minutes
  2. Utilisation falls from 67% to 44% → that is where the waiting time goes

This assumes random (Poisson) arrivals and exponential service, so validate with measured data.

Average utilization is 75%, so why is there still a queue?
Arrivals are random and bursty. A burst of jobs arrives faster than the server can handle even though the average load is below capacity, so waiting occurs; response time rises as 1/(1 - U).
To save money, a team plans to run its application servers at 90% CPU. Service time is 1 s, and the response target is 3 s. Under M/M/1, is the plan safe?

No.

  1. M/M/1: R = S / (1 - U) gives 10 s at 90%, far over target
  2. Meeting 3 s needs U of 2/3 or less: 1 / (1 - 0.67) = 3

Size the headroom from the response target and measured workload; there is no universally safe percentage.

Arrivals and service capacity are both 30 requests/hour. Can M/M/1 predict a finite mean response time?
No. U = 1, so the steady-state denominator µ - λ is zero. The model requires λ < µ; equality leaves no spare capacity to drain random bursts.

Multiple servers, queue layouts and price/performance

Compare faster single server, parallel queues and one shared queue; plus how to size servers for a target and measure price/performance.

Multi-server formulas

  • a = λS = offered load; ρ = a/c = utilization per identical server
  • Balanced separate M/M/1 queues → R = S/(1-ρ)
  • One shared M/M/c queue → lecture approximation R ≈ S/(1-ρ^c); the appendix gives exact Erlang C
  • Require ρ < 1
  • Offered load a can exceed 1; an individual server’s utilization cannot

Sizing example

2 customers/min, S = 1.5 min, target queueing time under 3 min.

  • Offered load a = 2 x 1.5 = 3 → ρ = 3/c; target R < S + 3 = 4.5 min
  • Parallel queues: S/(1-ρ) < 4.5 needs ρ < 2/3
    • c = 5 (ρ = 0.6, R = 3.75 min)
    • c = 4 gives R = 6 min, too slow
  • Single queue: need ρ^c < 2/3
    • c = 4 works (ρ = 0.75, ρ^4 = 0.32, R about 2.2 min)
    • c = 3 is saturated (ρ = 1)

The deck leaves these as exercises; these numbers apply its formulas.

Shared vs separate queues

  • For identical workers under the lecture’s queue assumptions
  • Shared queue avoids idle workers while another queue has waiting jobs → lower response than separate queues
  • Lecture’s equal-capacity comparison ranking:
    • one 3x faster worker best
    • shared queue next
    • separate queues worst
  • Not a guarantee for specialised jobs or real distributed systems

Additional workers

  • Additional workers move the saturation point
  • But response still rises sharply as per-server utilization approaches 100%
  • Size for the response target and required failure headroom, not just the minimum stable server count

Price/performance

  • Price/performance = cost / throughput (e.g. $/tps)
  • TPC benchmarks use price per transaction
  • Google's cluster design → chose cheap mid-range PC-like servers
    • selected on cost per query
    • = (capital expense with depreciation plus operating costs) divided by performance
    • expecting a server to last only 2-3 years

Keep the metrics distinct

  • Response = waiting + service
  • Capacity limits sustainable throughput
  • Arrival rate determines throughput below that limit

A quicker response does not necessarily increase throughput when demand is unchanged.

ρ (rho)
Per-server utilization ρ = λS/c for identical workers; steady-state queue formulas require ρ < 1.
c(M/M/1)
c servers, each with its own queue.
M/M/c
c servers sharing one queue.
Price/performance
Cost divided by throughput, e.g. $ per tps or cost per query.

Performance tactics and load balancing

The tactic families (control demand, manage resources) and design heuristics, then how load balancing improves throughput and speed and its state problem.

Architect for performance

  1. Apply tactics
  2. Validate by performance modelling
  3. Validate by prototyping

Performance tactics: two groups

  • Control resource demand:
    • manage arrival rate
    • prioritize input
  • Manage resources:
    • increase resources
    • increase resource efficiency
    • multiple copies of compute
    • multiple copies of data
    • reduce overhead
    • schedule resources

Heuristics to apply

  • Load balancing
  • Caching
  • Pre-computation
  • Reduce algorithmic complexity
  • Avoid or reduce bottlenecks (may trade off with cost)

Load balancing

  • Distributes requests across instances
  • Lowers queueing when it uses spare capacity effectively
  • Need not reduce a request’s own processing time
  • Splitting one job into independent parallel subtasks is a separate way to reduce service time

Distribution policies

  • Round robin
  • Random
  • Server load
  • Least response time
  • Traffic served
  • Number of active connections
  • Geographic location
  • Capabilities

Policy choice matters because uneven or blind distribution leaves some servers hot.

State breaks free distribution

  • Server holds client state (e.g. a session) → client must keep returning to that server (sticky)
  • Risks:
    • availability if it fails
    • uneven distribution
  • Otherwise state must be externalized
Load balancing
Distributing requests across multiple servers to improve throughput, speed and availability.
Sticky session
Routing a client always to the server that holds its session state.

Check yourself

Adding a second server behind a load balancer halved average response time, although each request's processing time did not change. Why?
  • Each server's utilisation roughly halved → requests spend far less time waiting in queues
  • Response time = waiting + service; the service time is unchanged

To cut service time, you would need faster processing or parallel work within the request itself.

A load balancer uses least-connections with sticky sessions. After a campaign, one server holds 60% of active users and is overloaded. Diagnose it and fix it.
  • Diagnosis: stickiness overrides the balancing policy → users stay pinned to the server that first held their session
  • Fix: move session state out of the servers into a shared store → any server can take any request

The cost is a network hop to the state store.

A partner's month-end batch job floods the system with requests, and interactive users time out. Which tactic family applies, and what would you do?

Control resource demand.

  • Manage the arrival rate → throttle the partner
  • Prioritise input → interactive requests go ahead of batch

The batch job takes longer as a result. Adding resources would also work, but costs more for a predictable monthly peak.

Servers of different sizes (8 and 32 cores) sit behind a round-robin load balancer, and the small ones are overloaded. What would you change?
  • Round robin ignores capability → the 8-core servers get the same share as the 32-core ones
  • Fix: use a capability-weighted or server-load policy, or least response time → work follows actual capacity

Caching and precomputation

Caches trade extra storage for faster access; their value depends on hit ratio, relative access times and cost, and precomputation applies the same idea to computed results.

Cache basics

  • Cache stores data for faster access
  • Types:
    • memory (often database results)
    • browser
    • web server
    • remote servers
  • Hit → finds the data in cache
  • Miss → goes to the source; costs cache lookup + source access

Expected access time

Weighted average over hits and misses. Cache 5 ms, data source 50 ms:

  • Hit = 5 ms; miss = 5 + 50 = 55 ms
  • 20% hits: 0.2 x 5 + 0.8 x 55 = 1 + 44 = 45 ms
  • vs 50 ms with no cache → worth it
  • Break-even for this hit ratio = cache access time of 10 ms (5 + 0.8 x 50 = 45; 10 + 0.8 x 50 = 50)
  • Above that → the cache hurts

Why access times differ

  • Fast storage is expensive, hence small
  • Location: local machine, local network, near or far remote
  • Operation: simple primary-key lookup vs complex query

Cache benefit has a cost

  • Consider storage and bandwidth vs response or throughput gain
  • Lecture’s measured totals, benefit/GB ranking:
    • B (30 ms/20 GB)
    • A (10/10)
    • C (10/30)
  • With only 15 GB: use partial-cache hit-rate measurements before assuming B retains that average benefit or allocating all space to it

Popularity affects hit ratio

  • Assumes equal-sized items kept in popularity order
  • Power-law distribution → favours caching a small hot set
  • Uniform access → roughly proportional benefit
  • Lecture’s “half the cache gives at least half the hits” relies on these assumptions, not every eviction policy or changing workload

Precomputation

  • Trades write/computation cost for cheaper reads

  3. → h must exceed 30%

Below that, the cache adds cost and latency.

A social app's feed reads outnumber posts 50 to 1, and one account has 20 million followers. Fan-out on write, fan-out on read, or a hybrid?

A hybrid.

  • Fan-out on write precomputes timelines → the dominant reads are cheap
  • 20-million-follower account: writing to every follower's timeline on each post is too costly → merge its posts in at read time

Trade-off: extra read-time work for followers of such accounts, as in the lecture's Twitter example.

With 15 GB of cache and data types A (10 GB, 10 ms), B (20 GB, 30 ms), C (30 GB, 10 ms), what do you cache?
  • Full-cache average benefit/GB ranks B, A, C
  • But B needs 20 GB for its measured 30 ms gain, and there is only 15 GB
  • → measure partial hit ratios and marginal benefits, then allocate the available space

The full-cache ratios alone do not prove the best split.

A product catalogue has 1 million items. In shop X, access is spread evenly across them; in shop Y, it follows a power law. A cache holds 1% of the items. Where does it help?

In shop Y.

  • Shop Y, power law: a small set of popular items gets most of the requests → 1% of items can yield a high hit ratio
  • Shop X, uniform access: a 1% cache gives roughly a 1% hit ratio → not worth it

Measure the access distribution before sizing a cache.

Algorithmic complexity, data placement and flow control

Reduce work growth with better algorithms, put computation where data movement is smallest, optimise storage, and control flow to protect shared resources.

Big O and algorithmic complexity

  • Big O describes growth, not exact seconds (ignoring constants)
  • O(1) → stays bounded
  • O(n) → grows tenfold for 10x input
  • O(n^2) → grows hundredfold
  • Compare algorithms at the expected data size; constants, memory and I/O still affect measured performance

Where code runs changes network cost

Job-candidate matching case: score every pair, return the top 1000.

  • Scoring in the app server → pulls all the data across the network
  • Pushing it into the database server → transfers only results
  • Weigh growth in scoring operations (time complexity) vs growth in network transfers

Optimize the data store

  • Reads and writes to storage are often the bottleneck
  • The right index helps greatly
  • The right storage technology matters too → e.g. a graph database for relationship-heavy data like social networks

Flow control protects capacity

  • Analogies in the deck:
    • spam calls
    • an over-eager student
    • a customer ordering 25 packets ahead of you
    • a burger shop with 5 staff and 20 sudden customers
  • Motivate limiting rates
  • Fair queueing
  • Separate lanes or roles

So one demanding user or burst cannot starve others.

Check yourself

A matching job takes 2 s for 10,000 candidates using an O(n^2) algorithm. Data will grow to 100,000. Would you buy 10x hardware or change the algorithm?

Change the algorithm.

  1. O(n^2) means 100 times the work → about 200 s
  2. Even with 10x hardware that scales perfectly → still takes about 20 s, and every further growth repeats the problem
  3. O(n log n) → grows only about 12.5 times for 10 times the data

Verify with measurements at the expected size, because constants and I/O also matter.

Scoring every candidate-job pair currently happens in the application server, which pulls all the rows over the network to return the top 1,000. When should the scoring move into the database server?

When the data volume is large and the result small, as here.

  • Running it in the database → transfers only 1,000 results instead of every row
  • Trade-off: load on the database server, which is usually harder to scale → check its spare capacity first
A 'friends of friends within 3 hops' query on a relational store takes 9 seconds. What would you investigate?
  1. The data store, which is often the bottleneck
  2. First the indexes on the relationship tables
  3. Then whether the storage technology fits → relationship-heavy traversals like this suit a graph database

Switching stores is costly → prove the gain with a prototype first.

One API customer sends 25 large requests at once, and everyone else's requests wait behind them. What would you add?

Flow control.

  • Per-client rate limits
  • Plus fair queueing or separate lanes
  • → one demanding client or burst cannot starve the others

That customer's batch then takes longer, which you can offer as a paid higher limit if it matters.

Validating the design and documenting performance

Use simulation, prototyping and benchmarking to verify performance early, and document performance-relevant parts of the architecture at the right level.

Validate by modelling and prototyping

  • Queue-modelling simulators (e.g. the open source JMT) → test how a design will behave
  • Prototyping and benchmarking → check the architecture meets targets before the whole system is built
  • Fail early, especially with unknown technology or experimental design

Prototyping steps

  1. Define goals
  2. Identify the extent of prototyping needed
  3. Build the prototype (possibly with instrumentation)
  4. Benchmark
  5. Repeat until performance risk is contained

Trade-off: level of confidence vs effort and cost.

Document performance with several views

  • Block diagram → components, e.g. service layer between front-end channels and back-end systems
  • Sequence diagram → calls in order, loops such as repeated back-end transform/send steps
  • Data flow diagram → messages, encoded vs decoded, audit logs

Document what matters: sweet spot of detail

  • What matters:
    • major components
    • large messages
    • calls carrying many records
    • high-frequency interactions
  • Not too high-level, not too low-level
  • Analyze related data together: one architecture may face heavy online transactions and timely complex reporting
  • Pick a viewpoint, draw and iterate; granularity varies by viewpoint

Appendix formulas

  • One outstanding request per client → average request rate = clients / (think time + end-to-end response time)
  • Add network latency separately only when excluded from response time
  • Exact M/M/c uses Erlang C for the probability an arrival must wait
  • The main lecture formula is an approximation

Exam-style questions

Answer aloud or on paper before opening.

A request passes a firewall (5 ms wait, 45 ms service, 10 tps capacity), a reverse proxy (10, 90, 16 tps), an app server (50, 550, 6 tps) and a database (30, 300, 20 tps), with 200 ms of network latency. (a) Find the response time and throughput. (b) You add a second app server. What is the new throughput, and what is the next bottleneck?
  1. (a) Response time and throughput
    • Response time = 50 + 100 + 600 + 330 = 1080 ms
    • Plus 200 ms latency → 1280 ms
    • Throughput = min(10, 16, 6, 20) = 6 tps, limited by the app server
  2. (b) Second app server
    • Two app servers give about 12 tps
    • Throughput = min(10, 16, 12, 20) = 10 tps → the firewall is now the bottleneck
    • Each request's service time is unchanged → response time improves only through less queueing at the app tier

To go beyond 10 tps, scale the firewall as well.

Each job needs 5 s of CPU, 80 I/Os on storage A (50 ms each) and 100 I/Os on storage B (30 ms each). Storage A is observed at 15.70 I/Os per second. Find the system throughput, the utilisations and the bottleneck. What would it take to double throughput?
  1. Forced Flow: λ_0 = 15.70 / 80 = 0.196 jobs/s
  2. Demands: CPU 5 s, A 4 s, B 3 s
  3. U = λ_0 x D: CPU 98%, A 78.4%, B 58.8%
  4. Bottleneck: the CPU; maximum throughput = 1 / 5 = 0.2 jobs/s
  5. To double to about 0.39 jobs/s: every demand must fall below about 2.56 s
    • Halving CPU demand alone leaves A as the limit at 1 / 4 = 0.25 jobs/s
    • So storage A, and storage B (3 s), also need faster devices, fewer visits or more parallel units

Bottlenecks move as you fix them.

A shop receives 20 requests an hour, and one server handles 30 an hour. Compute the utilisation and average time in system. Then, at 2 requests per minute with a 1.5-minute service time and a target of queueing under 3 minutes, a faster server is not possible: how many servers do you need with separate queues, and with one shared queue?
  1. Part 1: 20/hour arrivals, 30/hour capacity
    • U = 2/3
    • R = 6 minutes including service
  2. Part 2: λ = 2/min, S = 1.5 minutes
    • Offered load is 3 → ρ = 3/c
    • Waiting under 3 minutes → R < 4.5
    • Separate queues need c = 5
    • The lecture's approximate shared-queue model gives c = 4
    • Both need ρ < 1

A product-detail lookup takes 50 ms from the database. A cache would take 5 ms. Measured access is uniform across the catalogue, and a cache the size you can afford gives a 20% hit ratio. A teammate says to add the cache. Argue for or against, and say what would change your mind.

Against: the gain is weak.

  • Expected time = 0.2 x 5 + 0.8 x 55 = 45 ms against 50 ms → a 10% gain
  • Cost: the cache memory and an extra component
  • Stops paying at all if cache access reaches 10 ms or the hit ratio falls
  • Uniform access → a larger cache raises hits only in proportion to its size
  • What would change the decision
    • A power-law access pattern, where a small cache catches most requests
    • Precomputing the expensive part of the page
    • A source that is much slower than 50 ms

Measure before buying.

A web tier runs at 85% utilisation with 4 s average response time against a 2 s target, and 40% of requests fetch the same home-page data. Which tactics would you apply, in what order, and how would you verify them before building?
  1. First reduce demand: cache or precompute the home-page data → removes up to 40% of the work, lowering utilisation and queueing
  2. Then manage resources
    • Add servers behind a load balancer (shared queue) → per-server utilisation falls well below 85%
    • Fix any algorithmic or database bottleneck the measurements show
  3. If needed, throttle or deprioritise non-interactive load
  4. Verify before building
    • A queueing model or simulation (for example JMT)
    • An instrumented prototype benchmark under the real request mix
    • Repeat until the 2 s target holds with headroom
