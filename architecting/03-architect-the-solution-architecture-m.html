Architect the Solution Architecture (Method)

84 slides · about 40 min · open the deck · JSON

The method develops requirements, logical architecture and physical architecture through repeated outline, detail and review work. Each activity has ten tasks with named roles and work products. The IROne reservation example shows how requirements lead to components, deployment choices and documented decisions; revisit earlier assumptions when validation exposes a problem.

Big ideas

  • The method answers four questions: When (phases and iterations), Who (roles), What (work products) and How (activities made of tasks).
  • Three activities: Define Requirements, Logical Architecture and Physical Architecture. Logical and physical work each include outline, detail and review; iterate when new evidence changes the design.
  • Requirements work produces: stakeholder requests, glossary, system context, functional and non-functional requirements, prioritised requirements, and a reviewed Solution Architecture Document.
  • Architecturally significant requirements: critical functionality (80/20), critical quality, critical constraint, or technical/architectural risk.
  • Logical architecture is technology-neutral: architecture overview, functional model (boundary, control, entity components) and deployment model (locations, nodes).
  • Physical architecture realises the logical one with real technology (e.g. Java EE): logical elements map one-to-one, one-to-many or many-to-one onto physical elements, and nodes are sized to the non-functional requirements.
  • Every significant choice is recorded as an architecture decision (issue, decision, assumptions, alternatives, justification), and risk is reduced by verification, validation and a proof-of-concept.
  • The architect owns the Solution Architecture Document and must keep artefacts baselined and reviewed with stakeholders.

Fundamentals of the method

A method defines when, who, what and how; the architecture work sits inside a Unified Process style lifecycle and flows from requirements to logical to physical architecture.

  • A method is four things: When (phases and iterations), Who (roles: responsibilities of a person or team), What (work products: information produced or used) and How (activities, each a group of tasks; a task is a unit of work with a meaningful result).
  • The lifecycle is the Unified Process family (RUP from IBM, OpenUP, Agile UP, Enterprise UP): phases Inception, Elaboration, Construction, Transition, each with iterations. Requirements effort peaks early, architecture peaks in elaboration, development in construction, while test and project management run throughout.
  • Architecting is iterative, not a one-off. The flow is Define Requirements, then Outline Logical Architecture, then Detail Logical Architecture and Outline Physical Architecture, then Detail Physical Architecture. Outline work happens in the architecture discipline and detailing leans into development.
  • The reference method is Eeles and Cripps, The Process of Software Architecting, which focuses on how to architect (requirements, logical and physical architecture, role of the architect) rather than on software architecture concepts.
Work product
Information or entity produced and/or used by tasks (e.g. system context, functional model).
Activity
A grouping of tasks; here Define Requirements, Logical Architecture and Physical Architecture.
Unified Process
Popular iterative framework with Inception, Elaboration, Construction and Transition phases.

Check yourself

A team's process document lists tasks such as 'design the database' and 'write tests', but not who does them, what each produces or when they happen. What is missing, and why does it matter?
It has the 'how' (activities and tasks) but not the 'who' (roles), the 'what' (work products) or the 'when' (phases and iterations). Without roles nobody owns the outputs, and without work products nobody can tell when a task is done or what the next task takes as input. Adding them turns a to-do list into a method that can be planned and reviewed.
A project manager plans to start architecture work in Construction, 'once there is some code to look at'. Critique the plan.
In the Unified Process, architecture effort peaks in Elaboration, because the key structural decisions and risks must be settled before heavy construction. Starting late means building on unvalidated assumptions and paying for rework. Architecture does continue into Construction, as detailing and refinement, but it should not start there.
While detailing the physical architecture, the team learns that the payment provider accepts only batch files. Does the method require starting again from requirements?
No full restart: architecting is iterative. Record the new constraint in the requirements and revisit the affected logical elements (the payment boundary and its control flow). Then update the physical design and record the decision. Only the parts the constraint touches need to change.

Requirements I: stakeholders, vocabulary and system context

The first tasks of Define Requirements build the shared understanding: who cares, what the words mean, and what is inside and outside the system.

  • Define Requirements has 10 tasks: 1 Collect Stakeholder Requests, 2 Capture Common Vocabulary, 3 Define System Context, 4 Outline Functional Requirements, 5 Outline Non-Functional Requirements, 6 Prioritize Requirements, 7 Detail Functional Requirements, 8 Detail Non-Functional Requirements, 9 Update Solution Architecture Document, 10 Review Requirements with Stakeholders. Every task is described by roles, inputs, outputs and architect-specific tips.
  • Collect stakeholder requests: the architect makes sure the technical stakeholders are included (system administrator, owners of external systems) and that qualities and constraints are captured, not just features. The architect also helps prioritise by explaining the cost and time-to-market impact of one request over another. In IROne: system owner, customer, system administrator, show/park/hotel operators, reservation agent, enterprise architect.
  • Common vocabulary (glossary): define terms once and consistently, especially technical ones (IROne: Reservation, Amenity, Reservation Agent, Amenity Operator).
  • System context has three steps: identify actors (include external systems such as the payment gateway), identify actor locations (if an actor is found at several locations, introduce a new actor per location), and identify data flows between actors, including external systems, and the system. IROne locations: Show, Hotel, Park and Central Office; the central office holds owner, administrator, agents and the payment system.
Stakeholder request
A need, quality or constraint raised by anyone with an interest in the system.
Glossary
Agreed definitions of the domain and technical terms used in the project.
System context
The system as a black box with its actors, their locations and the data flows to and from it.

Check yourself

Stakeholder workshops for a hospital booking system included doctors, patients and the operations director only. What is missing, and what is likely to go wrong?
The technical stakeholders are missing: system administrators and the owners of external systems such as the patient-record and payment systems. Business stakeholders rarely state availability, operability and integration constraints, so those will surface late and force rework. The architect should make sure qualities and constraints are collected, not just features.
In a resort system, reservation agents work both at the central office and at each hotel's front desk, with different network access. How do you show them in the system context, and why?
Introduce a separate actor for each location, such as Central Office Reservation Agent and Hotel Reservation Agent. Each can then be placed, given its own data flows and reasoned about for connectivity and deployment. The cost is a slightly larger context diagram, in exchange for not hiding location-specific requirements.
Sales uses 'booking' to mean a confirmed, paid reservation, while operations uses it for any held slot. Why does the architect care?
Inconsistent terms lead to inconsistent requirements and data models: capacity counts, reports and integration messages would disagree about what a booking is. Capture a common vocabulary early and define each term once, because fixing it after the data model is built is far more expensive.

Requirements II: outlining functional and non-functional requirements

Outline what the system does for each actor and which qualities it must meet, stating clearly what is out of scope.

  • Functional requirements are outlined per actor from the system context, including technical users (operator, administrator), and the architect confirms what is not required. IROne: Search Slot, Reserve Slot, Administer Reservations, View Sales Report, each with its primary actors.
  • NFRs name qualities and constraints. IROne targets search availability of 99.9%, other availability of 99%, search response below 3 seconds, other responses below 5 seconds, 1000 concurrent users, accessibility, and web-service integration. These are outlines: detail the workload, measurement period and acceptance conditions before sizing or testing.
  • Outline first, detail later: these tasks capture breadth quickly; only architecturally significant items are detailed after prioritisation.
Functional requirement
A capability the system must provide to an actor (e.g. Reserve Slot).
Non-functional requirement
A quality or constraint such as availability, performance, scalability or integration.

Check yourself

An NFR reads: 'Search shall respond in under 3 seconds.' What would you add before using it for sizing or testing?
The conditions: the workload (concurrent users, request mix, think time), the measurement boundary (server only or end to end), whether 3 s is an average or a percentile such as 90% of requests, the test environment, and the measurement period. Without them, two teams can test the same system and both claim compliance with different results.
Is 'supports 1000 concurrent users' enough to size the servers?
No. Specify what users do, their request mix and think time, and the required response times. A concurrent-user count alone does not determine the request rate or the work each request needs.
The functional outline for a reservation system lists only customer use cases. Later, operations asks how to cancel a stuck reservation. What went wrong?
Functional requirements should be outlined per actor in the system context, including technical users such as administrators and operators. Missing 'Administer Reservations' means the function and its data access are added late, causing rework. The outline should also confirm explicitly what is out of scope.
Search must be 99.9% available, and every other function 99%. What does this split let the architect do?
Give search extra redundancy and isolate it from the less critical functions, instead of paying for 99.9% across the whole system. The cost is a more complex deployment with separately scaled parts, which is worth it only if search can actually run independently of the 99% components.

Requirements III: prioritise, detail, document and review

Pick the architecturally significant requirements, detail them as use cases and NFR scenarios, record them in the Solution Architecture Document, then review with stakeholders.

  • Architecturally significant requirements (ASRs) are those that: (1) relate to critical functionality without which there is no viable system (use the 80/20 rule), (2) relate to a critical quality such as performance, (3) relate to a critical constraint such as integration with a specific external system, or (4) carry a particular technical or architectural risk. The architect articulates the trade-offs during prioritisation.
  • Detail functional requirements as use cases focusing on the significant ones: description, primary and secondary actors, main flow, alternative flows (e.g. fail to validate, fail to reserve, fail to pay, each returning to a defined step), preconditions and postconditions. The architect also helps define data items and system-wide functions such as online help.
  • An NFR scenario has six parts: source, stimulus, artifact, environment, response and response measure. For availability, identify the fault and affected system, state normal or degraded conditions, describe detection and recovery, and specify the allowed interruption or degraded-service interval.
  • Solution Architecture Document (SAD) is owned by the architect and based on ISO/IEC/IEEE 42010 (formerly IEEE 1471). Structure: Introduction, Scope (stakeholders and their requests), Architectural Decisions, Architectural Mechanisms, Architectural Representation, Traceability (requirements linked to solution elements).
  • Review with stakeholders: baseline the artefacts and make sure technical questions are answered; changes flow through a change request and request log, and the outcome is a review record. Exercise 1 (Student Health System) practises detailed significant use cases, treating the system as a black box with no tiers or technology, including inputs, outputs and information reads and writes.
Architecturally significant requirement
A requirement that shapes the architecture: critical function, quality or constraint, or one that carries technical risk.
NFR scenario
Stimulus, source, artifact, environment, response and response measure describing a quality testably.
Traceability
The linkage from requirements to the solution elements that satisfy them.
Baseline
A reviewed, agreed version of an artefact that later changes must go through change control.

Check yourself

For a ticketing system, which of these are architecturally significant, and why: (a) the colour of the 'print receipt' button; (b) handling 30,000 buyers in the first 5 minutes of a sale; (c) integration with a national ID service's fixed API; (d) a streaming library nobody on the team has used?
(b) is a critical quality (performance and scalability), (c) is a critical constraint, and (d) carries technical risk, so all three are significant and shape the structure. (a) is a detail with no architectural impact. Significant requirements are worth detailing first because they are costly to change later.
Rewrite 'the system shall be available' as a six-part availability scenario for a payment-gateway outage.
Source: the external payment gateway. Stimulus: it stops responding. Artifact: the checkout service. Environment: normal operation at peak load. Response: detect the failure, hold orders and tell customers that payment is pending. Response measure: detection within 30 s, no confirmed order lost, and checkout degraded for no more than 10 minutes. Each part now gives the architect something to design and test against.
Late in the project, a stakeholder asks to drop the 'check hotel availability' requirement. How does the Solution Architecture Document help?
Its traceability section links the requirement to the components, interfaces and decisions that satisfy it, so you can see what would be removed or simplified and estimate the impact. Handle the change through a change request and the review process, and record the outcome. Without traceability, the impact is guesswork.

Logical architecture: the ten tasks and surveying assets

The logical architecture activity outlines then details functional and deployment elements; it starts by surveying reusable assets and recording decisions.

  • Logical architecture has two views, each outlined then detailed. Functional: subsystem, component, interface, operation, operation signature, mapping to data, pre/post-conditions. Deployment: location, node, deployment unit, connection. Outline gives the structure; detail adds signatures, contracts and assignments. Roles: Solution, Software, Data and Infrastructure Architect.
  • The ten tasks: 1 Survey Architecture Assets, 2 Define Architecture Overview, 3 Outline Functional Elements, 4 Outline Deployment Elements, 5 Verify Architecture, 6 Detail Functional Elements, 7 Detail Deployment Elements, 8 Validate Architecture, 9 Update Solution Architecture Document, 10 Review Architecture with Stakeholders. The same ten-task list repeats for the physical activity.
  • Survey assets before designing: look for reusable assets such as reference patterns and reference architectures. If a reference architecture or packaged solution is used, the architect may spend less effort on logical and more on physical.
  • Document architecture decisions and constraints as justification referenced in later phases. The template is: Issue, Decision, Assumptions, Alternatives, Justification. IROne example: develop a custom rules engine because only about 30 rules (at most 40) are expected; alternatives were buying a commercial engine (overkill, not cost effective) or embedding rules in code (violates separation of concerns and decoupling, harder to maintain).
Architecture decision
Recorded issue, decision, assumptions, alternatives and justification for a significant architectural choice.
Reference architecture
A reusable, proven template architecture for a class of systems.
Outline vs detail
Outline defines elements and structure; detail adds interfaces, signatures, contracts and assignments.

Check yourself

IROne built a custom rules engine on the assumption of about 30 to 40 rules. A year later, marketing wants 400 rules editable by business users. What does the decision record tell you to do?
The recorded assumption no longer holds, so the decision must be reviewed. The recorded alternatives, such as buying a commercial rules engine that was overkill at 30 rules, may now be justified. Reassess against the new needs rather than switching automatically; this is why decisions record assumptions and alternatives as well as the choice.
A client buys a packaged reservation product that covers 70% of the required functions. How does this change where architecture effort goes?
Less effort goes into logical structure, because the package supplies much of it. More goes into the physical architecture: fitting and configuring the package, and integrating the remaining 30%. The risk shifts too: the package's constraints now limit the design, so record them as decisions.
A decision log entry reads only 'Decision: use a message queue for hotel integration.' What is wrong with it?
It lacks the issue, assumptions, alternatives and justification. Later teams cannot tell why the queue was chosen, what was rejected, or what change (in volume or latency needs, for instance) should trigger a review. Record the full Issue, Decision, Assumptions, Alternatives, Justification template.

Logical architecture: overview and functional elements

Draw an overview of layers and zones from the system context, then identify boundary, control and entity components per use case.

  • The architecture overview starts from the system context and adds subsystems. It must show all actors and subsystems, cover the key logical structure (layers, locations and their relationships) and use consistent terms. A web-based IROne is layered: Presentation, Control (with Rules) and Data, with an Integration layer alongside, placed in zones (Internet, Internal Zone 1 with web, application, rules and integration tiers, Internal Zone 2 with hotel, show, park and payment systems). A thick-client variant has client-side storage.
  • Outline functional elements by classifying components in three types (robustness analysis). Boundary: interface to a primary actor, or to an external system to send or get data. Control: coordination logic, one controller per use case, split into sub-controllers only if too complex. Entity: encapsulates and manages the information.
  • Reserve Slot example: Reservation UI (boundary) talks to Reserve Slot Control (control), which uses Reservation Rules Checker, the hotel, show, park and payment system interfaces (boundary) and the Reservation Slot (entity). Reuse and review components identified for earlier use cases.
Boundary component
Handles interaction between the system and its environment (actor UI or external system interface).
Control component
Coordinates the logic of a use case; typically one controller per use case.
Entity component
Encapsulates and manages the information held by the system.

Check yourself

For a 'Cancel Booking' use case: the customer's web page, the logic that coordinates the cancellation and refund rules, the link to the payment gateway, and the Booking record. Classify each and say how many controllers you would start with.
The web page is a boundary (to the primary actor). The payment gateway link is a boundary (to an external system). The coordinating logic is a control component, and the Booking record is an entity. Start with one controller for the use case, and split it into sub-controllers only if it becomes too complex.
A design has one 'ReservationManager' component that renders screens, applies rules, calls the hotel system and stores the data. What is wrong, in robustness-analysis terms?
It mixes boundary, control and entity responsibilities, so a change to a screen, a rule or the hotel interface affects one large component. Split it into a reservation UI and hotel-system interface (boundaries), a reserve-slot control, and the reservation entity. The cost is more components and interfaces, and in return changes stay local.
The architecture overview leaves out the payment system that appears in the system context. How should this be caught?
Trace every actor, external system and data flow from the system context into the overview: the payment system needs a boundary or integration-layer element. Starting the overview from the context makes such omissions visible, but only if someone checks it item by item.

Logical architecture: deployment, verify, validate, review

Place logical components on logical nodes and locations, then verify and validate the architecture and review it with stakeholders.

  • Outline deployment elements: identify locations and nodes from the existing IT environment, architecture decisions, NFRs and system context. At this stage nodes are purely logical containers (Client PC in Internet; web, application, rules, integration and database servers in Central Office).
  • Detail functional elements: define component interfaces with operations and signatures, contracts (preconditions and postconditions) and the logical data model. Detail deployment elements: assign components (via subsystems) to nodes and define connections between nodes and locations.
  • Verify (task 5) vs validate (task 8): verification is a review of the outlined architecture, checking that cross-cutting concerns are handled consistently and capturing resulting decisions (plan, kickoff, individual review, verification meeting, rework follow-up). Validation is led by the architect and plans the session, creates an architectural proof-of-concept to reduce risk (from a conceptual sketch to a working prototype) and reviews the architecture, documenting findings, risks and recommendations.
  • Close out: update the Solution Architecture Document (architect is responsible) and review with stakeholders, ensuring products are baselined and technical questions answered.
Architecture proof-of-concept
A sketch or prototype that tests key architectural assumptions to reduce risk.
Cross-cutting concern
A concern such as security or logging that spans many components and must be handled consistently.
Pre/post-condition
Contract on an operation: what must hold before it is called and what it guarantees afterwards.

Check yourself

The team doubts whether the rules engine can evaluate 40 rules within the 3-second search target. Is a verification meeting enough?
No. Verification reviews the outlined architecture for consistency and cross-cutting concerns; it cannot measure performance. This is a risk that calls for validation: build an architectural proof of concept, measure it against the 3 s target with a realistic load, and document the findings and recommendations.
A logical deployment model labels the application node '2 x 16-core, 64 GB'. A reviewer objects. Why?
Hardware and sizing are physical decisions. At the logical stage, nodes only say which kinds of node exist, in which locations, and what runs on them. Fixing hardware before the technology is chosen and the NFRs are sized commits the design early and without evidence.
Two teams will build components that call each other, and so far they have agreed only on component names. What must the detailed functional model add before they code?
Interfaces with operations and signatures, contracts (preconditions and postconditions) and the logical data model they exchange. Without these, each team will assume different behaviour and the mismatch appears at integration.

Physical architecture: assets, overview and mapping to technology

The physical activity repeats the ten tasks but chooses concrete technology, mapping each logical element onto physical ones.

  • Survey assets and decide technology: record constraints as decisions. IROne: run in a Java EE server; decision use IBM WebSphere Application Server over Oracle WebLogic or Microsoft .NET Server, justified by existing skills in developing and deploying on WebSphere.
  • Logical-to-physical mapping has three patterns. One to one: a single physical element satisfies the full specification. One to many: one logical element realised by several physical elements, e.g. for availability. Many to one: several logical elements realised by one physical element, e.g. a packaged application.
  • IROne’s chosen Java EE mapping: person-facing boundaries become JSPs and servlets; system boundaries use JMS; controls become session EJBs; entities use JPA. Reserve Slot maps to a UI, servlet delegate, EJB facade and rules checker, JMS interfaces, and a JPA entity. This is one technology choice, not a universal mapping rule.
Session EJB
Java EE server-side component used to implement controller logic.
JMS
Java Message Service: messaging used to integrate with external systems.
JPA
Java Persistence API: maps entity components to a relational database.

Check yourself

Logical 'Reservation Control' must meet 99.9% availability. Logical 'Reporting', 'Billing' and 'CRM' are all covered by one packaged product. Which logical-to-physical mapping applies to each, and what does each cost?
Reservation Control maps one to many: several physical instances, so one failure does not stop the service. That needs load balancing and state handling. The packaged product is many to one: one physical element realises several logical ones, which ties them to that product's release cycle and limits.
A team maps every logical component, including the hotel-system interfaces, to synchronous REST controllers. The hotel systems are reachable only through message queues. Critique the mapping.
Each logical element must be mapped to technology that meets its specification and constraints. A system-facing boundary to queue-only hotel systems should map to messaging (IROne used JMS), while person-facing boundaries map to the web tier. Record the mapping choice per element as a decision, rather than applying one technology everywhere.
IROne chose an application server product because the team already had skills in it. A new CTO says to always choose the cheapest licence. How do you respond?
Existing skills reduce delivery and operating risk, which is part of the solution's viability, so the cheapest licence may not be the cheapest solution once training, mistakes and slower delivery are counted. The decision record holds this justification. If the team's skills change or licence cost becomes dominant, revisit the decision.

Physical architecture: deployment, sizing and integration

Define physical nodes sized to the NFRs, deploy components to them, specify integration endpoints, and summarise the deliverables.

  • Physical deployment elements: for each logical location define how many physical instances; for each logical node define the physical node(s); specify hardware and software for each; and size nodes to meet the non-functional requirements. IROne: web server (IBM pSeries, 2 x 2.0 GHz, 16 GB, AIX, Apache), application server (4 x 2.0 GHz, 32 GB, WebSphere, DB2, Java programs for rules), integration server (2 x 2.0 GHz, 16 GB, IBM MQ Series).
  • Detail deployment: show packages (WAR, JAR) deployed to nodes and manifesting the classes. The same logical design can be redeployed in a microservice style, e.g. a Reservation Service, Reservation Database and Integration Service on Amazon EC2 via ECS with Spring Boot in Docker images.
  • Integration endpoints record source, destination, protocol, format and transformation. The example uses HTTP/HTTPS with HTML/JSP on client–web and web–application links, and JMS with XML to show, hotel and park systems. Its transformation flags identify adapter work; two links having different formats alone does not explain the exact mapping needed.
  • Deliverables of the method: system context; functional and non-functional requirements; logical architecture overview, functional model and deployment model; physical architecture overview, functional model and deployment model. Exercise 2 applies the physical steps to the Student Health System.
Integration endpoint
A connection between two systems defined by source, destination, protocol, format and transformation.
Sizing
Choosing CPU, memory and instances for a node to meet NFRs.

Check yourself

Requirements: 1000 concurrent users and 99.9% search availability. A physical design has one web server and one application server, each sized for 1,200 users. Does it meet the NFRs?
Capacity may be enough, but availability is not met: each tier is a single point of failure. Use at least two nodes per tier, sized so that the survivors still handle 1000 users when one fails. Then confirm availability and capacity with the real workload.
The requirements specify web-service integration, but the physical example uses JMS. What should the architect do?
Treat it as a traceability issue. Confirm whether an approved decision changed the requirement or an adapter satisfies it; otherwise revise the physical design. The example's technology mapping alone is not evidence of compliance.
The integration endpoint table shows client to web over HTTPS/HTML, and application to hotel systems over messaging with XML, marked 'transformation: yes'. What work does that flag create?
An adapter that maps the application's structures to the hotel systems' formats and meanings, which must be specified and tested. The flag says mapping is needed; it does not define it. Use of XML or messaging alone does not prove a transformation is needed.
The same logical design must be redeployed as containerised microservices. What changes and what stays?
The logical functional model (components, interfaces, contracts) largely stays. The physical deployment changes: nodes become containers grouped into services, such as a reservation service with its own database and a separate integration service. Endpoints, sizing and the deployment mapping must be redone and validated against the NFRs.

Exam-style questions

Answer aloud or on paper before opening.

A clinic chain wants online booking within 6 months: 40 clinics, about 2,000 concurrent users at 8 am, and integration with a patient-record system that only accepts batch files overnight. (a) Pick three architecturally significant requirements and justify each. (b) Write one as a six-part scenario. (c) What decision would you record about the patient-record integration?
(a) The 8 am peak of 2,000 concurrent users is a critical quality, because it drives capacity and scaling. The overnight-only patient-record interface is a critical constraint. Booking itself is critical functionality, without which there is no viable system. (b) Source: 2,000 patients; stimulus: book an appointment; artifact: booking service; environment: the 8 am peak; response: the slot is confirmed; measure: 90% of confirmations within 3 s. (c) Issue: bookings must reach patient records, but only overnight batch is possible. Decision: store bookings in the booking system and export them nightly. Assumptions: clinics can tolerate next-day sync. Alternatives: real-time integration, which is not offered. Justification: it meets the constraint. Revisit if same-day record access becomes a requirement.
A requirements document says: 'The system must be fast, secure and user-friendly and support 1000 users.' It lists only customer use cases. As architect, critique it and say what you would do in Define Requirements.
None of the qualities are measurable, the user count gives no request mix or think time, and technical users and external systems are missing. Collect requests from technical stakeholders too (administrators, owners of external systems). Build a glossary and a system context with actors per location. Outline functional requirements per actor, including administration, and NFRs with targets and conditions. Prioritise the architecturally significant ones and detail them as use cases and six-part scenarios. Record them in the SAD with traceability, and review with stakeholders.
For a 'Transfer Ticket' use case (an owner transfers a ticket to a friend, the system checks transfer rules and notifies an external venue system), derive the boundary, control and entity components, then propose a physical mapping that supports high availability.
Boundaries: the transfer UI (owner) and the venue-system interface (external). Control: Transfer Ticket control, which coordinates the rules check, possibly using a rules component. Entities: Ticket and Transfer record. Physical mapping: the UI to the web tier; the control to a stateless application component deployed one to many across several instances; the venue interface to messaging, so venue outages don't block transfers; the entities to a persistent store with redundancy. Record each choice as a decision and check it against the availability target.
Logical model: web, application, rules and integration nodes at the central office. NFRs: 1000 concurrent users with 99.9% availability. A benchmark shows one application node handles 400 users at the response target. Size the physical application tier and explain your mapping.
Capacity alone needs 1000 / 400 = 2.5, so 3 nodes. To survive one node failure, the survivors must still carry 1000 users, so 4 nodes (3 survivors x 400 = 1,200). That is a one-to-many mapping of the logical application node, which requires stateless components or shared session state, and a load balancer. Confirm the 400-user figure with the production request mix, since benchmarks do not scale perfectly. Then specify the hardware, deployment units and endpoints.
A validation proof of concept shows the integration server handles 50 messages/s, but the peak need is 120 messages/s. How does this finding flow through the method, and what options would you weigh?
Validation documents the finding, its risk and recommendations, traced to the NFR it threatens. Options: deploy the integration node one to many (three instances give about 150 messages/s if it scales, which must be measured), batch or queue messages to smooth the peak if a short delay is acceptable, or reduce the work per message. Record the chosen option as a decision with its assumptions, update the SAD and review it with stakeholders. Repeat validation until the risk is acceptable.
