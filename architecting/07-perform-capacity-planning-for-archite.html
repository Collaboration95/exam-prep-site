Capacity Planning for Architecture

54 slides · about 27 min · open the deck · JSON

Capacity planning answers two questions: how much extra capacity will the system need, and when must it be in place. The deck gives one three-part recipe (predict the workload, relate workload to resource use, derive the resources needed) and applies it to disk, which is cumulative and trend driven, and to servers, which are peak driven and sized with benchmarks. It adds the forecasting formulas (linear regression, moving average, exponential smoothing), the scalability laws (Amdahl, USL), a worked benchmark-to-throughput example, procurement lead time and cloud elasticity. For the exam, expect to compute a forecast or a sizing figure and justify the method.

Big ideas

  • Capacity planning combines a workload forecast with a measured workload-to-resource relationship to predict how much capacity is needed and when.
  • Disk is cumulative-driven; servers are peak-driven. Disk is forecast with trend analysis; servers are sized from benchmarks, load tests and monitoring.
  • Linear regression: Y = a + bX. Moving average: M_t = (X_t + X_t-1 + ... + X_t-N+1) / N. Exponential smoothing: s_t = alpha x_(t-1) + (1 - alpha) s_(t-1), s_0 = x_0.
  • Scaling is non-linear: doubling machines does not double throughput. Amdahl's law: S(N) = 1 / ((1 - P) + P/N); USL adds a crosstalk term so throughput can fall as N grows.
  • The lecture’s simplified benchmark estimate divides reference throughput by scenario slowness, then weights those values by the mix to obtain 38.8 tps. Validate that estimate with representative mixed-load testing.
  • Real data beats guesses: use vendor benchmarks, self-benchmarking, or historical monitoring, and measure over enough time to catch patterns, seasonality and time zones.
  • Procurement lead time (7 weeks in the deck's template, plus downtime approval) must go in the project plan: too late means no capacity, too early means paying more because prices fall.
  • Elasticity: scale up aggressively, scale down conservatively, and avoid the ping-pong effect by keeping the thresholds apart.

Why and how to plan capacity

The goal, the three-part prediction model, where the data comes from and what to measure.

Goal of capacity planning

  • Make sure enough computing resources exist for the expected workload
  • ...to run at an acceptable service level
  • Needed for a new system and for an existing one facing:
    • user growth
    • cumulative growth from usage
    • new features

Capacity planning tasks

  • Predict the required resources from the expected workload
  • Decide how much extra capacity to buy and when it is needed (servers, storage)
  • Let the system scale automatically with workload (elasticity)

Core model

  1. Forecast workload
  2. Apply the workload-to-resource relationship
  3. Derive capacity

For storage this may be record count x bytes/record; for servers use measured workload and resource demand. The relationship is not literally addition of unlike units.

Sources of data

  • Published vendor benchmarks
  • Self-benchmarking
  • Historical monitoring of metrics

Monitoring is the best source when a system is already running.

What to collect

  • Web/app server:
    • requests/sec
    • active sessions
    • busy threads
  • System:
    • disk utilisation
    • I/O wait
    • RAM
    • CPU
    • used storage
  • Database:
    • queries/sec
    • open connections
    • cache hit rate
    • master/slave lag
  • Application-level metrics, e.g. Flickr's:
    • photos uploaded per day (daily and cumulative)
    • average photo size
    • registrations
    • API requests per key
Capacity planning
Ensuring enough resources for the expected workload at an acceptable service level.
Application metric

Planning disk capacity

Disk grows cumulatively, so work out data feeds and growth over the retention period and add fixed overhead.

Disk analysis is cumulative driven

  1. Measure by back-of-the-envelope estimate, monitoring or logging
  2. Then forecast data volume over the retention period

Size data feeds separately

  • Customer, transaction and other data each have their own count and average size
  • Add a baseline for OS and database software
  • Allow separately for logs, indexes and any replicated copies that grow with usage
  • State whether MB/TB are decimal units

Deck example 1: linear growth

  • Transactions grow from 1 million to 20 million at 1 MB per record
  • 20 million x 1 MB = 20 TB
  • + fixed overhead (and a buffer)

24-month growth example

  • Month k has 1M x 1.1^(k-1) transactions (starting with month 1 at 1M)
  • First 24 months total 1M x (1.1^24 - 1)/0.1 = 88.50M transactions
  • = 88.50 TB at 1 MB each using decimal units

This is a first-24-month accumulation, not a lifetime limit; revisit the rolling retention window as arrivals grow.

Deck example 3: only a history chart

  • You only know the past monthly transaction counts
  • → extrapolate with trend analysis from historical data (next section)
Fixed overhead
Baseline storage independent of workload; growing logs, indexes and replicas require separate allowances.
Data feed
One source of stored data (customers, transactions...) sized separately.

Trend analysis and forecasting methods

Classify the demand pattern, then forecast with regression, moving average or exponential smoothing, and answer 'when do we run out?'.

Historical demand: three patterns

  • Random
  • Trending (steady rise or fall)
  • Seasonal (repeating cycles)

Choose the method to match.

Linear regression

  • Y = a + bX (+ error term)
  • With n points:
  • b = [n(Sum xy) - (Sum x)(Sum y)] / [n(Sum x^2) - (Sum x)^2]
  • a = [(Sum y)(Sum x^2) - (Sum x)(Sum xy)] / [n(Sum x^2) - (Sum x)^2]
  • a = the intercept; b = the growth per period

Moving average and exponential smoothing

  • Moving average → uses the latest N periods to smooth variation
  • Simple exponential smoothing → weights the latest observation against the previous forecast
  • s_t = alpha x_(t-1) + (1-alpha)s_(t-1), with s_0 = x_0 (lecture’s notation)
  • Neither simple method alone models recurring seasonality or an ongoing trend → examine those patterns explicitly

Excel forecasting tools

  • FORECAST/TREND → fit linear growth
  • GROWTH → fits exponential growth
  • Lecture data: 20 daily consumption readings, from 202 to 280.7 GB, with 500 GB capacity
  • Fit a model and solve for when predicted use reaches 500 GB
  • Keep the day index and units explicit

Extrapolation is uncertain

  • Linear fit to those readings → roughly Y = 194.1 + 4.35X, reaching 500 GB near day 70 (when day 1 is the first observation)
  • Exponential fit → predicts an earlier crossing
  • Compare fits and recent behaviour
  • Allow forecast error and revise with new observations

Neither extrapolation reveals the actual future date.

Trending / seasonal / random
The three historical demand patterns.
Moving average
Mean of the last N periods.
Exponential smoothing
Forecast weighting recent data by alpha, older data by (1 - alpha).

Server sizing: benchmarks and mapping

Server capacity is peak driven and sized from benchmarks; the key skill is scaling a reference benchmark to your scenarios.

Server analysis is peak driven

  • Measure with benchmarks, load testing, monitoring and logging
  • Benchmark = runs standard tests to assess relative performance
  • Benchmark metrics:
    • requests/sec
    • latency (ms per connection or request)
    • throughput (bytes/sec)
  • ...under a varying load of clients and requests per client

Reference benchmark and slowness factor

  • Ideally run it on the same machine type for each significant scenario
  • Much easier on cloud than buying hardware
  • If not possible → estimate a slowness factor
  • Scenario twice as slow as the reference → roughly half the reference throughput

TPC-C

  • OLTP benchmark introduced in the lecture
  • Five concurrent transaction types over nine table types
  • Measured in tpmC
  • A published result = evidence for its tested workload and configuration
  • Not automatically the capacity of your application

Non-linearity

Deck's benchmark, max TPS:

  • 17.04 on 1 machine
  • 30.81 on 2
  • 55.76 on 4
  • Doubling machines → about 1.8x, not 2x
  • App server CPU stays at 95-98% at max TPS; DB server almost idle (under 1% to 2.25% CPU)
  • → the app tier is the bottleneck

Never assume capacity scales linearly with servers.

Benchmark
Running standard tests to assess relative performance of a server.
TPC-C
Industry OLTP benchmark, measured in transactions per minute (tpmC).
Slowness factor
How many times slower a scenario is than the reference benchmark.

A service averages 200 requests/s, peaks at 900 requests/s on Monday mornings, and its data grows by 5 GB a day. How do you size the servers and the disk?

No.

  • → 8 machines might give about 101 tps if the trend holds, and it may get worse
  • The application servers' CPU was already at 95-98% at maximum load

A reporting scenario is 4 times slower than the reference benchmark of 55.76 tps on 4 machines, and the business needs 30 report requests/s. Is 4 machines enough?

No.

  • Estimated throughput: 55.76 / 4 → about 13.9 tps, less than half the need
  • Adding machines will not scale linearly

Disagree.

  • A bigger database adds nothing until the application tier is scaled out or made cheaper per request

Non-linearity: Amdahl's law and USL

Two models explain why adding servers gives diminishing (or negative) returns and let you predict scaling from a few measurements.

Amdahl's law

  • S(N) = 1 / ((1 - P) + P/N)
  • S(N) = speedup with N processors
  • P = parallel proportion of the program (0 < P < 1)
  • N = number of processors
  • Also applies to machine scalability generally
  • Worked check: P = 0.9, N = 10 → S = 1 / (0.1 + 0.09) = 5.26

Interpreting Amdahl

  • 100% parallel → linear scalability
  • 100% serial → cannot scale
  • More parallelism → improves scalability
  • Serial sources:
    • accessing or updating the same data
    • quotas on resources
    • inefficient algorithms
  • Ceiling = 1 / (1 - P) however many servers you add

Two ways to use Amdahl

  • Measure P by load testing with increasing numbers of servers, then predict
  • Guesstimate P and refine it later

Load-test results are very sensitive to workload mix, so the test must mimic real usage.

Universal Scalability Law (USL)

  • X(N) = gamma N / (1 + sigma(N-1) + kappa N(N-1))
  • Gamma → scales one-node performance
  • Sigma → serialisation/contention
  • Kappa → crosstalk/coherency cost
  • With crosstalk, throughput may peak and decline
  • Fit coefficients to measurements; do not infer them from the technology name

Lecture case study: Java vs Node.js

  • Fitted Java results → lower serialisation but higher crosstalk than the Node.js implementation
  • Different peaks
  • Possible explanations: concurrency design or implementation quality

These measurements compare those systems; they do not establish a general language ranking.

Amdahl's law
Speedup limit set by the serial fraction of work: S(N) = 1/((1-P)+P/N).
Serialisation (sigma)
USL coefficient for contention; sets the throughput ceiling.
Crosstalk (kappa)
USL coefficient for coherency cost; makes throughput decline beyond a peak.

Check yourself

A workload is 90% parallel. Going from 10 to 20 servers, how much speedup do you gain, and what is the ceiling?
  1. Amdahl's law: S(10) = 1 / (0.1 + 0.09) → about 5.26
  2. S(20) = 1 / (0.1 + 0.045) → about 6.90
  3. → doubling the servers gives only about 31% more speedup
  4. Ceiling = 1 / (1 - 0.9) = 10, however many you add

Reducing the serial part pays more than adding servers.

Throughput rises up to 8 nodes, then falls at 12. Which model explains this, and what does it say about the cause?

USL, not Amdahl: Amdahl's speedup flattens but never falls.

  • Cause of the decline: the crosstalk (coherency) term, kappa → nodes spend more and more effort coordinating with each other
  • Fit sigma and kappa to the measurements → find the peak
  • Reduce cross-node coordination if you need to scale further
The parallel fraction P was measured with a load test that sent only login requests. Should you trust the resulting scaling prediction?

No.

  • P depends on the workload mix: logins may parallelise well, while checkouts update shared data serially
  • Unrepresentative test → the wrong P → the wrong server count

Repeat the test with a production-like mix.

Load tests show that a single shared stock-count row is updated on every order. How does that affect scaling, and what would you change?
  • Effect: every order serialises on that row → lowers the parallel fraction P → caps speedup at 1 / (1 - P)
  • Change: reduce the serial part, for example by partitioning the stock count or updating it asynchronously

Accept the trade-off in exactness or consistency of the count.

Sizing a system from a benchmark

Reproduce the lecture’s simplified weighted benchmark estimate, state its assumptions and validate the production mix with load testing.

Step 1: slowness factors

Each scenario gets a factor against the 4-machine reference of 55.76 tps; estimated throughput = 55.76 / slowness.

  • Login 1.0 = 55.76
  • Search 2.0 = 27.88
  • Item Details 1.5 = 37.17
  • Add to cart 1.5 = 37.17
  • Checkout 2.0 = 27.88
  • Payment 4.0 = 13.94

Lecture estimate: weight by workload mix

Multiply each scenario’s estimated throughput by its workload share:

  1. Login 30% → 16.73
  2. Search 20% → 5.576
  3. Details 15% → 5.576
  4. Add to cart 20% → 7.434
  5. Checkout 10% → 2.788
  6. Payment 5% → 0.697
  7. 16.73 + 5.576 + 5.576 + 7.434 + 2.788 + 0.697 ≈ 38.8 tps

This is the deck’s simplified sizing procedure, not a general law for combining mixed-workload capacities.

State and test assumptions

  • Four machines of the benchmark specification
  • The stated mix and slowness factors
  • A uniform slowness factor across application and database tiers
  • A production mix may stress resources differently

Benchmark it directly before treating 38.8 tps as deployable capacity.

No benchmark?

  • No production server → run simulated load tests:
    • JMeter (configured by UI)
    • Artillery.io (declarative)
    • both let you define scenarios and arrival rates and give response time and throughput
  • With a production server → analyse your monitoring data, which is the best source

Using existing data and measurement time

Existing monitoring gives the best data, but only if you measure across long enough windows to see patterns.

Time matters

Patterns, seasonality and time zones all shape load.

  • One-hour view → looks flat
  • Daily view → reveals the day cycle
  • Weekly view → reveals weekday peaks

Looking at the wrong window gives the wrong peak.

Time zones

  • Time zones shift the peak
  • e.g. US West and East usage curves are offset
  • → a global service sees blended peaks

  3. Take the weekly peaks and apply the same trend analysis as for storage

Procurement lead time and elasticity

Buying capacity takes time that must be planned; the cloud shortens it with auto-scaling governed by sensible policies.

Procurement steps to plan for

  1. Internal procurement procedure
  2. Hardware lead time
  3. Hardware installation
  4. Software installation
  5. Integration into production
  6. Testing
  7. Downtime needed and lead time to get downtime approved

All of this goes into the project plan; cloud and automation can cut much of it.

Deck template: extra application server

  1. Internal procurement: 3 working days
  2. PO to delivery: 4 weeks
  3. Hardware installation: 3-5 days
  4. Software installation: 0.5 day
  5. Production setup: 1 day
  6. Testing: 0.5 day
  7. Planning buffer: 1 week
  8. Total about 7 weeks

Estimated downtime or reduced SLA: 4 hours, with 1 week lead time for downtime approval.

Timing trade-off

  • Late procurement → risks insufficient capacity
  • Early procurement → ties up money and may miss later price reductions
  • Use the forecast, uncertainty, actual lead times and failure headroom to plan a safe date

Elasticity

  • Cloud providers auto-scale instances using a policy of:
    • scaling adjustment
    • adjustment type
    • cooldown period
  • Historical data → scheduled scaling is an alternative

Auto-scaling design guidelines

  • Be proactive (allow for application startup time)
  • Scale up aggressively, scale down conservatively
  • Set thresholds from scalability analysis
  • Avoid ping-pong: requests per second per node
    • after scaling up must stay above the scale-down threshold
    • after scaling down must stay below the scale-up threshold

Summary

  • Capacity planning rests on assumptions
  • → simplify
  • → add a buffer for errors
  • → be systematic, so it is easy to communicate and to revise
Cooldown period
Time after a scaling action before another is allowed.
Ping-pong effect
Repeated scale up then scale down caused by thresholds set too close.
Scheduled scaling
Scaling at planned times based on historical patterns.

Check yourself

New instances take 5 minutes to start, and traffic doubles within 3 minutes at 9 am every weekday. How should the scaling work?

Use scheduled scaling from the historical pattern.

  • Reactive scaling will always be late → demand doubles before new instances are ready
  • Add capacity shortly before 9 am
  • Scale up aggressively for unexpected surges
  • Scale down conservatively afterwards → briefly holding spare capacity costs little compared with failing users
Two nodes handle 120 requests/s. Scale-out triggers above 55/node and scale-in below 45/node. Why might adding one node cause ping-pong?
  1. Before scale-out: each handles 60/s
  2. After adding a third: each handles 40/s → below the 45/s scale-in threshold
  3. Removing one returns to 60/s

Set thresholds and adjustments so the new state does not immediately trigger the opposite action; use cooldown as well.

The forecast says capacity runs out in 6 weeks. The procurement template totals about 7 weeks, plus 1 week to get downtime approved. What do you do now, and what do you change for next time?

You are already late for the normal process.

  • Now
    • Look for interim capacity: temporary cloud capacity, expedited delivery, or reducing or throttling demand
    • Start procurement immediately, running the downtime approval in parallel
  • Next time: trigger procurement from the forecast with the full lead time plus a buffer

Buying very early has its own cost, tying up money and missing price drops, so plan the date rather than stockpiling.
