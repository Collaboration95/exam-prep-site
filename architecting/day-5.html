Day 5 mock questions

Do these after all of today's topics. Give your choice, reason and trade-off before opening an answer.

Whole day

The disk may fill in eight weeks, procurement takes seven, and moving to a new store also risks breaking clients. How would you combine capacity planning and maintainability?
Validate the forecast first: compare linear and exponential fits and include logs and indexes, because the earlier date may already be inside the lead time. Start procurement or interim capacity now, with a buffer. Protect clients by putting storage behind a stable interface, using compatibility checks and staging the migration with a rollback path. Use monitoring and fitness checks to confirm capacity and catch failures after the change.
Forecast peak demand is 80 requests/s, and each node sustainably handles 35 requests/s. How many nodes do you need to survive the loss of one node, and what would make that number wrong?
Four: three survivors give 105 requests/s, while two would give only 70. The number is wrong if the 35 requests/s came from a benchmark with a different request mix, if scaling is sub-linear (shared data or crosstalk, per Amdahl and USL), or if a shared dependency such as the database saturates first. Verify with a load test at the production mix, and test failover.
A SaaS product's pricing rules change monthly, and its tenant count doubles every year. A teammate proposes per-tenant code branches to handle client-specific rules. Respond, covering both maintainability and capacity.
Reject per-tenant branches: every fix must be repeated across branches, and the cost of change grows with every tenant. Use deferred binding instead, with per-tenant configuration or workflows loaded at run time behind defined variation points. For capacity, the doubling tenant count drives both cumulative storage and peak server load, so forecast both from tenant growth, using application metrics such as tenants and requests per tenant. Check the scaling with load tests, since a configuration lookup on every request adds work.

Capacity Planning for Architecture

A database disk has 280 GB used of 500 GB, and the last 20 days of readings fit a linear trend of about 4.35 GB a day. Procurement takes about 7 weeks, plus 1 week for downtime approval. When does the disk fill, and when must you act? What could make the forecast wrong?
(500 - 280) / 4.35 is about 51 days, roughly 7 weeks, so the disk fills at about the point a normal 7-week procurement would deliver. With a buffer, and possibly the extra week for downtime approval, you must act now. What could go wrong: growth may be exponential rather than linear, which brings the date forward; logs and indexes may grow faster than the data; and 20 days of history is short. Compare linear and exponential fits, keep revising with new readings, and plan from the earlier date.
Estimate storage for 1 million transactions a month growing 10% a month, retained for 2 years, at 1 MB per record, with indexes adding 30% and one replica. Then explain what happens to storage in year 3.
The first 24 months hold 1M x (1.1^24 - 1) / 0.1, about 88.5M records, or 88.5 TB. With 30% for indexes that is about 115 TB, and with the replica about 230 TB, plus the fixed OS and database baseline and a buffer. In year 3, the oldest months expire, but each new month (about 9.8M records by month 25) is far larger than the month it replaces (1M), so storage keeps growing. Forecast the moving 24-month window, not a one-off total.
The 4-machine reference benchmark gives 55.76 tps. Slowness factors are Login 1.0, Search 2.0, Details 1.5, Cart 1.5, Checkout 2.0 and Payment 4.0, and the mix is 30/20/15/20/10/5%. The forecast peak is 45 tps, and the business wants to survive one machine failure. Estimate the capacity and recommend a machine count.
Weighted estimate: 16.73 + 5.58 + 5.58 + 7.43 + 2.79 + 0.70, about 38.8 tps on 4 machines, short of 45 tps. Scaling has been sub-linear (about 1.8x per doubling), so 45 tps needs more than a proportional 4.6 machines; and to survive one failure, the survivors must still deliver 45 tps. If the 1.8x-per-doubling trend holds, 5 machines give about 47 tps, so plan for 6 (5 survivors after a failure), and confirm it by benchmarking with the production mix. The estimate assumes uniform slowness across tiers and the benchmark's configuration, so validate it with a mixed load test.
Load tests measure 1,000 req/s on 1 node, 1,800 on 2, 3,000 on 4 and 3,200 on 8. Explain the pattern, estimate what 16 nodes would give, and recommend what to do.
Returns diminish quickly: 4 to 8 nodes adds only 7%. That suggests a large serial part (shared data, quotas) and possibly crosstalk. Amdahl caps speedup at 1 / (1 - P), and USL allows throughput to fall past a peak, so 16 nodes may give little or even less than 3,200 req/s. Fit USL's sigma and kappa to these points to find the peak, and don't buy 16 nodes without testing. Better value comes from reducing the serial work, such as shared-row updates or cross-node coordination, and rerunning the tests with a production-like mix.
Design an auto-scaling policy for a web tier with a Monday 9 am peak of 900 requests/s, nodes that handle 100 requests/s at the response target, and a 3-minute start-up time. Include thresholds that avoid ping-pong.
Use scheduled scaling from the weekly trend to reach about 10 nodes before 9 am: 9 for the load, plus 1 for headroom. React to surprises by scaling up aggressively, since start-up takes 3 minutes, and scale down conservatively with a cooldown. Thresholds, for example: scale out above 80 requests/s per node, scale in below 50. Check them: 4 nodes at 80 is 320 requests/s, which spread over 5 nodes gives 64, above the scale-in threshold; 5 nodes at 50 is 250, which over 4 nodes gives 62.5, below the scale-out threshold. So neither action immediately triggers the other. Revisit the thresholds as the Monday trend grows.

Ensuring Maintainable Architecture

A product's discount and eligibility rules change every quarter, and three of its 20 enterprise clients need their own approval flow. The business wants changes shipped without redeployment. Recommend a design and its costs.
Defer binding for the kinds of change that recur: hold rule parameters in configuration, which business users edit through an admin screen, behind a single point of definition. Use a workflow engine to run per-tenant approval flows designed by the implementation team. Encapsulate the domain actions the workflows call, and define the supported variation points. This lowers the cost of each change but raises development cost, and needs UX and domain work. Behaviour outside the variation points still needs a code change, so choose the variation points from the expected changes.
An online learning platform has a layered monolith, five teams and frequent collisions between releases. It plans to add analytics, recommendations and partner integrations over two years. Compare a modular monolith, microservices and an event-driven approach for modifiability, and recommend one.
Modular monolith: business modules contain changes and avoid distributed costs, but everything still deploys as one unit, so release collisions remain. Microservices: independent deployment per capability if each owns its data and APIs evolve compatibly, but they add operational cost, and shared tables or call chains can still spread change. Event-driven: analytics and recommendations can subscribe to existing events (CourseCompleted, LessonViewed) without producer changes if the payloads carry what they need, with a schema registry and compatibility rules. Recommend modularising first, then extracting services where team collisions are worst, and publishing events for the new consumers.
A public REST API has about 200 external consumers you do not control. Over the next year you must add fields, rename one concept and change one response structure. Which code-level tactics keep the API evolvable?
Use request and response objects with optional fields, so additions don't break signatures. Add the renamed concept alongside the old one and deprecate the old name with a support period. Put the structural change in a new API version, keeping the old one running during migration. Encapsulate the implementation behind the API, define the shared data types once, and use standard formats. Test existing consumer contracts, because flexible JSON syntax alone does not guarantee compatibility.
During an incident, a payment fails somewhere across six microservices. It takes four hours to find the cause because logs are local to each container and have no common identifier. Redesign for analyzability.
Add automated error detection and alerting, so the failure is noticed rather than reported by users. Centralise logs with an agent, storage and searchable dashboard (for example EFK), so they survive container restarts. Propagate a correlation id from the entry point through every call and event, so one request's entries can be retrieved together. Log enough context, such as inputs, the dependency called and the error, and expose metrics through standard monitoring. The fix itself is then deployed like any other change, through the reliable-change pipeline.
A layered system's dependency rules are eroding, releases often break production, and rollbacks are manual. Design a pipeline that makes change reliable and stops further erosion.
Keep everything in version control, including environment configuration as code, with secrets in a secrets manager. Run automated unit, integration and end-to-end tests on each change. Add fitness functions before promotion: a dependency test that fails on layer violations, plus performance, security, resiliency and observability checks. Automate deployment with a tested rollback path and reversible migrations, and use hypothesis-driven testing for risky changes. Fitness functions guard only what they encode, so add rules as the architecture evolves.
