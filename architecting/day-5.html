Whole day

The disk may fill in eight weeks, procurement takes seven, and moving to a new store also risks breaking clients. How would you combine capacity planning and maintainability?
  • Validate the forecast first
    • Compare linear and exponential fits
    • Include logs and indexes
    • The earlier date may already be inside the lead time
  • Capacity: start procurement or interim capacity now, with a buffer
  • Maintainability: protect clients
    • Put storage behind a stable interface
    • Use compatibility checks
    • Stage the migration with a rollback path
  • After the change: monitoring and fitness checks to confirm capacity and catch failures
Forecast peak demand is 80 requests/s, and each node sustainably handles 35 requests/s. How many nodes do you need to survive the loss of one node, and what would make that number wrong?

Four nodes: three survivors give 105 requests/s, while two would give only 70.

  • What makes it wrong
    • The 35 requests/s came from a benchmark with a different request mix
    • Sub-linear scaling (shared data or crosstalk, per Amdahl and USL)
    • A shared dependency such as the database saturates first
  • Verify with a load test at the production mix, and test failover
A SaaS product's pricing rules change monthly, and its tenant count doubles every year. A teammate proposes per-tenant code branches to handle client-specific rules. Respond, covering both maintainability and capacity.

Reject per-tenant branches.

  • Maintainability: every fix must be repeated across branches → the cost of change grows with every tenant
  • Deferred binding instead: per-tenant configuration or workflows loaded at run time behind defined variation points
  • Capacity: the doubling tenant count drives both cumulative storage and peak server load
    • Forecast both from tenant growth, using application metrics such as tenants and requests per tenant
  • Load tests to check the scaling, since a configuration lookup on every request adds work

Capacity Planning for Architecture

A database disk has 280 GB used of 500 GB, and the last 20 days of readings fit a linear trend of about 4.35 GB a day. Procurement takes about 7 weeks, plus 1 week for downtime approval. When does the disk fill, and when must you act? What could make the forecast wrong?
  1. Time to fill: (500 - 280) / 4.35 → about 51 days, roughly 7 weeks
  2. → the disk fills at about the point a normal 7-week procurement would deliver
  3. With a buffer, and possibly the extra week for downtime approval → you must act now
  4. What could go wrong
    • Growth may be exponential rather than linear → brings the date forward
    • Logs and indexes may grow faster than the data
    • 20 days of history is short

Compare linear and exponential fits, keep revising with new readings, and plan from the earlier date.

Estimate storage for 1 million transactions a month growing 10% a month, retained for 2 years, at 1 MB per record, with indexes adding 30% and one replica. Then explain what happens to storage in year 3.
  1. First 24 months: 1M x (1.1^24 - 1) / 0.1 → about 88.5M records, or 88.5 TB
  2. With 30% for indexes → about 115 TB
  3. With the replica → about 230 TB
  4. Plus the fixed OS and database baseline and a buffer
  5. Year 3: storage keeps growing
    • The oldest months expire
    • But each new month (about 9.8M records by month 25) is far larger than the month it replaces (1M)

Forecast the moving 24-month window, not a one-off total.

The 4-machine reference benchmark gives 55.76 tps. Slowness factors are Login 1.0, Search 2.0, Details 1.5, Cart 1.5, Checkout 2.0 and Payment 4.0, and the mix is 30/20/15/20/10/5%. The forecast peak is 45 tps, and the business wants to survive one machine failure. Estimate the capacity and recommend a machine count.
  1. Weighted estimate: 16.73 + 5.58 + 5.58 + 7.43 + 2.79 + 0.70 → about 38.8 tps on 4 machines, short of 45 tps
  2. Sub-linear scaling (about 1.8x per doubling) → 45 tps needs more than a proportional 4.6 machines
  3. Survive one failure → the survivors must still deliver 45 tps
  4. If the 1.8x-per-doubling trend holds, 5 machines give about 47 tps
  5. → plan for 6 (5 survivors after a failure), and confirm it by benchmarking with the production mix

The estimate assumes uniform slowness across tiers and the benchmark's configuration, so validate it with a mixed load test.

Load tests measure 1,000 req/s on 1 node, 1,800 on 2, 3,000 on 4 and 3,200 on 8. Explain the pattern, estimate what 16 nodes would give, and recommend what to do.
  • Pattern: returns diminish quickly; 4 to 8 nodes adds only 7%
  • Suggests a large serial part (shared data, quotas) and possibly crosstalk
  • 16 nodes may give little or even less than 3,200 req/s
    • Amdahl caps speedup at 1 / (1 - P)
    • USL allows throughput to fall past a peak
  • Recommend
    • Fit USL's sigma and kappa to these points → find the peak
    • Don't buy 16 nodes without testing
    • Better value comes from reducing the serial work, such as shared-row updates or cross-node coordination
    • Rerun the tests with a production-like mix
Design an auto-scaling policy for a web tier with a Monday 9 am peak of 900 requests/s, nodes that handle 100 requests/s at the response target, and a 3-minute start-up time. Include thresholds that avoid ping-pong.
  1. Scheduled scaling from the weekly trend → about 10 nodes before 9 am: 9 for the load, plus 1 for headroom
  2. React to surprises: scale up aggressively, since start-up takes 3 minutes; scale down conservatively with a cooldown
  3. Thresholds, for example: scale out above 80 requests/s per node, scale in below 50
  4. Check them for ping-pong
    • 4 nodes at 80 = 320 requests/s, spread over 5 nodes, gives 64 → above the scale-in threshold
    • 5 nodes at 50 = 250, over 4 nodes, gives 62.5 → below the scale-out threshold
    • So neither action immediately triggers the other

Revisit the thresholds as the Monday trend grows.

Ensuring Maintainable Architecture

A product's discount and eligibility rules change every quarter, and three of its 20 enterprise clients need their own approval flow. The business wants changes shipped without redeployment. Recommend a design and its costs.

Defer binding for the kinds of change that recur.

  • Rule parameters in configuration, which business users edit through an admin screen, behind a single point of definition
  • A workflow engine runs per-tenant approval flows designed by the implementation team
  • Encapsulate the domain actions the workflows call, and define the supported variation points
  • Costs: this lowers the cost of each change but raises development cost, and needs UX and domain work

Behaviour outside the variation points still needs a code change, so choose the variation points from the expected changes.

An online learning platform has a layered monolith, five teams and frequent collisions between releases. It plans to add analytics, recommendations and partner integrations over two years. Compare a modular monolith, microservices and an event-driven approach for modifiability, and recommend one.

Recommend modularising first, then extracting services where team collisions are worst, and publishing events for the new consumers.

  • Modular monolith
    • Business modules contain changes and avoid distributed costs
    • But everything still deploys as one unit → release collisions remain
  • Microservices
    • Independent deployment per capability, if each owns its data and APIs evolve compatibly
    • But they add operational cost, and shared tables or call chains can still spread change
  • Event-driven
    • Analytics and recommendations can subscribe to existing events (CourseCompleted, LessonViewed) without producer changes
    • Only if the payloads carry what they need, with a schema registry and compatibility rules
A public REST API has about 200 external consumers you do not control. Over the next year you must add fields, rename one concept and change one response structure. Which code-level tactics keep the API evolvable?
  • Request and response objects with optional fields → additions don't break signatures
  • Renamed concept: add it alongside the old one, and deprecate the old name with a support period
  • Structural change: put it in a new API version, keeping the old one running during migration
  • Encapsulate the implementation behind the API, define the shared data types once, and use standard formats
  • Test existing consumer contracts

Flexible JSON syntax alone does not guarantee compatibility.

During an incident, a payment fails somewhere across six microservices. It takes four hours to find the cause because logs are local to each container and have no common identifier. Redesign for analyzability.
  • Automated error detection and alerting → the failure is noticed rather than reported by users
  • Centralise logs with an agent, storage and searchable dashboard (for example EFK) → they survive container restarts
  • Propagate a correlation id from the entry point through every call and event → one request's entries can be retrieved together
  • Log enough context, such as inputs, the dependency called and the error
  • Expose metrics through standard monitoring

The fix itself is then deployed like any other change, through the reliable-change pipeline.

A layered system's dependency rules are eroding, releases often break production, and rollbacks are manual. Design a pipeline that makes change reliable and stops further erosion.
  1. Keep everything in version control, including environment configuration as code, with secrets in a secrets manager
  2. Automated tests on each change: unit, integration and end-to-end
  3. Fitness functions before promotion
    • A dependency test that fails on layer violations
    • Plus performance, security, resiliency and observability checks
  4. Automate deployment with a tested rollback path and reversible migrations
  5. Hypothesis-driven testing for risky changes

Fitness functions guard only what they encode, so add rules as the architecture evolves.
