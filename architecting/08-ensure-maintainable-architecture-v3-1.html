Ensuring Maintainable Architecture

41 slides · about 22 min · open the deck · JSON

Maintainability is the ease with which software can be corrected, enhanced, adapted or have its performance improved, and it usually dominates lifecycle cost. The deck splits it into changeability (modifiability) and analyzability, then covers how architecture style, code-level tactics, defer-binding techniques, logging and monitoring, and automated safeguards such as fitness functions make change cheap and safe. For the exam, expect to pick tactics for a change scenario and compare how monolith, microservices and event-driven styles support change.

Big ideas

  • The lecture cites maintenance costs of 80–90% of lifecycle cost to motivate designing for change; treat this as a cited estimate rather than a universal percentage.
  • The lecture focuses on modifiability and analyzability, supported by reliable-change practices; the earlier ISO 25010:2011 model also names modularity, reusability and testability.
  • Four modifiability tactics: split modules, increase cohesion, reduce coupling, defer binding.
  • Cost of change vs cost of development trade off: code change (high/low), configuration (medium/medium), customizable by implementers (medium/high), customizable by end user (low/high).
  • Events let a new consumer use an existing event without changing its producer, provided the event has the needed information. Versioned schemas support evolution but still require compatibility discipline.
  • Code-level tactics: contain change, extensible interfaces, design techniques that ease change, variation points, standard extension points.
  • Analyzability needs automated error detection, good logging (agent, storage, dashboard, correlation id) and monitoring (JMX/SNMP).
  • Reliable change: version control, automated tests, CI, rollback, infrastructure as code, hypothesis-driven testing and fitness functions guarding architecture rules.

What maintainability is and why it matters

The IEEE definition, the lifecycle-cost argument and the practical benefits of maintainable software.

  • Definition (IEEE 610.12-90): the ease with which a system or component can be modified to correct faults, improve performance or other attributes, or adapt to a changed environment.
  • Lifecycle cost matters. The lecture cites an 80–90% maintenance share as motivation for reducing future change effort. The architectural decision is where likely changes justify investment, rather than assuming that percentage applies to every project.
  • What maintainable software lets you do quickly and easily: fix a bug without introducing a new one; add features without altering existing ones; improve usability and performance; make a fix that prevents future bugs; support new environments, operating systems or tools; and onboard new developers.
Maintainability
Ease of correcting faults, improving attributes or adapting to a changed environment.

Check yourself

Two designs for a loyalty system: A ships in 2 months with the reward rules hard-coded; B takes 3 months with the rules isolated behind an interface and held in configuration. Marketing expects to change the rules monthly for 5 years. Which do you choose?
B. With about 60 rule changes expected, the extra month is repaid by cheaper, safer changes, and most lifecycle cost falls in maintenance (the lecture cites 80-90%). A would need a code change, test and release for every rule tweak. If the system were a short-lived campaign, A would be the better choice.
A team says it will 'make the code maintainable later, once we have users'. Do you agree?
Only partly. Detailed refactoring can wait, but boundaries, interfaces and variation points are architectural and cost far more to add once code depends on their absence. Put them where change is likely now, and defer the rest. How much to invest depends on the expected changes and the system's lifetime.

Sources of change and how to incorporate it

Change is ubiquitous; the choice is who can make it and what it costs to build and to apply.

  • Change is inevitable and ubiquitous (Software Architecture in Practice). Sources: functional, platform, integration and growth. Likelihood of change is higher with deferred functionality, requirement gaps, vague requirements and open-ended requirements.
  • Four ways to incorporate change, trading build cost against change cost: Code change (developer; change cost high, development cost low; any change possible). Configuration change (developer/operations; medium, medium; cost depends on how modifiable the architecture is). Customizable by implementation team (medium change, high development cost; mostly B2B, each tenant has a dedicated implementation team). Customizable by end user (low change cost, high development cost; difficult, but best value when done right).
  • Rule: the more you invest up front in making change possible without code, the cheaper each later change, so invest where change is likely.
  • This topic focuses on modifiability and analyzability, then practices for reliable change. Reliable change is a supporting practice, not a replacement name for the ISO model’s maintainability sub-characteristics.
Modifiability
Ease of changing the system; also called changeability.
Variation likelihood
Deferred, gap, vague or open-ended requirements signal that change is coming.

Check yourself

For an insurance product, actuaries change pricing factors monthly, and the screen layout changes about once a year. Which way of incorporating change suits each?
Pricing factors: configuration, or end-user customisation by the actuaries, because the change is frequent and each code change would be expensive. Layout: a code change is fine, because it is rare and the development cost of making it customisable would not pay back. Invest in cheap change where change is likely.
A requirements document says 'the system shall support other payment methods in future' and 'reporting: to be decided in phase 2'. What does this tell the architect?
These are open-ended and deferred requirements, which signal a high likelihood of change. Put variation points there: a payment-method interface, and reporting fed from well-defined data. Spending the same effort on areas with stable requirements would be wasted.
A B2B SaaS product has five enterprise clients, each with a dedicated implementation team, and each wants its own approval rules. Which change mechanism fits?
Customisable by the implementation team: build configurable rules or workflows that each client's team sets up. Development cost is high, but each change is medium-cost and needs no core code change. Full end-user customisation would cost even more to build and isn't needed when trained implementers do the changes.

Architecture styles and modifiability

The four tactics, and how monolith, microservices and event-driven styles apply split, cohesion and coupling.

  • Modifiability tactics: 1 Split modules, 2 Increase cohesion, 3 Reduce coupling, 4 Defer binding. The first three are examined at architecture level and code level.
  • Monolith: a single deployable. Unstructured it is tangled classes behind one UI; a layered monolith (presentation, business rules, persistence, database) separates concerns by technical layer; a modular monolith groups classes into modules and components, all still deployed as one unit (a quantum). Changes stay inside a layer or module only if boundaries are respected.
  • Microservices put capability-specific logic and data behind service APIs, allowing independent deployment when contracts remain compatible. Splitting services does not automatically enforce low coupling: shared data, synchronous call chains or coordinated API changes can still make change spread.
  • Event-driven extension: add an analytics consumer of an existing event without changing producers if its payload already meets the need. Broker topology routes events among processors; mediator topology coordinates workflow steps. Events still couple consumers to payload meaning and delivery behaviour.
  • Schema registry: stores versioned payload schemas, and messages identify the schema used (the lecture illustrates an id and version). Consumers use that definition to read the payload. A registry makes schema evolution manageable; incompatible field or meaning changes still require coordination and compatibility checks.
Cohesion
How closely a module's responsibilities belong together; increase it.
Coupling
Dependence between modules; reduce it.
Schema registry
Store of versioned message schemas used by producers and consumers.
Mediator
Event-driven component that orchestrates a workflow across processes.

Check yourself

A team wants to add a fraud-analytics consumer to the existing OrderPlaced events, but the event does not carry the customer's IP address, which the model needs. Is this still a change-free extension?
No. A new consumer avoids producer changes only when the existing payload already meets its needs. Here the producer must add the field, ideally as an optional addition registered as a compatible new schema version, so existing consumers keep working. Events still couple consumers to the payload's content and meaning.
Five microservices read and write one shared customer table, and renaming a column needs a coordinated release of all five. What has gone wrong?
Shared data has coupled the services, defeating independent deployment. Give the customer data a single owning service and have the others use its API or events. If that split is not worth it, a modular monolith may contain changes just as well at lower operational cost.
A producer renames the field 'amount' to 'total' and registers the change as version 2 in the schema registry. Are consumers safe?
No. The registry stores versioned schemas and lets consumers find the one a message uses, but an incompatible change still breaks consumers that expect 'amount'. Add 'total' alongside 'amount', migrate the consumers, and only then remove the old field, following compatibility rules.
In a layered monolith, adding a 'gift card' feature touches the presentation, business and persistence layers. Would a modular monolith help?
Yes, for this kind of change. A modular monolith groups code by business module, so a gift-card module contains its own UI, logic and data access, and the change stays inside it. It still deploys as one unit, so you don't get independent deployment; that would need services.

Code-level maintainability tactics

Five design tactic groups contain changes and provide extension points; reliable-change practices are covered later.

  • Contain change. Encapsulation (keep change inside a component, e.g. a Discount Engine using the Strategy pattern); separation of concerns (clear distinct responsibilities); single point of definition (data types, algorithms, config, schemas defined once, so no need to synchronise changes).
  • Create extensible interfaces: object parameters can grow without a method-signature change; optional fields and flexible JSON/XML formats can support compatibility. Keep old fields and meanings usable, test existing consumers, and version incompatible changes with a clear support policy. A flexible format alone does not make a change safe.
  • Apply design techniques that facilitate change. Abstraction and layering (minimal impact of one part on others); generalisation (group similar scenarios into a general pattern handled by one component); inversion of control (components can be reconfigured).
  • Build variation points. Make elements replaceable; parameterise changeable properties in configuration; separate physical from logical processing (convert many physical formats into one logical structure); break processes into steps so change is confined to some steps.
  • Use standard extension points built into technologies: ODBC/JDBC for different databases, JSON/SOAP/REST for calling services, JCA as the standard Java adapter.
Encapsulation
Hiding details inside a component so callers are unaffected by change.
Single point of definition
Define each type, algorithm or config once.
Inversion of control
Components are wired or configured externally, allowing reconfiguration.
Variation point
Deliberate place where behaviour can be swapped or configured.

Check yourself

A public API method has 7 parameters, and clients keep breaking whenever a parameter is added. What would you change?
Pass a single request object, so new optional fields can be added without changing the method signature. Old clients must still be served correctly: keep existing fields and meanings, give new fields defaults, and test existing consumers. Version the API for changes that cannot be compatible.
A bank receives statements from 12 partners in CSV, XML and fixed-width formats, and parsing logic is spread across the system. What would you change?
Separate physical from logical processing: convert each physical format into one standard logical structure at the edge, and use only that structure in the rest of the system. A new partner format then changes only a converter. The cost is one more mapping layer to maintain.
A discount rate of 0.15 is hard-coded in 9 places, and the last change missed one. Which tactic would have prevented this?
Single point of definition: define the rate once, in configuration or a constant used everywhere, so a change never has to be synchronised across copies. Parameterising it in configuration also lets you change it without a code release.
A JSON API adds a mandatory field to every request. Is it backward compatible because the method signature is unchanged?
No. Existing callers omit the new field and may fail validation. Add it as optional with suitable behaviour for old callers, or version the breaking contract and migrate consumers.

Defer binding: customisation and workflow engines

Push decisions to run time so users or implementers change behaviour without recompiling.

  • Defer binding means making the application customisable at run time. Making it fully user-customisable needs good UX expertise and domain understanding. The deck's example is Amplitude analytics, whose customisable cohort analyser lets users analyse retention across cohorts without writing data-munging logic.
  • Workflow engine pattern: an admin or implementer designs a workflow for a specific tenant or role; the workflow logic is persisted. At run time the engine deserialises the tenant or role's workflow and executes it, calling domain logic. Result: logic customisation without recompiling, e.g. a different approval workflow per client.
  • Many engines provide a visual designer, which lowers the skill needed to change behaviour. This is the 'customizable by implementation team' end of the change-cost table.
Defer binding
Postpone choosing behaviour until run time, by configuration or user customisation.
Workflow engine
Component that executes persisted, designable workflows at run time.

Check yourself

Each of 30 corporate clients wants a different expense-approval chain, and the chains change a few times a year. How would you design it?
Defer binding with a workflow engine: an implementer designs each client's workflow, it is stored per tenant, and at run time the engine loads and executes it, calling shared domain logic. Changes need no recompiling or redeployment. The cost is building or adopting the engine and limiting workflows to the steps it supports.
For a 3-month MVP, a team proposes fully end-user-customisable reports. Do you agree?
Probably not. End-user customisation has the lowest change cost when done well, but the highest development cost, and it needs strong UX and domain understanding that an MVP rarely has. Ship a few fixed reports, learn which variations users actually want, and add customisation where that demand is clear.

Analyzability: detecting and diagnosing problems

How to detect problems, find the root cause and monitor systems, including logging in microservices.

  • Analyzability asks: how do we detect problems, identify the root cause, and make and deploy the fix (the last step is like any other change).
  • Tactics: automated error detection and reporting (e.g. UNIX core dump, log file monitoring); good logging practice with enough information to support an investigation; allow system monitoring through standard protocols such as JMX (Java) and SNMP (devices).
  • Logging in microservices has three components: a logging agent, log storage, and a log dashboard with search.
  • EFK stack on Kubernetes: Fluentd is the agent collecting logs from the nodes, Elasticsearch is the storage, Kibana is the dashboard.
  • Propagate a correlation id so entries from one request can be matched across services. Central storage alone does not show which records belong together. Missing identifiers make reconstruction harder and less reliable.
JMX / SNMP
Standard protocols for monitoring and managing applications (Java) and network devices.
EFK
Fluentd (agent), Elasticsearch (storage), Kibana (dashboard).
Correlation id
Identifier passed across services to trace one request in the logs.

Check yourself

A checkout error appears in the logs of four services, but nothing links the entries. What would you add?
A correlation id created at the entry point and passed with every call and event, and written in each service's log entries. Then the entries for one request can be pulled together for root-cause analysis. Central log storage alone does not show which records belong together.
Container logs disappear when pods restart, and engineers SSH into nodes to grep for errors. What would you change?
Add the three logging components: an agent on each node that ships logs, central log storage, and a dashboard with search (EFK is the lecture's example stack). Logs then survive restarts and can be searched across services. The cost is running and sizing the logging infrastructure itself.
A legacy application crashes every night and leaves nothing useful behind. Which analyzability tactics apply?
Automated error detection and reporting (core dumps, log file monitoring that raises alerts), logging with enough context to investigate, and monitoring through standard protocols such as JMX or SNMP. Together these turn 'it crashed' into a diagnosable fault.

Reliable change and fitness functions

Practices that make changes safe, and fitness functions that automatically guard architectural rules.

  • Reliable change needs a reproducible process: track changes in version control, automate tests and build/integration checks, support deployment rollback, manage environment configuration as code, and apply hypothesis-driven testing. Integrate secrets management without committing secret values. Automating release/deployment extends the delivery process beyond CI alone.
  • Fitness function: an automated check that an architectural characteristic still holds. In the deck's pipeline, after unit test, build and deploy, integration and end-to-end tests, a set of checks (code quality, resiliency, observability and performance testing, compliance standards, security code analysis, operability standards) must pass before promote.
  • Example: a unit test using a dependency-analysis tool (JDepend) asserts that persistence and web packages depend on util as allowed, so the build fails if any code breaks layer dependencies in a layered architecture.
Fitness function
Automated test of an architectural characteristic, run in the delivery pipeline.
Infrastructure as code
Versioned definitions of infrastructure and environment configuration, integrated with separate secrets management.

Check yourself

The architecture rule says the web layer must not call the persistence layer directly. Code reviews keep missing violations. What would you add?
A fitness function: an automated test using a dependency-analysis tool that fails the build when web code depends on persistence packages. It checks the rule on every build, which review cannot do reliably. It guards only the rules you actually encode, so add checks for other key characteristics as well.
A release breaks checkout, and reverting takes 3 hours because the database migrations cannot be undone. What should the release process have included?
Rollback designed in: reversible or backward-compatible migrations, and the ability to redeploy the previous version quickly. Even tested changes fail in production, and fast reversal limits the damage. Version control, automated tests and environment configuration as code make that reversal reliable.
A release works in staging but fails in production, because the two environments were configured by hand and differ. A developer suggests committing the production passwords into the repository so everything is in one place. Respond.
Manage environment configuration as code, so staging and production are built from the same versioned definitions. Do not commit secret values: integrate a secrets-management tool, and reference secrets from the configuration. Reproducible environments without leaked credentials make change reliable.

Code quality tools

Static analysis tools help track relative quality, but only if you understand the metrics.

  • The lecture’s static-analysis examples include FindBugs, Checkstyle, PMD and SonarQube for code issues and metrics, plus CodeCity for visualising code structure. Learn what a result reveals rather than memorising product names as proof of quality.
  • Use with care: understand what each metric means. They are useful for the relative quality progression of one code base over time, not for absolute comparison between systems.
  • Connect the models: this topic stresses analyzability, changeability, stability and testability. For an ISO 25010:2011 classification question, use modularity, reusability, analyzability, modifiability and testability from the foundations lecture.
SonarQube
Platform that analyses code quality and reports issues and metrics.

Check yourself

A quality dashboard improves after a release. Does that prove the architecture is easier to maintain?
No. Check what changed in the metrics and whether they reflect relevant change or diagnostic effort. Combine trends with actual change scenarios and fitness checks; a score is evidence for its measured properties, not all maintainability.
A manager wants to rank three teams' systems by their static-analysis scores to decide bonuses. Do you agree?
No. These metrics are useful for tracking one code base's relative progress over time, not for comparing different systems in absolute terms, since size, language and domain differ. Using them for bonuses also invites gaming. Compare each team against its own trend, alongside real change effort.

Exam-style questions

Answer aloud or on paper before opening.

A product's discount and eligibility rules change every quarter, and three of its 20 enterprise clients need their own approval flow. The business wants changes shipped without redeployment. Recommend a design and its costs.
Defer binding for the kinds of change that recur: hold rule parameters in configuration, which business users edit through an admin screen, behind a single point of definition. Use a workflow engine to run per-tenant approval flows designed by the implementation team. Encapsulate the domain actions the workflows call, and define the supported variation points. This lowers the cost of each change but raises development cost, and needs UX and domain work. Behaviour outside the variation points still needs a code change, so choose the variation points from the expected changes.
An online learning platform has a layered monolith, five teams and frequent collisions between releases. It plans to add analytics, recommendations and partner integrations over two years. Compare a modular monolith, microservices and an event-driven approach for modifiability, and recommend one.
Modular monolith: business modules contain changes and avoid distributed costs, but everything still deploys as one unit, so release collisions remain. Microservices: independent deployment per capability if each owns its data and APIs evolve compatibly, but they add operational cost, and shared tables or call chains can still spread change. Event-driven: analytics and recommendations can subscribe to existing events (CourseCompleted, LessonViewed) without producer changes if the payloads carry what they need, with a schema registry and compatibility rules. Recommend modularising first, then extracting services where team collisions are worst, and publishing events for the new consumers.
A public REST API has about 200 external consumers you do not control. Over the next year you must add fields, rename one concept and change one response structure. Which code-level tactics keep the API evolvable?
Use request and response objects with optional fields, so additions don't break signatures. Add the renamed concept alongside the old one and deprecate the old name with a support period. Put the structural change in a new API version, keeping the old one running during migration. Encapsulate the implementation behind the API, define the shared data types once, and use standard formats. Test existing consumer contracts, because flexible JSON syntax alone does not guarantee compatibility.
During an incident, a payment fails somewhere across six microservices. It takes four hours to find the cause because logs are local to each container and have no common identifier. Redesign for analyzability.
Add automated error detection and alerting, so the failure is noticed rather than reported by users. Centralise logs with an agent, storage and searchable dashboard (for example EFK), so they survive container restarts. Propagate a correlation id from the entry point through every call and event, so one request's entries can be retrieved together. Log enough context, such as inputs, the dependency called and the error, and expose metrics through standard monitoring. The fix itself is then deployed like any other change, through the reliable-change pipeline.
A layered system's dependency rules are eroding, releases often break production, and rollbacks are manual. Design a pipeline that makes change reliable and stops further erosion.
Keep everything in version control, including environment configuration as code, with secrets in a secrets manager. Run automated unit, integration and end-to-end tests on each change. Add fitness functions before promotion: a dependency test that fails on layer violations, plus performance, security, resiliency and observability checks. Automate deployment with a tested rollback path and reversible migrations, and use hypothesis-driven testing for risky changes. Fitness functions guard only what they encode, so add rules as the architecture evolves.
