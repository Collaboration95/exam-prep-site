Ensuring Maintainable Architecture

41 slides · about 22 min · open the deck · JSON

Maintainability is the ease with which software can be corrected, enhanced, adapted or have its performance improved, and it usually dominates lifecycle cost. The deck splits it into changeability (modifiability) and analyzability, then covers how architecture style, code-level tactics, defer-binding techniques, logging and monitoring, and automated safeguards such as fitness functions make change cheap and safe. For the exam, expect to pick tactics for a change scenario and compare how monolith, microservices and event-driven styles support change.

Big ideas

  • The lecture cites maintenance costs of 80–90% of lifecycle cost to motivate designing for change; treat this as a cited estimate rather than a universal percentage.
  • The lecture focuses on modifiability and analyzability, supported by reliable-change practices; the earlier ISO 25010:2011 model also names modularity, reusability and testability.
  • Four modifiability tactics: split modules, increase cohesion, reduce coupling, defer binding.
  • Cost of change vs cost of development trade off: code change (high/low), configuration (medium/medium), customizable by implementers (medium/high), customizable by end user (low/high).
  • Events let a new consumer use an existing event without changing its producer, provided the event has the needed information. Versioned schemas support evolution but still require compatibility discipline.
  • Code-level tactics: contain change, extensible interfaces, design techniques that ease change, variation points, standard extension points.
  • Analyzability needs automated error detection, good logging (agent, storage, dashboard, correlation id) and monitoring (JMX/SNMP).
  • Reliable change: version control, automated tests, CI, rollback, infrastructure as code, hypothesis-driven testing and fitness functions guarding architecture rules.

What maintainability is and why it matters

The IEEE definition, the lifecycle-cost argument and the practical benefits of maintainable software.

Definition (IEEE 610.12-90)

The ease with which a system or component can be modified to:

  • Correct faults
  • Improve performance or other attributes
  • Adapt to a changed environment

Lifecycle cost matters

  • Lecture cites an 80–90% maintenance share
  • → motivation for reducing future change effort
  • Architectural decision: where likely changes justify investment

Don't assume that percentage applies to every project.

What maintainable software lets you do

...quickly and easily:

  • Fix a bug without introducing a new one
  • Add features without altering existing ones
  • Improve usability and performance
  • Make a fix that prevents future bugs
  • Support new environments, operating systems or tools
  • Onboard new developers
Maintainability
Ease of correcting faults, improving attributes or adapting to a changed environment.

Check yourself

Two designs for a loyalty system: A ships in 2 months with the reward rules hard-coded; B takes 3 months with the rules isolated behind an interface and held in configuration. Marketing expects to change the rules monthly for 5 years. Which do you choose?

Choose B.

  • About 60 rule changes expected → the extra month is repaid by cheaper, safer changes
  • Most lifecycle cost falls in maintenance (the lecture cites 80-90%)
  • A would need a code change, test and release for every rule tweak

If the system were a short-lived campaign, A would be the better choice.

A team says it will 'make the code maintainable later, once we have users'. Do you agree?

Only partly.

  • Detailed refactoring can wait
  • Boundaries, interfaces and variation points are architectural → cost far more to add once code depends on their absence
  • Put them where change is likely now, and defer the rest

How much to invest depends on the expected changes and the system's lifetime.

Sources of change and how to incorporate it

Change is ubiquitous; the choice is who can make it and what it costs to build and to apply.

Change is inevitable and ubiquitous

(Software Architecture in Practice)

  • Sources of change:
    • functional
    • platform
    • integration
    • growth
  • Likelihood of change is higher with:
    • deferred functionality
    • requirement gaps
    • vague requirements
    • open-ended requirements

Four ways to incorporate change

Trading build cost against change cost:

  1. Code change
    • by developer
    • change cost high, development cost low
    • any change possible
  2. Configuration change
    • by developer/operations
    • change cost medium, development cost medium
    • cost depends on how modifiable the architecture is
  3. Customizable by implementation team
    • change cost medium, development cost high
    • mostly B2B: each tenant has a dedicated implementation team
  4. Customizable by end user
    • change cost low, development cost high
    • difficult, but best value when done right

Rule: invest where change is likely

  • The more you invest up front in making change possible without code
  • → the cheaper each later change
  • → so invest where change is likely

Focus of this topic

  • Modifiability and analyzability
  • Then practices for reliable change
  • Reliable change is a supporting practice, not a replacement name for the ISO model’s maintainability sub-characteristics
Modifiability
Ease of changing the system; also called changeability.
Variation likelihood
Deferred, gap, vague or open-ended requirements signal that change is coming.

Check yourself

For an insurance product, actuaries change pricing factors monthly, and the screen layout changes about once a year. Which way of incorporating change suits each?
  • Pricing factors → configuration, or end-user customisation by the actuaries: the change is frequent and each code change would be expensive
  • Layout → a code change is fine: it is rare, and the development cost of making it customisable would not pay back

Invest in cheap change where change is likely.

A requirements document says 'the system shall support other payment methods in future' and 'reporting: to be decided in phase 2'. What does this tell the architect?

Open-ended and deferred requirements signal a high likelihood of change → put variation points there:

  • A payment-method interface
  • Reporting fed from well-defined data

Spending the same effort on areas with stable requirements would be wasted.

A B2B SaaS product has five enterprise clients, each with a dedicated implementation team, and each wants its own approval rules. Which change mechanism fits?

Customisable by the implementation team.

  • Build configurable rules or workflows that each client's team sets up
  • Development cost is high, but each change is medium-cost and needs no core code change
  • Full end-user customisation would cost even more to build → isn't needed when trained implementers do the changes

Architecture styles and modifiability

The four tactics, and how monolith, microservices and event-driven styles apply split, cohesion and coupling.

Modifiability tactics

  1. Split modules
  2. Increase cohesion
  3. Reduce coupling
  4. Defer binding

The first three are examined at architecture level and code level.

Monolith

A single deployable.

  • Unstructured → tangled classes behind one UI
  • Layered monolith → presentation, business rules, persistence, database: separates concerns by technical layer
  • Modular monolith → groups classes into modules and components, all still deployed as one unit (a quantum)

Changes stay inside a layer or module only if boundaries are respected.

Microservices

  • Put capability-specific logic and data behind service APIs
  • Allow independent deployment when contracts remain compatible
  • Splitting services does not automatically enforce low coupling
  • Change can still spread via:
    • shared data
    • synchronous call chains
    • coordinated API changes

Event-driven extension

  • Add an analytics consumer of an existing event without changing producers, if its payload already meets the need
  • Broker topology → routes events among processors
  • Mediator topology → coordinates workflow steps
  • Events still couple consumers to payload meaning and delivery behaviour

Schema registry

  • Stores versioned payload schemas
  • Messages identify the schema used (lecture illustrates an id and version)
  • Consumers use that definition to read the payload
  • Makes schema evolution manageable
  • Incompatible field or meaning changes still require coordination and compatibility checks
Cohesion
How closely a module's responsibilities belong together; increase it.
Coupling
Dependence between modules; reduce it.
Schema registry
Store of versioned message schemas used by producers and consumers.
Mediator
Event-driven component that orchestrates a workflow across processes.

Check yourself

A team wants to add a fraud-analytics consumer to the existing OrderPlaced events, but the event does not carry the customer's IP address, which the model needs. Is this still a change-free extension?

No.

  • A new consumer avoids producer changes only when the existing payload already meets its needs
  • Here the producer must add the field, ideally as an optional addition registered as a compatible new schema version → existing consumers keep working

Events still couple consumers to the payload's content and meaning.

Five microservices read and write one shared customer table, and renaming a column needs a coordinated release of all five. What has gone wrong?

Shared data has coupled the services, defeating independent deployment.

  • Fix: give the customer data a single owning service, and have the others use its API or events
  • Alternative: if that split is not worth it, a modular monolith may contain changes just as well at lower operational cost
A producer renames the field 'amount' to 'total' and registers the change as version 2 in the schema registry. Are consumers safe?

No.

  • The registry stores versioned schemas and lets consumers find the one a message uses
  • But an incompatible change still breaks consumers that expect 'amount'
  • Safe path, following compatibility rules
    • Add 'total' alongside 'amount'
    • Migrate the consumers
    • Only then remove the old field
In a layered monolith, adding a 'gift card' feature touches the presentation, business and persistence layers. Would a modular monolith help?

Yes, for this kind of change.

  • A modular monolith groups code by business module
  • → a gift-card module contains its own UI, logic and data access, and the change stays inside it

It still deploys as one unit, so you don't get independent deployment; that would need services.

Code-level maintainability tactics

Five design tactic groups contain changes and provide extension points; reliable-change practices are covered later.

Contain change

  • Encapsulation → keep change inside a component (e.g. a Discount Engine using the Strategy pattern)
  • Separation of concerns → clear distinct responsibilities
  • Single point of definition → data types, algorithms, config, schemas defined once, so no need to synchronise changes

Create extensible interfaces

  • Object parameters can grow without a method-signature change
  • Optional fields and flexible JSON/XML formats can support compatibility
  • Keep old fields and meanings usable
  • Test existing consumers
  • Version incompatible changes with a clear support policy

A flexible format alone does not make a change safe.

Design techniques that facilitate change

  • Abstraction and layering → minimal impact of one part on others
  • Generalisation → group similar scenarios into a general pattern handled by one component
  • Inversion of control → components can be reconfigured

Build variation points

  • Make elements replaceable
  • Parameterise changeable properties in configuration
  • Separate physical from logical processing → convert many physical formats into one logical structure
  • Break processes into steps → change is confined to some steps

Use standard extension points

Built into technologies:

  • ODBC/JDBC → for different databases
  • JSON/SOAP/REST → for calling services
  • JCA → the standard Java adapter
Encapsulation
Hiding details inside a component so callers are unaffected by change.
Single point of definition
Define each type, algorithm or config once.
Inversion of control
Components are wired or configured externally, allowing reconfiguration.
Variation point
Deliberate place where behaviour can be swapped or configured.

Check yourself

A public API method has 7 parameters, and clients keep breaking whenever a parameter is added. What would you change?
  • Pass a single request object → new optional fields can be added without changing the method signature
  • Old clients must still be served correctly
    • Keep existing fields and meanings
    • Give new fields defaults
    • Test existing consumers
  • Version the API for changes that cannot be compatible
A bank receives statements from 12 partners in CSV, XML and fixed-width formats, and parsing logic is spread across the system. What would you change?

Separate physical from logical processing.

  • Convert at the edge: each physical format → one standard logical structure
  • Use only that structure in the rest of the system
  • → a new partner format then changes only a converter

The cost is one more mapping layer to maintain.

A discount rate of 0.15 is hard-coded in 9 places, and the last change missed one. Which tactic would have prevented this?

Single point of definition.

  • Define the rate once, in configuration or a constant used everywhere → a change never has to be synchronised across copies
  • Parameterising it in configuration also lets you change it without a code release
A JSON API adds a mandatory field to every request. Is it backward compatible because the method signature is unchanged?
No. Existing callers omit the new field and may fail validation. Add it as optional with suitable behaviour for old callers, or version the breaking contract and migrate consumers.

Defer binding: customisation and workflow engines

Push decisions to run time so users or implementers change behaviour without recompiling.

Defer binding

  • Making the application customisable at run time
  • Fully user-customisable needs good UX expertise and domain understanding
  • Deck's example: Amplitude analytics → customisable cohort analyser lets users analyse retention across cohorts without writing data-munging logic

Workflow engine pattern

  1. An admin or implementer designs a workflow for a specific tenant or role
  2. The workflow logic is persisted
  3. At run time the engine deserialises the tenant or role's workflow
  4. ...and executes it, calling domain logic

Result: logic customisation without recompiling, e.g. a different approval workflow per client.

Visual designer

  • Many engines provide a visual designer
  • → lowers the skill needed to change behaviour
  • = the 'customizable by implementation team' end of the change-cost table
Defer binding
Postpone choosing behaviour until run time, by configuration or user customisation.
Workflow engine
Component that executes persisted, designable workflows at run time.

Check yourself

Each of 30 corporate clients wants a different expense-approval chain, and the chains change a few times a year. How would you design it?

Defer binding with a workflow engine.

  1. An implementer designs each client's workflow
  2. It is stored per tenant
  3. At run time the engine loads and executes it, calling shared domain logic
  4. → changes need no recompiling or redeployment

The cost is building or adopting the engine, and limiting workflows to the steps it supports.

For a 3-month MVP, a team proposes fully end-user-customisable reports. Do you agree?

Probably not.

  • End-user customisation has the lowest change cost when done well, but the highest development cost
  • It needs strong UX and domain understanding that an MVP rarely has
  • Instead: ship a few fixed reports → learn which variations users actually want → add customisation where that demand is clear

Analyzability: detecting and diagnosing problems

How to detect problems, find the root cause and monitor systems, including logging in microservices.

Analyzability asks

  1. How do we detect problems?
  2. Identify the root cause?
  3. Make and deploy the fix? (the last step is like any other change)

Analyzability tactics

  • Automated error detection and reporting → e.g. UNIX core dump, log file monitoring
  • Good logging practice → enough information to support an investigation
  • Allow system monitoring through standard protocols:
    • JMX (Java)
    • SNMP (devices)

Logging in microservices

Three components:

  • Logging agent
  • Log storage
  • Log dashboard with search

EFK stack on Kubernetes

  • Fluentd → the agent, collecting logs from the nodes
  • Elasticsearch → the storage
  • Kibana → the dashboard

Propagate a correlation id

  • So entries from one request can be matched across services
  • Central storage alone does not show which records belong together
  • Missing identifiers → reconstruction harder and less reliable
JMX / SNMP
Standard protocols for monitoring and managing applications (Java) and network devices.
EFK
Fluentd (agent), Elasticsearch (storage), Kibana (dashboard).
Correlation id
Identifier passed across services to trace one request in the logs.

Check yourself

A checkout error appears in the logs of four services, but nothing links the entries. What would you add?

A correlation id.

  • Created at the entry point and passed with every call and event
  • Written in each service's log entries
  • → the entries for one request can be pulled together for root-cause analysis

Central log storage alone does not show which records belong together.

Container logs disappear when pods restart, and engineers SSH into nodes to grep for errors. What would you change?

Add the three logging components (EFK is the lecture's example stack):

  • An agent on each node that ships logs
  • Central log storage
  • A dashboard with search
  • → logs survive restarts and can be searched across services

The cost is running and sizing the logging infrastructure itself.

A legacy application crashes every night and leaves nothing useful behind. Which analyzability tactics apply?
  • Automated error detection and reporting: core dumps, log file monitoring that raises alerts
  • Logging with enough context to investigate
  • Monitoring through standard protocols such as JMX or SNMP

Together these turn 'it crashed' into a diagnosable fault.

Reliable change and fitness functions

Practices that make changes safe, and fitness functions that automatically guard architectural rules.

Reproducible process for reliable change

  • Track changes in version control
  • Automate tests and build/integration checks
  • Support deployment rollback
  • Manage environment configuration as code
  • Apply hypothesis-driven testing
  • Integrate secrets management without committing secret values

Automating release/deployment extends the delivery process beyond CI alone.

Fitness function

An automated check that an architectural characteristic still holds. Deck's pipeline:

  1. Unit test
  2. Build and deploy
  3. Integration and end-to-end tests
  4. A set of checks must pass:
    • code quality
    • resiliency
    • observability and performance testing
    • compliance standards
    • security code analysis
    • operability standards
  5. Promote

Fitness function example: JDepend

  • A unit test using a dependency-analysis tool (JDepend)
  • Asserts that persistence and web packages depend on util as allowed
  • → the build fails if any code breaks layer dependencies in a layered architecture
Fitness function
Automated test of an architectural characteristic, run in the delivery pipeline.
Infrastructure as code
Versioned definitions of infrastructure and environment configuration, integrated with separate secrets management.

Check yourself

The architecture rule says the web layer must not call the persistence layer directly. Code reviews keep missing violations. What would you add?

A fitness function.

  • An automated test using a dependency-analysis tool → fails the build when web code depends on persistence packages
  • It checks the rule on every build, which review cannot do reliably

It guards only the rules you actually encode, so add checks for other key characteristics as well.

A release breaks checkout, and reverting takes 3 hours because the database migrations cannot be undone. What should the release process have included?

Rollback designed in.

  • Reversible or backward-compatible migrations
  • The ability to redeploy the previous version quickly
  • Why: even tested changes fail in production → fast reversal limits the damage

Version control, automated tests and environment configuration as code make that reversal reliable.

A release works in staging but fails in production, because the two environments were configured by hand and differ. A developer suggests committing the production passwords into the repository so everything is in one place. Respond.
  • Manage environment configuration as code → staging and production are built from the same versioned definitions
  • Do not commit secret values → integrate a secrets-management tool, and reference secrets from the configuration

Reproducible environments without leaked credentials make change reliable.

Code quality tools

Static analysis tools help track relative quality, but only if you understand the metrics.

Static-analysis examples

  • FindBugs, Checkstyle, PMD, SonarQube → code issues and metrics
  • CodeCity → visualising code structure

Learn what a result reveals rather than memorising product names as proof of quality.

Use with care

  • Understand what each metric means
  • Useful for the relative quality progression of one code base over time
  • Not for absolute comparison between systems

Connect the models

  • This topic stresses analyzability, changeability, stability and testability
  • For an ISO 25010:2011 classification question, use (from the foundations lecture):
    • modularity
    • reusability
    • analyzability

Platform that analyses code quality and reports issues and metrics.

Check yourself

A quality dashboard improves after a release. Does that prove the architecture is easier to maintain?

No.

  • Check what changed in the metrics, and whether they reflect relevant change or diagnostic effort
  • Combine trends with actual change scenarios and fitness checks

A score is evidence for its measured properties, not all maintainability.

A manager wants to rank three teams' systems by their static-analysis scores to decide bonuses. Do you agree?

No.

  • These metrics are useful for tracking one code base's relative progress over time, not for comparing different systems in absolute terms
  • Size, language and domain differ between systems
  • Using them for bonuses also invites gaming

Compare each team against its own trend, alongside real change effort.

Exam-style questions

Answer aloud or on paper before opening.

A product's discount and eligibility rules change every quarter, and three of its 20 enterprise clients need their own approval flow. The business wants changes shipped without redeployment. Recommend a design and its costs.

Defer binding for the kinds of change that recur.

  • Rule parameters in configuration, which business users edit through an admin screen, behind a single point of definition
  • A workflow engine runs per-tenant approval flows designed by the implementation team
  • Encapsulate the domain actions the workflows call, and define the supported variation points
  • Costs: this lowers the cost of each change but raises development cost, and needs UX and domain work

Behaviour outside the variation points still needs a code change, so choose the variation points from the expected changes.

An online learning platform has a layered monolith, five teams and frequent collisions between releases. It plans to add analytics, recommendations and partner integrations over two years. Compare a modular monolith, microservices and an event-driven approach for modifiability, and recommend one.

Recommend modularising first, then extracting services where team collisions are worst, and publishing events for the new consumers.

  • Modular monolith
    • Business modules contain changes and avoid distributed costs
    • But everything still deploys as one unit → release collisions remain
  • Microservices
    • Independent deployment per capability, if each owns its data and APIs evolve compatibly
    • But they add operational cost, and shared tables or call chains can still spread change
  • Event-driven
    • Analytics and recommendations can subscribe to existing events (CourseCompleted, LessonViewed) without producer changes
    • Only if the payloads carry what they need, with a schema registry and compatibility rules
A public REST API has about 200 external consumers you do not control. Over the next year you must add fields, rename one concept and change one response structure. Which code-level tactics keep the API evolvable?
  • Request and response objects with optional fields → additions don't break signatures
  • Renamed concept: add it alongside the old one, and deprecate the old name with a support period
  • Structural change: put it in a new API version, keeping the old one running during migration
  • Encapsulate the implementation behind the API, define the shared data types once, and use standard formats
  • Test existing consumer contracts

Flexible JSON syntax alone does not guarantee compatibility.

During an incident, a payment fails somewhere across six microservices. It takes four hours to find the cause because logs are local to each container and have no common identifier. Redesign for analyzability.
  • Automated error detection and alerting → the failure is noticed rather than reported by users
  • Centralise logs with an agent, storage and searchable dashboard (for example EFK) → they survive container restarts
  • Propagate a correlation id from the entry point through every call and event → one request's entries can be retrieved together
  • Log enough context, such as inputs, the dependency called and the error
  • Expose metrics through standard monitoring

The fix itself is then deployed like any other change, through the reliable-change pipeline.

A layered system's dependency rules are eroding, releases often break production, and rollbacks are manual. Design a pipeline that makes change reliable and stops further erosion.
  1. Keep everything in version control, including environment configuration as code, with secrets in a secrets manager
  2. Automated tests on each change: unit, integration and end-to-end
  3. Fitness functions before promotion
    • A dependency test that fails on layer violations
    • Plus performance, security, resiliency and observability checks
  4. Automate deployment with a tested rollback path and reversible migrations
  5. Hypothesis-driven testing for risky changes

Fitness functions guard only what they encode, so add rules as the architecture evolves.
