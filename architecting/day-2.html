Whole day

A physical diagram already names products and server sizes, but the team has not agreed the business rules or the peak load. How would you get the architecture process back on track?
  1. Go back to Define Requirements
    • Stakeholders (including technical ones), a glossary, a system context
    • Then functional requirements and NFRs with measurable targets and conditions
  2. Prioritise the architecturally significant ones
  3. Derive the logical architecture (boundary, control and entity components, logical nodes) and verify it
  4. Only then map it to technology
    • Size the nodes against the NFRs
    • Keep the existing product choices as recorded decisions with alternatives and assumptions → they can be overturned if the requirements contradict them
IROne-style requirements: search 99.9% available within 3 s, other functions 99% within 5 s, 1000 concurrent users, and integration with hotel systems reachable only through messaging. A benchmark shows one application node handles 300 users at target. Outline the logical-to-physical decisions you would record.
  • Search: map one to many
    • Capacity: 1000 / 300 ≈ 3.3 → 4 nodes
    • Survive one failure: 5 (4 survivors x 300 = 1,200)
  • Other functions can share fewer nodes if they are isolated from search
  • Hotel boundaries → messaging; flag the transformation in the endpoint table as adapter work to specify and test
  • Record each choice in the Issue, Decision, Assumptions, Alternatives, Justification format, especially the 300-user figure
  • Validate it with a proof of concept under the real request mix

Architect the Solution Architecture (Method)

A clinic chain wants online booking within 6 months: 40 clinics, about 2,000 concurrent users at 8 am, and integration with a patient-record system that only accepts batch files overnight. (a) Pick three architecturally significant requirements and justify each. (b) Write one as a six-part scenario. (c) What decision would you record about the patient-record integration?
  1. (a) Three architecturally significant requirements
    • 8 am peak of 2,000 concurrent users → critical quality: drives capacity and scaling
    • Overnight-only patient-record interface → critical constraint
    • Booking itself → critical functionality: without it there is no viable system
  2. (b) Six-part scenario
    • Source: 2,000 patients
    • Stimulus: book an appointment
    • Artifact: booking service
    • Environment: the 8 am peak
    • Response: the slot is confirmed
    • Measure: 90% of confirmations within 3 s
  3. (c) Decision record for the patient-record integration
    • Issue: bookings must reach patient records, but only overnight batch is possible
    • Decision: store bookings in the booking system and export them nightly
    • Assumptions: clinics can tolerate next-day sync
    • Alternatives: real-time integration, which is not offered
    • Justification: it meets the constraint
    • Revisit if same-day record access becomes a requirement
A requirements document says: 'The system must be fast, secure and user-friendly and support 1000 users.' It lists only customer use cases. As architect, critique it and say what you would do in Define Requirements.
  • Critique
    • None of the qualities are measurable
    • The user count gives no request mix or think time
    • Technical users and external systems are missing
  • In Define Requirements
    • Collect requests from technical stakeholders too (administrators, owners of external systems)
    • Build a glossary and a system context with actors per location
    • Outline functional requirements per actor, including administration, and NFRs with targets and conditions
    • Prioritise the architecturally significant ones and detail them as use cases and six-part scenarios
    • Record them in the SAD with traceability, and review with stakeholders
For a 'Transfer Ticket' use case (an owner transfers a ticket to a friend, the system checks transfer rules and notifies an external venue system), derive the boundary, control and entity components, then propose a physical mapping that supports high availability.
  • Boundaries: the transfer UI (owner) and the venue-system interface (external)
  • Control: Transfer Ticket control, which coordinates the rules check, possibly using a rules component
  • Entities: Ticket and Transfer record
  • Physical mapping
    • UI → web tier
    • Control → stateless application component, deployed one to many across several instances
    • Venue interface → messaging, so venue outages don't block transfers
    • Entities → persistent store with redundancy

Record each choice as a decision and check it against the availability target.

Logical model: web, application, rules and integration nodes at the central office. NFRs: 1000 concurrent users with 99.9% availability. A benchmark shows one application node handles 400 users at the response target. Size the physical application tier and explain your mapping.
  1. Capacity alone: 1000 / 400 = 2.5 → 3 nodes
  2. Survive one node failure: the survivors must still carry 1000 users → 4 nodes (3 survivors x 400 = 1,200)
  3. Mapping: a one-to-many mapping of the logical application node → requires stateless components or shared session state, and a load balancer
  4. Confirm the 400-user figure with the production request mix, since benchmarks do not scale perfectly
  5. Then specify the hardware, deployment units and endpoints
A validation proof of concept shows the integration server handles 50 messages/s, but the peak need is 120 messages/s. How does this finding flow through the method, and what options would you weigh?
  • Validation documents the finding, its risk and recommendations, traced to the NFR it threatens
  • Options
    • Deploy the integration node one to many: three instances give about 150 messages/s if it scales, which must be measured
    • Batch or queue messages to smooth the peak, if a short delay is acceptable
    • Reduce the work per message
  • Record the chosen option as a decision with its assumptions, update the SAD and review it with stakeholders
  • Repeat validation until the risk is acceptable
