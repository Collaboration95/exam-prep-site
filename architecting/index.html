Whole-course questions

Try after all the days. Explain your choices before opening the answer.

A resort reservation system must take 1,500 concurrent bookings at the 8 am release of holiday slots, survive the loss of any one server, and let the business change its booking rules every quarter without a release. How would you turn these goals into a defensible architecture, and what evidence would you need before committing?
Write each goal as a measurable scenario (for example, '90% of bookings confirmed within 3 s with 1,500 concurrent users at 8 am') and rank them in a utility tree. Derive boundary, control and entity components, then map the booking control one to many across nodes sized so the survivors still carry the peak. Put the rules behind a configuration or rules-engine variation point, and record that decision with its assumptions. Before committing, benchmark the booking scenario with the real request mix, calculate end-to-end availability including shared dependencies, and test failover. Benchmarks rarely scale linearly, and a topology label proves nothing.
Two million smart meters each send a reading every 15 minutes, and most send in the first minute of each window. The current design writes every reading synchronously into one primary database with one read replica, and it is falling behind. Propose a plan to scale the writes and name two side effects to monitor.
The average is about 2,200 writes/s, but the real peak is about 33,000/s if most of the 2 million arrive within 60 s, and that is what to size for. Put a durable queue or event stream in front of the database, so ingestion absorbs the burst and writers drain it at a sustainable rate. Then partition (shard) the readings by meter id across several primaries, since a read replica adds no write capacity, and batch the inserts. Side effects to monitor: queue lag, meaning how stale the latest reading is, against any freshness requirement; and uneven shards or hot partitions. Cross-shard queries and reports also become harder, so feed them from the stream or a separate analytics store.
A teammate proposes 'number of monthly active users' as the metric showing that a booking platform is scalable and highly available. Do you agree? What would you measure instead?
No. Monthly active users measures adoption volume, not how the system behaves as load grows or how often it is unavailable. A high count says nothing about response time at peak, and could rise while users suffer outages. For scalability, measure throughput and response-time percentiles against load (for example p90 response at 1x, 2x and 4x peak) and how throughput grows as nodes are added. For availability, measure (agreed service time - downtime) / agreed service time per critical function, plus MTTR.
A logical packaging and deployment model puts the web front end, booking service and payment adapter in one deployable on a single node in the DMZ, with the database on the same node. Identify the undesirable decisions and propose corrective actions.
First, everything sits in the DMZ: compromising the web front end exposes the booking logic, payment adapter and data. Keep only the web tier or reverse proxy in the DMZ, and place the services and database behind an inner firewall with only the required traffic allowed. Second, one node and one deployable is a single point of failure that cannot scale by tier. Separate the deployables, run the booking service one to many behind a load balancer, and give the database its own redundant nodes. Third, the payment adapter is bundled with unrelated code, so a payment change forces a full redeploy. Make it its own unit behind a stable interface. Each correction adds nodes and operating cost, which must be justified against the availability, security and modifiability scenarios.
