Whole-course questions

Try after all the days. Explain your choices before opening the answer.

A resort reservation system must take 1,500 concurrent bookings at the 8 am release of holiday slots, survive the loss of any one server, and let the business change its booking rules every quarter without a release. How would you turn these goals into a defensible architecture, and what evidence would you need before committing?
  • Measurable scenarios: write each goal as one, e.g. '90% of bookings confirmed within 3 s with 1,500 concurrent users at 8 am'; rank them in a utility tree
  • Logical design: derive boundary, control and entity components
  • Survive one server loss: map the booking control one to many across nodes sized so the survivors still carry the peak
  • Quarterly rule changes: put the rules behind a configuration or rules-engine variation point; record that decision with its assumptions
  • Evidence before committing
    • Benchmark the booking scenario with the real request mix
    • Calculate end-to-end availability including shared dependencies
    • Test failover

Benchmarks rarely scale linearly, and a topology label proves nothing.

Two million smart meters each send a reading every 15 minutes, and most send in the first minute of each window. The current design writes every reading synchronously into one primary database with one read replica, and it is falling behind. Propose a plan to scale the writes and name two side effects to monitor.
  • Size for the peak
    • Average ≈ 2,200 writes/s
    • Real peak ≈ 33,000/s if most of the 2 million arrive within 60 s
  • Durable queue or event stream in front of the database → ingestion absorbs the burst; writers drain it at a sustainable rate
  • Partition (shard) the readings by meter id across several primaries (a read replica adds no write capacity), and batch the inserts
  • Side effects to monitor
    • Queue lag: how stale the latest reading is, against any freshness requirement
    • Uneven shards or hot partitions

Cross-shard queries and reports become harder → feed them from the stream or a separate analytics store.

A teammate proposes 'number of monthly active users' as the metric showing that a booking platform is scalable and highly available. Do you agree? What would you measure instead?

No. Monthly active users measures adoption volume, not how the system behaves as load grows or how often it is unavailable.

  • Why not: a high count says nothing about response time at peak, and could rise while users suffer outages
  • Scalability: throughput and response-time percentiles against load (e.g. p90 response at 1x, 2x and 4x peak), and how throughput grows as nodes are added
  • Availability: (agreed service time - downtime) / agreed service time per critical function, plus MTTR
A logical packaging and deployment model puts the web front end, booking service and payment adapter in one deployable on a single node in the DMZ, with the database on the same node. Identify the undesirable decisions and propose corrective actions.
  1. Everything sits in the DMZ
    • Compromising the web front end exposes the booking logic, payment adapter and data
    • Fix: keep only the web tier or reverse proxy in the DMZ; place the services and database behind an inner firewall with only the required traffic allowed
  2. One node, one deployable → single point of failure that cannot scale by tier
    • Fix: separate the deployables, run the booking service one to many behind a load balancer, give the database its own redundant nodes
  3. Payment adapter bundled with unrelated code → a payment change forces a full redeploy
    • Fix: make it its own unit behind a stable interface

Each correction adds nodes and operating cost, which must be justified against the availability, security and modifiability scenarios.
